SpringBoot自定义注解与AOP实现业务逻辑

发表于 2026-05-17 更新于 2026-05-31 分类于 SpringBoot 本文字数： 1.8k 阅读时长 ≈ 6 分钟

概述

在 Spring Boot 中，自定义注解 + AOP 是横切业务逻辑的常用方式：把「操作审计、防重、幂等、权限、租户隔离」等从 Controller/Service 方法里抽离，做到声明式、可复用、可开关。

本仓库已落地：

注解 切面 文档
@OperLog OperLogAspect AOP日志与操作审计
@RepeatSubmit RepeatSubmitAspect 防重提交与接口幂等
@Idempotent IdempotentAspect 同上

本文说明从零实现一套注解切面的通用步骤，并以示例 @BizCheck（按业务场景开关 + 前置校验）贯穿全文；读者可照此模式扩展自己的业务注解。

一、何时用注解 + AOP

方式 适用
自定义注解 + AOP 与具体方法绑定、可带参数、需环绕/前后增强（日志、锁、审计）
Filter / Interceptor 全站 HTTP 层（鉴权头、TraceId），与具体业务方法弱相关
@ControllerAdvice 统一异常、参数校验（见 统一返回体与全局异常）
纯 Service 调用 强业务分支、需单元测试的核心规则

原则：横切、重复、可配置 → 注解 + AOP；核心领域规则 → 仍写在 Service，AOP 只做入口守卫或记录。

二、依赖

Spring Boot 4 会自动启用 AspectJ 自动代理，一般无需再写 @EnableAspectJAutoProxy。

4. SpEL 动态参数（可选）

注解属性可写 SpEL，在切面里用 MethodBasedEvaluationContext 解析方法参数，例如 @BizCheck(scene = "#dto.type")。适合场景码依赖入参；复杂度较高时更推荐在 Service 内显式校验。

5. 异步与事务

  • @Async：切面在调用线程执行，proceed() 之后才进入异步（除非切面内再开线程）。
  • @Transactional：默认仅对 public 代理方法生效；@Around 若在外层，注意事务边界与 proceed() 的关系（事务切面通常 Order 较低）。

本仓库（cloud）当前未集成 Dubbo。服务间调用使用 OpenFeign（如 cloud-order → cloud-stock），注册发现使用 Nacos，见 订单下单与库存扣减.md、集成Nacos.md。本文供与 SCA 同栈 时扩展参考。

SpringBoot数据库连接池：HikariCP与Druid对比与落地

发表于 2026-05-17 更新于 2026-05-31 分类于 SpringBoot 本文字数： 1.8k 阅读时长 ≈ 6 分钟

概述

JDBC 连接池负责复用数据库连接，避免每次请求都新建 TCP 与认证开销。本仓库（Spring Boot 4.0.6 + dynamic-datasource + MyBatis-Flex）默认使用 HikariCP；本文对比 HikariCP 与 Druid，并给出在本项目中的配置方式、监控与选型建议。

前置阅读：多环境配置、集成MyBatis-Flex与多数据源。

一、为什么需要连接池

无池 有池
每次 getConnection() 走完整握手 从池中借出已建连，用完归还
高并发下连接数暴涨、DB 被打满 maximum-pool-size 上限保护数据库
慢请求拖垮数据库 等待队列 + 超时（connection-timeout）可控

应用线程 ≠ 数据库连接：Web 线程可在等待 IO 时释放连接回池，供其他请求使用。

二、HikariCP 与 Druid 对比

1. 定位

维度 HikariCP Druid（Alibaba）
Spring Boot 默认 Boot 2+ 内置默认（spring-boot-starter-jdbc） 需额外依赖与配置
设计目标 极致性能、代码精简、稳定 性能 + 监控统计 + SQL 防火墙
监控 JMX / Micrometer（连接数、等待时间等） StatViewServlet、慢 SQL、Wall 防注入
多数据源 与 dynamic-datasource 天然搭配（本项目现状） 支持，配置项更多
社区与许可 BSD，Spring 生态一等公民 Apache 2.0，国内 Java 项目常见
典型适用 云原生、微服务、追求默认即最优 需要 SQL 审计、慢查询分析、运维可视化

2. 性能与资源（经验结论）

  • HikariCP：字节码级优化、锁粒度小，Benchmark 中长期领先，内存占用通常更低；Spring 官方默认有其理由。
  • Druid：性能同样优秀，额外功能（Filter、Wall、监控页）带来一定开销；换来可观测与 SQL 治理能力。

二者在生产环境都能稳定运行；差异更多在运维需求而非「能不能用」。

3. 功能差异（程序员需知道的）

能力 HikariCP Druid
连接泄漏检测 leak-detection-threshold remove-abandoned 等
慢 SQL 需配合 P6Spy / datasource-proxy / APM 内置 stat Filter
SQL 防火墙 无（靠 ORM / 预编译） WallFilter 防全表更新等
Web 控制台 无 /druid/* 统计页
Actuator 指标 hikaricp.connections.* 需 Druid Spring Boot Starter 集成

4. 关键参数调优

参数 含义 建议
maximum-pool-size 最大连接数 ≤ DB max_connections / 实例数；本模板 20 适合 dev
minimum-idle 最小空闲连接 与峰值无关，略低于 max 即可
connection-timeout 借连接最长等待（ms） 30s；过短易误报超时
max-lifetime 连接最大存活（ms） 略小于 DB/中间件 wait_timeout，防服务端踢连接
idle-timeout 空闲回收 仅当 minimum-idle < maximum-pool-size 时生效
keepalive-time 保活探测间隔 长连接场景减少「半死连接」

估算：若应用部署 N 个实例，每实例 maximum-pool-size=M，MySQL 侧至少预留 N × M（再加 admin、批任务余量）。

四、可选方案：切换为 Druid

若团队需要 慢 SQL 统计、Web 监控页、Wall 防火墙，可在本项目中改为 Druid（或仅生产启用 Druid）。

1. 添加依赖

注意：Druid 官方 starter 版本需与 Spring Boot 4 / Jakarta 匹配；升级 Boot 大版本时务必核对 release note。

2. dynamic-datasource + Druid 配置

  • 引入 Druid starter 且配置 spring.datasource.dynamic.druid.* 后，dynamic-datasource 会为各数据源创建 DruidDataSource（以当前 starter 行为为准，切换后应跑一遍全量测试）。

3. Druid 监控页（仅 dev / 内网）

生产务必：关闭公网暴露、强密码、或完全禁用 StatViewServlet，改走 Prometheus + 日志。

4. Wall 防火墙示例

防止误执行 DROP TABLE、多语句注入等（不能替代参数化查询与权限最小化）。

五、单数据源场景（无 dynamic-datasource）

若某模块仅 一个 MySQL，可只用 Boot 默认 Hikari，无需 Baomidou：

六、选型建议（本仓库）

场景 建议
默认开发、与 Spring Boot 对齐、依赖最少 HikariCP（当前）
需要 Druid 监控页、慢 SQL 榜单、Wall 评估 Druid，建议 dev 启用监控、prod 收紧暴露
多数据源 继续 dynamic-datasource + 任选池；@DS 用法不变
链路/指标 Hikari → Micrometer；Druid → stat + 可选接入 Grafana
单元测试 测试 profile 使用 H2（见 MyBatis-Flex 文档），减小对真实池大小的依赖

七、常见问题

现象 可能原因 处理
Connection is not available, request timed out 池过小或连接泄漏 增大 maximum-pool-size；查未关闭的 Connection；Hikari 开 leak-detection-threshold
Communications link failure 间歇出现 连接被 DB 踢掉 调 max-lifetime；开 keepalive-time
切换 @DS 无效 同类自调用、事务传播 确保经 Spring 代理调用；检查 @DS 在类/方法位置
MySQL Too many connections 实例数 × 池大小超限 降 M 或升 DB max_connections；用连接池全局规划
Druid 监控 404 stat-view-servlet 未开或路径不对 核对 url-pattern 与安全 allow

概述

核心链路：下单 POST /order/place（cloud-order）→ OpenFeign → 扣库存 POST /stock/goods/deduct（cloud-stock）。成功时写入 t_order 并减少 goods.stock；失败时由 Seata 全局事务 回滚（默认开启）。测试数据见 sql/test-data-goods.sql。

概述

Apache Seata 在本项目中以 AT 模式 协调 cloud-order（TM）与 cloud-stock（RM）的跨库事务。默认 开启（SEATA_ENABLED 默认 true），TC 地址 192.168.1.22:30014。与 dynamic-datasource 联用时关闭自动数据源代理，改由 spring.datasource.dynamic.seata: true 接入。

架构



sequenceDiagram
  participant TM as cloud-order
  participant TC as Seata TC :30014
  participant RM as cloud-stock
  participant DB1 as MySQL order
  participant DB2 as MySQL stock

  TM->>TC: begin(xid)
  TM->>DB1: INSERT order (branch)
  TM->>RM: Feign deduct
  RM->>DB2: UPDATE goods (branch)
  alt 成功
    TM->>TC: commit
    TC->>DB1: commit branch
    TC->>DB2: commit branch
  else 失败
    TM->>TC: rollback
    TC->>DB1: undo
    TC->>DB2: undo（若有 UPDATE）
  end

集成SpringCloudGateway

发表于 2026-05-17 更新于 2026-05-31 分类于 SpringCloud 本文字数： 770 阅读时长 ≈ 3 分钟

概述

cloud-gateway 基于 Spring Cloud Gateway（WebFlux），端口 9000，作为对外统一入口。路由使用 lb://服务名 经 Spring Cloud LoadBalancer 从 Nacos 取实例；同时启用 discovery locator 可按服务名自动生成路由。

架构



flowchart LR
  C[Client] --> G[Gateway :9000]
  G -->|/user/**| U[cloud-user]
  G -->|/web/**| A[cloud-app]
  G -->|/order/**| O[cloud-order]
  G -->|/stock/**| S[cloud-stock]
  G --> N[(Nacos)]
  U --> N
  O --> N

Maven 依赖

cloud-gateway/pom.xml 核心：

  • spring-cloud-starter-gateway-server-webflux（或项目内等价 Gateway 起步依赖）
  • spring-cloud-starter-loadbalancer
  • spring-cloud-starter-alibaba-nacos-discovery
  • Sentinel Gateway 适配（与 application-shared.yml 中 spring.cloud.sentinel.enabled 配合）

路由配置

cloud-gateway/src/main/resources/application.yml：

路径前缀 目标服务 示例
/web/** cloud-app GET /web/...
/user/** cloud-user GET /user/...
/order/** cloud-order POST /order/place
/stock/** cloud-stock GET /stock/goods/1

注意：直连服务 Swagger 用 http://host:8003/swagger-ui.html；经网关访问文档需额外路由或直连端口（本仓库推荐联调 API 走 9000，文档开发时直连各服务端口）。

配置 import

Profile 的 application-dev.yml 再引入 optional:nacos:application.yml。

验证

成功时 code 为 0；库存不足等业务失败常为 code: 1（见订单专题）。

常见问题

Q：504 / 503 Service Unavailable？
A：下游未注册到 Nacos，或网关先于下游启动。先起 stock/order，再起 gateway；在 Nacos 服务列表确认实例健康。

Q：GET /order/place 报错？
A：place 是 POST 接口；GET /order/{id} 仅匹配数字 id，避免把 place 当成 id。

Q：路径要不要 StripPrefix？
A：本仓库各服务 Controller 带完整前缀（如 /order），网关 未 剥离前缀，转发路径与直连一致。

生产注意

与 cloud 架构总览 上线清单配合使用。

项 建议
唯一公网入口 仅暴露 9000（或前置 Caddy/HAProxy）；业务 8001–8004 不对公网
discovery.locator 生产宜关闭或严格限制，避免 Nacos 新服务被自动暴露
HTTPS / 鉴权 TLS 在边缘终结；JWT 等用 GlobalFilter 统一验签
超时 配置 httpclient.response-timeout，与 Feign、客户端超时逐层对齐
重试 POST /order/place 等非幂等接口禁止盲目 Retry
Sentinel 为热点路由配 QPS/慢调用，见 集成 Sentinel
多实例 Gateway 无状态，≥2 副本 + readiness；最后启动（下游已在 Nacos）
可观测 SkyWalking Agent、Prometheus gateway.requests、访问日志 GlobalFilter
Swagger/Actuator 生产勿经网关暴露；或 IP 白名单

环境变量与 Nacos import 见 Spring Cloud 多环境配置与 Nacos。

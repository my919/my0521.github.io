RedLock = 多个独立 Redis 主节点 + 过半写入成功才算加锁成功
目的：彻底解决主从切换丢锁问题

六、RedLock 加锁成功规则（必须记住）

3个节点：
必须 ≥ 2 个节点加锁成功 + 加锁耗时 < 锁超时时间
才算加锁成功。

5个节点：
必须 ≥ 3 个节点加锁成功

七、RedLock 看门狗（自动续期）生效吗？

生效！

RedLock 会对每个节点的锁自动续期。
只要过半节点存活，锁就不会失效。

八、生产使用注意事项（非常重要）

1. 必须使用 奇数个节点

3、5、7 个，不能用 2、4、6 个。

2. 节点之间完全独立

不能是主从、不能是集群，必须是独立 Master。

3. 性能比普通锁低

因为要写多个 Redis，高并发秒杀可以接受。

4. 核心业务才用 RedLock

  • 秒杀、库存、订单、支付、账务 → 用 RedLock
  • 后台任务、非核心 → 普通锁即可

5. 不要把 leaseTime 设置太长

默认 30s 足够，看门狗会自动续期。

九、最终结论

RedLock 是生产上唯一能彻底解决 Redis 主从丢锁的方案
金融、电商、支付、秒杀必须使用！

启动

说明：bind 与 quic_bind 都写 127.0.0.1:4433 时，在 Linux 上可同时监听 TCP 与 UDP（端口号相同、协议不同）。这样 Chrome / Firefox / Edge 打开 https://127.0.0.1:4433/ 会先走 TCP TLS 拿到页面；支持 HTTP/3 的浏览器还可能通过 Alt-Svc 等机制再尝试 QUIC。若坚持只开 UDP（例如 cfg.bind = []），多数浏览器无法仅靠 https:// 完成首次加载，因为常见实现会先做 TCP 连接。

为何浏览器还常要 TCP、和 QUIC 设计是否冲突

不冲突。 QUIC（RFC 9000）只规定跑在 UDP 上；HTTP/3 也完全可以在只有 UDP 的情况下工作（例如本节的 aioquic 客户端直连 quic_bind）。

浏览器在地址栏输入 https://主机:端口/ 时，多数实现仍沿用历史习惯：先按「TLS over TCP」去建第一条连接，再通过响应里的 Alt-Svc、或 DNS HTTPS/SVCB 等线索，得知同一站点也可用 HTTP/3，之后才发起 QUIC。这是浏览器与 Web 生态的部署/发现策略，不是 QUIC 协议里「必须先有 TCP」的要求。本地演示若没有 DNS、没有事先缓存的 Alt-Svc，只监听 UDP 时，用户只输入 https:// 就容易连不上，因此示例里同时开同端口的 TCP TLS 是为了兼容这种建连路径，属于工程上的折中，与 QUIC 规范无矛盾。

在浏览器里打开时的证书提示

自签名证书会触发「不安全」或「您的连接不是私密连接」：本地实验可在 高级 中选择继续访问（Chrome），或把 cert.pem 导入系统/浏览器的受信任根（更安全、少打扰）。不要用这种方式处理公网真实用户流量。

MyBatis-Flex 分页原理（通俗易懂 + 流程拆解 + 和 MP 对比）

一、核心结论

MyBatis-Flex 底层也是基于 MyBatis 拦截器，原理和 MyBatis-Plus 大体一样，但设计更轻、SQL 解析更强、自动 count 更智能。

核心逻辑：
MyBatis 拦截器 → 拦截查询SQL → 自动生成 count 总数 → 原SQL 拼接 LIMIT → 封装分页结果

二、核心组件

  1. MyBatisFlexInterceptor
    Flex 全局核心拦截器，替代 MP 的 MybatisPlusInterceptor
  2. PageInterceptor
    专门负责分页拦截，Flex 分页核心逻辑都在这
  3. Page、IPage
    分页载体，和 MP 几乎一模一样：当前页、页大小、总条数、分页数据

三、完整分页执行流程（流程图版）

四、和 MyBatis-Plus 分页原理关键区别

对比点 MyBatis-Plus MyBatis-Flex
拦截器结构 插件嵌套式，较重 极简拦截器，更轻量
Count SQL 生成 简单直接，复杂SQL容易生成低效count 智能优化：自动去掉 order by、优化嵌套SQL
多表/复杂SQL 偶尔分页解析失败 解析器更强，兼容复杂联表、子查询
分页参数传递 必须 Mapper 方法带 Page 参数 支持 Mapper、也支持 Db 静态工具直接分页
配置 必须手动注册分页插件 自动配置，开箱即用，不用手动@Bean

五、代码使用（和 MP 几乎一模一样）

1. 无需手动配置分页插件

Flex 自动自动注入分页拦截器，不用写任何 @Bean 配置

2. 业务分页代码

写法和 MP 完全兼容，无缝切换。

六、底层关键亮点（Flex 比 MP 强的地方）

  1. 自动优化 Count SQL
    原SQL 有 order by，Flex 会自动剔除，避免 count 也排序，提升性能。
  2. 无需手动配置拦截器
    自动装配，少写配置类，少踩坑。
  3. 支持更多数据库方言
    MySQL、PostgreSQL、Oracle、SQLite 等自动适配 LIMIT 语法。
  4. Lambda 分页更丝滑
    不用写 Wrapper，链式直接分页。

七、一句话总结

MyBatis-Flex 分页原理：
复用 MyBatis 拦截机制 → 拦截SQL → 智能生成count → 自动加LIMIT → 封装分页
和 MP 原理同源，但解析更强、配置更少、性能更好、坑更少。

Java动态数据源

发表于 2026-05-04 分类于 Java 本文字数： 897 阅读时长 ≈ 3 分钟

简介

多数据源常见于：主从读写分离、按库分业务、迁移期新旧库并存等。Baomidou 的 dynamic-datasource 在 Spring Boot 下用统一抽象管理多个 DataSource，通过注解或上下文切换当前线程使用的数据源，对 MyBatis-Plus、MyBatis、Spring Data JDBC、JdbcTemplate 等常见访问方式都适用。

下文以 Spring Boot 4、MyBatis-Plus 3.5.x 与 dynamic-datasource 4.x 为例（Boot 3 请改用 dynamic-datasource-spring-boot3-starter、mybatis-plus-spring-boot3-starter 坐标）。

添加依赖

说明：

  • 切面：@DS 依赖 AOP，此处使用 spring-boot-starter-aspectj（与当前工程一致）。
  • MyBatis-Plus：与 Boot 4 配套使用 mybatis-plus-spring-boot4-starter；Boot 3 使用 mybatis-plus-spring-boot3-starter。具体版本与 MyBatis-Plus 安装说明 及 JDK 要求一致即可。
  • 版本：其余坐标与 Spring Boot、JDK 对齐，以 Maven Central 上各 artifact 说明为准。

Spring Boot 配置

要点：

  • primary：未加 @DS 时默认使用的数据源逻辑名，需与 datasource 下某一键一致。
  • 逻辑名：mysql、pgsql 等为自定义别名，在 @DS("pgsql") 等处引用。

使用 @DS 切换数据源

在 类 或 方法 上使用 @DS("逻辑名")；方法级优先于类级。

Controller 上也可标注，但更推荐标在 Service 或 Mapper 层，避免 Web 层与持久化策略绑死。

编程式切换

需要按参数、分支在运行时决定库时，可使用上下文（用完建议清理，避免线程池复用线程时串库）：

与 @DS 混用时，以官方文档当前版本行为为准；同一调用链内尽量只采用一种风格，降低心智负担。

事务与边界情况

  • 同一事务内：已进入 @Transactional 且已绑定连接后，再切换数据源通常不会按预期切到新库（连接已固定）。多数据源写操作应拆到不同事务方法，或调整事务边界，使切换发生在开启事务之前。
  • 只读事务：若使用 @Transactional(readOnly = true)，仍要注意连接从哪个数据源取得，与 @DS 所在方法的事务传播一致。
  • 自调用：同类内 this.method() 不会经过 Spring 代理，@DS 可能不生效，应抽到另一个 Bean 或通过代理调用。

与 MyBatis-Plus / MyBatis 的配合

引入 MyBatis-Plus 后，SqlSessionFactory 仍使用 Spring 容器中的动态 DataSource，与 dynamic-datasource 无额外冲突。Mapper（含继承 BaseMapper 的接口）或 XML 无需单独为多数据源改一套配置即可随当前线程数据源路由；若某几个 Mapper 固定走副库，可在 Mapper 接口上加 @DS("pgsql")。

常见问题

现象 可能原因
始终走 primary 未走到带 @DS 的代理方法；或自调用绕过代理
切换无效 已在事务中取连接；或 push 后未 poll 导致线程本地状态错乱
启动报错找不到驱动 driver-class-name 与 runtimeOnly 驱动依赖不一致
Boot 版本不匹配 Boot 4 用 spring-boot4-starter，Boot 3 用 spring-boot3-starter

更细的读写分离、分片与 Seata 等组合方案见 Baomidou 动态数据源文档。

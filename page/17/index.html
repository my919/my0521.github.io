Go 并发编程入门

概念基础：Go 并发编程是什么/为什么

  1. 并发是语言内建能力：Go 在语言层面提供 goroutine 与 channel，无需第三方库即可写出高并发程序，这是 Go 最具辨识度的特性。
  2. CSP 模型：遵循「不要通过共享内存来通信，而要通过通信来共享内存」，用 channel 在 goroutine 之间传递数据与所有权。
  3. M:N 调度：运行时把成千上万个轻量 goroutine 复用到少量 OS 线程上，创建成本远低于线程，适合海量并发任务。
  4. 传统同步工具仍在：sync.Mutex/WaitGroup/Once 处理共享状态与协作，context 统一传递取消与超时。
  5. 工程红线清晰：goroutine 泄漏、循环变量捕获、无界并发是三大常见陷阱；开发与 CI 应常开 go test -race 竞态检测。

一、goroutine 与调度模型

  • goroutine：用 go f() 启动；栈初始很小、可按需增长，创建成本远低于操作系统线程，因此可以大量存在。
  • 调度器：运行时把许多 goroutine 映射到少量 OS 线程（M:N 模型），在阻塞或抢占点切换，避免「一线程一连接」把机器拖垮。
  • 何时用：IO 密集、扇出扇入、后台任务；CPU 密集仍要控制并发度（见第六节），否则和线程池一样会抢满核心。

二、channel：通信优先于共享内存

  • 声明与创建：var ch chan int 为 nil，发送/接收会永久阻塞；ch := make(chan int) 无缓冲；make(chan int, 10) 带容量为缓冲 channel。
  • 无缓冲：发送方与接收方必须同时就绪，完成一次「交接」，常用于同步节拍。
  • 缓冲：未满时可先发送，常用于限流或解耦；容量为 0 与无缓冲语义一致。
  • 关闭：仅发送方应调用 close(ch)；接收方可用 v, ok := <-ch，ok == false 表示 channel 已关闭且无剩余数据。
  • 单向 channel：类型 chan<- T（只发）、<-chan T（只收）用于函数签名，约束使用方式、减少误用。

三、select：多路等待与超时

  • select 在多个 channel 操作上等待，随机选择一个可执行的 case；若都阻塞且无 default，则阻塞；有 default 则立即走默认分支（常用于非阻塞尝试）。
  • 超时模式：用 time.After 或 context（推荐生产代码）控制最长等待。

四、sync 包：锁与协作原语

4.1 Mutex / RWMutex

  • 多 goroutine 读写同一内存且无 channel 串行化时，用 sync.Mutex 保护临界区；读多写少可考虑 RWMutex。
  • 锁粒度要小、持有时间要短；避免在持锁时做 IO 或可能阻塞很久的逻辑。

4.2 WaitGroup

  • Add / Done / Wait：主 goroutine Wait() 等待一组子任务结束；Add 要在启动 goroutine 之前（或确保不竞态地提前 Add），避免 Wait 早于 Add 导致计数错误。

4.3 Once

  • sync.Once 保证 Do(f) 里的 f 全局只执行一次，常用于懒初始化单例。

五、context：取消、超时与传值

  • context.Context 贯穿调用链：超时（WithTimeout）、手动取消（WithCancel）、截止时间（WithDeadline）；下游应监听 ctx.Done() 并尽快返回。
  • 值传递：WithValue 适合传请求范围元数据（如 trace id）；不要塞业务大对象，也不要把 Context 放进结构体字段长期保存（应作为函数首参传递）。

六、常见陷阱与实践建议

  • main 退出即进程退出：未 Wait 或未收完结果的 goroutine 会被直接掐掉；要有明确的汇合点（WaitGroup、channel 关闭、errgroup 等）。
  • 泄漏 goroutine：向无人接收的 channel 发送、或 goroutine 永远阻塞在 select，都会导致泄漏；长生命周期任务要设计退出信号。
  • 闭包与循环变量：在循环里 go func() { ... } 若引用循环变量，应用参数传入当前值，避免经典「全部打印最后一个」问题（Go 1.22+ 对循环变量语义有调整，仍建议显式传参以增强可读性与兼容旧版本）。
  • CPU 密集：用 runtime.NumCPU() 或带缓冲的 worker channel 限制并发 worker 数量，而不是无节制 go。
  • 竞态检测：开发与 CI 中开启 go test -race，能发现大量数据竞态。

整体上，Go 鼓励用 channel 表达所有权与流水线，在热点路径或简单共享计数时用 Mutex；取消与超时交给 context，代码意图会更清晰、也更容易在团队中保持一致。

本章小结

要点 结论
goroutine go f() 启动轻量协程，M:N 调度，海量并发不靠海量线程
channel 无缓冲同步交接、缓冲解耦限流；仅发送方 close，v, ok := <-ch 判关闭
超时与取消 select + time.After 应急，生产推荐 context 贯穿调用链
共享状态 热点计数用 Mutex，读多写少用 RWMutex；-race 常开测竞态
三大陷阱 main 退出即进程退出、goroutine 泄漏、循环变量捕获，均需汇合点与显式传参

第一章：ClickHouse 列式存储入门

概念基础：ClickHouse 是什么

  1. 列式存储：ClickHouse 按列组织数据，SELECT avg(price) 只读 price 一列，IO 远小于行存全表扫描——这是它分析查询快的根源。
  2. 向量化执行：数据按列块批量进入对 CPU 缓存友好的计算路径，充分利用批量计算，吞吐远高于逐行解释执行。
  3. 专为 OLAP 而生：适合大规模聚合、日志与事件分析；不适合高并发单行点查、频繁小事务更新（OLTP 仍用 第一章：MySQL DDL 语句与表设计入门 等）。
  4. MergeTree 引擎家族：核心表引擎支持分区、排序键、TTL、副本，是绝大多数分析表的底座。
  5. 双协议接入：HTTP 8123（curl、JDBC HTTP、BI 工具）与 Native 9000（clickhouse-client、官方驱动）按场景选择。

Oracle

概念基础：Oracle 是什么/为什么

  1. 企业级关系型数据库：Oracle Database 是老牌商业 RDBMS，在银行、电信、政务等对稳定性、安全合规与厂商支持要求高的核心系统中长期占主导地位。
  2. 实例与数据库分离：Instance（内存 SGA + 后台进程）挂载并打开 Database（物理文件集合），多实例可共享访问同一套库（即 RAC）。
  3. 逻辑存储分层：数据组织在表空间（SYSTEM / SYSAUX / USERS / TEMP / UNDO）中，向下再划分为段、区、块。
  4. 高可用与容灾：RAC 多节点共享存储集群、Data Guard 主备容灾，配合 RMAN 备份恢复构成企业级方案。
  5. PL/SQL 过程化扩展：存储过程、包、触发器可在库内实现复杂业务逻辑，减少应用与数据库之间的往返。

  • Instance：内存结构（SGA）+ 后台进程（PMON、SMON、DBWn、LGWR 等），挂载并打开数据库。
  • Schema：用户拥有的对象集合（表、视图、过程等），常口语中与「用户」混用。

2. 连接方式

  • 监听器（Listener）：客户端通过 HOST:PORT/SERVICE_NAME 或 SID 连接。
  • 常用客户端：SQL*Plus、SQL Developer、JDBC（jdbc:oracle:thin:@//host:1521/orclpdb）。

第一章：MongoDB 概述与入门

概念基础：MongoDB 是什么

  1. 文档数据库：MongoDB 是面向文档的 NoSQL 数据库，数据以 JSON/BSON 文档存储，字段可嵌套、可数组——一个文档天然对应一个业务对象。
  2. 层级模型：Database → Collection → Document，类似关系库的「库 → 表 → 行」，但 Collection 不强制固定 Schema，同一集合内文档字段可以不一致，适合业务快速演进。
  3. 主键默认自带：每个文档有唯一 ObjectId 主键 _id，无需提前设计自增列。
  4. 默认端口与工具：默认监听 27017，交互用 mongosh（替代旧版 mongo CLI），命令风格贴近 JavaScript。
  5. 定位与取舍：需要强事务、复杂 JOIN 时关系库更成熟；需要灵活文档 + 水平扩展时 MongoDB 更常见——二者互补而非替代。

定位与概念

1. 文档模型

  • Database → Collection → Document（类似关系库中的库 → 表 → 行，但文档是 JSON/BSON 结构，字段可嵌套、可数组）。
  • 无固定 Schema：同一 Collection 内文档字段可以不完全一致，适合业务快速演进。
  • 默认 _id：每个文档有唯一 ObjectId 主键。

2. 适用场景

物联网 / 日志 时序或半结构化事件写入

缓存替代 部分场景可替代「大 JSON 存 Redis」，但内存与持久化策略不同

第一章：PostgreSQL 概述与 DDL 入门

发表于 2026-05-01 更新于 2026-08-30 分类于 PostgreSQL 本文字数： 1.6k 阅读时长 ≈ 5 分钟

第一章：PostgreSQL 概述与 DDL 入门

概念基础：PostgreSQL 与 DDL 是什么

  1. PostgreSQL 是开源的对象-关系型数据库：以 SQL 标准兼容与丰富的数据类型、扩展生态著称；数据按 数据库 → 模式（SCHEMA）→ 表 分层组织，客户端用 psql 或 JDBC 等驱动访问。
  2. SQL 按职责分两层：DDL（数据定义语言）管结构——库、模式、表、列、索引等对象的创建与变更；DML（数据操作语言）管数据——行级增删改查。本章聚焦 DDL。
  3. 为什么从 DDL 学起：结构是一切的地基——后面的高级查询、索引与性能、并发与 MVCC 都建立在「先有表结构」之上；类型与约束设计得当，能直接挡住一大批脏数据。
  4. 一条主线：CREATE 建、ALTER 改、DROP 删；生产环境永远先确认影响面（活跃连接、依赖对象），并养成 IF EXISTS 幂等习惯。

先看一条 DDL 在「客户端 → 引擎」链路中的位置：

DDL：数据定义语言

DDL：Data Definition Language 数据定义语言
作用：定义/修改/删除 数据库、模式（SCHEMA）、表、字段、索引等对象结构，不直接操作「行级业务数据」本身（数据由 DML 写入）。

客户端到引擎

第一章：MySQL DDL 语句与表设计入门

概念基础：DDL 与表结构是什么

DDL（Data Definition Language，数据定义语言）是 MySQL 中定义「结构」的语言：

  1. 管结构，不管数据：DDL 负责定义/修改/删除数据库、表、字段、索引、视图等对象，不操作表里的业务数据；管数据的是 DML（INSERT / UPDATE / DELETE / SELECT）——一句话记忆：「DDL 改架子，DML 改数据」。
  2. 建表即建模：把业务对象翻译成表，核心是选字段类型（INT / VARCHAR / DATETIME…）与定约束（主键、非空、唯一、默认值、外键）；结构一次设计、长期使用，返工成本高，所以建表是数据库学习的第一课。
  3. 结构最终落在存储引擎上：客户端 SQL 经 MySQL Server 交给 InnoDB，数据按主键组织成 B+ 树，通过 Buffer Pool 缓存、Redo Log 保证崩溃安全——表与索引结构如何组织，直接决定后面的查询性能（详见第五章、第六章）。
  4. 三大类对象：库操作、表操作，以及视图 / 索引 / 存储过程等对象定义；语句形式永远是 CREATE / ALTER / DROP 三板斧。
  5. 约束的权衡：FOREIGN KEY、UNIQUE 等约束由数据库兜底完整性，但会带来额外维护开销、且不利于分库分表，互联网业务常改用「逻辑外键」；入门先学会用，进阶再权衡取舍。

第一章：Redis 概述、安装与 CLI 入门

概念基础：Redis 是什么

Redis（REmote DIctionary Server）是一个基于内存的键值（KV）存储系统：

  1. 数据在内存：读写不落盘，单次操作微秒级，比磁盘数据库快 1~2 个数量级；同时提供 RDB / AOF 持久化把数据落到磁盘。
  2. KV 模型，值有类型：键（key） 永远是字符串；值（value） 支持多种数据类型（String / Hash / List / Set / ZSet 等），不同类型对应不同命令族与底层结构，这是 Redis 与 Memcached 这类「纯字符串 KV」最大的差别。
  3. 单线程命令执行：命令在单线程事件循环中顺序执行（基于 epoll / IO 多路复用），单个命令天然原子；Redis 6.0+ 引入的「多线程」只用于网络 IO 读写，命令执行仍是单线程。
  4. 为什么快：内存操作 + IO 多路复用 + 单线程无锁竞争 + 针对各类型优化的高效底层结构（SDS、跳表、quicklist 等）。
  5. 定位：缓存为主，兼任分布式锁、计数器、排行榜、消息队列、地理位置等；缓存 ≠ 数据库，关键数据以关系库为准，Redis 丢数据要有降级与重建预案。

概念基础：MyBatis-Plus 是什么、为什么

MyBatis-Plus（简称 MP） 是 MyBatis 的增强工具，定位是「只做增强不做改变」：

  1. 通用 CRUD：Mapper 继承 BaseMapper 即可获得 selectById、insert、update 等单表增删改查能力，免写 XML。
  2. 插件体系：通过 MybatisPlusInterceptor 注册分页、乐观锁、防全表更新等内部拦截器，按需装配。
  3. 分页零侵入：内置 PaginationInnerInterceptor，基于 MyBatis 拦截器自动生成 count 语句、改写 SQL 拼接 LIMIT，业务代码只传 Page 参数。
  4. 代码生成：配合 IDEA 插件（如 MyBatisX-Generator）可从数据库表直接生成 Entity / Mapper / Service 代码。
  5. Spring Boot 集成：提供 mybatis-plus-spring-boot*-starter 起步依赖，配好 mapper-locations 与驼峰映射即可使用。

一、核心一句话

MP 分页本质：MyBatis 拦截器 + 自动改写 SQL

  1. 你传入 Page<>(当前页,每页条数)
  2. MP 分页拦截器拦截 Mapper 查询方法

    MP 真正的分页拦截器，核心逻辑全在这。
  3. Page / IPage
    分页参数载体，存：当前页、每页条数、总记录数、总页数、分页数据。

四、为什么不用自己写 limit、不用自己写 count？

MP 拦截器动态解析 SQL、动态拼接 limit、动态生成 count，完全无侵入。

五、分页两个重要特性

1. 分页合理化 reasonable=true

  • 输入页码 <=0 自动变成第 1 页
  • 输入页码 大于总页数 自动返回最后一页

2. 溢出总页数后是否查最后一页

PaginationInnerInterceptor 可配置，防止页码乱输报错。

六、常见坑（原理衍生出来的）

  1. 没配置 PaginationInnerInterceptor → 分页无效，查全部数据
  2. 只有 Mapper 层用 Page 参数才生效，Service 自己写 list 不分页
  3. 自定义 XML SQL 也能自动分页，MP 照样拦截加 limit、count
  4. 多表联查、复杂 SQL 也支持，拦截器会解析原有 SQL 结构

七、极简总结

MP 分页 = 拦截器拦截SQL → 自动查总数 → 自动拼接LIMIT → 封装分页结果

不用手写 count、不用手写 limit，全靠拦截器动态代理实现。

本章小结

要点 结论
引入方式 mybatis-plus-spring-boot4-starter 起步依赖 + @MapperScan 扫描 Mapper 包
分页生效条件 必须注册 MybatisPlusInterceptor 并添加 PaginationInnerInterceptor，否则分页无效
分页原理 拦截器自动生成 count SQL 并改写原 SQL 拼接 LIMIT，两条 SQL 完成分页后封装进 IPage
实用特性 分页合理化 reasonable、溢出回退末页；自定义 XML 与多表联查 SQL 同样支持
常见坑 仅 Mapper 方法携带 Page 参数才触发分页；Service 自行 list() 不会分页

概念基础：Gradle 是什么、为什么

Gradle 是基于 JVM 的现代构建工具，广泛用于 Java / Kotlin / Android 项目：

  1. 脚本即代码：构建脚本用 Groovy DSL（build.gradle）或 Kotlin DSL（build.gradle.kts）编写，比 XML 更简洁、可编程。

  5. 与 Maven 的取舍：Maven 约定优先、上手简单；Gradle 更灵活、性能更好，但脚本自由度高，团队需要统一规范。

第一章：Maven 构建工具：安装、配置与常用命令

概念基础：Maven 是什么、为什么

Maven 是 Java 生态最主流的项目构建与依赖管理工具：

  1. 构建自动化：一条 mvn 命令即可完成编译、测试、打包、安装全流程，无需手工调用 javac、维护 classpath。
  2. 约定优于配置：默认标准目录结构（src/main/java、src/test/resources 等）与标准构建生命周期，代码按约定放置即可构建。

  5. 生命周期与插件：clean、compile、test、package、install 等命令本质是调用绑定在生命周期上的插件目标，可按需扩展。

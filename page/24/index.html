第三章：MongoDB 索引、聚合与模式设计

发表于 2026-05-01 更新于 2026-09-01 分类于 MongoDB 本文字数： 1.4k 阅读时长 ≈ 5 分钟

第三章：MongoDB 索引、聚合与模式设计

概念基础

  1. MongoDB 慢查询九成是索引问题：无索引的 find 是全集合扫描（COLLSCAN）；建对索引变成 IXSCAN，与关系库的「先看执行计划」哲学一致。
  2. ESR 原则定复合索引字段序：Equality（等值）→ Sort（排序）→ Range（范围），顺序排对一条复合索引能同时服务过滤与排序。
  3. 聚合管道是 MongoDB 的「SQL+ETL」：$match → $group → $sort → $project ... 流水线处理，能下推的尽量下推（先 $match 后 $group）。
  4. 模式设计决定性能上限：文档模型核心取舍是内嵌（embed）还是引用（reference）——按「一起读写就内嵌、各自更新就引用」判断。
  5. explain 是证据不是感觉：executionStats 里的 totalKeysExamined / totalDocsExamined / nReturned 三值关系直接给出诊断。

本章承接 第一章：MongoDB 概述与入门 的 CRUD 与 第二章：Docker 部署 MongoDB 实践 的环境；mongosh 语法按 MongoDB 7.x 官方文档书写（沙箱无实例，未逐条运行验证）。

一、explain：诊断查询

三个关键数字：

字段 含义 健康标准
nReturned 实际返回条数 —
totalKeysExamined 扫过的索引条目 接近 nReturned
totalDocsExamined 扫过的文档数 接近 nReturned（远大=回表浪费）

同时确认 winningPlan 里是 IXSCAN 而非 COLLSCAN；SORT_STAGE 出现说明排序没吃到索引（内存排序 32MB 上限会直接报错）。

二、索引体系

实践要点：

  • 每个额外索引都拖慢写入——索引不是越多越好，按真实查询建。
  • db.orders.getIndexes() 盘点存量；低效索引用 dropIndex 清理。
  • 大集合建索引用后台滚动构建（4.2+ 默认后台方式），避开写入高峰。
  • 最左前缀同样适用：{ userId, status, createdAt } 可服务 userId 与 userId+status 的查询。

三、聚合管道进阶

管道优化口诀：

原则 说明
$match/$limit 放最前 能被索引下推，后面的阶段数据越少越好
$project 砍字段 减少内存与网络传输
$group 用 _id: null 全表聚合（配合 $facet 一次算多组指标）
允许近似 超大集合统计可接受秒级误差时用 $sample 或预聚合

四、模式设计：内嵌还是引用

判断口诀：

场景 选择
1:1 或 1:少量（生命周期一致） 内嵌
1:多且子文档无限增长（评论、日志） 引用（或「内嵌最近 N 条 + 冷数据独立集合」）
多对多 引用
内嵌文档 16MB 上限 逼近上限必须拆

常见增强：$lookup 慢的高频关联可冗余一份 userName 到订单文档（写入时双写），用读时免 JOIN 换写时多一步——文档模型下的「反范式」是常规操作。

五、事务与批量写入

单文档天然原子：把需要原子性的关联数据内嵌进同一文档，很多「事务需求」就直接消失了——这是文档建模的隐藏红利。

本章小结

要点 结论
explain 看 COLLSCAN→IXSCAN；DocsExamined ≈ nReturned 才健康
复合索引 ESR（等值→排序→范围）定字段序；索引数量克制
特殊索引 TTL 管过期数据、partialFilterExpression 省空间、多键自动支持数组
聚合 $match 尽早、$project 砍字段、$lookup 对方 _id 要有索引
模式设计 一起读写就内嵌，独立增长就引用；单文档原子性替代小事务

第一章：MongoDB 概述与入门

概念基础

  1. 文档数据库：MongoDB 是面向文档的 NoSQL 数据库，数据以 JSON/BSON 文档存储，字段可嵌套、可数组——一个文档天然对应一个业务对象。
  2. 层级模型：Database → Collection → Document，类似关系库的「库 → 表 → 行」，但 Collection 不强制固定 Schema，同一集合内文档字段可以不一致，适合业务快速演进。
  3. 主键默认自带：每个文档有唯一 ObjectId 主键 _id，无需提前设计自增列。
  4. 默认端口与工具：默认监听 27017，交互用 mongosh（替代旧版 mongo CLI），命令风格贴近 JavaScript。
  5. 定位与取舍：需要强事务、复杂 JOIN 时关系库更成熟；需要灵活文档 + 水平扩展时 MongoDB 更常见——二者互补而非替代。

定位与概念

1. 文档模型

  • Database → Collection → Document（类似关系库中的库 → 表 → 行，但文档是 JSON/BSON 结构，字段可嵌套、可数组）。
  • 无固定 Schema：同一 Collection 内文档字段可以不完全一致，适合业务快速演进。
  • 默认 _id：每个文档有唯一 ObjectId 主键。

2. 适用场景

缓存替代 部分场景可替代「大 JSON 存 Redis」，但内存与持久化策略不同

第一章：PostgreSQL 概述与 DDL 入门

概念基础

  1. PostgreSQL 是开源的对象-关系型数据库：以 SQL 标准兼容与丰富的数据类型、扩展生态著称；数据按 数据库 → 模式（SCHEMA）→ 表 分层组织，客户端用 psql 或 JDBC 等驱动访问。
  2. SQL 按职责分两层：DDL（数据定义语言）管结构——库、模式、表、列、索引等对象的创建与变更；DML（数据操作语言）管数据——行级增删改查。本章聚焦 DDL。
  3. 为什么从 DDL 学起：结构是一切的地基——后面的高级查询、索引与性能、并发与 MVCC 都建立在「先有表结构」之上；类型与约束设计得当，能直接挡住一大批脏数据。
  4. 一条主线：CREATE 建、ALTER 改、DROP 删；生产环境永远先确认影响面（活跃连接、依赖对象），并养成 IF EXISTS 幂等习惯。

发表于 2026-05-01 更新于 2026-09-01 分类于 MySQL 本文字数： 1.8k 阅读时长 ≈ 6 分钟

第一章：MySQL DDL 语句与表设计入门

概念基础

DDL（Data Definition Language，数据定义语言）是 MySQL 中定义「结构」的语言：

  1. 管结构，不管数据：DDL 负责定义/修改/删除数据库、表、字段、索引、视图等对象，不操作表里的业务数据；管数据的是 DML（INSERT / UPDATE / DELETE / SELECT）——一句话记忆：「DDL 改架子，DML 改数据」。
  2. 建表即建模：把业务对象翻译成表，核心是选字段类型（INT / VARCHAR / DATETIME…）与定约束（主键、非空、唯一、默认值、外键）；结构一次设计、长期使用，返工成本高，所以建表是数据库学习的第一课。
  3. 结构最终落在存储引擎上：客户端 SQL 经 MySQL Server 交给 InnoDB，数据按主键组织成 B+ 树，通过 Buffer Pool 缓存、Redo Log 保证崩溃安全——表与索引结构如何组织，直接决定后面的查询性能（详见第五章、第六章）。
  4. 三大类对象：库操作、表操作，以及视图 / 索引 / 存储过程等对象定义；语句形式永远是 CREATE / ALTER / DROP 三板斧。
  5. 约束的权衡：FOREIGN KEY、UNIQUE 等约束由数据库兜底完整性，但会带来额外维护开销、且不利于分库分表，互联网业务常改用「逻辑外键」；入门先学会用，进阶再权衡取舍。

  1. 库操作：CREATE / ALTER / DROP 数据库
  2. 表操作：CREATE / ALTER / DROP 数据表

第一章：Redis 概述、安装与 CLI 入门

概念基础

Redis（REmote DIctionary Server）是一个基于内存的键值（KV）存储系统：

  1. 数据在内存：读写不落盘，单次操作微秒级，比磁盘数据库快 1~2 个数量级；同时提供 RDB / AOF 持久化把数据落到磁盘。
  2. KV 模型，值有类型：键（key） 永远是字符串；值（value） 支持多种数据类型（String / Hash / List / Set / ZSet 等），不同类型对应不同命令族与底层结构，这是 Redis 与 Memcached 这类「纯字符串 KV」最大的差别。
  3. 单线程命令执行：命令在单线程事件循环中顺序执行（基于 epoll / IO 多路复用），单个命令天然原子；Redis 6.0+ 引入的「多线程」只用于网络 IO 读写，命令执行仍是单线程。
  4. 为什么快：内存操作 + IO 多路复用 + 单线程无锁竞争 + 针对各类型优化的高效底层结构（SDS、跳表、quicklist 等）。
  5. 定位：缓存为主，兼任分布式锁、计数器、排行榜、消息队列、地理位置等；缓存 ≠ 数据库，关键数据以关系库为准，Redis 丢数据要有降级与重建预案。

理解了定位，再看它与周边的关系：

官网与定位

  • Redis 文档（当前产品站）：https://redis.io/docs/
  • 下载与发行说明：https://redis.io/downloads/
  • 命令参考：https://redis.io/commands/

Redis 以键值为核心，值支持多种数据类型（字符串、哈希、列表等）；默认监听 6379。与关系型数据库不同，数据主要在内存中，须结合淘汰策略、持久化与备份设计，避免单点丢数。

第三章：MyBatis-Plus 快速上手与分页原理

概念基础

MyBatis-Plus（简称 MP） 是 MyBatis 的增强工具，定位是「只做增强不做改变」：

  1. 通用 CRUD：Mapper 继承 BaseMapper 即可获得 selectById、insert、update 等单表增删改查能力，免写 XML。
  2. 插件体系：通过 MybatisPlusInterceptor 注册分页、乐观锁、防全表更新等内部拦截器，按需装配。
  3. 分页零侵入：内置 PaginationInnerInterceptor，基于 MyBatis 拦截器自动生成 count 语句、改写 SQL 拼接 LIMIT，业务代码只传 Page 参数。
  4. 代码生成：配合 IDEA 插件（如 MyBatisX-Generator）可从数据库表直接生成 Entity / Mapper / Service 代码。
  5. Spring Boot 集成：提供 mybatis-plus-spring-boot*-starter 起步依赖，配好 mapper-locations 与驼峰映射即可使用。

MyBatis-Plus 分页原理

一、核心一句话

MP 分页本质：MyBatis 拦截器 + 自动改写 SQL

  1. 你传入 Page<>(当前页,每页条数)
  2. MP 分页拦截器拦截 Mapper 查询方法
  3. 自动帮你生成 count 总数SQL + 拼接 limit 分页SQL
  4. 执行两条 SQL：查总数 → 查当前页数据
  5. 把总数、页码、数据封装到 IPage 返回

二、关键核心组件

  1. MybatisPlusInterceptor
    MP 核心插件容器，所有插件（分页、防全表更新、乐观锁）都往里注册。
  2. PaginationInnerInterceptor
    MP 真正的分页拦截器，核心逻辑全在这。
  3. Page / IPage
    分页参数载体，存：当前页、每页条数、总记录数、总页数、分页数据。

三、完整执行流程（一步一步走）

1. 配置分页拦截器（必须配置，否则分页无效）

2. 业务代码使用

3. 底层执行步骤

  1. 进入 Mapper 方法前
    PaginationInnerInterceptor 拦截到 selectPage 查询。
  2. 判断是否是分页查询
    检测方法参数里有没有 IPage/Page 对象，有就走分页逻辑。
  3. 自动生成 COUNT 语句
    原SQL：select id,name from user
    自动生成：select count(*) from user → 查询总记录数
  4. 改写原SQL 加 LIMIT
    原SQL 被改写为：
    select id,name from user limit 0,10
  5. 执行两条 SQL
    • 第一条：查总条数
    • 第二条：查分页数据
  6. 封装分页信息
    把总条数、当前页、每页大小、总页数、数据列表 全部塞进 IPage 返回。

四、为什么不用自己写 limit、不用自己写 count？

MP 拦截器动态解析 SQL、动态拼接 limit、动态生成 count，完全无侵入。

五、分页两个重要特性

1. 分页合理化 reasonable=true

  • 输入页码 <=0 自动变成第 1 页
  • 输入页码 大于总页数 自动返回最后一页

2. 溢出总页数后是否查最后一页

PaginationInnerInterceptor 可配置，防止页码乱输报错。

六、常见坑（原理衍生出来的）

  1. 没配置 PaginationInnerInterceptor → 分页无效，查全部数据
  2. 只有 Mapper 层用 Page 参数才生效，Service 自己写 list 不分页
  3. 自定义 XML SQL 也能自动分页，MP 照样拦截加 limit、count
  4. 多表联查、复杂 SQL 也支持，拦截器会解析原有 SQL 结构

七、极简总结

MP 分页 = 拦截器拦截SQL → 自动查总数 → 自动拼接LIMIT → 封装分页结果

不用手写 count、不用手写 limit，全靠拦截器动态代理实现。

要点 结论
引入方式 mybatis-plus-spring-boot4-starter 起步依赖 + @MapperScan 扫描 Mapper 包
分页生效条件 必须注册 MybatisPlusInterceptor 并添加 PaginationInnerInterceptor，否则分页无效
分页原理 拦截器自动生成 count SQL 并改写原 SQL 拼接 LIMIT，两条 SQL 完成分页后封装进 IPage
实用特性 分页合理化 reasonable、溢出回退末页；自定义 XML 与多表联查 SQL 同样支持
常见坑 仅 Mapper 方法携带 Page 参数才触发分页；Service 自行 list() 不会分页

groupId 没写包名前缀，项目名重复 中央仓库/私有仓库上传冲突，别人用你的 jar 时坐标撞车 用反域名：com.my919.xxx；内部项目至少 cn.mycorp.xxx，不要用裸 demo、common
version 写死 RELEASE / 依赖无版本 Maven 3.9+ 已拒绝无版本依赖；构建不稳定 所有依赖显式写版本；多模块用 <dependencyManagement> 统一版本（父 POM 里声明 <version>，子模块继承省略）
依赖冲突：同一 jar 两个版本共存 运行报 NoSuchMethodError、ClassNotFoundException，与本地运行不一致 用 mvn dependency:tree -Dincludes=:log4j 定位冲突；<exclusions> 排除传递依赖，或在最近的 <dependencyManagement> 锁定版本
dependency 写在父 POM 而不是 dependencyManagement 所有子模块强制继承这些依赖，哪怕根本用不到 版本管理放 <dependencyManagement>（只管版本，不引入）；真正要引入的才写 <dependencies>
<scope>provided</scope> 忘写 servlet-api、lombok、JDK 自带的包打进 war → 部署冲突或类重复 J2EE 容器/Tomcat 自带的、编译期注解处理（lombok）统一 provided；测试专用写 test
国内镜像配错 mvn 卡死在下载、超时或 404 ~/.m2/settings.xml 的 <mirror> 写 mirrorOf=central 或内网 Nexus；不要盲用 * 把所有仓库都镜像成一个（会错过 JBoss/Google 等第三方源）
快照（SNAPSHOT）用作生产发布 mvn install 拉到别人刚推的新 SNAPSHOT，行为变了都不知道 发版前必须 mvn release:prepare 或手工去 -SNAPSHOT；生产环境禁用 <updatePolicy>always</updatePolicy>
mvn clean package 没跑测试就上线 单元测试本来挂着，被本地 -DskipTests 习惯掩盖 CI 必须不跳过测试；本地临时跳过用 -DskipTests（编译测试类），少用 -Dmaven.test.skip=true（连编译都跳过）
多模块循环依赖 构建阶段报错 “The projects in the reactor contain a cyclic reference” 抽公共代码到第三模块 common；或模块内拆 package，不要用「A 依赖 B，B 依赖 A」
target/ 目录提交到 Git 仓库中出现一堆 class/jar，每次 PR 冲突 项目根放 .gitignore，至少忽略：target/、*.iml、.idea/、.classpath、.project
本地仓库脏了 以前失败下载留下 _remote.repositories 标记，死活不再拉取 find ~/.m2 -name "*.lastUpdated" -delete；或直接清出问题包的整个目录让 Maven 重新下
JDK 版本与 maven.compiler.source 不一致 用 JDK 21 编译成 8，String.valueOf 某些重载、Record 等编译报错 固定 <java.version>21</java.version> 并引用 ${java.version}；CI 用 actions/setup-java 同 JDK 大版本

第八章：FastAPI：现代 Python Web API 框架入门

概念基础

FastAPI 是近年 Python 社区增长最快的 Web 框架，专精 API 服务开发：

  1. 现代框架组合：Web 层基于 Starlette（异步 ASGI 框架），数据层基于 Pydantic（类型校验与序列化），强强联合。
  2. 类型驱动开发：请求参数、请求体、响应模型都用 Python 类型标注声明，框架自动完成解析、校验、错误提示——写类型就是写约束，也是写文档。
  3. 自动交互文档：启动即得 Swagger UI（/docs）与 ReDoc（/redoc），接口可在浏览器里直接调试，无需手写接口文档。
  4. 异步原生：基于 ASGI 规范，支持 async/await，配合 Uvicorn 的 uvloop / httptools 加速组件获得高并发 IO 性能。
  5. 定位取舍：相比 Django 的「全家桶」（ORM / Admin / 认证内置），FastAPI 只聚焦 API 层，数据库与认证按需组合，适合微服务、数据服务与 AI 推理接口。

常见避坑

坑 现象 正确做法
路径参数类型漏声明 /items/{id} 全按字符串收，内部 int(id) 可能抛 500 用 Pydantic 模型或 def read_item(id: int)，FastAPI 自动 422 + 友好错误
Body 参数忘加 Body(...) / Pydantic Model 单参数接口 Swagger 里永远是 query，不是 JSON body 显式 Body() 或定义 class Item(BaseModel)，两者二选一向 FastAPI 表明”从 body 读”
依赖注入（Depends）忘记调用 写了 get_db: Session = Depends(get_db)，但里面写的是同步 yield 却在异步路由里混用 同步路由 + 同步依赖，异步路由 + async def 依赖；数据库连接池按场景配 async-sqlalchemy 或同步库
422 但请求体没错 自定义模型里字段默认值用了 mutable [] / {}，数据互相污染 默认值永远写 Field(default_factory=list)，不要 items: list = []
CORS 没开或顺序错 前端浏览器报 No 'Access-Control-Allow-Origin'，Postman 却正常 最前面加 app.add_middleware(CORSMiddleware, …)，在路由注册之前；允许的 origins/headers/methods 写全
用了 run_in_threadpool 的同步 DB 查询也阻塞 Starlette 默认线程池小，并发高时排队 用 async SQLAlchemy + asyncpg 或 encode/databases；或 anyio.to_thread.run_sync + 调大 worker 数
Pydantic v1 vs v2 API 混用 旧教程的 @validator 提示不存在，Config 写成 class Config 报错 Pydantic v2 用 @field_validator，配置写 model_config = ConfigDict(...)；项目锁定 pydantic 大版本
响应模型写 response_model=None / 没写 数据库对象（带密码哈希）直接返回给前端，泄露敏感字段 严格定义 ReadUser、UpdateUser 等分离模型，显式写 response_model=
单文件 app.py 上千行 路由冲突、调试困难、import 循环 用 APIRouter 拆分模块：routers/users.py 中 router = APIRouter(prefix="/users")，主应用 app.include_router(router)
--reload 在生产用 内存泄漏、CPU 浪费、文件监听误触发重启 生产用 gunicorn -k uvicorn.workers.UvicornWorker 或 uvicorn main:app --workers 4，关闭 reload

UART

发表于 2026-05-01 更新于 2026-05-31 分类于 Embedded 本文字数： 377 阅读时长 ≈ 1 分钟

UART（Universal Asynchronous Receiver/Transmitter，通用异步收发器）是最常见的串行异步通信硬件：两根线（TX/RX）逐 bit 传输，无同步时钟线。下面从「帧格式 → 波特率 → 与 RS232/RS485 的关系 → MCU 配置要点 → 调试」顺序写清楚。

点对点连接



flowchart LR
  MCU1[MCU A TX] -->|RX| MCU2[MCU B RX]
  MCU2 -->|TX| MCU1

一、异步帧结构

  • 空闲：线路高电平。
  • 起始位：拉低，通知接收方开始采样。
  • LSB 先发：数据位从低位到高位。
  • 校验：None / Odd / Even（可选）。
  • 停止位：1 或 2 位高电平，恢复空闲。

二、波特率

常见：9600、115200、921600。收发双方波特率必须一致（误差通常 < 2%）。

三、电平与接口层

层次 说明
TTL UART MCU 引脚 3.3V/5V，直连 USB-TTL 模块
RS232 ± 电平，PC 老式串口、部分工业设备
RS485 差分、半双工、多机总线，常经 UART+收发器

UART 指控制器逻辑；对外物理层常加 MAX232、MAX485 等芯片。

四、应用与调试

  • 日志打印、AT 指令（4G/Wi-Fi 模块）、GPS NMEA、Bootloader。
  • Linux：/dev/ttyUSB0，minicom / picocom / screen。
  • 注意：TX 接 RX 交叉；共地 GND 必须连接。

与 SPI、I2C 对照：UART 线少、距离短（TTL）、协议简单，无硬件从机地址。

Modbus ASCII

发表于 2026-05-01 更新于 2026-05-31 分类于 Modbus 本文字数： 360 阅读时长 ≈ 1 分钟

Modbus ASCII 用 ASCII 十六进制字符 传输 Modbus PDU，帧以 : 开始、CR LF 结束，校验为 LRC（纵向冗余）。适合人工调试与部分老式设备；工业现场吞吐量通常不如 Modbus RTU。下面从「帧格式 → LRC 计算 → 与 RTU 选型 → 示例」顺序写清楚。

与 RTU 对比



flowchart LR
  subgraph ascii [Modbus ASCII]
    A1[可读 HEX 字符] --> A2[LRC 校验]
  end
  subgraph rtu [Modbus RTU]
    R1[二进制 ADU] --> R2[CRC16]
  end
  M[主站] --> ascii
  M --> rtu

一、帧格式

示例（读保持寄存器，概念）：

  • : 起始。
  • 每字节用 两个 ASCII 十六进制字符（0-9 A-F）。
  • CR LF 结束（0x0D 0x0A）。

二、LRC

对 地址到数据末字节 求和（8 位），取二进制补码（256 - sum），再转两个 ASCII 十六进制字符。

RTU 使用 CRC16；ASCII 用 LRC，检错能力较弱但实现简单。

三、与 RTU / TCP

变体 编码 效率 场景
RTU 二进制 高 RS485 主流
ASCII 文本 HEX 低（约 2× 字节） 调试、老设备
TCP 二进制 + MBAP 高 以太网

同一 PDU 功能码 语义一致；切换链路层时注意地址与寄存器映射相同。

四、调试

  • 串口终端可直接粘贴 : 帧（若设备支持 ASCII 模式）。
  • 物理层常为 RS232 或 RS485 + UART。
  • 生产系统优先 RTU 或 TCP，ASCII 多用于维护口。

Modbus TCP

Modbus TCP 将 Modbus PDU 封装在 TCP/IP 上：默认端口 502，增加 MBAP（Modbus Application Protocol Header），无 CRC（由 TCP 保证）。下面从「MBAP 头 → 与 RTU 的 PDU 关系 → 连接模型 → 与网关 → 安全」顺序写清楚。

TCP 连接模型

  PLC --> RTU[Modbus RTU 从站 经串口]

一、MBAP 头（7 字节）

字段 长度 说明
Transaction ID 2 事务标识，请求/响应配对
Protocol ID 2 固定 0
Length 2 后续字节数（Unit ID + PDU）
Unit ID 1 设备地址（经网关映射 RTU 从站）

其后为与 Modbus RTU 相同的 功能码 + 数据（无 CRC）。

三、连接模型

  • 单连接多事务：常见一客户端对一 PLC 长连接 502。
  • 并发：多客户端连同一设备需注意 PLC 连接数限制。
  • 与 HTTP：不同协议；工业网关可能同时提供 Modbus TCP 与 OPC UA。

四、串口网关

Modbus TCP ↔ RTU 网关：
Unit ID 映射 RS485 从站地址；网关内维护 RS485 轮询时序。

五、安全

  • 502 明文、无认证 → 仅放工控内网或 VPN；勿暴露公网。
  • 现代方案：TLS 隧道、VPN、专用安全网关。
  • 与 Modbus ASCII 比：TCP 适合跨交换机、远程 SCADA。

Modbus RTU

发表于 2026-05-01 更新于 2026-05-31 分类于 Modbus 本文字数： 453 阅读时长 ≈ 2 分钟

Modbus RTU 是 Modbus 协议在二进制串行链路上的实现，最常见物理层为 RS485：主站轮询、从站地址、功能码、CRC16 结尾。下面从「ADU 帧 → 常用功能码 → 时序与 3.5 字符 → 与 ASCII/TCP 对照 → 调试工具」顺序写清楚。

主从轮询



sequenceDiagram
  participant M as 主站 PLC
  participant S as 从站 地址 1
  M->>S: 读保持寄存器 FC03
  S-->>M: 数据 + CRC
  M->>S: 写单个寄存器 FC06
  S-->>M: ACK

一、RTU 帧结构

  • 地址 0：广播（从站不应应答）。
  • CRC：对地址到数据末字节计算 Modbus CRC16。

示例（读保持寄存器 0x03）：主站发 01 03 00 00 00 0A C5 CD（含义依上下文解析）。

二、常用功能码

码 名称 说明
0x01 Read Coils 读线圈（位）
0x03 Read Holding Registers 读保持寄存器（16 位）
0x04 Read Input Registers 读输入寄存器
0x06 Write Single Register 写单寄存器
0x10 Write Multiple Registers 写多寄存器

异常应答：功能码 + 0x80，后跟异常码。

三、时序（RTU 特有）

帧间静默 ≥ 3.5 字符时间（与波特率相关），用于帧界定；波特率高时该间隔很短，实现需精确。

  • 115200 下对 MCU 中断延迟更敏感。
  • 半双工 RS485 需在发送前使能 DE。

四、与其它 Modbus

变体 链路 帧界定
RTU RS485/RS232 静默 + CRC
ASCII 串口 : 起 CRLF 止，LRC
TCP 以太网 MBAP 头 + 无 CRC

寄存器地址映射（40001 等）在文档与 PDU 偏移间需 减 1 转换，避免 off-by-one。

五、调试

  • Modbus Poll / Slave（Windows）、pymodbus、QModMaster（Linux）。
  • 抓包：串口监听或 RS485 分析仪。
  • 与 UART 关系：RTU 是应用层协议，底下是异步串口 + 485 收发器。

Modbus 组织：https://modbus.org/

QUIC 详解：基于 UDP 的可靠传输、TLS 集成与 HTTP/3

发表于 2026-05-01 更新于 2026-05-31 分类于 QUIC 本文字数： 1.6k 阅读时长 ≈ 5 分钟

QUIC（IETF QUIC，RFC 9000）在 UDP 之上实现加密、多路复用、连接迁移与类 TCP 的可靠传输；HTTP/3（RFC 9114）将 HTTP 语义映射到 QUIC 流上。下面从「设计目标 → 连接与完整通信流程（握手、传数据、关闭） → 流、可靠性与拥塞控制 → Connection ID 与端口 → TLS 1.3 → HTTP/3 与 HTTP/2 → 抓包与可观测性 → curl/Python 验证 → 运维注意」顺序写清楚。

一、设计目标与作用

1. 解决什么问题

  • 在 UDP 上重建可靠管道：丢包检测、重传、拥塞控制发生在 QUIC 层，而不依赖 TCP 单一流上的队头阻塞。
  • 默认加密：传输与握手深度绑定 TLS 1.3（RFC 9001），减少「明文旁路」与分层带来的额外往返。
  • 多流与连接标识：Stream 隔离应用数据；Connection ID 让四元组变化时仍能延续同一逻辑连接（连接迁移）。

2. 相对 TCP + TLS 的典型取舍

问题 TCP + TLS 常见表现 QUIC 思路
队头阻塞 TCP 字节流级丢包会阻塞后续所有应用数据 QUIC 在流级相对独立地做丢包恢复
握手 RTT 常需 TCP 三次握手再叠 TLS 往返 常把加密与传输握手合并，目标 1-RTT 建连（0-RTT 为可选加速）
NAT 重绑定 四元组变化常被视作「新连接」 Connection ID 标识逻辑连接，支持连接迁移
中间设备 TCP 成熟、穿透好 依赖 UDP 放行（如 UDP/443）；企业网策略需对齐

二、连接与完整通信流程（原理）

QUIC 报文封装在 UDP 数据报中（常见 HTTPS 场景为 UDP/443）。以下极度简化，省略版本协商、重试包、地址验证等细节。

1. 建立连接（简化）

首包常带 TLS ClientHello；成功后在 1-RTT 密钥下发送应用数据。0-RTT 可在重复连接时提前带数据，见第五节安全注意。

2. 关闭连接（简化）

任一方可发送 CONNECTION_CLOSE 帧；对端进入排空（draining）期，不再发送新数据。与 TCP 的 FIN/ACK 不同，QUIC 在连接粒度表达关闭，内部再回收流与 UDP 套接字资源。

3. 与典型「套接字 / 协议栈」的对应

与 TCP 的 connect/accept 由内核一条龙完成不同，QUIC 一般由用户态库（如 ngtcp2、quiche、MsQuic、aioquic）或浏览器网络栈实现：底层仍是 UDP sendto/recvfrom，其上是 TLS 1.3、ACK/重传、流控与 HTTP/3 帧。HTTP/3 客户端日常通过 curl --http3-only 或内置 HTTP/3 的 SDK 使用，而不是手写裸 UDP 报文。

三、流、可靠性与拥塞控制（原理要点）

  • Connection：加密上下文、ACK 与拥塞控制的归属单位（类似「一条加密了的类 TCP 管道」）。
  • Stream：单向或双向；HTTP/3 将请求/响应映射到不同流，减轻应用级队头阻塞。
  • Packet Number：单调递增，配合 ACK 范围与密钥更新，降低与 TCP 序号相关的歧义；重传不重用旧 PN（新包新号）。
  • 拥塞控制：在 Connection 上运作（如 Cubic、BBR 等实现依栈而定），与 TCP 一样受网络条件约束，但并非「一条字节流管所有多路复用对象」。

四、Connection ID、端口与「会话标识」

  • UDP 四元组仍用于路由首个报文；Connection ID 使源 IP/端口变化（如蜂窝切换 Wi-Fi）后，对端仍能识别同一 QUIC 连接。
  • 公网 HTTP/3 常见端口为 443（UDP），与 TCP 443 并存、互不替代。
  • 服务端可协商 CID 长度与轮换策略，以兼顾隐私与路由。

五、TLS 1.3 与 QUIC（原理）

QUIC 使用 TLS 1.3 做身份认证与密钥导出；载荷由 AEAD 保护，PADDING 等机制缓解流量分析。0-RTT 可加速重复连接，但存在重放风险：对金融类写操作应禁用或在应用层做幂等与二次校验。

六、HTTP/3 与 HTTP/2 对比（概念）

项 HTTP/2 over TCP HTTP/3 over QUIC
传输 TCP 字节流 UDP 上的 QUIC
多路复用 H2 帧共享一条 TCP 连接 QUIC 流级隔离，丢包影响面更小
TLS 传统分层（先 TCP 再 TLS） 与 QUIC 握手紧耦合

HTTP 语义（方法、状态码、首部）仍见 HTTP 一文；HTTPS 在 HTTP/3 场景下体现为 QUIC + TLS 1.3 的组合。

RPC 概念详解：原理、形态与 JSON-RPC / curl 示例

发表于 2026-05-01 更新于 2026-05-31 分类于 Protocol 本文字数： 598 阅读时长 ≈ 2 分钟

RPC（Remote Procedure Call，远程过程调用）是一种编程抽象：像调用本地函数一样发起远程执行，由 stub 负责序列化参数、经网络发送、在服务端 skeleton 反序列化并调度真实实现，再返回结果。下面从「原理与边界 → 常见序列化与传输 → 失败语义与幂等 → JSON-RPC 2.0 与 curl 示例 → 与 REST、gRPC 对比」顺序写清楚；gRPC 见 gRPC，Java Dubbo 见 Dubbo。

一、原理（.stub 与存根）

RPC 不规定具体字节格式；可由 JSON、protobuf、Thrift 等定义。

二、作用与典型场景

  • 微服务内部：低延迟、强类型契约（常选 gRPC）。
  • 链上节点：Ethereum JSON-RPC 等文本 RPC。
  • 脚本自动化：轻量 JSON-RPC 管理接口。

三、传输与序列化（对照表）

组合 说明
JSON + HTTP 人可读，易调试
protobuf + HTTP/2 gRPC 默认路径
二进制 + 自定义 TCP 高性能私有协议

四、失败语义与幂等（原理）

  • 超时：客户端不知服务端是否已执行；重试可能导致重复扣款。
  • 对策：幂等键、去重表、At-least-once 消费语义与业务配合。

MQTT 详解：发布订阅、QoS 与 mosquitto / Python 示例

发表于 2026-05-01 更新于 2026-05-31 分类于 Protocol 本文字数： 660 阅读时长 ≈ 2 分钟

MQTT 是轻量级发布/订阅消息传输协议（OASIS MQTT v3.1.1 / v5.0），面向低带宽与不稳定链路，常用于 IoT 与遥测。客户端连接 Broker，按 Topic 发布与订阅消息，彼此解耦。下面从「模型与作用 → 主题与通配符 → QoS 语义（原理） → 会话与遗嘱（v5 简述） → mosquitto 命令行示例 → Python paho-mqtt 示例」顺序写清楚；传输层通常为 TCP 1883 或 TLS 8883，与 HTTP 请求/响应模型不同。

发布订阅模型



flowchart TB
  P1[Publisher 传感器] -->|publish topic/sensor| B[MQTT Broker]
  P2[Publisher 设备] --> B
  B -->|subscribe| C1[Consumer 大屏]

一、模型与作用（原理）

Broker 根据 Topic 字符串路由消息；发布者不必知道订阅者列表。

二、主题与通配符（作用）

  • 层级：用 / 分层，如 factory/line1/temp。
  • 单级通配 +：匹配一层，如 factory/+/temp。
  • 多级通配 #：匹配剩余层级，须在末尾（细节以 v5 文档为准）。

Topic 大小写敏感；$SYS/ 常为 Broker 系统主题（依实现）。

三、QoS（原理）

QoS 名称 语义
0 至多一次 可能丢，不重试
1 至少一次 可能重复，需业务幂等
2 恰好一次 四次握手，开销最大

QoS 在发布方向与订阅方向可分别指定，最终有效语义取二者较高一侧规则（以 Broker 实现与文档为准）。

四、遗嘱消息（Last Will，概念）

连接异常断开时 Broker 可代发预设 Payload 到指定 Topic，用于设备离线告警；须正确配置 Keep Alive 与心跳。

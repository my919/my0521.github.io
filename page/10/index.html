第六章：OpenSSL 数字签名与 HMAC：完整性、身份与推荐用法

概念基础：签名与 HMAC 是什么、为什么需要

  1. 数字签名 = 私钥签名 + 公钥验证：一次性保证完整性（内容未被篡改）、身份认证（签名者身份可信）与不可否认（只有私钥持有者能签出）。
  2. 标准流程：先对消息做哈希（SHA-256，见第三章），再用私钥对摘要签名；验证方用公钥复算比对——这也是「对大数据直接 RSA 签名」是错误做法的原因。
  3. HMAC 是对称认证：双方共享同一 secret，用 HMAC-SHA256 计算带密钥的摘要；快、实现简单，但双方都能生成，因此不可否认。
  4. 怎么选：公开分发场景（软件发布、证书、JWT）→ 数字签名；双方已有共享密钥的场景（API / Webhook 鉴权）→ HMAC。
  5. 常见坑：对明文直接 RSA 签名大数据、HMAC 密钥硬编码进代码、验签时不检查证书链——本章末尾「常见错误」逐条纠正。

场景选型

场景 推荐 说明
软件发布、固件、JWT（RS256/ES256） RSA-PSS / ECDSA / Ed25519 + SHA-256 公钥可公开分发
TLS 证书链 CA 私钥签名 + SHA-256 见 第一章：OpenSSL 命令行入门与常用操作总览
API 请求鉴权（双方已有密钥） HMAC-SHA256 Webhook、AWS Signature V4 同类思路
口令验证存储 不适用裸 HMAC 用 PBKDF2 / Argon2 见 第七章：OpenSSL 密钥派生与随机数：PBKDF2、rand 与推荐用法

第五章：OpenSSL 非对称加密与密钥交换：RSA、Ed25519、X25519

概念基础：非对称加密是什么、为什么需要

  1. 非对称加密：公钥 / 私钥成对，公钥公开分发、私钥绝对保密——解决了对称加密「密钥如何安全送达」的死结（对称加密见第四章）。
  2. 三大用途：数字签名（私钥签、公钥验，见第六章）、密钥交换（ECDHE/X25519 在不安全信道协商会话密钥）、小数据加密（RSA-OAEP 加密对称密钥）。
  3. 为什么 TLS 用混合方案：非对称慢（比对称慢几个数量级），只用于握手阶段；海量数据用协商出的对称会话密钥（AES-GCM）加密。
  4. 前向保密（PFS）：握手使用临时密钥对（X25519 / ECDHE），即使服务器长期私钥日后泄露，历史会话也解不开——静态 RSA 密钥传输因此被淘汰。
  5. 选型一句话：签名与证书新系统优先 Ed25519 / ECDSA P-256，密钥交换用 X25519，RSA 2048+ 仍是最普遍的兼容选择。

推荐选型（2020s）

用途 推荐 避免 / legacy
TLS 证书 / 代码签名 ECDSA P-256、Ed25519；RSA 仍普遍 RSA < 2048 bit
TLS 密钥交换 X25519（ECDHE） 静态 RSA 密钥传输、DHE 1024 bit
SSH / 现代签名 Ed25519 DSA
小数据 RSA 加密 RSA-OAEP 2048+（仅短载荷） PKCS#1 v1.5 加密、裸 RSA
长期根 CA RSA 4096 或 EC P-384 RSA 1024

第四章：OpenSSL 对称加密：AES-GCM、ChaCha20 与推荐用法

发表于 2026-05-01 更新于 2026-08-30 分类于 OpenSSL 本文字数： 1.2k 阅读时长 ≈ 4 分钟

第四章：OpenSSL 对称加密：AES-GCM、ChaCha20 与推荐用法

概念基础：对称加密是什么、为什么这样选

  1. 对称加密：加密与解密使用同一把密钥，速度快、开销低，适合大块数据（文件、磁盘、TLS 记录层流量）。
  2. 两大要素：算法 + 工作模式（如 AES-256-GCM）决定安全性质；密钥来自随机数或口令派生（PBKDF2，见第七章）。
  3. 为什么推荐 AEAD：GCM / ChaCha20-Poly1305 属于认证加密，同时提供保密性 + 完整性（Auth Tag 防篡改）；裸 CBC / ECB 无认证，存在填充 oracle 等风险。
  4. Nonce 纪律：GCM 的 (key, nonce/IV) 绝不能重复，否则密钥流泄露、安全性崩塌——这是使用 AEAD 的头号大坑。
  5. 口令 ≠ 密钥：人类口令熵低、可猜测，必须经 KDF（salt + 高迭代） 派生密钥；生产环境更推荐随机 32 字节密钥。

推荐算法（2020s 生产）

优先级 算法 / 模式 用途
首选 AES-256-GCM 文件加密、磁盘、API 载荷（须唯一 nonce）
首选（无 AES 硬件加速时） ChaCha20-Poly1305 移动端、部分 TLS 1.3 套件
可用 AES-256-CBC + HMAC（Encrypt-then-MAC） 老系统；须正确实现
避免 AES-CBC 无 MAC、ECB、DES/3DES、RC4 填充 oracle、模式泄露、已淘汰

第三章：OpenSSL 哈希算法：SHA-256、SHA-3 与推荐用法

发表于 2026-05-01 更新于 2026-08-30 分类于 OpenSSL 本文字数： 1k 阅读时长 ≈ 3 分钟

第三章：OpenSSL 哈希算法：SHA-256、SHA-3 与推荐用法

概念基础：哈希是什么、为什么需要

  1. 哈希（Hash）是单向函数：任意长度输入 → 固定长度摘要（SHA-256 输出 256 bit），不可逆——无法从摘要还原原文。
  2. 三大特性：确定性（同输入必得同输出）、雪崩效应（改动 1 bit，摘要面目全非）、抗碰撞性（极难找到两个不同输入对应同一摘要）。
  3. 为什么需要：完整性校验（下载包比对、防篡改）、签名输入（先哈希再签名，见第六章）、口令派生（加盐迭代，见第七章）、区块链 Merkle 树等。
  4. 哈希 ≠ 加密：哈希不可逆、无密钥，用于完整性与指纹；对称加密可逆、有密钥，用于保密性（本章末尾有对照表）。
  5. 选型一句话：新系统一律 SHA-256 / SHA-512，需要算法多样性时上 SHA-3；MD5、SHA-1 仅用于遗留系统兼容。

算法选型（推荐）

文件完整性校验、软件发布 SHA-256、SHA-512 MD5、SHA-1
密码存储 Argon2 / bcrypt（应用层库）+ 盐；OpenSSL 侧用 PBKDF2-HMAC-SHA256 见 第七章：OpenSSL 密钥派生与随机数：PBKDF2、rand 与推荐用法 裸 SHA-256(password)
证书/CSR 签名摘要 SHA-256 SHA-1
长数据流式哈希 SHA-256 —
新标准/长摘要需求 SHA-3-256 —

第一章：OpenSSL 命令行入门与常用操作总览

概念基础：OpenSSL 是什么、为什么无处不在

  1. OpenSSL 是一个开源密码学工具包：对外提供 openssl 命令行工具（生成密钥、证书、加解密、签名），对内提供底层密码库（libcrypto / libssl），是 TLS/HTTPS 生态的事实标准。
  2. 它解决三类安全问题：保密性（对称 / 非对称加密）、完整性（哈希 / HMAC）、身份认证（数字证书 + CA 信任链）；HTTPS 正是三者的组合应用。
  3. 四个核心对象：私钥（.key / .pem，必须保密，用于解密、签名）；公钥（从私钥导出，公开分发，用于加密、验签）；证书（.crt / .pem，包含公钥 + 身份信息 + 签名，证明公钥合法）；CSR（证书签名请求，.csr，向 CA 机构申请正式证书的文件）。
  4. 为什么重要：Nginx、curl、Python、Java、手机系统等几乎所有软件的加密通信都依赖它——掌握 OpenSSL 命令行，等于掌握证书、加密、签名的通用钥匙。
  5. 本章定位：侧重命令行实操，给出从摘要、密钥到证书签发、格式转换的完整工作流；各算法的原理与选型详见后续章节。

OpenSSL 是生成、管理非对称密钥和数字证书的标准工具，广泛用于 第四章：HTTPS 详解：TLS 握手、证书与 openssl/curl 示例、SSL/TLS、身份认证等。能力概览见 第二章：OpenSSL 功能全景与自建局域网 CA 实战；算法分类与推荐用法见下表。

GraphQL

概念基础：GraphQL 是什么/为什么

  1. API 查询语言：GraphQL 由 Facebook 开源，客户端在单一端点上按需声明「要哪些字段」，服务端精确返回同构数据，避免多余传输。

  5. 生态成熟：Apollo（Server/Client）、GraphiQL 调试 IDE、Hasura 自动生成等工具链完善。

一、核心概念

  • Schema（模式）：用强类型定义数据结构与关系，是 GraphQL 的“契约”，包含：
    • Query：查询（读操作）入口
    • Mutation：变更（写操作）入口
    • Subscription：订阅（实时更新，基于 WebSocket）
  • Type（类型）：定义对象结构，如 User、Post，含字段与类型（标量/对象/列表/非空）。
  • Resolver（解析器）：服务端函数，负责按字段获取/处理数据（数据库、微服务、第三方 API 均可）。
  • Query（查询）：客户端声明式请求，结构即响应结构。
  • Mutation（变更）：用于创建/更新/删除数据，语法类似 Query。

二、核心优势（对比 REST）

维度 GraphQL REST
数据获取 客户端精准指定字段，无过度获取 固定返回结构，易冗余
请求次数 单一请求获取多资源（如用户+文章） 需多端点请求，易“请求瀑布”
版本控制 Schema 渐进演进，无需版本号 需维护 v1/v2 多版本
文档 基于 Schema 自动生成（如 GraphiQL） 需手动维护（Swagger 等）
实时能力 原生支持 Subscription（WebSocket） 需轮询/SSE，成本高
缓存 依赖客户端/实体缓存（如 Apollo） 天然适配 HTTP 缓存

关键结论：GraphQL 显著减少数据传输量与请求次数，弱网/移动端收益极大；REST 更简单、成熟、缓存友好，适合简单场景。

三、工作流程

  1. 定义 Schema：服务端用 SDL（Schema Definition Language）定义类型、Query、Mutation。
  2. 实现 Resolver：每个字段对应解析器，对接数据源。
  3. 客户端请求：发送 POST 到单一端点（如 /graphql），携带 Query/Mutation。
  4. 服务端执行：校验 Query → 调用 Resolver → 按请求结构返回 JSON。
  5. 客户端接收：响应结构与 Query 完全一致，直接渲染。

四、适用场景

  • ✅ 复杂前端应用（如电商、社交）：多数据关联、按需字段。
  • ✅ 移动端/弱网环境：减少请求与数据体积。
  • ✅ 微服务架构：统一网关聚合多服务数据。
  • ✅ 实时功能（聊天、通知、实时看板）：Subscription 原生支持。
  • ❌ 简单 CRUD 服务：REST 更轻量、易维护。
  • ❌ 高缓存吞吐场景：REST HTTP 缓存更高效。

  • 客户端：Apollo Client（React/Vue/Angular）、Relay（Meta）、urql。
  • 开发工具：GraphiQL（内置 IDE）、Playground、GraphQL Voyager（可视化 Schema）。

第四章：RocketMQ 核心概念与架构

概念基础：RocketMQ 是什么

Apache RocketMQ 是源自阿里巴巴电商场景的分布式消息中间件：低延迟、高并发、业务消息能力开箱即用。本文侧重 MQ / 微服务视角。

  1. 本质是「Topic + Queue」：消息按 Topic 分类，每个 Topic 切成多个 Message Queue（读写队列），Queue 是并行与顺序的基本单位——角色类似 Kafka 的 Partition，但围绕它的消费语义更「业务」。
  2. 为什么业务系统选它：延迟消息、事务消息、顺序消息、消费重试与死信队列都是内置能力，不必像 Kafka 那样自建重试 Topic / 延迟调度器。
  3. 三大角色：NameServer（无状态路由中心）、Broker（存储与转发）、Producer / Consumer。客户端先问 NameServer 拿路由，再直连 Broker 收发。
  4. 权衡：流式生态（Streams / Connect 类）不如 Kafka；但 Java 技术栈、国内云厂商与 Spring Cloud Alibaba 集成更顺。对照见本章「与 Kafka 的对照」小节。

先看整体架构：

架构组件



flowchart TB
  P[Producer] --> B[Broker Master]
  B --> NS[NameServer 路由]

组件 作用 要点
NameServer 路由注册中心，轻量、无状态 节点间互不通信，客户端轮询任一节点；几乎没有运维成本
Broker 存储与转发，分 Master / Slave 所有消息写入 CommitLog（单一文件顺序写），再异步分发到各 Queue 的索引
Producer 发送消息 与 Broker 直连发送；NameServer 只用于找地址
Consumer 拉取消息 Push 模式底层是长轮询拉取，并非服务端真推送

客户端通过 NameServer 发现 Broker 地址；Broker 每 30s 向 NameServer 上报路由，客户端在本地缓存路由表。

Topic 与 Queue

  • Topic：逻辑分类。
  • Message Queue：Topic 下分片（类似 Kafka 分区，语义略有不同）；Queue 数 = 消费并行度上限。
  • Tag / Key：Tag 用于消费端二级过滤；Key 建立哈希索引，供控制台按业务键查询。

理解要点：与 Kafka「分区数决定并行度」同理，Consumer 实例数超过 Queue 数时多出的实例空闲；规划 Topic 时先估消费并行度再定 Queue 数。

消费模型

模式 说明
CLUSTERING 同组负载均衡，一条消息只被一个实例消费
BROADCASTING 组内每实例全量接收
重试 / DLQ 消费失败进入重试队列（%RETRY%组名）延时重投，默认 16 次，超限进死信（%DLQ%组名）

理解要点：重试 + 死信是 RocketMQ 相对 Kafka 最大的「开箱能力差」——消费失败自动按递增间隔重试，业务只需监听死信 Topic 做人工兜底，不需要自建重试机制。

消息可靠性：刷盘与复制

维度 同步 异步
刷盘 SYNC_FLUSH：落盘才返回成功，不丢但延迟高 ASYNC_FLUSH：写入 page cache 即返回，宕机可能丢少量
复制 SYNC_MASTER：Slave 同步完成后返回 ASYNC_MASTER：默认，性能优先

生产常见组合：ASYNC_FLUSH + SYNC_MASTER（或 DLedger 自动主从切换）；金融级再上同步刷盘。这与 Kafka 的 acks=all + ISR 解决的是同一件事——「写成功」的定义。

顺序、延迟与事务

1. 顺序消息

同一 MessageQueue 内 FIFO；发送端按 orderId 等 sharding key 用 MessageQueueSelector 固定路由，消费端用 Orderly 监听器串行处理。代价：该 Queue 所在实例故障期间，对应分片的顺序消费会短暂阻塞。

2. 延迟消息

内置延迟级别（1s、5s、1m…2h 共 18 级），适合订单超时关闭、失败退避重试；5.x 起支持任意时间精度（基于时间轮）。

3. 事务消息

Half 消息 + 本地事务 + 回查：先发半消息（对消费者不可见）→ 执行本地事务 → 提交 / 回滚；Broker 对未决事务定时回查生产者。与 Seata 同步事务可对照选型（见 第一章：cloud 微服务工程架构总览与生产落地 当前 Feign + Seata 链路）。

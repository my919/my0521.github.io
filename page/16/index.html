第一章：Linux 常用命令与运维入门

概念基础

  1. 内核与发行版：Linux 内核只有一份，日常使用的是「内核 + 包管理器 + 软件仓库」组成的发行版（RHEL 系、Debian 系、Arch 等），选型直接决定包管理器与生态。
  2. 一切皆文件：配置（/etc）、可变数据（/var）、设备与进程信息都以文件形式呈现，运维工作的本质常常就是「读文件、改文件、管进程」。
  3. 权限模型：每个文件有 user / group / other 三组 rwx 权限，chmod / chown 是多用户系统的第一道防线。
  4. Shell 是操作入口：默认多为 bash，脚本首行 #!/bin/bash；服务器运维的主战场是命令行而非图形界面。
  5. 服务由 systemd 托管：常驻服务以 .service 单元交给 systemd 管理，systemctl / journalctl 是服务排障的标配工具。

发行版与 Shell

系列 包管理 典型用途
RHEL / Rocky / Alma dnf/yum 企业服务器、K8s 节点
Debian / Ubuntu apt 云主机、桌面、CI
Arch pacman 滚动更新、开发者桌面

默认 Shell 多为 bash；脚本首行 #!/bin/bash，交互与运维命令在终端执行。

文件系统与权限

  • 根目录 /：/etc 配置、/var 可变数据、/home 用户家目录、/tmp 临时。
  • 软/硬链接：ln -s 与 ln。
  • 查找：find、grep（或 ripgrep）。

进程与服务

  • systemd：.service 单元管理守护进程。
  • cron / timer：定时任务。
  • ulimit：打开文件数、进程数限制（高并发服务需调优）。

网络

DNS、路由、iptables/nftables 排障是运维常见技能；协议细节见 第一章：TCP 协议详解：连接、可靠传输与编程示例、第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例。

包管理与容器

第一章：Docker 容器基础 与 第二章：Kubernetes 容器编排入门 多数运行在 **Linux** 内核特性（namespace、cgroup）之上。

WSL 与开发环境

Windows 上可用 WSL2 运行 Linux 发行版，与 Docker Desktop、VS Code Remote 配合。本站 第二章：Windows 上 WSL（Rocky Linux）与 Docker Desktop 记录 Rocky Linux 子系统安装与注意点。

学习路径建议

  1. 熟练 Vim/nano、ssh、scp/rsync
  2. 理解 systemd、日志与磁盘（df/du/lsof）
  3. 会写 bash 脚本处理批量运维
  4. 结合 第一章：Nginx 入门与静态服务、数据库与中间件 Docker 文章做实战

第四章：PyTorch 部署与分布式

第四章：PyTorch 部署与分布式

概念基础

  1. 训练与推理是两种工程：训练求快求全（Python 动态图），部署求稳求小（静态图、无 Python 依赖、常驻服务）。
  2. ONNX 是推理通用货币：把模型导出为 ONNX 后，可用 ONNX Runtime、OpenCV cv2.dnn（见 第五章：视频与深度学习）、TensorRT 等引擎推理，摆脱 Python 环境。
  3. DDP 是多卡标配：每卡一份完整模型 + 独立 DataLoader 分片，前向各算各的、反向自动同步梯度——比早期的 DP 快且稳。
  4. 服务化就是套壳 HTTP：FastAPI 包一层推理函数即可上线；关键在 batch 合并、并发与预热，不在框架。
  5. 大模型时代的延伸：单卡装不下 → 模型并行/ZeRO（FSDP）；Hugging Face Transformers（见 第三章：LLM 大语言模型基础）把这一层封装好。

二、FastAPI 服务化

上线三件事：model.eval() + inference_mode()（必做）；推理进程与训练进程分开部署；给服务加超时与限流（Nginx 层见 第三章：Nginx HTTPS 与安全）。

三、DDP 多卡训练

DDP 三条铁律：模型先 .to(device) 再包 DDP；DataLoader 必须用 DistributedSampler；保存权重用 model.module.state_dict() 且只在 rank 0 做。

四、大规模训练一瞥

技术 一句话 工具
FSDP / ZeRO 参数/梯度/优化器状态分片到各卡，单卡装得下超大模型 torch.distributed.fsdp
梯度检查点 用算力换显存（第三章） torch.utils.checkpoint
量化 INT8/INT4 推理，显存除以 4~8 bitsandbytes、torchao
混合精度 FP16/BF16 训练标配（第三章） torch.amp

一般工程结论：多卡数据并行（DDP）覆盖绝大多数场景；模型大到单卡放不下才进 FSDP/量化的世界。

第三章：PyTorch GPU 加速与混合精度

发表于 2026-05-01 更新于 2026-09-01 分类于 AI 本文字数： 1.1k 阅读时长 ≈ 4 分钟

第三章：PyTorch GPU 加速与混合精度

概念基础

  1. GPU 擅长并行不擅长分支：大矩阵乘/卷积在 GPU 上快几十倍；数据搬运（CPU↔GPU）反而是瓶颈，少拷贝、大批次是优化方向。
  2. 设备要对齐：模型与数据必须在同一设备，RuntimeError: Expected all tensors to be on the same device 是新手第一错。
  3. AMP 混合精度的本质：前向用 FP16/BF16 省显存提速，梯度更新用 FP32 保精度；autocast + GradScaler（FP16 场景）成对出现。
  4. 显存不够不等于换卡：梯度累积等效大 batch、梯度检查点用算力换显存、小批次 + 累加，都是工程正解。
  5. 测量优先：torch.cuda.synchronize() + 计时、nvidia-smi 看占用，先定位瓶颈（数据加载 or 计算 or 搬运）再优化。

本章承接 第二章：PyTorch 模型与训练 的训练模板。代码按 PyTorch 2.x 官方 API 书写（沙箱无 GPU 与 torch，未逐条运行验证）。

一、设备管理

省一个错误的三行习惯：

别在循环里写 torch.cuda.current_device() 之类的查询；多卡选卡用 CUDA_VISIBLE_DEVICES=1,2 python train.py 从环境层面隔离最干净。

二、混合精度训练（AMP）

要点：

环节 说明
autocast 只包前向 + loss；backward 在上下文外
GradScaler FP16 必需；BF16 不需要 scaler（dtype=torch.bfloat16）
梯度裁剪 必须夹在 unscale_ 与 step 之间
显存收益 权重/激活约省一半，batch 可开大一倍以上

A100/H100 等新卡优先 BF16：指数位与 FP32 相同，无下溢问题，代码更简单（省去 scaler）。

三、显存不够怎么办

1. 梯度累积：小 batch 等效大 batch

2. 梯度检查点：用算力换显存

3. 其他手段

定位显存泄漏：

泄漏最常见原因：把带计算图的 loss/tensor 存进了 list（应 loss.item()），或在验证循环里忘了 no_grad()。

四、torch.compile：内核融合提速

适用 不适用
固定 shape 的静态网络（CNN、MLP） 动态 shape 频繁变化（重编译开销大）
长时间训练（编译费一次摊薄） 短脚本/交互调试

五、测量：瓶颈在哪

瓶颈判别：

现象 瓶颈 对策
GPU 利用率忽高忽低 数据加载跟不上 num_workers 加大、persistent_workers=True、预取
GPU 利用率恒定但很慢 计算本身 AMP、torch.compile、减小模型
memory_allocated 不高但 OOM 显存碎片 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
CPU 单核吃满 DataLoader 简化 __getitem__、预处理离线化

本章小结

要点 结论
设备 模型与每个 batch 都 .to(device)；non_blocking + pin_memory 提速搬运
AMP autocast 包前向，FP16 配 GradScaler；BF16 免 scaler
显存 梯度累积等效大 batch；checkpoint 换显存；memory_allocated 定位泄漏
编译 torch.compile 对固定 shape 长训练收益最大
测量 计时前 synchronize()；GPU 忽高忽低查数据加载

第二章：PyTorch 模型与训练

发表于 2026-05-01 更新于 2026-09-01 分类于 AI 本文字数： 1k 阅读时长 ≈ 3 分钟

第二章：PyTorch 模型与训练

概念基础

  1. nn.Module 是模型的骨架：继承后在 __init__ 里声明层、在 forward 里组织数据流；参数注册、.to(device)、state_dict 保存全部自动获得。
  2. Dataset/DataLoader 解耦数据与模型：Dataset 定义「第 i 条样本怎么取」，DataLoader 负责批量化、打乱、多进程预取——大数据训练的前提。
  3. 训练循环是固定四步：optimizer.zero_grad() → forward → loss.backward() → optimizer.step()，一切复杂训练都是这四步的变体。
  4. train/eval 切换不可少：Dropout、BatchNorm 在训练与推理行为不同；验证前必须 model.eval()，验证后 model.train()。
  5. 泛化靠工程手段：验证集监控、早停、学习率调度、正则化（weight_decay/Dropout）共同决定模型能否落地。

本章承接 第一章：PyTorch 入门与张量 的张量与 autograd。代码按 PyTorch 2.x 官方 API 书写（沙箱未装 torch，未逐条运行验证）。

一、定义模型：nn.Module

常用层速查：

层 用途
nn.Linear(in, out) 全连接
nn.Conv2d(cin, cout, k) 图像卷积
nn.BatchNorm2d(c) / LayerNorm 归一化（稳定训练）
nn.ReLU / GELU 激活
nn.Embedding(vocab, dim) 离散 ID → 向量（NLP 必备）
nn.LSTM / nn.TransformerEncoder 序列建模

二、Dataset 与 DataLoader

  • num_workers：多进程预取，CPU 密集的预处理必开；Windows 下要在 if __name__ == "__main__": 里跑。
  • pin_memory=True：页锁定内存加速 CPU→GPU 拷贝（配合第三章）。
  • 变长序列：用 collate_fn 自定义打包（padding + mask）。

三、训练循环：完整模板

四大高频翻车点：

症状 原因
loss 不降 学习率过大/过小；标签与 logits 形状不配
loss 变 NaN lr 过大爆炸、除零、FP16 溢出（见第三章 GradScaler）
验证 acc 虚高 忘了 model.eval()，Dropout 还在随机丢弃
显存随轮次上涨 把带计算图的 loss 累加到 list（应 loss.item()）

四、断点续训：保存与恢复

推荐保存 state_dict() 而非整个模型对象：反序列化整个对象要求类定义路径一致，state_dict 只存权重、跨代码结构可用。

五、回归与二分类的损失选择

任务 输出层 损失函数
多分类 Linear(→n_classes) CrossEntropyLoss
二分类 Linear(→1) BCEWithLogitsLoss
回归 Linear(→1) MSELoss / HuberLoss
多标签 Linear(→n) BCEWithLogitsLoss（标签 multi-hot）

本章小结

要点 结论
模型 继承 nn.Module，__init__ 声明层、forward 串数据流
数据 Dataset 取样 + DataLoader 批量化；变长数据用 collate_fn
训练四步 zero_grad → forward → backward → step；验证前 model.eval()
排障 NaN 查 lr/精度；显存涨查计算图泄漏；acc 虚高查 eval 切换
存取 存 state_dict() + 优化器状态，跨机器恢复

第一章：PyTorch 入门与张量

概念基础

  1. 动态图是 PyTorch 的性格：写 Python 即写模型，前向传播边执行边建图，调试跟普通程序一样打断点——科研与工业界均为主流选择。
  2. Tensor 是唯一主角：torch.Tensor 是带 GPU 加速与自动求导的多维数组，接口与 NumPy 高度相似，会 NumPy 就会一半 PyTorch。
  3. autograd 自动微分：requires_grad=True 的张量参与运算时自动记录计算图，backward() 一步拿到所有梯度，模型训练的地基。
  4. 形状思维：深度学习 90% 的报错是 shape 不对——view/reshape/squeeze/permute 这组变形记必须滚瓜烂熟。
  5. 生态覆盖全链路：torchvision/torchaudio 领域库、Hugging Face 预训练模型（见 第三章：LLM 大语言模型基础）、ONNX 导出部署、DDP 分布式训练。

第三章：LLM 大语言模型基础

第三章：LLM 大语言模型基础

概念基础

  1. 大语言模型（LLM）是在海量文本语料上以自监督方式预训练的超大 Transformer 网络，能理解与生成自然语言。
  2. 训练三阶段：预训练（下一词预测，学通用语言与知识）→ 监督微调（SFT） 对齐「助手」行为 → RLHF / DPO 对齐人类偏好。
  3. 交互单位是 Token：模型受上下文窗口（Context Window）限制，一次只能处理有限的 Token；长文档需分块或 RAG。
  4. 幻觉与增强：模型可能一本正经地编造内容，用**检索增强生成（RAG）接入私有知识、用工具调用（Function Calling）**连接真实 API 来缓解。
  5. 落地三路线：Prompt 工程最轻量，微调（LoRA/QLoRA）注入领域知识，RAG + Agent 组合解决知识时效与工具执行。

生命周期

阶段 说明
预训练 下一词预测（Causal LM）或掩码语言模型，学通用语言与知识
监督微调（SFT） 指令数据上对齐「助手」行为
RLHF / DPO 等 人类偏好或偏好对优化安全性与有用性

第二章：DL 深度学习基础

概念基础

  1. 深度学习（DL）是机器学习的分支：用多层神经网络自动从数据中学习层次化特征表示，大幅减少手工特征工程。
  2. 核心机制：前向传播计算输出与损失，反向传播按链式法则求梯度，SGD/Adam 等优化器迭代更新权重。
  3. 非线性是关键：层间插入激活函数（ReLU / Sigmoid / GELU 等），否则多层线性堆叠仍等价于单层线性模型，无法拟合复杂模式。
  4. 架构按数据形态选：MLP 管表格向量、CNN 管图像空间模式、RNN/LSTM 管序列、Transformer 用 Self-Attention 建模长距离依赖并成为 LLM 的基座。
  5. 算力与工程：训练依赖 GPU/CUDA，配合 PyTorch 等框架与混合精度、学习率调度等技巧才能稳定高效。

神经网络基础



flowchart LR
  X[输入] --> F[前向传播]
  F --> L[损失 Loss]
  L --> B[反向传播梯度]
  B --> U[更新权重]
  • 前向传播：输入 → 各层线性变换 + 非线性激活 → 输出。
  • 损失函数：分类 Cross-Entropy、回归 MSE 等。
  • 反向传播：链式法则计算梯度，SGD/Adam 等优化器更新参数。

1. 为什么需要非线性激活

若每层只有线性变换 ，多层堆叠仍等价于单层线性模型，无法拟合 XOR、边界弯曲等复杂模式。激活函数 引入非线性，使网络能学习层次化特征。

2. 常见激活函数

函数 公式 值域 特点
ReLU 计算快；正区间梯度恒为 1，缓解梯度消失
Sigmoid 输出可解释为概率；两端饱和，易梯度消失
GELU 近似 平滑、非单调；Transformer 默认选择之一

ReLU： 时输出 0， 时等于 ；负半轴梯度为 0（Dead ReLU），实践中仍是最常用的隐层默认项。

Sigmoid：把实数压到 ，适合二分类输出层或门控（LSTM 门）；隐层深层堆叠时两端饱和导致梯度接近 0，训练变慢。

GELU：在 0 附近平滑过渡，负值有小幅度非零响应；BERT、GPT 等 Transformer 隐层常用，表达力与训练稳定性通常优于 ReLU，但计算略贵。

3. 如何选择（以及为什么）

场景 推荐 原因
CNN / MLP 隐层 ReLU 实现简单、收敛快；大量视觉与表格任务验证有效
输出层（二分类概率） Sigmoid 输出天然在 ，与 BCE 损失配套
输出层（多分类） Softmax（非 Sigmoid） 各类概率和为 1
Transformer / 大语言模型 GELU 平滑非线性利于深层 Self-Attention 训练；与 Layer Norm 等组合成熟
RNN / 门控结构 Sigmoid / Tanh 门控需要 或有界输出；Tanh 零中心，有时优于 Sigmoid
需要概率且要可导 Sigmoid / GELU Sigmoid 有界；GELU 在 0 附近更平滑，梯度更友好

经验法则：

  1. 没有特殊理由时，隐层先用 ReLU（或 Leaky ReLU 减轻 Dead ReLU）。
  2. 输出层跟任务走：回归用线性/无激活，分类用 Softmax 或 Sigmoid。
  3. 复现 Transformer 或 LLM 结构时用 GELU，与论文和主流实现一致。
  4. 深层旧架构（VGG 之前） 曾广泛用 Sigmoid/Tanh，现多被 ReLU 取代，除非门控或概率语义需要。

典型架构

架构 适用
MLP 表格、简单向量
CNN 图像、局部空间模式
RNN/LSTM/GRU 序列（较长依赖现多被 Transformer 补充）
Transformer NLP、多模态；Self-Attention 建模长距离依赖

ResNet、U-Net、BERT、GPT 等均建立在上述组件之上。

训练技巧

  • Batch Normalization / Layer Norm：稳定训练。
  • Dropout：减轻过拟合。
  • 学习率调度：Warmup、Cosine Decay。
  • 混合精度（AMP）：FP16/BF16 加速、省显存。
  • 梯度裁剪：RNN/大模型训练防爆炸。

数据：增强（随机裁剪、翻转）、归一化；划分训练/验证，早停（Early Stopping）。

框架与硬件

  • PyTorch：研究与应用主流（见 第一章：PyTorch 入门与张量）。
  • TensorFlow/JAX：生产与 TPU 生态。
  • GPU/CUDA：大规模训练依赖；推理可用 ONNX Runtime、TensorRT 等。

与 ML、LLM

  • 传统 第一章：ML 机器学习基础：小数据、表格、可解释场景仍常用 GBDT。
  • DL：表示学习为主。
  • 第三章：LLM 大语言模型基础：超大 Transformer 预训练 + 微调/对齐；视觉侧有 ViT、Diffusion 等并行发展。

计算机视觉入门可结合 OpenCV。

激活函数 隐层默认 ReLU，二分类输出 Sigmoid，多分类 Softmax，Transformer 用 GELU

第一章：ML 机器学习基础

第一章：ML 机器学习基础

概念基础

  1. 机器学习（ML）是让计算机从数据中自动学习规律，再用学到的模型对新数据做预测或决策，而无需为每条规则手工编程。
  2. 三大问题类型：监督学习（有标签，学输入→输出映射：分类、回归）、无监督学习（无标签，发现结构：聚类、降维）、强化学习（智能体与环境交互最大化回报）。
  3. 标准工作流：问题定义 → 数据收集与清洗 → 特征工程 → 模型训练与验证 → 部署与监控，从原始数据到线上服务是一条完整链路。
  4. 泛化是核心目标：模型要在没见过的数据上表现好，因此要防过拟合（正则、Dropout、交叉验证），并权衡偏差-方差。
  5. 定位与分工：表格数据、小样本、可解释性要求高的场景传统 ML（尤其树模型）仍很强；图像、语音等复杂表示交给 DL，自然语言任务交给 LLM。

问题类型

类型 目标 示例
监督学习 有标签，学输入→输出映射 分类（垃圾邮件）、回归（房价）
无监督学习 无标签，发现结构 聚类、降维、异常检测
强化学习 智能体与环境交互最大化回报 游戏、机器人控制

典型流程



flowchart LR
  Raw[原始数据] --> Clean[清洗特征]
  Clean --> Train[训练模型]
  Train --> Eval[验证集评估]
  Eval --> Deploy[部署推理]
  1. 问题定义与指标（准确率、F1、AUC、RMSE 等）。
  2. 数据收集与清洗：缺失值、异常值、泄漏（train/test 混用未来信息）。
  3. 特征工程：数值缩放、类别编码、时间特征。
  4. 模型训练与验证：训练集 / 验证集 / 测试集或 K 折交叉验证。
  5. 部署与监控：数据漂移、模型退化、在线 A/B。

常用算法（概览）

  • 线性模型：逻辑回归、线性回归、SVM（核方法）。
  • 树模型：决策树、随机森林、GBDT、XGBoost/LightGBM（表格数据仍强）。
  • 距离方法：KNN。
  • 无监督：K-Means、PCA、t-SNE（可视化）。

过拟合与正则

  • 过拟合：训练集很好、泛化差 → 更多数据、简化模型、L1/L2 正则、Dropout（神经网络侧）。
  • 偏差-方差权衡：模型容量与数据量匹配。
  • 交叉验证：稳定估计泛化性能。

与 DL、LLM 的分工

层次 说明

DL（第二章：DL 深度学习基础） 图像、语音、复杂非线性表示
LLM（第三章：LLM 大语言模型基础） 自然语言理解与生成；下游常 微调 或 RAG

深度学习框架见 第一章：PyTorch 入门与张量；Python 工程见 第一章：Python 的 UV 工具：极速 Python 环境与包管理。

要点 结论

第二章：Kubernetes 容器编排入门

概念基础

  1. Kubernetes（K8s） 是容器编排平台：把大量容器按声明式期望调度到多台机器上运行，并自动维持「实际状态 = 声明状态」。
  2. 为什么需要编排：单机 Docker 解决不了多机调度、故障自愈、扩缩容、服务发现与负载均衡——这些正是 K8s 的核心能力。
  3. 声明式 API：不写「怎么做」的脚本，而是提交 YAML 描述期望（副本数、镜像、端口），由控制循环持续把集群调到期望状态。
  4. 核心对象：Pod 是最小调度单元；Deployment 管理副本与滚动更新；Service 提供稳定访问入口；ConfigMap / Secret 管理配置与密钥。
  5. 定位：生产环境容器编排的事实标准；本地可用 minikube / kind / k3s 学习，集群上的应用包管理则交给 Helm（见第四章）。

第一章：Docker 容器基础

概念基础

  1. Docker 是基于容器的应用打包、分发与运行平台：把应用连同依赖环境一起封进镜像，实现「一次构建，到处运行」，解决「在我机器上是好的」的环境漂移问题。
  2. 镜像与容器：镜像（Image） 是只读分层文件系统加元数据；容器（Container） 是镜像的可运行实例，在镜像之上附加一层可写层。
  3. 与虚拟机相比，容器共享宿主机内核、不含客户机 OS，启动秒级、资源密度高；隔离性弱于完整 VM，敏感多租户需额外加固。
  4. 核心工作流：Dockerfile 描述构建过程 → docker build 产出镜像 → 推送到 Registry（Docker Hub / Harbor）→ 任意机器 docker run 拉起容器，多容器栈用 Compose 编排。
  5. 为什么学它：数据库、中间件、应用皆可容器化（本站各 *-Docker 文章即基于此）；单机之上是多机编排与生产化，由 Kubernetes 承接（见第二章）。

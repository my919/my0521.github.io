Rust

概念基础：Rust 是什么/为什么

  1. 系统级编程语言：Rust 定位与 C/C++ 相同，面向操作系统、数据库、网络服务等对性能与控制力要求极高的场景，编译为原生机器码，无虚拟机、无 GC。
  2. 内存安全是核心卖点：通过所有权（ownership）与借用检查在编译期阻止悬垂引用、use-after-free 与数据竞争，不依赖运行时垃圾回收兜底。
  3. 零成本抽象：Option/Result、迭代器、泛型与 trait 等高层抽象编译后不引入额外运行时开销，安全与性能可以兼得。
  4. 现代化工程体验：官方工具 Cargo 集构建、测试、文档与依赖管理于一体，配合 crates.io 社区仓库，上手与协作成本远低于传统 C/C++。
  5. 适用场景广泛：CLI 工具、Web 后端、Wasm、嵌入式，也可通过 FFI 与 C/C++ 混编，为既有系统替换性能或安全热点。

一、所有权模型

1. 三条规则

  1. 每个值有且仅有一个所有者。
  2. 所有者离开作用域，值被 drop。
  3. 同一时间只能有一个可变引用，或任意多个不可变引用（不能同时存在可变与不可变引用）。

2. 借用

编译器在编译期拒绝悬垂引用与数据竞争，而非运行时 GC。

二、基本语法

  • struct + impl：方法与关联函数。
  • trait：类似接口，支持默认实现与泛型约束。
  • enum：代数数据类型，Option / Result 是错误与空值建模基础。

三、错误处理

? 运算符：在返回 Result 的函数中传播错误。生产代码常用 thiserror / anyhow 简化错误类型。

四、并发

Send / Sync trait 标记类型能否跨线程传递/共享；async/await（Tokio、async-std）用于高并发 IO。

五、生态与场景

领域 crate / 项目
CLI clap、ripgrep
Web axum、actix-web
Wasm wasm-pack
系统 驱动、嵌入式 no_std

与 C 语言核心概念与编程基础 互操作：FFI、bindgen；与 Go 并发编程入门 对照：Rust 更偏零成本抽象 + 编译期安全，Go 更偏简单并发 + GC。

安装：rustup（https://rustup.rs/） · 文档：https://doc.rust-lang.org/book/

本章小结

要点 结论
所有权 每个值一个所有者，赋值即移动，出作用域自动 drop
借用规则 同一时刻要么一个 &mut，要么多个 &，编译期拒绝数据竞争
错误处理 Option/Result + ? 显式建模空值与错误，无异常机制
并发 Send/Sync 标记线程安全，async/await（Tokio）支撑高并发 IO
生态 Cargo + crates.io 一站式工程化，CLI/Web/Wasm/嵌入式均有成熟方案

第一章：Netty 网络编程框架入门

概念基础：Netty 是什么/为什么

  1. Netty 是基于 Java NIO 的异步事件驱动网络应用框架：帮你快速开发高性能、高可维护性的协议服务器与客户端，而不必直面原生 NIO 的复杂 API。
  2. 为什么不用原生 NIO：Selector 空轮询、缓冲区切换、线程模型搭建等细节繁琐易错；Netty 把这些封装成事件驱动的组件，开发者只写 Handler。
  3. Reactor 模型：少量 EventLoop 线程通过 Selector 监视大量 Channel，以事件驱动取代「一条连接一条线程」，是高并发服务器的经典模型。
  4. 零拷贝与缓冲：ByteBuf 池化、CompositeByteBuf 等减少拷贝（具体依版本与平台），降低 GC 与内存开销。
  5. 协议栈与生态：内置或社区 Codec（HTTP、Redis、MQTT 等），也可自定义帧解码；典型用户：Dubbo、gRPC-Java（部分）、Elasticsearch、游戏网关、物联网接入。

第二章：IO 多路复用与 Netty 线程模型

发表于 2026-05-01 更新于 2026-08-30 分类于 Netty 本文字数： 1.6k 阅读时长 ≈ 5 分钟

第二章：IO 多路复用与 Netty 线程模型

概念基础：IO 多路复用是什么/为什么

  1. I/O 多路复用在干什么：一条线程调用 Selector.select() 阻塞等待，直到一批 Channel 上有就绪的 I/O 事件（可读、可写等），再依次分发处理——一条线程可以注册并监视成千上万个连接，而不是为每个连接各开一条阻塞线程。
  2. 「很多连接」≠「每条连接占满一条线程」：大量长连接（推送、网关、IM 在线）中许多连接长时间无读写，适合交给一个 Selector 统一等就绪；高 QPS 短连接的瓶颈常在 CPU、GC、协议栈，与「单 Selector 挂很多空闲连接」不是同一维度的问题。
  3. Netty 扮演的角色：在 Java NIO / Epoll（Linux） 之上封装了 Reactor 风格的 EventLoop、Pipeline、内存与缓冲策略，让你用少量 EventLoop 线程管理大量 Channel，并把编解码、业务入 ChannelPipeline。
  4. 线程模型与前提：Boss 负责 accept 新连接并注册给 Worker；每个 Worker EventLoop 是「一条线程 + 一个 Selector」。业务若阻塞（重度 CPU、同步 JDBC、大 Thread.sleep）会占满该 EventLoop 上的所有 Channel——阻塞操作必须丢到业务线程池，这是多路复用发挥作用的前提。
  5. 上量边界：连接规模还受进程最大打开文件数、内核参数、堆外内存约束，多路复用属于应用层模型，不能替代容量规划。

Netty 常见线程模型（Boss / Worker）

1. 典型服务端写法（概念）

  • bossGroup：线程数常为 1（也可更多），负责接受新连接并把 SocketChannel 注册进 workerGroup 中某个 EventLoop 的 Selector。
  • workerGroup：每个 NioEventLoop 内一条线程 + 一个 Selector，多路复用其上的所有 Channel 的读/写就绪事件。整体是少量线程 + 大量连接，业务逻辑仍在 Pipeline 里按事件触发执行。

2. 一张逻辑关系（文字版）

角色 大致职责
Boss EventLoop accept，建 Channel，注册到某个 Worker
Worker EventLoop 已连接 Channel 的读/写就绪事件、入站出站 Pipeline

业务若阻塞（重度 CPU、同步 JDBC、大 Thread.sleep），会占满该 EventLoop 上的所有 Channel，拖慢整组连接——因此阻塞操作应丢到业务线程池或异步组件，这是多路复用能发挥作用的前提。

大量连接下的系统侧（简述）

要把多路复用撑到很大连接数，通常还要：

  1. 进程最大打开文件数（ulimit -n）调到足够大。
  2. Linux 上 TCP、端口范围、somaxconn 等与接入能力相关的内核参数按运维规范调整。
  3. 堆外内存、直接内存、-Xmx 与 Netty 的 ByteBuf 分配策略匹配业务量，避免 OOM。

这些属于容量规划与运维，单靠应用层多路复用无法替代。

第十二章：JupyterHub 入门：多用户架构与部署要点

概念基础：JupyterHub 是什么/为什么

JupyterHub 把「一人一个 Jupyter」升级为「团队共用一个入口」的多用户平台：

  1. 多用户入口：一台 Hub 服务为每个登录用户拉起独立的单用户服务器，实现「一人一环境」，互不干扰。
  2. 三大角色分工：Hub（处理登录、会话与用户服务启停）、Proxy（按 URL 路径把请求转发给对应用户）、Spawner（决定用户进程怎么启动：本机进程 / Docker / K8s Pod）。
  3. 解决三个核心命题：「谁能登录（认证）、登录后跑什么环境（镜像与 Spawner）、如何回收资源（会话与配额）」——团队、教学、科研平台的刚需。
  4. 能力边界：不替代 Python 依赖管理，也不等于 Kubernetes；生产上常与 K8s、反向代理、OAuth 组合使用。
  5. 安全优先：多用户系统第一关是认证与隔离——HTTPS、强认证、cookie_secret、容器隔离缺一不可，先读安全章节再谈上线。

官网与适用边界

  • JupyterHub 文档：https://jupyterhub.readthedocs.io/
  • 教程与部署指南：https://jupyterhub.readthedocs.io/en/stable/tutorial/index.html
  • 多用户「零到部署」参考（Kubernetes）：https://z2jh.jupyter.org/

JupyterHub 解决的是「谁可以登录、登录后跑哪个镜像/环境、如何回收资源」；不替代 Python 依赖管理，也不等于 Kubernetes 本身——但生产上常与 K8s、反向代理 组合使用。

架构角色

组件 作用
Hub 处理登录、会话与启动/停止用户服务器
Proxy 把浏览器请求按用户路径转发到对应单用户进程（常见为 configurable-http-proxy）
Single-user server 每个用户自己的 Jupyter Server（界面多为 JupyterLab 或 Notebook）
Spawner 决定「如何启动」单用户进程（本机进程、Docker、K8s Pod 等）

理清「Hub 进程」与「用户内核进程」分离，有助于排查端口、Cookie 与 WebSocket 转发问题。

配置与安全要点

1. jupyterhub_config.py

--generate-config 会生成 jupyterhub_config.py 模板，其中可设置：

  • 认证：PAM（类 Unix）、OAuth（GitHub / OIDC 等，需注册应用与回调 URL）
  • Spawner：默认 LocalProcessSpawner 适合单机试用；DockerSpawner、KubeSpawner 用于隔离与弹性
  • c.JupyterHub.bind_url：监听地址与端口，与反向代理 scheme 对齐

2. HTTPS 与 Cookie

浏览器 Cookie、Secure 与 SameSite 与是否 HTTPS 强相关；对外服务应在 Hub 前放置 TLS 终结（Nginx、Traefik 或云负载均衡），并按文档设置 c.JupyterHub.cookie_secret 等密钥文件权限。

3. 资源与隔离

多用户共享一台机时，注意 CPU / 内存 / 磁盘 配额与恶意代码风险；生产常用容器或 K8s 做进程隔离，并限制出站网络。

生产与 Kubernetes

  • 单机 / 虚拟机：PAM + Nginx + HTTPS + systemd 管理 Hub，Spawner 选 Docker 等。
  • Kubernetes：参考 Zero to JupyterHub（Z2JH）：https://z2jh.jupyter.org/ ，用 Helm 维护 Hub、Proxy、用户镜像 与存储类。

上线前务必完成：身份源审计、镜像供应链、持久化 home、升级与回滚策略。

第十一章：JupyterLab 入门：安装、工作区与扩展

概念基础：JupyterLab 是什么/为什么

JupyterLab 是 Jupyter 官方推出的下一代前端，把零散工具整合成一个完整工作台：

  1. 多标签工作台：Notebook、Console、终端、文本编辑器、文件浏览器同屏多标签，可拖拽分栏排布，比经典单页 Notebook 更接近 IDE 体验。
  2. 与经典 Notebook 的关系：共享同一套 .ipynb 与内核模型，文件无需转换，二者可同环境并存——迁移成本只是「换启动命令」。
  3. Workspace 机制：界面布局（打开哪些标签、窗口位置）可保存与恢复，多项目切换不丢现场。
  4. 扩展生态：JupyterLab 3+ 起多数扩展以 pip 包分发（如 jupyterlab-git），pip install 后重启即用，不再折腾前端构建。
  5. 能力边界：它仍是单用户工具；团队级登录、配额与资源隔离请交给 第十二章：JupyterHub 入门：多用户架构与部署要点。

  • JupyterLab 文档：https://jupyterlab.readthedocs.io/
  • Jupyter 总览：https://jupyter.org/

Go 并发编程入门

发表于 2026-05-01 更新于 2026-08-30 分类于 Golang 本文字数： 1.4k 阅读时长 ≈ 5 分钟

Go 并发编程入门

概念基础：Go 并发编程是什么/为什么

  1. 并发是语言内建能力：Go 在语言层面提供 goroutine 与 channel，无需第三方库即可写出高并发程序，这是 Go 最具辨识度的特性。
  2. CSP 模型：遵循「不要通过共享内存来通信，而要通过通信来共享内存」，用 channel 在 goroutine 之间传递数据与所有权。
  3. M:N 调度：运行时把成千上万个轻量 goroutine 复用到少量 OS 线程上，创建成本远低于线程，适合海量并发任务。
  4. 传统同步工具仍在：sync.Mutex/WaitGroup/Once 处理共享状态与协作，context 统一传递取消与超时。
  5. 工程红线清晰：goroutine 泄漏、循环变量捕获、无界并发是三大常见陷阱；开发与 CI 应常开 go test -race 竞态检测。

CSP 模型



flowchart LR
  G1[goroutine A] -->|send| Ch[channel]
  Ch -->|recv| G2[goroutine B]

一、goroutine 与调度模型

  • goroutine：用 go f() 启动；栈初始很小、可按需增长，创建成本远低于操作系统线程，因此可以大量存在。
  • 调度器：运行时把许多 goroutine 映射到少量 OS 线程（M:N 模型），在阻塞或抢占点切换，避免「一线程一连接」把机器拖垮。
  • 何时用：IO 密集、扇出扇入、后台任务；CPU 密集仍要控制并发度（见第六节），否则和线程池一样会抢满核心。

二、channel：通信优先于共享内存

  • 声明与创建：var ch chan int 为 nil，发送/接收会永久阻塞；ch := make(chan int) 无缓冲；make(chan int, 10) 带容量为缓冲 channel。
  • 无缓冲：发送方与接收方必须同时就绪，完成一次「交接」，常用于同步节拍。
  • 缓冲：未满时可先发送，常用于限流或解耦；容量为 0 与无缓冲语义一致。
  • 关闭：仅发送方应调用 close(ch)；接收方可用 v, ok := <-ch，ok == false 表示 channel 已关闭且无剩余数据。
  • 单向 channel：类型 chan<- T（只发）、<-chan T（只收）用于函数签名，约束使用方式、减少误用。

三、select：多路等待与超时

  • select 在多个 channel 操作上等待，随机选择一个可执行的 case；若都阻塞且无 default，则阻塞；有 default 则立即走默认分支（常用于非阻塞尝试）。
  • 超时模式：用 time.After 或 context（推荐生产代码）控制最长等待。

四、sync 包：锁与协作原语

4.1 Mutex / RWMutex

  • 多 goroutine 读写同一内存且无 channel 串行化时，用 sync.Mutex 保护临界区；读多写少可考虑 RWMutex。
  • 锁粒度要小、持有时间要短；避免在持锁时做 IO 或可能阻塞很久的逻辑。

4.2 WaitGroup

  • Add / Done / Wait：主 goroutine Wait() 等待一组子任务结束；Add 要在启动 goroutine 之前（或确保不竞态地提前 Add），避免 Wait 早于 Add 导致计数错误。

4.3 Once

  • sync.Once 保证 Do(f) 里的 f 全局只执行一次，常用于懒初始化单例。

五、context：取消、超时与传值

  • context.Context 贯穿调用链：超时（WithTimeout）、手动取消（WithCancel）、截止时间（WithDeadline）；下游应监听 ctx.Done() 并尽快返回。
  • 值传递：WithValue 适合传请求范围元数据（如 trace id）；不要塞业务大对象，也不要把 Context 放进结构体字段长期保存（应作为函数首参传递）。

六、常见陷阱与实践建议

  • main 退出即进程退出：未 Wait 或未收完结果的 goroutine 会被直接掐掉；要有明确的汇合点（WaitGroup、channel 关闭、errgroup 等）。
  • 泄漏 goroutine：向无人接收的 channel 发送、或 goroutine 永远阻塞在 select，都会导致泄漏；长生命周期任务要设计退出信号。
  • 闭包与循环变量：在循环里 go func() { ... } 若引用循环变量，应用参数传入当前值，避免经典「全部打印最后一个」问题（Go 1.22+ 对循环变量语义有调整，仍建议显式传参以增强可读性与兼容旧版本）。
  • CPU 密集：用 runtime.NumCPU() 或带缓冲的 worker channel 限制并发 worker 数量，而不是无节制 go。
  • 竞态检测：开发与 CI 中开启 go test -race，能发现大量数据竞态。

整体上，Go 鼓励用 channel 表达所有权与流水线，在热点路径或简单共享计数时用 Mutex；取消与超时交给 context，代码意图会更清晰、也更容易在团队中保持一致。

概念基础：ClickHouse 是什么

  1. 列式存储：ClickHouse 按列组织数据，SELECT avg(price) 只读 price 一列，IO 远小于行存全表扫描——这是它分析查询快的根源。

Oracle

概念基础：Oracle 是什么/为什么

  1. 企业级关系型数据库：Oracle Database 是老牌商业 RDBMS，在银行、电信、政务等对稳定性、安全合规与厂商支持要求高的核心系统中长期占主导地位。

第一章：MongoDB 概述与入门

概念基础：MongoDB 是什么

  1. 文档数据库：MongoDB 是面向文档的 NoSQL 数据库，数据以 JSON/BSON 文档存储，字段可嵌套、可数组——一个文档天然对应一个业务对象。
  2. 层级模型：Database → Collection → Document，类似关系库的「库 → 表 → 行」，但 Collection 不强制固定 Schema，同一集合内文档字段可以不一致，适合业务快速演进。
  3. 主键默认自带：每个文档有唯一 ObjectId 主键 _id，无需提前设计自增列。
  4. 默认端口与工具：默认监听 27017，交互用 mongosh（替代旧版 mongo CLI），命令风格贴近 JavaScript。
  5. 定位与取舍：需要强事务、复杂 JOIN 时关系库更成熟；需要灵活文档 + 水平扩展时 MongoDB 更常见——二者互补而非替代。

定位与概念

1. 文档模型

  • Database → Collection → Document（类似关系库中的库 → 表 → 行，但文档是 JSON/BSON 结构，字段可嵌套、可数组）。
  • 无固定 Schema：同一 Collection 内文档字段可以不完全一致，适合业务快速演进。
  • 默认 _id：每个文档有唯一 ObjectId 主键。

2. 适用场景

物联网 / 日志 时序或半结构化事件写入
实时分析 配合 Change Streams、聚合管道
缓存替代 部分场景可替代「大 JSON 存 Redis」，但内存与持久化策略不同

高可用与扩展（概念）

  • 复制集（Replica Set）：一主多从，自动故障转移，读可扩展至从节点（注意读一致级别）。
  • 分片（Sharded Cluster）：按 Shard Key 水平切分数据，适合超大数据量；运维复杂度高于单复制集。
  • 事务：多文档 ACID 事务在复制集上可用（4.0+），但仍有性能与使用范围约束。

生产注意

  • 备份：mongodump / mongorestore 或云厂商快照；复制集不等于备份。
  • 安全：启用认证、限制网络暴露、最小权限用户；勿将 27017 裸奔到公网。

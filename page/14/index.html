第五章：RS232

概念基础：RS232 是什么/为什么

  1. RS232 是 EIA 定义的串行物理层标准，规定电气电平、信号线与连接器（DB9）——「PC 老式 COM 口」背后的标准。
  2. 负逻辑电平：逻辑 1 是负电压（-5V~-15V），逻辑 0 是正电压（+5V~+15V），与 MCU 的 TTL UART（0/3.3V）完全不同，必须经 MAX232 等芯片做电平转换。
  3. 点对点、单端：一收一发加共地，抗干扰弱、典型距离 < 15m，速率与距离反相关。
  4. 为什么仍要学：工业仪器、老式 PLC、条码枪仍大量保留 DB9 口；PC 侧 USB 转 RS232 线依然是常用调试手段。
  5. 与 UART 的关系：UART 是控制器逻辑，RS232 是物理层电气标准；其上仍可跑 Modbus RTU 或自定义帧协议。

先看典型的 DTE-DCE 连接：

DTE-DCE 连接



flowchart LR
  PC[DTE PC] -->|TXD RXD GND| Conv[USB-RS232 转换]
  Conv --> Dev[DCE 设备]

一、电平与特点

  • 逻辑 1：负电压（如 -5V ~ -15V）
  • 逻辑 0：正电压（如 +5V ~ +15V）
  • 单端：抗干扰弱于 第六章：RS485 差分；距离通常 < 15m（与波特率反相关）。
  • 点对点：多机需额外切换，不像 RS485 总线型。

MCU 侧为 TTL 第四章：UART（0/3.3V），需 MAX232、SP3232 等芯片做电平转换。

二、最小三线连接

交叉连接 TX/RX；不要把 RS232 口直接接 MCU UART 引脚。

三、流控（可选）

信号 作用
RTS/CTS 硬件流控，防缓冲区溢出
DTR/DSR 设备就绪（Modem 时代遗留）
软件流控 XON/XOFF 字符

嵌入式调试常 115200 8N1 无流控。

四、应用场景

  • 工业仪器、老式 PLC、条码枪 DB9 口。
  • USB 转 RS232 dongle 在 PC 上模拟 COM 口。
  • 长距离、多机、抗干扰场景优先 RS485 或 以太网（第二章：Modbus TCP）。

协议层仍可能是 第一章：Modbus RTU 或自定义 ASCII 帧。

本章小结

要点 结论
电平 负逻辑：1 = -5V-15V，0 = +5V+15V，与 TTL 不兼容
拓扑 点对点、单端，典型距离 < 15m，多机换 RS485
连接 最小三线 TXD/RXD/GND，TX/RX 交叉；禁止直连 MCU 引脚
电平转换 MCU TTL UART 经 MAX232/SP3232 接入
定位 老设备/仪器调试口；新设计长距离优先 RS485 或以太网

第四章：UART

概念基础：UART 是什么/为什么

  1. UART（通用异步收发器）是异步串行通信控制器：只用 TX/RX 两根信号线加共地，不传时钟，收发双方按约定的波特率各自采样。
  2. 异步帧：起始位(0) + 数据位(通常 8) + 可选校验位 + 停止位(1)；空闲为高电平，起始位拉低完成一次同步，数据 LSB 先发。
  3. 为什么无处不在：实现极简、调试直观，日志打印、AT 指令、GPS NMEA、Bootloader 都走 UART，是嵌入式最基础的调试与互联手段。
  4. 只是逻辑层：UART 引脚是 TTL 电平（0/3.3V），接 PC 老串口或工业总线需 MAX232（RS232）、MAX485（RS485） 等收发器转换物理层。
  5. 点对点：无从机地址、无仲裁，多机组网要靠上层协议或改用总线型物理层。

先看最基本的连接形态：

点对点连接



flowchart LR
  MCU1[MCU A TX] -->|RX| MCU2[MCU B RX]
  MCU2 -->|TX| MCU1

一、异步帧结构

  • 空闲：线路高电平。
  • 起始位：拉低，通知接收方开始采样。
  • LSB 先发：数据位从低位到高位。
  • 校验：None / Odd / Even（可选）。
  • 停止位：1 或 2 位高电平，恢复空闲。

二、波特率

常见：9600、115200、921600。收发双方波特率必须一致（误差通常 < 2%）。

三、电平与接口层

层次 说明
TTL UART MCU 引脚 3.3V/5V，直连 USB-TTL 模块
第五章：RS232 ± 电平，PC 老式串口、部分工业设备
第六章：RS485 差分、半双工、多机总线，常经 UART+收发器

UART 指控制器逻辑；对外物理层常加 MAX232、MAX485 等芯片。

四、应用与调试

  • 日志打印、AT 指令（4G/Wi-Fi 模块）、GPS NMEA、Bootloader。
  • Linux：/dev/ttyUSB0，minicom / picocom / screen。
  • 注意：TX 接 RX 交叉；共地 GND 必须连接。

与 第八章：SPI、第七章：I2C 对照：UART 线少、距离短（TTL）、协议简单，无硬件从机地址。

本章小结

要点 结论
本质 两线异步串行控制器，不传时钟，靠约定波特率采样
帧格式 起始位 + 数据位（LSB 先发）+ 可选校验 + 停止位
关键参数 双方波特率必须一致（误差 < 2%），常见 9600/115200
物理层 TTL 引脚直连需共地；上 RS232/RS485 需收发器转换
调试要点 TX/RX 交叉、必须共地；Linux 用 minicom/picocom/screen

第三章：Modbus ASCII

概念基础：Modbus ASCII 是什么/为什么

  1. Modbus ASCII 是 Modbus 的文本编码变体：每个字节用两个 ASCII 十六进制字符（0-9 A-F）表示，帧以 : 开始、CR LF 结束。
  2. 为什么存在：早期调制解调器/串口终端时代，文本帧人眼可读、可直接粘贴调试，字符间容忍度也比 RTU 严格的 3.5 字符静默宽松。
  3. 校验不同：RTU 用 CRC16，ASCII 用 LRC（8 位求和取补码）——检错能力较弱但实现极简。
  4. 代价：同样数据传输长度约 2 倍、带宽利用率低，新项目工业现场几乎都选 RTU，ASCII 只保留在老设备与维护口。
  5. 同一套 PDU：与 RTU/TCP 的功能码与寄存器语义完全一致，切换链路层不影响上层应用逻辑。

先直观对比两种编码：

与 RTU 对比

  subgraph ascii [Modbus ASCII]
    A1[可读 HEX 字符] --> A2[LRC 校验]
  end
  subgraph rtu [Modbus RTU]
    R1[二进制 ADU] --> R2[CRC16]
  end
  M[主站] --> ascii
  M --> rtu

一、帧格式

示例（读保持寄存器，概念）：

  • : 起始。
  • 每字节用 两个 ASCII 十六进制字符（0-9 A-F）。
  • CR LF 结束（0x0D 0x0A）。

二、LRC

对 地址到数据末字节 求和（8 位），取二进制补码（256 - sum），再转两个 ASCII 十六进制字符。

RTU 使用 CRC16；ASCII 用 LRC，检错能力较弱但实现简单。

三、与 RTU / TCP

变体 编码 效率 场景
RTU 二进制 高 RS485 主流
ASCII 文本 HEX 低（约 2× 字节） 调试、老设备
第二章：Modbus TCP 二进制 + MBAP 高 以太网

同一 PDU 功能码 语义一致；切换链路层时注意地址与寄存器映射相同。

四、调试

  • 串口终端可直接粘贴 : 帧（若设备支持 ASCII 模式）。
  • 物理层常为 第五章：RS232 或 第六章：RS485 + 第四章：UART。
  • 生产系统优先 RTU 或 TCP，ASCII 多用于维护口。

本章小结

要点 结论
帧格式 : 起、CRLF 止，每字节展开为两个 ASCII HEX 字符
校验 LRC 8 位求和取补码，弱于 RTU 的 CRC16
效率 传输体积约 2 倍，工业新项目首选 RTU
价值 可读可粘贴，适合调试与老设备维护
兼容 PDU 功能码语义与 RTU/TCP 完全一致

第二章：Modbus TCP

概念基础：Modbus TCP 是什么/为什么

  1. Modbus TCP 把 Modbus 的主从语义搬到以太网/TCP：报文仍是「功能码 + 数据」，但帧定界交给 TCP、校验交给 TCP 校验和，因此没有 CRC、没有静默时序。
  2. MBAP 头（7 字节）取代 RTU 的「从站地址 + 静默界定」：Transaction ID 让一条连接可区分多个并发事务，Unit ID 负责映射网关后的串口从站。
  3. 默认端口 502：约定俗成；接入即用，可跨交换机、跨网段访问远程设备，无需 485 布线与收发方向切换。
  4. 网关共存：大量存量设备仍是 RTU 串口设备，TCP ↔ RTU 网关完成两者转换，是工业现场新旧系统融合的典型形态。
  5. 边界：明文、无认证，安全只能靠工控内网隔离、VPN、TLS 隧道，绝不能直接暴露公网。

先看典型的连接模型：

  PLC --> RTU[Modbus RTU 从站 经串口]

一、MBAP 头（7 字节）

字段 长度 说明
Transaction ID 2 事务标识，请求/响应配对
Protocol ID 2 固定 0
Length 2 后续字节数（Unit ID + PDU）
Unit ID 1 设备地址（经网关映射 RTU 从站）

其后为与 第一章：Modbus RTU 相同的 功能码 + 数据（无 CRC）。

三、连接模型

  • 单连接多事务：常见一客户端对一 PLC 长连接 502。
  • 并发：多客户端连同一设备需注意 PLC 连接数限制。
  • 与 第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例：不同协议；工业网关可能同时提供 Modbus TCP 与 OPC UA。

四、串口网关

Modbus TCP ↔ RTU 网关：
Unit ID 映射 RS485 从站地址；网关内维护 第六章：RS485 轮询时序。

五、安全

  • 502 明文、无认证 → 仅放工控内网或 VPN；勿暴露公网。
  • 现代方案：TLS 隧道、VPN、专用安全网关。
  • 与 第三章：Modbus ASCII 比：TCP 适合跨交换机、远程 SCADA。

本章小结

要点 结论
帧变化 无 CRC、无静默界定；MBAP 头（7 字节）+ PDU
并发 Transaction ID 支持单连接多事务；留意 PLC 连接数上限
网关 TCP ↔ RTU 网关：Unit ID 映射 485 从站地址与轮询时序
安全 502 明文无认证，仅限工控内网 / VPN / TLS 隧道
选型 跨网段、远程 SCADA 选 TCP；现场总线仍是 RTU 主流

第一章：Modbus RTU

发表于 2026-05-01 更新于 2026-08-30 分类于 Embedded 本文字数： 774 阅读时长 ≈ 3 分钟

第一章：Modbus RTU

概念基础：Modbus RTU 是什么/为什么

  1. Modbus 是 Modicon 于 1979 年为 PLC 设计的应用层主从协议，如今是工业通信最通用的事实标准之一；RTU 是其中「二进制编码 + 异步串口」的变体。
  2. 主从轮询模型：一个主站（PLC/SCADA）按从站地址轮询，从站永不主动上报，只有被寻址才应答——模型简单、时序确定、实现成本低。
  3. 帧结构极简：地址 + 功能码 + 数据 + CRC16，一帧即一次完整的请求/应答；统一的寄存器语义（线圈、保持寄存器等）让不同厂商设备能用同一套报文访问。
  4. 为什么选 RTU：跑在 RS485 差分总线上，一根双绞线可挂多设备、传数百米，抗干扰强、布线便宜，是工业现场最常见组合。
  5. 边界：RTU 只定义数据读写语义，不含认证加密；帧界定靠静默时间而非特殊字符，底层串口由 UART 控制器提供。

理解了定位，先看最典型的主从轮询交互：

主从轮询



sequenceDiagram
  participant M as 主站 PLC
  participant S as 从站 地址 1
  M->>S: 读保持寄存器 FC03
  S-->>M: 数据 + CRC
  M->>S: 写单个寄存器 FC06
  S-->>M: ACK

一、RTU 帧结构

  • 地址 0：广播（从站不应应答）。
  • CRC：对地址到数据末字节计算 Modbus CRC16。

示例（读保持寄存器 0x03）：主站发 01 03 00 00 00 0A C5 CD（含义依上下文解析）。

二、常用功能码

码 名称 说明
0x01 Read Coils 读线圈（位）
0x03 Read Holding Registers 读保持寄存器（16 位）
0x04 Read Input Registers 读输入寄存器
0x06 Write Single Register 写单寄存器
0x10 Write Multiple Registers 写多寄存器

异常应答：功能码 + 0x80，后跟异常码。

三、时序（RTU 特有）

帧间静默 ≥ 3.5 字符时间（与波特率相关），用于帧界定；波特率高时该间隔很短，实现需精确。

  • 115200 下对 MCU 中断延迟更敏感。
  • 半双工 第六章：RS485 需在发送前使能 DE。

四、与其它 Modbus

变体 链路 帧界定
RTU RS485/RS232 静默 + CRC
第三章：Modbus ASCII 串口 : 起 CRLF 止，LRC
第二章：Modbus TCP 以太网 MBAP 头 + 无 CRC

寄存器地址映射（40001 等）在文档与 PDU 偏移间需 减 1 转换，避免 off-by-one。

五、调试

  • Modbus Poll / Slave（Windows）、pymodbus、QModMaster（Linux）。
  • 抓包：串口监听或 RS485 分析仪。
  • 与 第四章：UART 关系：RTU 是应用层协议，底下是异步串口 + 485 收发器。

Modbus 组织：https://modbus.org/

本章小结

要点 结论
协议本质 应用层主从轮询协议，从站只应答、不主动上报
帧结构 地址 + 功能码 + 数据 + CRC16，帧间静默 ≥ 3.5 字符时间
核心功能码 0x01/0x03/0x04 读，0x06/0x10 写；异常应答 = 功能码 + 0x80
物理搭配 半双工 RS485 总线，发送前使能 DE
调试 Modbus Poll/pymodbus/QModMaster + 串口抓包

第二章：Vite 工程化构建与部署

概念基础：Vite 是什么/为什么

  1. 下一代前端工具链：开发态用原生 ESM 按需编译（不打包整图），生产态用 Rollup 打包，一套配置覆盖 dev / build。
  2. 为什么快：依赖用 esbuild（Go 实现）预构建，比 JS 工具链快一个量级；HMR 速度与项目规模解耦。
  3. 约定优于配置：零配置即可启动，vite.config.ts 按需增强（别名、代理、插件）。
  4. 框架无关：官方插件支持 Vue / React / Svelte 等，也是 Nuxt 3 等元框架的底层构建器。
  5. 边界：dev 与 build 行为有差异（原生 ESM vs 打包产物），上线前必须 vite build && vite preview 验证。

一、为何快：Dev 与 Build 的分工



flowchart LR
  subgraph dev [开发 vite dev]
    SRC[源码 ESM] --> ESB[esbuild 预构建 deps]
    ESB --> HMR[浏览器 HMR]
  end
  subgraph prod [生产 vite build]
    SRC2[源码] --> ROL[Rollup 打包]
    ROL --> DIST[dist 静态资源]
  end
阶段 机制
开发 按需编译单文件，不打包整图；依赖用 esbuild 预打包
HMR 模块热替换，保留应用状态（依模块类型）
生产 Rollup Tree-shaking、代码分割、资源哈希

对比 Webpack dev：大型项目冷启动与 HMR 通常明显更快。

二、创建项目与常用脚本

常用模板：vanilla-ts、vue-ts、react-ts、vue。

  • preview：用本地静态服务器预览 dist，是上线前发现「dev 正常、build 出错」的第一道检查。

三、vite.config.ts 核心配置

  • alias：@ 指向 src，免除深层相对路径。
  • server.proxy：开发期把 /api 转发到后端，规避 CORS；生产环境由 Nginx 承担同样角色。

四、环境变量与模式

  • .env.development / .env.production 按模式加载；只有 VITE_ 前缀变量暴露给客户端，通过 import.meta.env.VITE_XXX 访问。
  • 密钥不要放进 VITE_*：客户端代码可见，后端密钥走服务端环境。
  • import.meta.env.MODE / import.meta.env.PROD 可在代码中区分环境分支。

五、插件生态

  • @vitejs/plugin-vue / plugin-react
  • vite-plugin-vue-devtools
  • Legacy：@vitejs/plugin-legacy 为旧浏览器注入 polyfill

SSR：vite-plugin-ssr 或框架内置方案（Nuxt 3 等基于 Vite）。

六、生产构建与部署

  • 第一章：Vue 3 核心概念与组件开发 官方推荐 **Vite** 作为默认脚手架。
  • 生产 dist 为静态文件，由 Nginx 或 CDN 托管；try_files 支持 SPA history 路由。
  • base：部署在子路径（如 /blog/）时需设置，资源引用前缀随之改变。

官方文档：https://vite.dev/

本章小结

要点 结论
双引擎 开发 原生 ESM + esbuild，生产 Rollup 打包
速度 依赖预构建 + 按需编译，HMR 与项目规模解耦
配置 vite.config.ts：alias、proxy、build 渐进增强
环境变量 仅 VITE_* 前缀暴露到客户端；密钥不进前端
部署 dist 静态托管；SPA 依赖 try_files 回退 index.html

第一章：Vue 3 核心概念与组件开发

概念基础：Vue 3 是什么/为什么

  1. 渐进式框架：既可以只在页面局部做交互增强，也可以配合 Vue Router / Pinia / Vite 构建完整的单页应用（SPA），复杂度随项目成长。
  2. 响应式系统：基于 Proxy 实现，用 ref / reactive 包装数据，模板自动追踪依赖、精确更新 DOM，几乎无需手写 DOM 操作。
  3. 组合式 API：Composition API（script setup 语法糖 + useXxx 组合式函数）让逻辑按功能组织而非按选项分散，复用与 TS 推导更友好。
  4. 编译期优化：单文件组件（SFC） 在编译期做静态提升、patch flags 等优化，运行时 diff 开销低于传统虚拟 DOM 方案。
  5. 生态成熟：脚手架 Vite、路由 Vue Router 4、状态 Pinia、类型检查 vue-tsc；官方文档 https://vuejs.org/ 。

一、核心概念

  • 单文件组件（SFC）：.vue 文件含 <template>（模板）、<script>（逻辑）、<style>（样式）三段。
  • 响应式：ref（包装任意值，经 .value 访问）/reactive（代理对象）包装数据，模板自动追踪依赖并更新 DOM。
  • 虚拟 DOM + 编译优化：静态提升、补丁标志减少运行时开销。

与 Vue 2 的主要差异：移除 Vue.set、$on 等 API；全局 API 改为 createApp 应用实例；Options API（data/methods/computed）仍兼容，但新项目推荐 Composition API。

二、组件与数据流

  • props 单向下行：父 → 子传数据；子组件不要直接修改 props，需要变更时用 emit 上报事件，由父组件修改数据源。
  • 单向数据流：数据流向清晰可追踪，是组件可维护性的基础。

三、Composition API

  • script setup：编译期糖，少写 export default，顶层绑定直接在模板可用。
  • computed：带缓存的派生值，依赖不变不重算；副作用用 watch / watchEffect。
  • 生命周期：onMounted / onUnmounted / onUpdated 等组合式写法替代 Vue 2 的选项式钩子。
  • 组合式函数（Composables）：useXxx() 抽离可复用逻辑（如 useFetch、useMouse），是组合式 API 最大的工程价值。

  • 作用域插槽：子组件把内部数据暴露给父组件的插槽内容，适合列表项模板定制。

  • 何时需要全局状态：跨页面共享（登录态、主题）或多组件深层传递；局部状态优先留在组件内。
  • 导航守卫：beforeEach 常用于登录校验与权限拦截。

第十五章：QUIC 详解：基于 UDP 的可靠传输、TLS 集成与 HTTP/3

概念基础：QUIC 是什么/为什么

QUIC（Quick UDP Internet Connections）是运行在 UDP 之上的可靠、加密、多路复用传输协议，是 HTTP/3 的底座：

  1. 解决什么问题：TCP 字节流「一丢全等」的队头阻塞、TCP + TLS 分层握手往返多、四元组一变连接即断——QUIC 在 UDP 上逐一重构。
  2. 三大关键设计：流（Stream）级隔离让丢包影响面缩小；内置 TLS 1.3 把加密与传输握手合并（目标 1-RTT 建连，0-RTT 可选加速）；Connection ID 让网络切换后连接依旧存活（连接迁移）。
  3. 实现在用户态：与 第一章：TCP 协议详解：连接、可靠传输与编程示例 内核栈不同，QUIC 多由用户态库（ngtcp2、quiche、MsQuic 等）实现，迭代快但排障更依赖日志与指标。
  4. 代价与前提：依赖 UDP/443 放行与企业网策略对齐；0-RTT 有重放风险，写操作需谨慎。

先看设计目标与作用的全貌：

一、设计目标与作用

1. 解决什么问题

  • 在 UDP 上重建可靠管道：丢包检测、重传、拥塞控制发生在 QUIC 层，而不依赖 第一章：TCP 协议详解：连接、可靠传输与编程示例 单一流上的队头阻塞。
  • 默认加密：传输与握手深度绑定 TLS 1.3（RFC 9001），减少「明文旁路」与分层带来的额外往返。
  • 多流与连接标识：Stream 隔离应用数据；Connection ID 让四元组变化时仍能延续同一逻辑连接（连接迁移）。

2. 相对 TCP + TLS 的典型取舍

问题 第一章：TCP 协议详解：连接、可靠传输与编程示例 + TLS 常见表现 QUIC 思路
队头阻塞 TCP 字节流级丢包会阻塞后续所有应用数据 QUIC 在流级相对独立地做丢包恢复
握手 RTT 常需 TCP 三次握手再叠 TLS 往返 常把加密与传输握手合并，目标 1-RTT 建连（0-RTT 为可选加速）
NAT 重绑定 四元组变化常被视作「新连接」 Connection ID 标识逻辑连接，支持连接迁移
中间设备 TCP 成熟、穿透好 依赖 第五章：UDP 协议详解：数据报语义、MTU 与示例代码 放行（如 UDP/443）；企业网策略需对齐

二、连接与完整通信流程（原理）

QUIC 报文封装在 UDP 数据报中（常见 HTTPS 场景为 UDP/443）。以下极度简化，省略版本协商、重试包、地址验证等细节。

1. 建立连接（简化）

首包常带 TLS ClientHello；成功后在 1-RTT 密钥下发送应用数据。0-RTT 可在重复连接时提前带数据，见第五节安全注意。

2. 关闭连接（简化）

任一方可发送 CONNECTION_CLOSE 帧；对端进入排空（draining）期，不再发送新数据。与 第一章：TCP 协议详解：连接、可靠传输与编程示例 的 FIN/ACK 不同，QUIC 在连接粒度表达关闭，内部再回收流与 UDP 套接字资源。

3. 与典型「套接字 / 协议栈」的对应

与 第一章：TCP 协议详解：连接、可靠传输与编程示例 的 connect/accept 由内核一条龙完成不同，QUIC 一般由用户态库（如 ngtcp2、quiche、MsQuic、aioquic）或浏览器网络栈实现：底层仍是 第五章：UDP 协议详解：数据报语义、MTU 与示例代码 sendto/recvfrom，其上是 TLS 1.3、ACK/重传、流控与 HTTP/3 帧。HTTP/3 客户端日常通过 curl --http3-only 或内置 HTTP/3 的 SDK 使用，而不是手写裸 UDP 报文。

三、流、可靠性与拥塞控制（原理要点）

  • Connection：加密上下文、ACK 与拥塞控制的归属单位（类似「一条加密了的类 TCP 管道」）。
  • Stream：单向或双向；HTTP/3 将请求/响应映射到不同流，减轻应用级队头阻塞。
  • Packet Number：单调递增，配合 ACK 范围与密钥更新，降低与 第一章：TCP 协议详解：连接、可靠传输与编程示例 序号相关的歧义；重传不重用旧 PN（新包新号）。
  • 拥塞控制：在 Connection 上运作（如 Cubic、BBR 等实现依栈而定），与 第一章：TCP 协议详解：连接、可靠传输与编程示例 一样受网络条件约束，但并非「一条字节流管所有多路复用对象」。

四、Connection ID、端口与「会话标识」

  • UDP 四元组仍用于路由首个报文；Connection ID 使源 IP/端口变化（如蜂窝切换 Wi-Fi）后，对端仍能识别同一 QUIC 连接。
  • 公网 HTTP/3 常见端口为 443（UDP），与 第一章：TCP 协议详解：连接、可靠传输与编程示例 443 并存、互不替代。
  • 服务端可协商 CID 长度与轮换策略，以兼顾隐私与路由。

五、TLS 1.3 与 QUIC（原理）

QUIC 使用 TLS 1.3 做身份认证与密钥导出；载荷由 AEAD 保护，PADDING 等机制缓解流量分析。0-RTT 可加速重复连接，但存在重放风险：对金融类写操作应禁用或在应用层做幂等与二次校验。

六、HTTP/3 与 第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例 对比（概念）

项 HTTP/2 over 第一章：TCP 协议详解：连接、可靠传输与编程示例 HTTP/3 over QUIC
传输 TCP 字节流 第五章：UDP 协议详解：数据报语义、MTU 与示例代码 上的 QUIC
多路复用 H2 帧共享一条 TCP 连接 QUIC 流级隔离，丢包影响面更小

第十四章：RPC 概念详解：原理、形态与 JSON-RPC / curl 示例

概念基础：RPC 是什么/为什么

RPC（Remote Procedure Call，远程过程调用）的目标：让调用远程服务像调用本地函数一样自然：

  1. 解决什么问题：分布式系统中，网络通信的序列化、连接管理、协议细节不应散落在业务代码里，RPC 框架把它们收敛到 stub（存根）。
  2. 如何做到：客户端 stub 把调用序列化成消息发出去；服务端 stub 反序列化、执行、再原路返回——开发者只见函数签名。
  3. 不规定字节格式：JSON-RPC（人可读易调试）、protobuf（见 第十三章：gRPC 详解：Protobuf、HTTP/2 与 grpcurl / Python 示例）、Thrift 等都是可选载体，传输可用 HTTP 或自定义 TCP。
  4. 核心难点：网络不可靠——超时后客户端不知道服务端是否已执行，重试可能重复扣款，必须用幂等设计兜底。

一、原理（.stub 与存根）

RPC 不规定具体字节格式；可由 JSON、protobuf、Thrift 等定义。

  • 微服务内部：低延迟、强类型契约（常选 第十三章：gRPC 详解：Protobuf、HTTP/2 与 grpcurl / Python 示例）。
  • 链上节点：Ethereum JSON-RPC 等文本 RPC。
  • 脚本自动化：轻量 JSON-RPC 管理接口。

第十三章：gRPC 详解：Protobuf、HTTP/2 与 grpcurl / Python 示例

概念基础：gRPC 是什么/为什么

gRPC 是构建在 HTTP/2 与 protobuf 之上的高性能 RPC 框架，用「强类型契约」生成多语言调用代码：

  1. 解决什么问题：手写 HTTP+JSON 接口缺契约、字段易错、序列化慢；gRPC 的 .proto 文件即契约，protoc 生成 stub，序列化体积小、编解码快。
  2. 为什么基于 HTTP/2：二进制分帧 + 单连接多路复用，一条连接并发多个调用，且天然支持流式。
  3. 四种调用类型：Unary 一问一答、Server streaming、Client streaming、Bidirectional streaming——流式是一等公民。
  4. 典型场景：微服务内部低延迟、强类型调用（同族范式见 第十四章：RPC 概念详解：原理、形态与 JSON-RPC / curl 示例）；浏览器直连受限，对外常配 gRPC-Web 或网关。

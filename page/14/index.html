第十三章：gRPC 详解：Protobuf、HTTP/2 与 grpcurl / Python 示例

概念基础：gRPC 是什么/为什么

gRPC 是构建在 HTTP/2 与 protobuf 之上的高性能 RPC 框架，用「强类型契约」生成多语言调用代码：

  1. 解决什么问题：手写 HTTP+JSON 接口缺契约、字段易错、序列化慢；gRPC 的 .proto 文件即契约，protoc 生成 stub，序列化体积小、编解码快。
  2. 为什么基于 HTTP/2：二进制分帧 + 单连接多路复用，一条连接并发多个调用，且天然支持流式。
  3. 四种调用类型：Unary 一问一答、Server streaming、Client streaming、Bidirectional streaming——流式是一等公民。
  4. 典型场景：微服务内部低延迟、强类型调用（同族范式见 第十四章：RPC 概念详解：原理、形态与 JSON-RPC / curl 示例）；浏览器直连受限，对外常配 gRPC-Web 或网关。

第十二章：MQTT 详解：发布订阅、QoS 与 mosquitto / Python 示例

概念基础：MQTT 是什么/为什么

MQTT（Message Queuing Telemetry Transport）是面向 IoT 的轻量级发布/订阅消息协议，默认运行在 TCP 1883：

  1. 解决什么问题：设备多、带宽窄、网络不稳——MQTT 报文头最小仅 2 字节，支持断线重连、遗嘱消息与会话保持。
  2. 角色解耦：发布者与订阅者都只连 Broker，按 Topic 字符串路由，双方互不知晓对方存在。
  3. QoS 三档：0 至多一次 / 1 至少一次 / 2 恰好一次，按业务对丢失与重复的容忍度选择。
  4. 为什么适合物联网：低功耗设备常发小遥测消息，Pub/Sub 天然一对多广播；对比 第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例 请求-响应模型更省连接与电量。

先看发布订阅模型的总体结构：

发布订阅模型



flowchart TB
  P1[Publisher 传感器] -->|publish topic/sensor| B[MQTT Broker]
  P2[Publisher 设备] --> B
  B -->|subscribe| C1[Consumer 大屏]
  B --> C2[Consumer 规则引擎]

一、模型与作用（原理）

Broker 根据 Topic 字符串路由消息；发布者不必知道订阅者列表。

二、主题与通配符（作用）

  • 层级：用 / 分层，如 factory/line1/temp。
  • 单级通配 +：匹配一层，如 factory/+/temp。
  • 多级通配 #：匹配剩余层级，须在末尾（细节以 v5 文档为准）。

Topic 大小写敏感；$SYS/ 常为 Broker 系统主题（依实现）。

三、QoS（原理）

QoS 名称 语义
0 至多一次 可能丢，不重试
1 至少一次 可能重复，需业务幂等
2 恰好一次 四次握手，开销最大

QoS 在发布方向与订阅方向可分别指定，最终有效语义取二者较高一侧规则（以 Broker 实现与文档为准）。

四、遗嘱消息（Last Will，概念）

连接异常断开时 Broker 可代发预设 Payload 到指定 Topic，用于设备离线告警；须正确配置 Keep Alive 与心跳。

第十一章：WebSocket 详解：握手、帧与 Python 示例

概念基础：WebSocket 是什么/为什么

WebSocket 是建立在 TCP 上的全双工应用层协议：借一次 HTTP 握手完成「升级」，此后双方随时互发帧：

  1. 解决什么问题：HTTP 是请求-响应模型，服务器无法主动推送；轮询延迟高、空耗连接，WebSocket 用一条长连接双向实时通信。
  2. 与 HTTP 的关系：握手就是 HTTP 101 Switching Protocols（同端口、复用反代与证书基建），升级后传输的是 WebSocket 帧，不再走 HTTP 语义。
  3. 帧级多路复用：文本帧、二进制帧、Ping/Pong 心跳、关闭帧都在单 TCP 连接上交错传输，消息可分片。
  4. 典型场景：行情推送、协作编辑、聊天、游戏状态、IoT 面板实时刷新；服务端单向文本流更轻的替代是 SSE。

先看握手与全双工时序：

握手与全双工



sequenceDiagram
  participant C as Client
  participant S as Server
  C->>S: HTTP Upgrade websocket
  S-->>C: 101 Switching Protocols
  C->>S: WebSocket 帧 文本/二进制
  S-->>C: WebSocket 帧 推送

一、作用与模型

  • 服务器推送：行情、协作编辑、游戏状态无需客户端轮询。
  • 双向二进制：除文本帧外可传 ArrayBuffer 类数据。
  • 与 SSE 对比：SSE 多为服务端单向文本流，仍基于 HTTP；WebSocket 真双向。

三、帧（原理要点）

类型 opcode 含义
0x1 文本（UTF-8）
0x2 二进制

0x9 / 0xA Ping / Pong

大消息可分片（FIN 位与 opcode 组合规则见 RFC 6455）。

  • 限流与最大消息长度，防内存与 CPU 耗尽。

第十章：DNS 详解：解析原理、记录类型与命令/代码示例

概念基础：DNS 是什么/为什么

DNS（Domain Name System）是互联网的「电话簿」：把人类易记的域名翻译成机器路由所需的 IP 地址：

  1. 解决什么问题：IP 难记且可能变化，域名稳定易读；DNS 把二者解耦，换机房只改记录、不改品牌。
  2. 分层委派：根 → TLD → 权威逐级授权，任何递归解析器都能沿这条链问出答案，无单点存储全部数据。
  3. 缓存与 TTL：各级结果按 TTL 缓存，命中秒回；副作用是记录变更存在生效延迟。
  4. 不只有「名字 → IP」：MX（邮件）、TXT（SPF/DKIM/域名验证）、PTR（反向解析）等记录支撑大量基础设施。
  5. 为什么重要：几乎所有 Web 访问的第一步；DNS 故障常表现为「ping IP 正常但域名不通」。

先看一次完整解析的全貌：

递归解析



flowchart LR
  App[应用] --> LR[本地递归解析器]
  LR --> Root[根 DNS]
  Root --> TLD[.com TLD]
  TLD --> Auth[权威 DNS]
  Auth --> IP[A 记录 IP]

一、分层与解析原理

1. 角色

角色 作用
Stub resolver 运行在终端或系统库内，把查询发给递归解析器
Recursive resolver 代客户端迭代问根、TLD、权威 直到拿到答案并缓存 TTL
Authoritative server 对某区（zone）拥有权威数据（NS 委派链终点）

2. 递归解析过程（概念）

查询 www.example.com.（末尾点表示根）时，递归器从根得到 .com 的 NS，再问 .com 得到 example.com 的 NS，最后问 example.com 权威得到 www 的 A / AAAA。结果按 TTL 缓存，命中则直接返回。

二、报文与传输（原理）

  • 传统 53 端口：多数查询用 第五章：UDP 协议详解：数据报语义、MTU 与示例代码，报文小、往返少。
  • 响应过大或区域传送等：回退 第一章：TCP 协议详解：连接、可靠传输与编程示例（TCP/53）。
  • DNS 消息结构（概念）：Header（ID、flags、各计数器）+ Question + Answer / Authority / Additional。

ID 用于匹配请求与响应；客户端应随机化 ID 与源端口以降低投毒风险（实现依赖系统解析器）。

三、常见记录类型（作用）

类型 作用
A 主机名 → IPv4
AAAA 主机名 → IPv6
CNAME 别名到另一域名（继续解析目标名）
MX 邮件交换：优先级 + 目标主机
NS 某区的权威服务器
TXT 任意文本（SPF、DKIM、域名验证等）
PTR IP → 主机名（反向解析）

四、DoT / DoH（加密与传输）

  • DoT（DNS over TLS）：853/tcp，整流加密。
  • DoH（DNS over HTTPS）：封装在 第四章：HTTPS 详解：TLS 握手、证书与 openssl/curl 示例 内，常走 443，与网页流量形态相近。

二者可防链路窃听，但递归器仍能看到查询内容；信任模型与日志策略需单独评审。

第九章：SSH 详解：加密远程登录、密钥与端口转发示例

概念基础：SSH 是什么/为什么

SSH（Secure Shell）是运行在 TCP 之上的加密远程管理与通道协议：

  1. 解决什么问题：Telnet / rlogin 等明文远程登录会把账号密码与全部数据暴露在链路上，SSH 用加密与完整性校验防窃听、防篡改。
  2. 两层认证：主机密钥证明「服务器是它自己」（首次连接写入 known_hosts），用户认证证明「你是你」（公钥 / 密码 / 证书，推荐公钥）。
  3. 不只是登录：SSH 还是加密隧道——端口转发（-L/-R/-D）、跳板（ProxyJump），并可承载 SFTP 等子系统。
  4. 为什么可靠：基于 第一章：TCP 协议详解：连接、可靠传输与编程示例 的可靠字节流，配合协议内建的密钥交换与重协商，全程不暴露明文凭据。

一、协议目标（作用）

  • 机密性与完整性：防窃听与篡改。
  • 身份认证：至少认证服务器；可双向证书或密钥。
  • 隧道能力：为其他 第一章：TCP 协议详解：连接、可靠传输与编程示例 应用提供加密通道。

第八章：SFTP 详解：SSH 子系统、协议栈与 sftp 示例

概念基础：SFTP 是什么

  1. 跑在 SSH 上的文件传输子系统：SFTP 是 SSH 协议族中的子系统，直接复用 SSH 的加密、完整性与认证——单端口（22）单连接搞定文件操作。
  2. 不是「FTP over SSH」：与 第七章：FTP 详解：双连接模型、主动/被动与 lftp 示例 的双连接模型无关；也不同 scp（单次拷贝）与 rsync（增量同步，协议不等同 SFTP）。
  3. 为什么是公网首选：默认强加密、防火墙只需放行一个端口、可复用 SSH 密钥免密认证；而 FTPS 虽加密仍保留双连接复杂性。
  4. 交互与批处理兼得：sftp 支持交互浏览目录（ls/cd/get/put），也支持 -b 批处理脚本，适合自动化。

第七章：FTP 详解：双连接模型、主动/被动与 lftp 示例

概念基础：FTP 是什么

  1. 历史最悠久的文件传输协议之一：在 TCP/IP 早期就提供跨异构系统的列目录、上传、下载与断点续传（由扩展命令支持程度决定），命令为可读文本（如 RETR、STOR、LIST），便于人机调试。
  2. 双连接模型是最大特点：TCP 21 的控制连接（命令/响应，全程保持）+ 每次传送动态建立的数据连接（文件内容 / LIST 输出）——与「单连接一用到底」的协议截然不同。
  3. 主动 PORT vs 被动 PASV：主动=服务端从 20 端口反向连出（客户端在 NAT 后时常失败）；被动=客户端连入服务端通告的端口（主流，防火墙须放行被动端口范围）。
  4. 明文是硬伤：用户名、密码与数据默认明文；FTPES 在 TLS 上加密但仍保留双连接复杂性——公网新系统优先 第八章：SFTP 详解：SSH 子系统、协议栈与 sftp 示例 或对象存储 HTTPS 上传。

先看它为什么这样设计：

设计动机（历史作用）

双连接模型（原理）

控制连接全程保持；每条数据传送动态建立数据连接。

主动 PORT 与被动 PASV

1. 主动（PORT）

服务端从 20 端口向客户端在 PORT 命令中声明的 IP:端口 主动连出。客户端在 NAT 后时常失败（内网端口对服务端不可达）。

2. 被动（PASV）（主流）

服务端在应答中给出监听 IP 与端口，客户端主动连入。防火墙须在服务端放行被动端口范围；NAT 下常需配置对外通告地址（如 masquerade_address）。

第六章：IP 协议详解：原理、编址与排障示例

概念基础：IP 是什么

  1. 网络层的「全局门牌号」：IP 给互联网上每台参与通信的主机接口分配 IP 地址，使跨网段寻址成为可能——IPv4 32 bit 点分十进制，IPv6 128 bit 冒号十六进制。
  2. 无连接、尽力交付（best-effort）：IP 不保证分组一定到达、不保证顺序、不负责重传；可靠性由上层（如 第一章：TCP 协议详解：连接、可靠传输与编程示例）或应用自行实现。
  3. 转发靠路由表：路由器按最长前缀匹配决定下一跳；主机用默认路由（0.0.0.0/0）把非本子网流量交给网关。
  4. 承上启下：向上用协议号区分载荷（TCP(6)、UDP(17)、ICMP(1)），向下适配以太网、Wi-Fi、隧道等链路；超过链路 MTU 时触发分片。

带着这四点看协议细节：

作用与设计目标

1. IP 解决什么问题

  • 统一寻址：给互联网上每台参与通信的主机接口分配 IP 地址，使跨网段寻址成为可能。
  • 无连接、尽力交付（best-effort）：IP 不保证分组一定到达、不保证顺序、不负责重传；可靠性由上层（如 第一章：TCP 协议详解：连接、可靠传输与编程示例）或应用自行实现。
  • 多路复用下层链路：无论是以太网、Wi‑Fi 还是隧道，都可承载 IP 分组。

2. 与上下层的关系（简图）

IP 地址 = 网络前缀 + 主机号。/24 表示前 24 bit 为网络部分，主机部分 8 bit，共 256 个地址（含网络地址与广播地址用法依场景而定）。同一二层广播域内主机须在同一子网才能「直连」互通；跨子网则须走默认网关（路由器）。

转发与路由（原理）

路由器根据路由表最长前缀匹配决定下一跳；主机则主要使用默认路由（0.0.0.0/0）把非本子网流量交给网关。NAT 可在私网与公网之间改写地址/端口，但 NAT 不是传输层协议；端到端排障仍要区分 「IP 层是否可达」 与 「端口映射/防火墙策略」。

IPv6 要点（与 IPv4 对照）

  • 128 bit 地址，冒号十六进制表示；存在链路本地、唯一本地、全局单播 等范围。
  • 邻居发现（NDP） 承担类似 IPv4 ARP 的链路地址解析角色。

第五章：UDP 协议详解：数据报语义、MTU 与示例代码

发表于 2026-05-01 更新于 2026-08-30 分类于 Protocol 本文字数： 2.2k 阅读时长 ≈ 7 分钟

第五章：UDP 协议详解：数据报语义、MTU 与示例代码

概念基础：UDP 是什么

  1. 无连接的数据报协议：与 第一章：TCP 协议详解：连接、可靠传输与编程示例 相对——无握手、无连接状态机，拿到目的地址首包即可发数据，每个数据报独立路由。
  2. 保留报文边界：一次 sendto 对应一个 UDP 数据报，对端 recvfrom 通常一次收到完整一报；而 TCP 是无消息边界的字节流。
  3. 尽力交付：不保证到达、不保证顺序、不负责重传；可靠性由应用或 第十五章：QUIC 详解：基于 UDP 的可靠传输、TLS 集成与 HTTP/3 等在 UDP 之上补充。
  4. 为什么快：首部仅 8 字节、无握手往返、无状态管理，延迟低、实现简单——适合 第十章：DNS 详解：解析原理、记录类型与命令/代码示例、实时音视频、指标上报。
  5. 代价与风险：载荷过大触发 IP 分片（丢一片常导致整组重组失败）；公网服务须防 UDP 反射放大与滥用。

先看它与 TCP 的本质差异：

设计目标与作用

1. 解决什么问题

  • 低延迟：无握手、无连接状态机，首包即可发数据。
  • 保留报文边界：一次 sendto 对应一个 UDP 数据报；对端 recvfrom 通常一次收到完整数据报（受缓冲区与实现限制；载荷过大时可能失败或行为依平台）。
  • 实现简单：适合 第十章：DNS 详解：解析原理、记录类型与命令/代码示例、实时音视频、指标上报；可靠性由应用或 第十五章：QUIC 详解：基于 UDP 的可靠传输、TLS 集成与 HTTP/3 等在 UDP 之上补充。

2. 与 TCP 的本质差异

维度 UDP 第一章：TCP 协议详解：连接、可靠传输与编程示例
连接 无 有（三次握手 / 四次挥手）
交付 尽力，可能丢、乱序、重复 可靠有序（重传隐藏丢包）
语义 保留消息边界（数据报） 字节流（无消息边界）
套接字 bind + recvfrom / sendto，无 listen/accept listen/accept/connect 等

无连接：通信流程（原理）

UDP 不建立会话状态；每个数据报独立路由，「流程」体现在应用与内核 API 的调用顺序上。

1. 完整通信流程（与套接字 API 对应）

  1. 服务端：socket(AF_INET, SOCK_DGRAM, 0) → bind 本地地址与端口 → 循环 recvfrom（每次返回一整报与对端地址 sockaddr）→ sendto 把应答写回该地址。无 listen、无 accept。
  2. 客户端：socket → 可直接 sendto 指定目的地址；首次发送时内核通常分配临时源端口。若需读回应，再 recvfrom（可配合超时或 select/poll）。
  3. 传数据：每个数据报自带目的信息；无序号、无确认，不保证与发送顺序一致，也不保证不丢。
  4. 关闭：close 仅释放本进程套接字资源；不会在协议层通知对端「连接结束」（与 第一章：TCP 协议详解：连接、可靠传输与编程示例 的 FIN 不同）。

UDP 首部与校验和（原理）

UDP 首部固定 8 字节：源端口、目的端口、长度、校验和。IPv6 下 UDP 校验和必填；IPv4 允许为 0（表示未使用校验和，实践中少见）。校验覆盖伪首部（含 IP 地址与协议号）+ UDP 首部 + 数据，用于检测传输错误；通过校验和 ≠ 应用层已处理完毕（仍可能丢包、乱序）。

MTU 与分片（为何要注意报文长度）

以太网常见 MTU 1500，扣掉 IP 首部后 UDP 载荷不宜过大，否则触发 IP 分片：任一片丢失常导致整组重组失败，丢包代价被放大。应用层常将 UDP 报文控制在 1200 字节左右以下（穿越未知路径更稳），或自行分片与重传。

第四章：HTTPS 详解：TLS 握手、证书与 openssl/curl 示例

发表于 2026-05-01 更新于 2026-08-30 分类于 Protocol 本文字数： 917 阅读时长 ≈ 3 分钟

第四章：HTTPS 详解：TLS 握手、证书与 openssl/curl 示例

概念基础：HTTPS 是什么

  1. HTTP + TLS，不是新协议：HTTPS 就是先经 TLS 加密、再传输 第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例 报文——URL 以 https:// 开头，默认端口 443（明文 HTTP 为 80）。
  2. TLS 提供三件事：机密性（对称加密防窃听）、完整性（MAC / AEAD 防篡改）、身份认证（X.509 证书链证明「服务器是它声称的那个」，可选客户端认证）。
  3. 握手定密钥，传输用对称：TLS 握手（1.3 常 1-RTT）协商出对称会话密钥，之后 HTTP 记录用对称算法加密以获得性能。
  4. 证书链是信任根基：浏览器校验证书是否由受信任 CA 签发、SAN 是否覆盖主机名、是否在有效期内；自签名证书仅限内网与开发。
  5. 不解决什么：TLS 不能替代应用层鉴权与输入校验，https:// 不等于站点没有 XSS/CSRF 等业务漏洞。

作用与威胁模型

1. TLS 提供什么

  • 机密性：对称加密载荷，防窃听。
  • 完整性：MAC / AEAD 防篡改。
  • 身份认证：服务端（可选客户端）X.509 证书链。

2. 不解决什么

TLS 不能替代应用层鉴权与输入校验；https:// 也不等于站点无 XSS/CSRF 等业务漏洞。

TLS 1.2 / 1.3 握手（原理简述）

1. 共同目标

客户端与服务端协商出对称会话密钥，后续 HTTP 记录用对称算法加密以获得性能。

2. TLS 1.3 特点（相对 1.2）

  • 常 1-RTT 完成握手（0-RTT 可选，有重放风险，敏感操作应禁用或二次校验）。
  • 废弃一批不安全算法；Hello 中即携带密钥共享材料。

证书链与主机名（作用）

浏览器/客户端会校验：

  1. 证书是否由受信任 CA 签发，链是否完整。
  2. Subject Alternative Name（SAN） 或兼容字段是否覆盖当前访问主机名。
  3. 有效期、吊销信息（OCSP Stapling 等）。

自签名证书仅适合内网或开发，公网须使用可信 CA 或组织内 PKI。

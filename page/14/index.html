第二章：图像基础操作

第二章：图像基础操作

概念基础

  1. OpenCV 的图像就是 NumPy 数组：所有「基础操作」本质是数组索引、切片、算术与广播——掌握 NumPy，OpenCV 基础就通了大半。
  2. 色彩空间是不同的「视角」：BGR 适合显示，GRAY 省一半数据，HSV 把颜色与亮度分离便于按色取物，Lab 接近人眼感知。
  3. 绘图是写回数组：circle/rectangle/line/putText 直接在数组上改像素，常用于可视化检测结果。
  4. 位运算做掩膜：bitwise_and 配合掩膜，实现「只保留感兴趣区域」或「按色抠图」，是抠图与合成的基石。
  5. 本章目标：覆盖数组操作、色彩空间、绘图、位运算、ROI 与掩膜，为后续滤波与特征打基础。

本章承接 第一章：OpenCV 计算机视觉入门 的「图像即数组」心智模型。

一、NumPy 数组操作

cv2.add vs +：cv2.add 饱和（255 封顶），numpy + 回绕（溢出取模）。图像合成用 cv2.add/cv2.addWeighted 防止颜色翻转。

二、色彩空间转换

HSV 按色取物（经典用法）

HSV 把颜色（H）、饱和度（S）、亮度（V）分离，按颜色范围抠图比 BGR 直观：

HSV 的 H 范围是 0–179（为适配 8bit），换算色相需 ×2。这是踩坑高发点。

三、绘图（可视化）

绘图函数直接修改输入数组，故常在副本上画，保留原图：

  • 坐标是 (x, y)（与 img[y, x] 相反，绘图统一用 x-y）。
  • -1 线宽表示填充。
  • 中文 putText 不支持：需用 PIL 绘制中文再转回 numpy，或用 cv2.putText 配英文。

四、ROI 与掩膜（位运算）

掩膜是单通道二值图（0/255），配合位运算实现区域选择：

位运算四件套：bitwise_and（与，掩膜取交集）、bitwise_or（或，合并）、bitwise_xor（异或）、bitwise_not（非，反色）。

五、图像算术与混合

要求两图同尺寸同通道；尺寸不同先 cv2.resize 或裁剪对齐。

六、性能提示

OpenCV 的 C++ 算子比纯 Python 循环快数百倍；像素级遍历是性能杀手，能用向量化/算子就别写双层循环。

七、常见陷阱

陷阱 说明
+ 溢出回绕 numpy + 超 255 取模致颜色翻转，用 cv2.add 饱和加
坐标顺序混淆 img[y,x] 行列，绘图 (x,y) 宽高，两套相反
HSV 的 H 是 0-179 不是 0-360，红色横跨 0 需两段合并
imread 不报错 路径错返回 None，后续 .shape 报 AttributeError
绘图改原图 直接修改输入数组，在 .copy() 上画
尺寸不匹配混合 addWeighted 要求同尺寸，否则报错
中文 putText 乱码 不支持中文，需 PIL 中转
像素循环慢 双层 Python 循环慢百倍，用向量化

本章小结

要点 结论
数组操作 切片取 ROI、.copy() 防视图、hstack/vstack 拼接
算术 cv2.add/addWeighted 饱和加；numpy + 会回绕
色彩空间 BGR 显示、GRAY 省流、HSV 按色取物、Lab 感知均匀
HSV 抠图 inRange 生成掩膜 + bitwise_and 取区域；H 范围 0-179
绘图 line/rectangle/circle/ellipse/putText/polylines，坐标 (x,y)，-1 填充
掩膜 单通道二值图，配 bitwise_and 区域选择
性能 向量化/算子替代像素循环

第三章：滤波与几何变换

发表于 2026-05-01 更新于 2026-09-01 分类于 OpenCV 本文字数： 1.6k 阅读时长 ≈ 5 分钟

第三章：滤波与几何变换

概念基础

  1. 滤波 = 用邻域算出新值：每个像素根据周围邻域（核）重新计算——模糊、锐化、边缘、形态学都是滤波的不同形式。
  2. 频域直觉：低通滤波（模糊）去噪但模糊边缘，高通滤波（锐化/边缘）增强细节但放大噪声，二者是图像处理的阴阳。
  3. 几何变换改位置不改值：缩放、旋转、仿射、透视改变像素「在哪」，需插值填补新格点的值。
  4. 阈值二值化是分割起点：把灰度图按阈值切成前景/背景，是许多检测流水线的第一步。
  5. 本章目标：掌握常用滤波（高斯/中值/双边）、形态学（腐蚀/膨胀/开闭运算）、几何变换（缩放/旋转/仿射/透视）、阈值化，能组合去噪与分割。

本章承接 第二章：图像基础操作 的数组与色彩基础。

一、模糊（低通滤波）

模糊 特点 适用
均值 简单均匀 轻度降噪
高斯 中心权重高，自然 通用降噪、预处理
中值 去孤立噪点 椒盐噪声
双边 同时考虑空间与灰度差，保边 保边去噪（美颜）

核大小必须为正奇数（5×5、7×7），偶数报错。

二、锐化与边缘（高通滤波）

  • filter2D：任意卷积核，-1 表示输出与输入同深度。
  • Canny 双阈值：低阈值 50 连边、高阈值 150 确认为强边，中间的靠连接保留。
  • CV_64F：梯度有负值，需用浮点防截断，显示前 convertScaleAbs 转回 uint8。

三、形态学运算

形态学作用于二值图，用结构元素（kernel）做邻域极值：

运算 等价 用途
腐蚀 min 去除小白点、细化
膨胀 max 连接断裂、加粗
开运算 腐蚀→膨胀 去小白点（噪声）
闭运算 膨胀→腐蚀 填小黑洞
梯度 膨胀−腐蚀 提取边缘

形态学也可用于灰度图（取邻域 max/min），但最常见于二值图后处理。

1. 缩放与翻转

resize 传 (W, H)（先宽后高），与 shape=(H,W) 相反，注意别混。

2. 仿射变换（旋转/平移/剪切）

仿射保持平行性与比例，用 2×3 变换矩阵：

3. 透视变换（3×3 矩阵）

透视可改非平行线，常用于文档矫正/俯视转换，由 4 对点定：

文档扫描、车牌校正的典型套路：检测四角 → 透视变换拉直。

五、阈值化

  • 全局阈值：光照均匀时够用。
  • 自适应阈值：光照不均（如文档阴影）按局部邻域二值化，11 是块大小（奇数），2 是减常数。
  • Otsu：自动找最佳阈值，配合 THRESH_OTSU 标志，阈值参数传 0。

六、常用组合：去噪→边缘→轮廓

七、常见陷阱

陷阱 说明
核用偶数 高斯/中值核须正奇数，偶数报错
resize 传 (H,W) resize 要 (W,H)，与 shape 相反
Sobel 截断负梯度 不用 CV_64F 会丢负值边缘
形态学忘二值化 形态学最适用二值图，灰度图效果不同
自适应阈值块用偶数 adaptiveThreshold 块大小须奇数且 >1
透视点顺序错 4 对点须一一对应，顺序错导致拉歪
边缘阈值全靠猜 用 Otsu 自动选，或先 pyplot.hist 看直方图

本章小结

要点 结论
高斯模糊 通用降噪首选；中值去椒盐；双边保边
边缘 Canny 最常用（双阈值完整流程）；Sobel 取方向梯度
形态学 腐蚀/膨胀为基础，开运算去噪、闭运算填洞、梯度取边
缩放 resize(img,(W,H)) 先宽后高，与 shape 相反
仿射 2×3 矩阵，保平行；getRotationMatrix2D 旋转
透视 3×3 矩阵，4 对点定；文档/车牌矫正
阈值 全局简单、自适应抗光照不均、Otsu 自动选阈值
流水线 灰度→高斯→Canny 是预处理黄金组合

第五章：视频与深度学习

发表于 2026-05-01 更新于 2026-09-01 分类于 OpenCV 本文字数： 1.8k 阅读时长 ≈ 6 分钟

第五章：视频与深度学习

概念基础

  1. 视频 = 时序帧序列：在单图处理之上多了「帧间关系」——运动检测、光流、跟踪都依赖相邻帧对比，是视频理解的核心。
  2. 背景建模分离运动：固定摄像头下，建立背景模型后，当前帧与背景之差即运动前景，是安防检测的经典思路。
  3. cv2.dnn 是推理不是训练：OpenCV 能加载 ONNX/Caffe/部分 TF 模型做前向推理，跨平台部署轻量模型；训练仍在 PyTorch 等框架完成。
  4. 前后处理是 OpenCV 的主场：深度模型要的 resize、归一化、BGR/RGB 转换、NMS、画框，全是 OpenCV 擅长的数组操作。
  5. 本章目标：掌握视频读写、光流、背景减除、dnn 推理与后处理，把前四章能力串成完整 CV 流水线。

本章承接 第四章：特征与几何，面向时序与深度模型衔接。视频编解码底层见 第一章：FFmpeg 音视频处理入门。

一、视频读写

1. VideoCapture 读取

摄像头/网络流 CAP_PROP_FRAME_COUNT 不可用；网络流用 cv2.CAP_FFMPEG 后端读 RTMP/RTSP。

2. VideoWriter 写出

  • fourcc：mp4v/avc1/X264 等，依后端可用编码；写不出时先换 fourcc。
  • 尺寸必须与帧一致，否则写空。
  • 底层依赖 FFmpeg 编解码——这就是 OpenCV 与 第一章：FFmpeg 音视频处理入门 的联系。

二、帧差法与背景减除（运动检测）

更鲁棒的背景建模（自动更新背景）：

  • 帧差法：简单但对静止目标失效。
  • MOG2/KNN：自适应背景，相机轻微抖动也能用，detectShadows 标阴影需二次阈值过滤。

三、光流（密集与稀疏）

光流估计像素运动场，用于跟踪与运动分析：

  • 稀疏 LK：跟踪特定角点，快，适合实时跟踪。
  • 密集 Farneback：全图运动，慢但信息全，可视化运动方向。

四、cv2.dnn 推理（加载 ONNX）

1. 加载模型与预处理

  • blobFromImage：scalefactor 缩放、size 目标尺寸、swapRB BGR→RGB、crop 是否中心裁剪。
  • swapRB=True：模型多按 RGB 训练，OpenCV 读的是 BGR，需交换。
  • GPU：编译时启用 CUDA 后端可 DNN_TARGET_CUDA 加速。

2. YOLO 风格后处理（NMS）

深度检测模型输出需后处理成最终框——解码框 + 置信度过滤 + NMS：

  • NMS（非极大值抑制）：重叠框只保留置信度最高的，0.4 是 IoU 阈值。
  • 训练用 第一章：PyTorch 入门与张量，导出 ONNX 后用 OpenCV 部署，是常见的轻量推理链路。

五、多目标跟踪：ByteTrack 思路（简述）

检测 + 关联是跟踪的通用框架：

  1. 每帧用检测器（YOLO/dnn）出框。
  2. 用 IoU 或卡尔曼预测把当前框与上一帧轨迹关联。
  3. 未匹配的检测开新轨迹，未匹配的轨迹保留若干帧后删除。

OpenCV 自带轻量跟踪器（单目标）：

多目标跟踪生产级多用 ByteTrack/ SORT + 深度检测器组合，OpenCV 负责检测前后处理与可视化。

六、完整流水线：视频检测可视化

七、常见陷阱

陷阱 说明
VideoWriter 尺寸不符 帧尺寸与构造参数不一致，写出空文件
fourcc 不支持 某些编码依赖后端，写失败先换 mp4v
blobFromImage 漏 swapRB BGR 送进 RGB 模型致检测错乱
忘归一化 不除 255 送 0-255 像素进模型，结果全错
NMS 阈值不当 IoU 阈值过小漏框、过大残留重复框
背景减除不去阴影 detectShadows 阴影为 127，需二次阈值
光流用彩色图 LK/Farneback 需灰度单通道输入
dnn 后端未编译 CUDA 设了 CUDA 后端但 OpenCV 未编译支持会回退或报错

本章小结

要点 结论
视频读写 VideoCapture 逐帧读、VideoWriter fourcc+尺寸写出；底层靠 FFmpeg
运动检测 帧差法简单、MOG2/KNN 背景减除自适应
光流 稀疏 LK 跟踪角点、密集 Farneback 全图运动场
dnn 推理 readNetFromONNX + blobFromImage 预处理 + forward；非训练
预处理 blobFromImage 一步 resize+归一化+swapRB+批维
后处理 置信度过滤 + NMSBoxes 去重复框
跟踪 检测+关联框架；OpenCV 单目标 CSRT/KCF，多目标用 ByteTrack

第四章：特征与几何

发表于 2026-05-01 更新于 2026-09-01 分类于 OpenCV 本文字数： 1.6k 阅读时长 ≈ 5 分钟

第四章：特征与几何

概念基础

  1. 特征 = 图像中可辨识的局部模式：角点、斑点、边缘交点等，在不同光照、尺度、视角下仍能被稳定检测与匹配，是图像配准、拼接、跟踪的基础。
  2. 检测 + 描述两步：先检测关键点位置，再计算描述子（高维向量）表征其邻域；匹配即比较描述子距离。
  3. 几何从像素到世界：单应性（Homography）描述两视图间的平面映射，4 对匹配点即可解出，用于拼接、AR、文档矫正。
  4. 轮廓是连通区域边界：从二值图提取轮廓，可算面积、外接矩形、近似多边形，是传统目标检测与计数的利器。
  5. 本章目标：掌握角点/特征检测与匹配、单应性求解、轮廓分析，理解传统 CV 几何处理的边界与深度模型的分工。

本章承接 第三章：滤波与几何变换。生产级检测/分割多交由 第一章：PyTorch 入门与张量 深度模型，OpenCV 负责几何与前后处理。

一、角点检测：Harris 与 Shi-Tomasi

角点在两方向都有强梯度，是稳定的特征点：

  • Harris：返回角点响应图，需自行阈值化。
  • goodFeaturesToTrack：直接返回前 N 个角点坐标，参数为（最大点数、质量阈值、最小间距）。

二、特征检测与描述：ORB/SIFT

1. SIFT（尺度不变）

SIFT 对尺度、旋转、光照变化鲁棒，4.x 起主包可用：

2. ORB（快速，免费）

ORB 速度远快于 SIFT 且无专利，实时场景首选：

3. 特征匹配

  • NORM_HAMMING：ORB 等二进制描述子用汉明距离；SIFT 等浮点描述子用 NORM_L2。
  • crossCheck=True：双向匹配，过滤误匹配。
  • 比值检验（Lowe’s ratio test）进一步筛优：近邻距离 / 次近邻 < 0.7 才保留。

三、单应性矩阵与图像拼接

由 4 对以上匹配点解 3×3 单应性矩阵，把一幅图「贴」到另一幅的平面：

应用：全景拼接、AR 平面贴合、文档/车牌矫正（第三章透视变换的进阶）。

单应性要求场景中存在平面（或纯旋转相机），非平面场景会有视差错位。

四、轮廓检测与分析

  • RETR_EXTERNAL：只取最外层轮廓；RETR_TREE 取全部层级。
  • CHAIN_APPROX_SIMPLE：压缩水平/垂直/对角冗余点，省内存。
  • 形状识别：approxPolyDP 顶点数 → 三角形 3、矩形 4、圆 >8。

五、模板匹配

在图中滑动模板找最相似位置（限定于平移、无尺度旋转）：

局限：matchTemplate 只对平移有效，目标有旋转/缩放则失效——这种情况改用特征匹配或深度模型。

六、传统 CV 与深度模型的分工

任务 传统（本章） 深度模型
图像配准/拼接 SIFT/ORB + 单应性 优势 少用
物体检测 模板匹配（仅平移）/轮廓 YOLO/DETR 优势
语义分割 阈值/分水岭 U-Net/Mask R-CNN 优势
几何测量 轮廓面积/周长 优势 —
实时跟踪 KCF/光流 Siamese 等深度跟踪

经验：几何与配准用传统 CV，识别与分割用深度模型，二者常组合——深度模型出框，OpenCV 做几何后处理。

七、常见陷阱

陷阱 说明
Harris 输入未转 float32 cornerHarris 需 float32 灰度，uint8 报错
ORB 用 L2 距离 ORB 二进制描述子须用 NORM_HAMMING
无比值检验误匹配多 只取最近邻会有大量误匹配，加 Lowe ratio test
单应性点不足 需 ≥4 对点，且不能共线，否则解不稳
轮廓忘过滤小面积 不滤噪点轮廓会画出一片碎点
模板匹配遇旋转 matchTemplate 不抗旋转缩放，需改特征匹配
findContours 改原图 该函数会修改输入图，传副本

第一章：FFmpeg 音视频处理入门

概念基础

  1. 音视频处理瑞士军刀：FFmpeg 是开源的转码、裁剪、截图、推流命令行工具集，几乎所有播放器、视频网站与转码服务背后都有它（Chrome、VLC、OBS 均基于或依赖其底层库）。
  2. 三大组件：ffmpeg（转码与处理）、ffprobe（查看媒体元信息）、ffplay（本地播放调试）。底层是四大库 libavcodec / libavformat / libavfilter / libavutil。
  3. 命令结构固定：ffmpeg [全局选项] -i 输入 [输出选项] 输出，理解「输入 → 滤镜 → 编码 → 封装」流水线即可举一反三。
  4. 容器与编解码分离：MP4/MKV 是封装容器，H.264/AAC 是编码格式；-c copy 只换容器不重编码，速度极快。
  5. 应用广泛：视频网站转码、HLS/RTMP 直播推流、GIF 生成、提取音频等日常需求一条命令搞定。

一、三大组件

组件 作用 典型用法
ffmpeg 转码、裁剪、滤镜、推流等一切处理 ffmpeg -i in.mp4 out.mp4
ffprobe 查看媒体元信息（容器、流、编码、时长、码率） ffprobe -show_format -show_streams in.mp4
ffplay 本地简易播放器，调试滤镜效果 ffplay -vf "scale=640:-2" in.mp4

先用 ffprobe 摸清输入再动手，是排查问题的第一步——它告诉你容器格式、有几路流、各路编码/分辨率/码率/时长。

二、命令结构与执行流水线

一条命令的内部流转：



flowchart LR
  IN[输入文件/流 -i] --> DEMUX[解封装 demux]
  DEMUX --> DEC[解码 decode]
  DEC --> FLT[滤镜 filter]
  FLT --> ENC[编码 encode]
  ENC --> MUX[封装 mux]
  MUX --> OUT[输出文件/流]

关键：滤镜与重编码都需先解码到原始帧再处理。-c copy 跳过「解码→编码」，直接拷贝原始码流到新容器，故秒级完成但无法改编码/分辨率/滤镜。

第五章：流媒体与直播推流

发表于 2026-05-01 更新于 2026-09-01 分类于 FFmpeg 本文字数： 1.7k 阅读时长 ≈ 6 分钟

第五章：流媒体与直播推流

概念基础

  1. 点播（VOD）转码生成完整文件供下载/拖拽；直播是持续产生的流，观众边产生边消费，时延与一致性是核心矛盾。
  2. 三大协议：RTMP（推流主流，低延迟、TCP）、HLS（拉流主流，切片+列表，高兼容、延迟高）、DASH（HLS 的国际版替代，类似机制）。WebRTC/SRT 面向超低延迟。
  3. 推流与拉流：推流（push）把本地媒体送到服务器，如 ffmpeg → RTMP 服务器；拉流（pull）从源拉取再转发，如 ffmpeg 拉一路 RTSP → 推给 HLS 切片。
  4. -re 是直播关键：按真实帧率读取输入，防止 ffmpeg 全速把文件瞬间推完，导致服务器缓冲溢出。
  5. 本章目标：掌握 RTMP 推流、HLS/DASH 切片、拉流转发、直播参数调优，能搭起最小直播链路。

本章承接 第四章：滤镜与滤镜图，面向实时场景。协议基础见 第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例、第十一章：WebSocket 详解：握手、帧与 Python 示例。

一、RTMP 推流

RTMP 基于 TCP，是推流到 B 站/斗鱼/自建 Nginx-RTMP 的主流协议：

  • -re：按帧率读取，直播必备（点播转 HLS 也常用）。
  • -f flv：RTMP 封装用 FLV。
  • -tune zerolatency：编码器零延迟模式，直播首选。
  • -preset ultrafast：实时编码优先速度。
  • -g：关键帧间隔，直播常设为帧率×2（如 60，对应 30fps 的 2 秒 GOP）。

推流地址需替换为实际服务器；自建可用 nginx-rtmp-module 或 SRS。

二、HLS 切片

HLS 把媒体切成小 .ts 片段 + .m3u8 播放列表，HTTP 分发，兼容性最好（iOS/Safari 原生支持）：

  • -hls_time N：每段约 N 秒（实际按 GOP 对齐）。
  • -hls_list_size N：列表保留 N 段；直播设小值（如 3–6），旧段自动滚动。
  • -hls_flags delete_segments：直播自动删旧段，防磁盘爆满。
  • -hls_playlist_type vod：点播固定列表；直播用 event（累积）或不设。
  • 延迟：HLS 延迟 ≈ hls_time × (hls_list_size + 1)，常 10–30 秒，不适合低延迟。

三、DASH 切片

DASH 机制类似 HLS，输出 .mpd 清单 + .m4s 分片，国际标准、Web 兼容好：

  • -seg_duration：分片时长。
  • -window_size：滑窗大小（直播用）。
  • 浏览器用 dash.js 播放；HLS 用 hls.js。

四、拉流与转发

从一路源拉取，转码或不转码后推到另一路，常用于「监控 RTSP 转 HLS 给浏览器」「转码适配多端」：

  • -rtsp_transport tcp：RTSP 用 TCP 传，比 UDP 稳（防丢包花屏）。
  • 拉流是「无限」的：源不断开，ffmpeg 不退出；运维需配合 systemd 或循环脚本保活。

第二章：编解码与转码

第二章：编解码与转码

概念基础

  1. 转码 = 解码 + 重新编码：把输入的某种编码（如 ProRes/HEVC）转成另一种（如 H.264），是 FFmpeg 最高频的操作，也是质量与体积权衡的主战场。
  2. 容器与编码两层独立：.mp4 是容器，可装 H.264/H.265/AV1 多种视频编码与 AAC/MP3 多种音频编码；改容器不一定要改编码，改编码也不一定要改容器。
  3. 质量来自编码器与参数：同一 H.264，libx264 的 -crf/-preset 决定「画质-体积-速度」三角；选错参数要么体积爆炸、要么画质崩坏。
  4. 码率模式三选一：CRF（恒定质量，最常用）、两次编码（精确体积，离线归档）、CBR/VBR（直播定码率）。
  5. 硬件编码提速：CPU 软编画质最好但慢；NVIDIA/Intel/Apple 硬件编码器数倍提速，适合实时与批量，画质略逊但多数场景可接受。

本章承接 第一章：FFmpeg 音视频处理入门 的命令骨架，把转码从「能跑」讲到「会调」。

一、容器与编码：两层概念

层 例子 作用
容器（封装） MP4、MKV、MOV、FLV、TS、WebM 打包音视频/字幕流 + 索引 + 时间戳
视频编码 H.264、H.265/HEVC、AV1、VP9、ProRes 压缩视频画面
音频编码 AAC、MP3、Opus、FLAC、PCM 压缩音频

-c copy 拷贝的是编码后的码流，故只能换容器、不能改编码或分辨率；要改必须重编码（解码→编码）。

二、常用编码器选择

1. 视频编码器

编码器 编码 特点 典型场景
libx264 H.264 软编，画质/兼容性最好，最常用 通用 Web/移动端
libx265 H.265/HEVC 同画质体积约省 40%，编码慢、兼容性次之 4K/高压缩归档
libvpx-vp9 VP9 开源，WebM 常用，慢 YouTube/WebM
libaom-av1 AV1 最新开源，压缩率最高，编码极慢 面向未来/带宽敏感
h264_nvenc H.264 NVIDIA 硬编，快 实时/批量
h264_qsv H.264 Intel QuickSync 硬编 Intel 服务器
h264_videotoolbox H.264 Apple 硬编 macOS/iOS

查可用编码器：ffmpeg -encoders | grep 264；查某编码器参数：ffmpeg -h encoder=libx264。

2. 音频编码器

编码器 编码 特点
aac AAC 通用首选，-b:a 128k 够用
libmp3lame MP3 兼容老设备
libopus Opus 低码率语音/直播最优
flac FLAC 无损，音乐归档
copy 原样 不重编码

三、CRF：恒定质量（最常用）

CRF（Constant Rate Factor） 让编码器按「目标画质」自适应分配码率——复杂场景多给字节、简单场景少给，体积随内容变化但画质恒定，是离线转码首选。

  • -crf 范围 0–51（libx264），越小质量越高、文件越大：
    • 18：视觉无损（归档）
    • 23：默认，画质与体积均衡
    • 28：可接受画质，体积小（预览）
  • -preset 权衡编码速度与压缩率，越慢压缩率越好（同画质体积更小）：
    ultrafast → superfast → veryfast → faster → fast → medium（默认）→ slow → slower → veryslow
  • -tune 针对内容调优：film（电影）、animation（动画）、fastdecode（易解码）等。

经验：离线归档用 -crf 18 -preset slow；日常转码 -crf 23 -preset medium；批量预览 -crf 28 -preset fast。

四、两次编码（2-pass）：精确体积

需控制输出体积（如限制 100MB）时，CRF 无法预测体积；用 2-pass：第一遍分析码率分布，第二遍按目标码率精准分配。

适用：视频网站固定码率档位、存储受限的归档。实时场景不可用（需两遍）。

五、码率与目标体积换算

例：1 小时视频，目标 1GB，则总码率 ≈ 1000MB×8 / 3600s ≈ 2.2 Mbps，分给视频约 2M、音频 128k。

-maxrate/-bufsize 配合做受限 VBR，防码率尖峰超限。

六、分辨率与帧率调整

缩放务必用 -2 而非 -1 作为偶数维度，H.264 要求宽高为偶数。

七、硬件编码

软编画质好但慢；硬件编码器数倍提速，CPU 占用低：

硬件编码器参数与软编不同（如 NVENC 用 -preset p1..p7、-cq/-rc vbr），查帮助：ffmpeg -h encoder=h264_nvenc。

取舍：

  • 实时直播/批量转码：硬件编码优先（速度、并发）。
  • 高画质离线归档：libx264 -preset slow 软编，画质同体积最优。
  • 兼容性：硬件编码器依赖驱动与编译选项，部署前确认 ffmpeg -encoders 含目标编码器。

八、常见陷阱

陷阱 说明
-c copy 改分辨率 copy 跳过编解码，分辨率/滤镜无效；要改必须重编码
容器与编码不匹配 如 HEVC 装进某些旧 MP4 profile 不被 Safari 播放；用 -tag:v hvc1 兼容
CRF 当直播用 CRF 体积不可控，直播应用 CBR/-maxrate 限码率
preset 误解 ultrafast 不是「最快且最好」，是「最快但体积大」；画质同则慢 preset 体积更小
音频忘了设编码 不指定 -c:a 时默认可能选不兼容编码；显式 -c:a aac
缩放奇数维度 H.264 要求偶数，奇数报错；用 -2 自动取偶
10bit 源降 8bit 崩色 加 -pix_fmt yuv420p 保证 8bit 兼容播放器

要点 结论
两层概念 容器（MP4/MKV）与编码（H.264/AAC）独立；-c copy 只换容器
编码器 通用首选 libx264；高压缩 libx265/AV1；实时用 h264_nvenc/qsv
CRF 恒定画质自适应码率，离线首选；18 视觉无损、23 默认、28 预览
preset 越慢压缩率越好；归档 slow、日常 medium
2-pass 精确体积，第一遍分析第二遍编码；实时不可用
码率 体积 ≈ 码率 × 时长；直播用 -maxrate/-bufsize 限峰
缩放 scale=W:-2 偶数；force_original_aspect_ratio=decrease 防放大
硬件 实时/批量优先，参数与软编不同；归档画质选软编

第三章：音视频编辑处理

发表于 2026-05-01 更新于 2026-09-01 分类于 FFmpeg 本文字数： 1.6k 阅读时长 ≈ 5 分钟

第三章：音视频编辑处理

概念基础

  1. 编辑操作多在「容器/时间」层：裁剪、截图、合并、抽取音轨，多数可 -c copy 不重编码，秒级完成；只有变速、加滤镜才需重编码。
  2. 时间精度取决于关键帧：-c copy 裁剪只能切在关键帧，可能比目标点晚几帧；要精确到帧需重编码或先对齐关键帧。
  3. 合并与拆分：同编码参数的多段用** concat 协议/滤镜**无损拼接；异构参数需重编码统一后再拼。
  4. GIF 是特殊输出：调色板优化是高质量 GIF 的关键，直接转 GIF 易有色带。
  5. 本章目标：覆盖日常编辑 90% 需求——裁剪、截图、GIF、提取/分离音轨、合并、变速、音量调整。

本章承接 第二章：编解码与转码，操作多可 -c copy，速度优先。

一、裁剪与切片

1. 按时间裁剪

  • -ss 在 -i 前：解封装快速跳转（推荐），可能不精确到帧。
  • -t：时长；-to：结束时间点。
  • -c copy：裁剪只能切在关键帧，开头可能略偏；要精确用重编码。

2. 等分切片

二、截图与序列帧

  • -frames:v 1：只输出 1 帧。
  • -vf "fps=N"：每秒 N 帧采样，用于连续截图/缩略图。

三、GIF 生成

直接转 GIF 易有色带，先生成调色板再引用是高质量做法：

  • fps=10：帧率（GIF 体积敏感，10–15 帧够用）。
  • scale=480:-1：宽度 480，高度按比例。
  • flags=lanczos：高质量缩放算法。
  • palettegen/paletteuse：生成与使用调色板，显著减少色带。

四、音频提取与分离

  • -vn：丢视频；-map 0:a:N：选第 N 路音轨（从 0 起）。
  • -c:a copy：原样抽出，不重编码（仅改封装）。

五、合并

1. concat 协议（同编码参数，无损最快）

-safe 0：允许 list.txt 用绝对路径或相对路径。

2. concat 滤镜（异构参数，需重编码）

n=2：段数；v=1:a=1：各段有 1 路视频 1 路音频。

3. 音视频合并（独立视频 + 独立音频）

-shortest：以最短流为准截断（防音频比视频长导致黑屏拖尾）。

六、变速

  • setpts=N*PTS：视频时间戳缩放，<1 加速、>1 慢放。
  • atempo=N：音频变速，范围 0.5–2.0；更大倍率需链式 atempo=2,atempo=2（4 倍）。

七、音量与静音处理

  • volume=N：线性增益，1.0 原音量。
  • loudnorm：EBU R128 响度归一化，适合多段混剪统一音量。

八、旋转与翻转

transpose：0=逆90、1=顺90、2=逆90+垂直翻转、3=顺90+垂直翻转。

九、常见陷阱

陷阱 说明
concat 协议参数不一 各段编码/分辨率/时间基不同会花屏或失败，需先用重编码统一
裁剪开头黑帧 -c copy 切在关键帧，开头可能有几帧偏差；精确需重编码
GIF 体积爆炸 不限帧率/尺寸 GIF 极大；用 fps+scale+调色板控制
变速没动音频 只 setpts 视频变速，音频仍原速，导致不同步；必须同步 atempo
合并音视频拖尾 音频比视频长，未加 -shortest 导致黑屏拖尾
截图无 -frames:v 1 不限制会输出该时间点后所有帧到文件序列
-map 选错流 多音轨源默认只取第一路；需用 -map 0:a:N 指定

本章小结

要点 结论
裁剪 -ss+-t/-to，-ss 在 -i 前快速；-c copy 切关键帧，精确需重编码
截图 -frames:v 1 单帧；fps=N 连续截图
GIF 先 palettegen 再 paletteuse，配 fps+scale+lanczos 控体积质量
音频提取 -vn 丢视频；-map 0:a:N 选音轨；-c:a copy 原样抽
合并 同参数用 concat 协议（无损）；异构用 concat 滤镜（重编码）
音视频合 -map 选流 + -shortest 防拖尾
变速 setpts 视频变速 + atempo 音频变速必须同步
音量 volume=N 线性增益；loudnorm 统一响度

第六章：高级技巧与性能调优

概念基础

  1. 批量与自动化：生产环境很少单条命令手敲，更多是批处理转码、管道串联、监听目录——把 ffmpeg 嵌入脚本与流水线。
  2. 硬件加速链路：单独用硬件编码器只是冰山一角，真正的提速是 解码→缩放→编码全链路走 GPU，避免 CPU↔GPU 来回拷贝。
  3. 性能瓶颈在 I/O 与编码：磁盘读写、编码 preset、滤镜复杂度决定吞吐；调优先量化（-progress/time），再针对性优化。
  4. 质量度量要客观：肉眼判断不可靠，PSNR/SSIM/VMAF 给出客观分数，用于对比编码器与参数。
  5. 本章定位：把前五章零散的硬件、批处理、监控手段系统化，给出生产级调优清单与陷阱汇总，是 FFmpeg 进阶的收尾。

本章综合 第二章：编解码与转码 编解码与 第五章：流媒体与直播推流 流媒体，面向高吞吐生产场景。

一、硬件加速全链路

仅用 -c:v h264_nvenc 只加速编码，解码与缩放仍走 CPU，且数据要 CPU↔GPU 拷贝。全链路 GPU 才是最大化提速：

  • -hwaccel cuda：硬件解码。
  • -hwaccel_output_format cuda：解码后帧留在 GPU 显存，避免拷回 CPU。
  • scale_cuda：GPU 缩放滤镜（替代 scale）。
  • h264_nvenc：GPU 编码。

对应 Intel QSV：-hwaccel qsv -c:v h264_qsv -vf scale_qsv；Apple VideoToolbox 链路类似。

取舍：全链路 GPU 提速数倍，但滤镜生态不如 CPU 丰富（subtitles/drawtext 等多在 CPU），需在 GPU 滤镜前后用 hwdownload/hwupload 转换，复杂度上升。纯转码提速用全链路；复杂滤镜用 CPU 或混合。

二、管道串联与多路输出

1. 管道：一帧编码下一工具接手

pipe:1/pipe:0 用标准输入输出串联，适合把 ffmpeg 接入已有处理管线。

2. 一条命令多路输出

一次解码多次编码，比跑三条命令快（解码只做一遍）。

维度 调优项

八、常见陷阱汇总

陷阱 说明
硬编画质差却不知 NVENC 默认参数偏弱，需 -preset p5+/-cq 调优，并用 VMAF 对比
GPU 显存泄漏 全链路 GPU 异常退出未释放显存，需监控 nvidia-smi
并行超 CPU 软编 -P 超核数反而争抢变慢
预设误用 归档用 ultrafast 导致体积翻倍；实时用 veryslow 跟不上
-c copy 改滤镜 任何滤镜都需重编码，copy 模式滤镜静默无效
批处理无 -y 输出已存在 ffmpeg 交互询问，脚本卡死；脚本必加 -y 或 -n
进度解析错 frame 是累计帧非实时；实时看 fps 与 speed
音频采样率不匹配 不同源混音/拼接前统一 -ar 44100，否则爆音或失败
10bit/HDR 降级 不加 -pix_fmt yuv420p 普通播放器黑屏或偏色

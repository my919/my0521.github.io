PostgreSQL DDL 语句

DDL：Data Definition Language 数据定义语言
作用：定义/修改/删除 数据库、模式（SCHEMA）、表、字段、索引等对象结构，不直接操作「行级业务数据」本身（数据由 DML 写入）。

DDL 主要分 3 大类

  1. 库 / 模式：CREATE / ALTER / DROP DATABASE；CREATE SCHEMA 等（SCHEMA 类似命名空间，用于组织表与权限）。
  2. 表与列：CREATE / ALTER / DROP TABLE；约束、默认值、自增（IDENTITY / SERIAL）。
  3. 其他对象：VIEW、INDEX、SEQUENCE、EXTENSION 等（入门可先把 表 + 索引 吃透）。

MySQL DDL 语句

DDL：Data Definition Language 数据定义语言
作用：定义/修改/删除 数据库、表、字段结构，不操作表里数据，只管「结构」

DDL 主要分 3 大类

  1. 库操作：CREATE / ALTER / DROP 数据库
  2. 表操作：CREATE / ALTER / DROP 数据表
  3. 其他（仍是 DDL：定义「对象结构」，不直接改表内业务行）
    • 视图（VIEW）：CREATE VIEW / ALTER VIEW / DROP VIEW。把一段查询保存成虚拟表名，查询时动态算出结果；本身不单独存一份业务数据，常用于简化复杂 SQL、封装列权限。
    • 索引（INDEX）：CREATE INDEX，或 ALTER TABLE ... ADD INDEX、DROP INDEX 等。在列（或列组合）上维护辅助查找结构，加快 SELECT，但会占磁盘、拖慢部分 INSERT/UPDATE/DELETE；与表强相关，属结构的延伸。
      存储过程、触发器等也可由 DDL 创建/删除对象。

FOREIGN KEY（外键约束）

  • 作用：子表某列（或列组合）只能取父表已存在的主键值（或父表上被引用的 UNIQUE 列），防止「悬挂引用」。

Redis 入门：安装、CLI 与数据类型

Redis 是内存型数据结构存储，常用作缓存、会话、排行榜、消息流与分布式锁等；单线程执行命令模型简单，但持久化、主从与集群仍须按业务规划。下面从「官网与概念 → 安装验证 → 启动与 redis-cli → 常用数据类型 → 持久化与安全要点 → 与容器部署的关系」顺序写清楚；命令在 Linux / macOS 终端或 Windows WSL 中均可使用（生产环境请固定版本并限制暴露面）。

一、官网与定位

  • Redis 文档（当前产品站）：https://redis.io/docs/
  • 下载与发行说明：https://redis.io/downloads/
  • 命令参考：https://redis.io/commands/

Redis 以键值为核心，值支持多种数据类型（字符串、哈希、列表等）；默认监听 6379。与关系型数据库不同，数据主要在内存中，须结合淘汰策略、持久化与备份设计，避免单点丢数。

五、持久化：RDB 与 AOF

方式 说明
RDB 按策略生成时间点快照（.rdb），恢复快、可能丢失最后一次快照后的写入
AOF 追加写日志（.aof），可配置 fsync 频率，更耐久、文件通常更大

配置在 redis.conf 中（包安装路径因发行版而异，常见 /etc/redis/redis.conf）。Docker 场景下常通过 redis-server 参数 或挂载配置覆盖，与 Docker 部署 Redis 中 --appendonly 等示例对照即可。

六、安全与网络要点

  1. 默认无密码时，只要网络能连上 6379 即可读写，仅允许本机或可信内网；公网暴露须配 requirepass 与 Redis ACL，并配合防火墙、TLS（视版本与部署形态）。
  2. bind：默认若监听 0.0.0.0，表示所有网卡可连；缩小监听地址可减少误暴露。
  3. 危险命令：FLUSHALL、CONFIG 等在生产应通过 rename-command 禁用或限制执行身份。

七、小结

场景 做法
安装验证 redis-server --version；redis-cli ping
本地读写 SET / GET；按业务选 Hash / List / ZSet 等
持久化 redis.conf 中 RDB / AOF 策略；容器见 Redis-Docker 文
安全 密码 / ACL + 网络隔离；避免公网裸 6379
容器与编排 Docker 部署 Redis

更深入的主从复制、Sentinel 高可用、Cluster 分片与客户端连接池调优，请以当前 Redis 大版本官方文档为准，并与业务 RPO/RTO 一起评审。

MyBatis-Plus 分页原理

一、核心一句话

MP 分页本质：MyBatis 拦截器 + 自动改写 SQL

  1. 你传入 Page<>(当前页,每页条数)
  2. MP 分页拦截器拦截 Mapper 查询方法
  3. 自动帮你生成 count 总数SQL + 拼接 limit 分页SQL
  4. 执行两条 SQL：查总数 → 查当前页数据
  5. 把总数、页码、数据封装到 IPage 返回

二、关键核心组件

  1. MybatisPlusInterceptor
    MP 核心插件容器，所有插件（分页、防全表更新、乐观锁）都往里注册。
  2. PaginationInnerInterceptor
    MP 真正的分页拦截器，核心逻辑全在这。
  3. Page / IPage
    分页参数载体，存：当前页、每页条数、总记录数、总页数、分页数据。

三、完整执行流程（一步一步走）

1. 配置分页拦截器（必须配置，否则分页无效）

2. 业务代码使用

3. 底层执行步骤

  1. 进入 Mapper 方法前
    PaginationInnerInterceptor 拦截到 selectPage 查询。
  2. 判断是否是分页查询
    检测方法参数里有没有 IPage/Page 对象，有就走分页逻辑。
  3. 自动生成 COUNT 语句
    原SQL：select id,name from user
    自动生成：select count(*) from user → 查询总记录数
  4. 改写原SQL 加 LIMIT
    原SQL 被改写为：
    select id,name from user limit 0,10
  5. 执行两条 SQL
  • 第一条：查总条数
  • 第二条：查分页数据
  1. 封装分页信息
    把总条数、当前页、每页大小、总页数、数据列表 全部塞进 IPage 返回。

四、为什么不用自己写 limit、不用自己写 count？

MP 拦截器动态解析 SQL、动态拼接 limit、动态生成 count，完全无侵入。

五、分页两个重要特性

1. 分页合理化 reasonable=true

  • 输入页码 <=0 自动变成第 1 页
  • 输入页码 大于总页数 自动返回最后一页

2. 溢出总页数后是否查最后一页

PaginationInnerInterceptor 可配置，防止页码乱输报错。

六、常见坑（原理衍生出来的）

  1. 没配置 PaginationInnerInterceptor → 分页无效，查全部数据
  2. 只有 Mapper 层用 Page 参数才生效，Service 自己写 list 不分页
  3. 自定义 XML SQL 也能自动分页，MP 照样拦截加 limit、count
  4. 多表联查、复杂 SQL 也支持，拦截器会解析原有 SQL 结构

七、极简总结

MP 分页 = 拦截器拦截SQL → 自动查总数 → 自动拼接LIMIT → 封装分页结果
不用手写 count、不用手写 limit，全靠拦截器动态代理实现。

第一章：Kafka 消息中间件入门：核心概念与架构

概念基础：Kafka 是什么

Apache Kafka 是分布式事件流平台：高吞吐、持久化、可回放的分区日志，用于消息队列、日志管道、流式处理与数据集成。本文侧重 MQ / 微服务视角。

  1. 本质是「分区日志」：每条消息只是追加到分区末尾的日志记录，不消费即删除，消费只移动游标（offset）——所以消息可以被多组消费者反复回放，这是它与 RabbitMQ 这类「消费即删除」传统 MQ 最大的差别。
  2. 为什么快：磁盘顺序写 + page cache + 零拷贝 + 批量压缩，单机即可达到十万级 TPS 量级；吞吐是 Kafka 设计的第一目标。
  3. 三大角色：当消息队列（削峰、解耦）、当日志总线（各系统日志/埋点统一进 Kafka）、当流计算数据源（Flink/Spark 从 Kafka 读）。本站对应：微服务集成见 第十一章：Spring Cloud 集成 RocketMQ：异步消息与事件驱动扩展，大数据总线见 第三章：Kafka 大数据数据总线。
  4. 权衡：为吞吐放弃了部分「业务 MQ」能力（无内置延迟消息、事务消息偏流式），这些场景通常选 RocketMQ（见本章对照小节与 第四章：RocketMQ 核心概念与架构）。

先看它的整体架构：

核心概念

概念 说明
Topic 逻辑消息流名称
Partition Topic 的分片，有序日志；并行度与分区数相关
Offset 分区内每条消息的唯一递增序号
Producer 写入消息，可指定 key 做分区路由
Consumer Group 组内消费者分摊分区，同组不重复消费同一分区
Broker 存储与 Serving 分区的服务器进程

消息持久化在磁盘（顺序写 + page cache），可配置保留时间与大小。

理解要点：「分区内有序、分区间无序」——需要顺序的业务（同一订单的状态变更）必须用同一 key 路由到同一分区；并行度上限 = 分区数，消费者实例多于分区数时空闲。

生产者与消费者

1. 生产者

  • acks：0 / 1 / all 权衡延迟与持久性。
  • 幂等生产者：避免重试导致重复（下游仍可能需要业务去重）。
  • 事务：跨分区 exactly-once 与 Kafka Streams 场景。

2. 消费者

  • auto.offset.reset：earliest / latest。
  • 手动提交 offset：处理成功后再 commitSync / commitAsync。
  • 再均衡（Rebalance）：组成员变化时重新分配分区；消费逻辑应支持幂等。

3. 投递语义（需业务配合）

语义 说明
At most once 先提交 offset 再处理，可能丢
At least once 先处理再提交，可能重复
Exactly once 事务 + 幂等存储，成本高

分区、副本与 ISR

  • Leader / Follower：每个分区一个 Leader 负责读写，Follower 同步。
  • ISR（In-Sync Replicas）：与 Leader 差距在阈值内的副本；min.insync.replicas 与 acks=all 共同定义「写成功」。
  • 扩容：增加分区数不会重分布历史 key；规划分区数宜前置。

KRaft 与 ZooKeeper

Kafka 3.x+ 可用 KRaft（内置 Raft 元数据）替代 ZooKeeper。新集群建议 KRaft；存量 ZK 集群按官方迁移指南操作。本站 第二章：Docker 部署 Kafka 实践 采用 KRaft 单节点示例。

与 RocketMQ 的对照

维度 Kafka RocketMQ
模型 分区日志、流式优先 Topic + Queue、顺序/延迟/事务消息
生态 Connect、Streams、Flink/Spark 国内电商、SCA 集成
典型场景 日志、指标、CDC、流计算 订单、定时、强业务 MQ

RocketMQ 入门见 第四章：RocketMQ 核心概念与架构；Spring Cloud 集成见 第十一章：Spring Cloud 集成 RocketMQ：异步消息与事件驱动扩展；Java 客户端示例见 第三章：Kafka Java 发布与消费实战。

部署与命令行探测

容器部署：第二章：Docker 部署 Kafka 实践。局域网中间件见 服务（:30006 等）。

生产注意事项

项 建议
分区数 与消费者并行度、磁盘并行写相关；不宜过少
保留 retention.ms 与磁盘容量；合规场景可能需归档到对象存储
监控 Under-replicated partitions、请求 P99、磁盘使用率
安全 SASL/SSL、ACL；勿将 9092 裸奔公网

官方文档：https://kafka.apache.org/documentation/

本章小结

要点 结论
本质 分区日志：追加写、可回放、消费只动 offset
顺序 分区内有序；同 key 同分区是保序手段
可靠性 acks + ISR + 幂等 共同定义「写成功」
消费模型 Consumer Group 分摊分区；Rebalance 需幂等兜底
元数据 新集群用 KRaft，不再依赖 ZooKeeper

Nginx

概念基础：Nginx 是什么/为什么

  1. 高性能 Web 服务器：Nginx 采用事件驱动、异步非阻塞架构，单机可承载数万并发连接，资源占用远低于传统的进程/线程模型。
  2. 反向代理与负载均衡：作为系统入口网关把请求转发给后端多实例（upstream），支持轮询、ip_hash、least_conn 等策略，是微服务架构标配。
  3. 静态资源服务：托管前端构建产物（dist）高效稳定，配合 try_files 无缝支持 SPA 的 history 路由。
  4. TLS 终结：在 Nginx 层统一卸载 HTTPS，后端走明文 HTTP，证书的申请与续期集中在一处管理。
  5. 模块化生态：限流、缓存、重写等能力开箱即用，也是 K8s Ingress Controller 的主流实现之一。

Git 版本控制入门

概念基础：Git 是什么/为什么

  1. 分布式版本控制：每个开发者本地都有完整的仓库与历史，提交、分支、回滚离线可用；GitHub/Gitee 等远端只是同步与协作节点。
  2. 三大工作区流转：工作区 → 暂存区（git add）→ 本地仓库（git commit）→ 远程仓库（git push），理解这条流水线就掌握了日常九成操作。
  3. 分支极其轻量：分支只是指向提交的可移动指针，创建与切换几乎零成本，因此鼓励「功能分支 + 合并」的协作方式。
  4. 改历史要克制：未推送的提交可用 reset 自由整理；已推送的公共历史应使用 revert 生成反向提交，避免强推坑队友。
  5. 配置先行：首次使用先全局配置 user.name / user.email，提交记录才有可信的作者信息。

第一章：Linux 常用命令与运维入门

概念基础：Linux 是什么

  1. 内核与发行版：Linux 内核只有一份，日常使用的是「内核 + 包管理器 + 软件仓库」组成的发行版（RHEL 系、Debian 系、Arch 等），选型直接决定包管理器与生态。
  2. 一切皆文件：配置（/etc）、可变数据（/var）、设备与进程信息都以文件形式呈现，运维工作的本质常常就是「读文件、改文件、管进程」。
  3. 权限模型：每个文件有 user / group / other 三组 rwx 权限，chmod / chown 是多用户系统的第一道防线。
  4. Shell 是操作入口：默认多为 bash，脚本首行 #!/bin/bash；服务器运维的主战场是命令行而非图形界面。
  5. 服务由 systemd 托管：常驻服务以 .service 单元交给 systemd 管理，systemctl / journalctl 是服务排障的标配工具。

发行版与 Shell

系列 包管理 典型用途
RHEL / Rocky / Alma dnf/yum 企业服务器、K8s 节点
Debian / Ubuntu apt 云主机、桌面、CI
Arch pacman 滚动更新、开发者桌面

默认 Shell 多为 bash；脚本首行 #!/bin/bash，交互与运维命令在终端执行。

文件系统与权限

  • 根目录 /：/etc 配置、/var 可变数据、/home 用户家目录、/tmp 临时。
  • 软/硬链接：ln -s 与 ln。
  • 查找：find、grep（或 ripgrep）。

进程与服务

  • systemd：.service 单元管理守护进程。
  • cron / timer：定时任务。

第三章：LLM 大语言模型基础

概念基础：大语言模型是什么

  1. 大语言模型（LLM）是在海量文本语料上以自监督方式预训练的超大 Transformer 网络，能理解与生成自然语言。
  2. 训练三阶段：预训练（下一词预测，学通用语言与知识）→ 监督微调（SFT） 对齐「助手」行为 → RLHF / DPO 对齐人类偏好。
  3. 交互单位是 Token：模型受上下文窗口（Context Window）限制，一次只能处理有限的 Token；长文档需分块或 RAG。
  4. 幻觉与增强：模型可能一本正经地编造内容，用**检索增强生成（RAG）接入私有知识、用工具调用（Function Calling）**连接真实 API 来缓解。
  5. 落地三路线：Prompt 工程最轻量，微调（LoRA/QLoRA）注入领域知识，RAG + Agent 组合解决知识时效与工具执行。

生命周期

预训练 下一词预测（Causal LM）或掩码语言模型，学通用语言与知识
监督微调（SFT） 指令数据上对齐「助手」行为
RLHF / DPO 等 人类偏好或偏好对优化安全性与有用性
推理部署 量化、批处理、KV Cache、投机解码

代表模型族：GPT、Llama、Qwen、DeepSeek 等（以各开源/商用许可为准）。

  • System / User / Assistant 角色消息构成对话。
  • Few-shot：在 Prompt 中给示例引导格式。
  • Context Window：模型一次可处理的 Token 上限；长文档需分块或 RAG。
  • Temperature / Top-p：控制采样随机性。

第二章：DL 深度学习基础

发表于 2026-05-01 更新于 2026-08-30 分类于 AI 本文字数： 1.4k 阅读时长 ≈ 5 分钟

第二章：DL 深度学习基础

概念基础：深度学习是什么

  1. 深度学习（DL）是机器学习的分支：用多层神经网络自动从数据中学习层次化特征表示，大幅减少手工特征工程。
  2. 核心机制：前向传播计算输出与损失，反向传播按链式法则求梯度，SGD/Adam 等优化器迭代更新权重。
  3. 非线性是关键：层间插入激活函数（ReLU / Sigmoid / GELU 等），否则多层线性堆叠仍等价于单层线性模型，无法拟合复杂模式。
  4. 架构按数据形态选：MLP 管表格向量、CNN 管图像空间模式、RNN/LSTM 管序列、Transformer 用 Self-Attention 建模长距离依赖并成为 LLM 的基座。
  5. 算力与工程：训练依赖 GPU/CUDA，配合 PyTorch 等框架与混合精度、学习率调度等技巧才能稳定高效。

神经网络基础



flowchart LR
  X[输入] --> F[前向传播]
  F --> L[损失 Loss]
  L --> B[反向传播梯度]
  B --> U[更新权重]
  • 前向传播：输入 → 各层线性变换 + 非线性激活 → 输出。
  • 损失函数：分类 Cross-Entropy、回归 MSE 等。
  • 反向传播：链式法则计算梯度，SGD/Adam 等优化器更新参数。

1. 为什么需要非线性激活

若每层只有线性变换 ，多层堆叠仍等价于单层线性模型，无法拟合 XOR、边界弯曲等复杂模式。激活函数 引入非线性，使网络能学习层次化特征。

2. 常见激活函数

函数 公式 值域 特点
ReLU 计算快；正区间梯度恒为 1，缓解梯度消失
Sigmoid 输出可解释为概率；两端饱和，易梯度消失
GELU 近似 平滑、非单调；Transformer 默认选择之一

ReLU： 时输出 0， 时等于 ；负半轴梯度为 0（Dead ReLU），实践中仍是最常用的隐层默认项。

Sigmoid：把实数压到 ，适合二分类输出层或门控（LSTM 门）；隐层深层堆叠时两端饱和导致梯度接近 0，训练变慢。

GELU：在 0 附近平滑过渡，负值有小幅度非零响应；BERT、GPT 等 Transformer 隐层常用，表达力与训练稳定性通常优于 ReLU，但计算略贵。

3. 如何选择（以及为什么）

场景 推荐 原因
CNN / MLP 隐层 ReLU 实现简单、收敛快；大量视觉与表格任务验证有效
输出层（二分类概率） Sigmoid 输出天然在 ，与 BCE 损失配套
输出层（多分类） Softmax（非 Sigmoid） 各类概率和为 1
Transformer / 大语言模型 GELU 平滑非线性利于深层 Self-Attention 训练；与 Layer Norm 等组合成熟
RNN / 门控结构 Sigmoid / Tanh 门控需要 或有界输出；Tanh 零中心，有时优于 Sigmoid
需要概率且要可导 Sigmoid / GELU Sigmoid 有界；GELU 在 0 附近更平滑，梯度更友好

经验法则：

  1. 没有特殊理由时，隐层先用 ReLU（或 Leaky ReLU 减轻 Dead ReLU）。
  2. 输出层跟任务走：回归用线性/无激活，分类用 Softmax 或 Sigmoid。
  3. 复现 Transformer 或 LLM 结构时用 GELU，与论文和主流实现一致。
  4. 深层旧架构（VGG 之前） 曾广泛用 Sigmoid/Tanh，现多被 ReLU 取代，除非门控或概率语义需要。

典型架构

架构 适用
MLP 表格、简单向量
CNN 图像、局部空间模式
RNN/LSTM/GRU 序列（较长依赖现多被 Transformer 补充）
Transformer NLP、多模态；Self-Attention 建模长距离依赖

ResNet、U-Net、BERT、GPT 等均建立在上述组件之上。

训练技巧

  • Batch Normalization / Layer Norm：稳定训练。
  • Dropout：减轻过拟合。
  • 学习率调度：Warmup、Cosine Decay。
  • 混合精度（AMP）：FP16/BF16 加速、省显存。
  • 梯度裁剪：RNN/大模型训练防爆炸。

数据：增强（随机裁剪、翻转）、归一化；划分训练/验证，早停（Early Stopping）。

框架与硬件

  • PyTorch：研究与应用主流（见 PyTorch）。
  • TensorFlow/JAX：生产与 TPU 生态。
  • GPU/CUDA：大规模训练依赖；推理可用 ONNX Runtime、TensorRT 等。

与 ML、LLM

  • 传统 第一章：ML 机器学习基础：小数据、表格、可解释场景仍常用 GBDT。
  • DL：表示学习为主。
  • 第三章：LLM 大语言模型基础：超大 Transformer 预训练 + 微调/对齐；视觉侧有 ViT、Diffusion 等并行发展。

第一章：ML 机器学习基础

概念基础：机器学习是什么

  1. 机器学习（ML）是让计算机从数据中自动学习规律，再用学到的模型对新数据做预测或决策，而无需为每条规则手工编程。
  2. 三大问题类型：监督学习（有标签，学输入→输出映射：分类、回归）、无监督学习（无标签，发现结构：聚类、降维）、强化学习（智能体与环境交互最大化回报）。
  3. 标准工作流：问题定义 → 数据收集与清洗 → 特征工程 → 模型训练与验证 → 部署与监控，从原始数据到线上服务是一条完整链路。
  4. 泛化是核心目标：模型要在没见过的数据上表现好，因此要防过拟合（正则、Dropout、交叉验证），并权衡偏差-方差。
  5. 定位与分工：表格数据、小样本、可解释性要求高的场景传统 ML（尤其树模型）仍很强；图像、语音等复杂表示交给 DL，自然语言任务交给 LLM。

问题类型

类型 目标 示例
监督学习 有标签，学输入→输出映射 分类（垃圾邮件）、回归（房价）
无监督学习 无标签，发现结构 聚类、降维、异常检测
强化学习 智能体与环境交互最大化回报 游戏、机器人控制

  Clean --> Train[训练模型]
  Train --> Eval[验证集评估]
  Eval --> Deploy[部署推理]
  1. 问题定义与指标（准确率、F1、AUC、RMSE 等）。
  2. 数据收集与清洗：缺失值、异常值、泄漏（train/test 混用未来信息）。
  3. 特征工程：数值缩放、类别编码、时间特征。
  4. 模型训练与验证：训练集 / 验证集 / 测试集或 K 折交叉验证。
  5. 部署与监控：数据漂移、模型退化、在线 A/B。

常用算法（概览）

  • 线性模型：逻辑回归、线性回归、SVM（核方法）。
  • 树模型：决策树、随机森林、GBDT、XGBoost/LightGBM（表格数据仍强）。
  • 距离方法：KNN。
  • 无监督：K-Means、PCA、t-SNE（可视化）。

过拟合与正则

  • 过拟合：训练集很好、泛化差 → 更多数据、简化模型、L1/L2 正则、Dropout（神经网络侧）。
  • 偏差-方差权衡：模型容量与数据量匹配。
  • 交叉验证：稳定估计泛化性能。

第二章：Kubernetes 容器编排入门

概念基础：Kubernetes 是什么/为什么

  1. Kubernetes（K8s） 是容器编排平台：把大量容器按声明式期望调度到多台机器上运行，并自动维持「实际状态 = 声明状态」。
  2. 为什么需要编排：单机 Docker 解决不了多机调度、故障自愈、扩缩容、服务发现与负载均衡——这些正是 K8s 的核心能力。
  3. 声明式 API：不写「怎么做」的脚本，而是提交 YAML 描述期望（副本数、镜像、端口），由控制循环持续把集群调到期望状态。
  4. 核心对象：Pod 是最小调度单元；Deployment 管理副本与滚动更新；Service 提供稳定访问入口；ConfigMap / Secret 管理配置与密钥。
  5. 定位：生产环境容器编排的事实标准；本地可用 minikube / kind / k3s 学习，集群上的应用包管理则交给 Helm（见第四章）。

第一章：Docker 容器基础

概念基础：Docker 是什么/为什么

  1. Docker 是基于容器的应用打包、分发与运行平台：把应用连同依赖环境一起封进镜像，实现「一次构建，到处运行」，解决「在我机器上是好的」的环境漂移问题。
  2. 镜像与容器：镜像（Image） 是只读分层文件系统加元数据；容器（Container） 是镜像的可运行实例，在镜像之上附加一层可写层。
  3. 与虚拟机相比，容器共享宿主机内核、不含客户机 OS，启动秒级、资源密度高；隔离性弱于完整 VM，敏感多租户需额外加固。
  4. 核心工作流：Dockerfile 描述构建过程 → docker build 产出镜像 → 推送到 Registry（Docker Hub / Harbor）→ 任意机器 docker run 拉起容器，多容器栈用 Compose 编排。
  5. 为什么学它：数据库、中间件、应用皆可容器化（本站各 *-Docker 文章即基于此）；单机之上是多机编排与生产化，由 Kubernetes 承接（见第二章）。

Dockerfile 要点

  • 多阶段构建：编译阶段用 JDK 镜像，运行阶段只保留 JRE 与产物，缩小体积。

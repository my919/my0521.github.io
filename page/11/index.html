第四章：特征与几何

概念基础：特征是可追踪的局部模式

  1. 特征 = 图像中可辨识的局部模式：角点、斑点、边缘交点等，在不同光照、尺度、视角下仍能被稳定检测与匹配，是图像配准、拼接、跟踪的基础。
  2. 检测 + 描述两步：先检测关键点位置，再计算描述子（高维向量）表征其邻域；匹配即比较描述子距离。
  3. 几何从像素到世界：单应性（Homography）描述两视图间的平面映射，4 对匹配点即可解出，用于拼接、AR、文档矫正。
  4. 轮廓是连通区域边界：从二值图提取轮廓，可算面积、外接矩形、近似多边形，是传统目标检测与计数的利器。
  5. 本章目标：掌握角点/特征检测与匹配、单应性求解、轮廓分析，理解传统 CV 几何处理的边界与深度模型的分工。

第一章：FFmpeg 音视频处理入门

概念基础：FFmpeg 是什么/为什么

  1. 音视频处理瑞士军刀：FFmpeg 是开源的转码、裁剪、截图、推流命令行工具集，几乎所有播放器、视频网站与转码服务背后都有它（Chrome、VLC、OBS 均基于或依赖其底层库）。
  2. 三大组件：ffmpeg（转码与处理）、ffprobe（查看媒体元信息）、ffplay（本地播放调试）。底层是四大库 libavcodec / libavformat / libavfilter / libavutil。
  3. 命令结构固定：ffmpeg [全局选项] -i 输入 [输出选项] 输出，理解「输入 → 滤镜 → 编码 → 封装」流水线即可举一反三。
  4. 容器与编解码分离：MP4/MKV 是封装容器，H.264/AAC 是编码格式；-c copy 只换容器不重编码，速度极快。
  5. 应用广泛：视频网站转码、HLS/RTMP 直播推流、GIF 生成、提取音频等日常需求一条命令搞定。

一、三大组件

组件 作用 典型用法
ffmpeg 转码、裁剪、滤镜、推流等一切处理 ffmpeg -i in.mp4 out.mp4
ffprobe 查看媒体元信息（容器、流、编码、时长、码率） ffprobe -show_format -show_streams in.mp4
ffplay 本地简易播放器，调试滤镜效果 ffplay -vf "scale=640:-2" in.mp4

先用 ffprobe 摸清输入再动手，是排查问题的第一步——它告诉你容器格式、有几路流、各路编码/分辨率/码率/时长。

二、命令结构与执行流水线

一条命令的内部流转：



flowchart LR
  IN[输入文件/流 -i] --> DEMUX[解封装 demux]
  DEMUX --> DEC[解码 decode]
  DEC --> FLT[滤镜 filter]
  FLT --> ENC[编码 encode]
  ENC --> MUX[封装 mux]
  MUX --> OUT[输出文件/流]

关键：滤镜与重编码都需先解码到原始帧再处理。-c copy 跳过「解码→编码」，直接拷贝原始码流到新容器，故秒级完成但无法改编码/分辨率/滤镜。

第五章：流媒体与直播推流

发表于 2026-05-01 更新于 2026-08-31 分类于 FFmpeg 本文字数： 1.7k 阅读时长 ≈ 6 分钟

第五章：流媒体与直播推流

概念基础：直播与点播的差异

  1. 点播（VOD）转码生成完整文件供下载/拖拽；直播是持续产生的流，观众边产生边消费，时延与一致性是核心矛盾。
  2. 三大协议：RTMP（推流主流，低延迟、TCP）、HLS（拉流主流，切片+列表，高兼容、延迟高）、DASH（HLS 的国际版替代，类似机制）。WebRTC/SRT 面向超低延迟。
  3. 推流与拉流：推流（push）把本地媒体送到服务器，如 ffmpeg → RTMP 服务器；拉流（pull）从源拉取再转发，如 ffmpeg 拉一路 RTSP → 推给 HLS 切片。
  4. -re 是直播关键：按真实帧率读取输入，防止 ffmpeg 全速把文件瞬间推完，导致服务器缓冲溢出。
  5. 本章目标：掌握 RTMP 推流、HLS/DASH 切片、拉流转发、直播参数调优，能搭起最小直播链路。

本章承接 第四章：滤镜与滤镜图，面向实时场景。协议基础见 第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例、第十一章：WebSocket 详解：握手、帧与 Python 示例。

一、RTMP 推流

RTMP 基于 TCP，是推流到 B 站/斗鱼/自建 Nginx-RTMP 的主流协议：

  • -re：按帧率读取，直播必备（点播转 HLS 也常用）。
  • -f flv：RTMP 封装用 FLV。
  • -tune zerolatency：编码器零延迟模式，直播首选。
  • -preset ultrafast：实时编码优先速度。
  • -g：关键帧间隔，直播常设为帧率×2（如 60，对应 30fps 的 2 秒 GOP）。

推流地址需替换为实际服务器；自建可用 nginx-rtmp-module 或 SRS。

二、HLS 切片

HLS 把媒体切成小 .ts 片段 + .m3u8 播放列表，HTTP 分发，兼容性最好（iOS/Safari 原生支持）：

  • -hls_time N：每段约 N 秒（实际按 GOP 对齐）。
  • -hls_list_size N：列表保留 N 段；直播设小值（如 3–6），旧段自动滚动。
  • -hls_flags delete_segments：直播自动删旧段，防磁盘爆满。
  • -hls_playlist_type vod：点播固定列表；直播用 event（累积）或不设。
  • 延迟：HLS 延迟 ≈ hls_time × (hls_list_size + 1)，常 10–30 秒，不适合低延迟。

三、DASH 切片

DASH 机制类似 HLS，输出 .mpd 清单 + .m4s 分片，国际标准、Web 兼容好：

  • -seg_duration：分片时长。
  • -window_size：滑窗大小（直播用）。
  • 浏览器用 dash.js 播放；HLS 用 hls.js。

四、拉流与转发

从一路源拉取，转码或不转码后推到另一路，常用于「监控 RTSP 转 HLS 给浏览器」「转码适配多端」：

  • -rtsp_transport tcp：RTSP 用 TCP 传，比 UDP 稳（防丢包花屏）。
  • 拉流是「无限」的：源不断开，ffmpeg 不退出；运维需配合 systemd 或循环脚本保活。

第四章：滤镜与滤镜图

概念基础：滤镜是加工流水线

  1. 滤镜（filter）加工每一帧：在解码后、编码前对原始帧做变换——缩放、裁剪、水印、字幕、调色等，是 FFmpeg 表达力最强也最易出错的部分。
  2. 三类入口：-vf（简单视频滤镜链，单输入）、-af（简单音频滤镜链）、-filter_complex（复杂滤镜图，多输入/多输出/多流合成，画中画、多路拼接必用）。
  3. 链与图：滤镜链（chain） 用逗号串多个滤镜顺序执行；滤镜图（graph） 用分号串多条链并行/分支。[label] 标记流的去向。
  4. 简单 vs 复杂：单输入单输出用 -vf/-af 足够；多输入（如视频+水印图、视频+字幕）必须 -filter_complex。
  5. 本章目标：掌握滤镜图语法、常用视频/音频滤镜、典型复杂滤镜图（水印、画中画、字幕烧录），能看懂并自己拼装。

第二章：编解码与转码

概念基础：为什么转码是核心

  1. 转码 = 解码 + 重新编码：把输入的某种编码（如 ProRes/HEVC）转成另一种（如 H.264），是 FFmpeg 最高频的操作，也是质量与体积权衡的主战场。
  2. 容器与编码两层独立：.mp4 是容器，可装 H.264/H.265/AV1 多种视频编码与 AAC/MP3 多种音频编码；改容器不一定要改编码，改编码也不一定要改容器。
  3. 质量来自编码器与参数：同一 H.264，libx264 的 -crf/-preset 决定「画质-体积-速度」三角；选错参数要么体积爆炸、要么画质崩坏。
  4. 码率模式三选一：CRF（恒定质量，最常用）、两次编码（精确体积，离线归档）、CBR/VBR（直播定码率）。
  5. 硬件编码提速：CPU 软编画质最好但慢；NVIDIA/Intel/Apple 硬件编码器数倍提速，适合实时与批量，画质略逊但多数场景可接受。

本章承接 第一章：FFmpeg 音视频处理入门 的命令骨架，把转码从「能跑」讲到「会调」。

一、容器与编码：两层概念

层 例子 作用
容器（封装） MP4、MKV、MOV、FLV、TS、WebM 打包音视频/字幕流 + 索引 + 时间戳
视频编码 H.264、H.265/HEVC、AV1、VP9、ProRes 压缩视频画面
音频编码 AAC、MP3、Opus、FLAC、PCM 压缩音频

-c copy 拷贝的是编码后的码流，故只能换容器、不能改编码或分辨率；要改必须重编码（解码→编码）。

三、CRF：恒定质量（最常用）

CRF（Constant Rate Factor） 让编码器按「目标画质」自适应分配码率——复杂场景多给字节、简单场景少给，体积随内容变化但画质恒定，是离线转码首选。

  • -crf 范围 0–51（libx264），越小质量越高、文件越大：
    • 18：视觉无损（归档）
    • 23：默认，画质与体积均衡
    • 28：可接受画质，体积小（预览）
  • -preset 权衡编码速度与压缩率，越慢压缩率越好（同画质体积更小）：
    ultrafast → superfast → veryfast → faster → fast → medium（默认）→ slow → slower → veryslow
  • -tune 针对内容调优：film（电影）、animation（动画）、fastdecode（易解码）等。

经验：离线归档用 -crf 18 -preset slow；日常转码 -crf 23 -preset medium；批量预览 -crf 28 -preset fast。

四、两次编码（2-pass）：精确体积

需控制输出体积（如限制 100MB）时，CRF 无法预测体积；用 2-pass：第一遍分析码率分布，第二遍按目标码率精准分配。

适用：视频网站固定码率档位、存储受限的归档。实时场景不可用（需两遍）。

一、硬件加速全链路

仅用 -c:v h264_nvenc 只加速编码，解码与缩放仍走 CPU，且数据要 CPU↔GPU 拷贝。全链路 GPU 才是最大化提速：

  • -hwaccel cuda：硬件解码。
  • -hwaccel_output_format cuda：解码后帧留在 GPU 显存，避免拷回 CPU。
  • scale_cuda：GPU 缩放滤镜（替代 scale）。
  • h264_nvenc：GPU 编码。

对应 Intel QSV：-hwaccel qsv -c:v h264_qsv -vf scale_qsv；Apple VideoToolbox 链路类似。

取舍：全链路 GPU 提速数倍，但滤镜生态不如 CPU 丰富（subtitles/drawtext 等多在 CPU），需在 GPU 滤镜前后用 hwdownload/hwupload 转换，复杂度上升。纯转码提速用全链路；复杂滤镜用 CPU 或混合。

GraphQL

概念基础：GraphQL 是什么/为什么

  1. API 查询语言：GraphQL 由 Facebook 开源，客户端在单一端点上按需声明「要哪些字段」，服务端精确返回同构数据，避免多余传输。
  2. Schema 即契约：用 SDL 强类型定义数据模型与入口（Query / Mutation / Subscription），前后端基于同一份 Schema 协作、自动生成文档。
  3. Resolver 解析数据：每个字段对应一个解析器函数，可对接数据库、微服务或第三方 API，天然适合多数据源聚合。
  4. 直击 REST 痛点：避免过度获取（over-fetching）与多次请求瀑布，弱网与移动端收益明显。
  5. 生态成熟：Apollo（Server/Client）、GraphiQL 调试 IDE、Hasura 自动生成等工具链完善。

一、核心概念

  • Schema（模式）：用强类型定义数据结构与关系，是 GraphQL 的“契约”，包含：
    • Query：查询（读操作）入口
    • Mutation：变更（写操作）入口
    • Subscription：订阅（实时更新，基于 WebSocket）
  • Type（类型）：定义对象结构，如 User、Post，含字段与类型（标量/对象/列表/非空）。
  • Resolver（解析器）：服务端函数，负责按字段获取/处理数据（数据库、微服务、第三方 API 均可）。
  • Query（查询）：客户端声明式请求，结构即响应结构。
  • Mutation（变更）：用于创建/更新/删除数据，语法类似 Query。

二、核心优势（对比 REST）

维度 GraphQL REST
数据获取 客户端精准指定字段，无过度获取 固定返回结构，易冗余
请求次数 单一请求获取多资源（如用户+文章） 需多端点请求，易“请求瀑布”
版本控制 Schema 渐进演进，无需版本号 需维护 v1/v2 多版本
文档 基于 Schema 自动生成（如 GraphiQL） 需手动维护（Swagger 等）
实时能力 原生支持 Subscription（WebSocket） 需轮询/SSE，成本高
缓存 依赖客户端/实体缓存（如 Apollo） 天然适配 HTTP 缓存

关键结论：GraphQL 显著减少数据传输量与请求次数，弱网/移动端收益极大；REST 更简单、成熟、缓存友好，适合简单场景。

三、工作流程

  1. 定义 Schema：服务端用 SDL（Schema Definition Language）定义类型、Query、Mutation。
  2. 实现 Resolver：每个字段对应解析器，对接数据源。
  3. 客户端请求：发送 POST 到单一端点（如 /graphql），携带 Query/Mutation。
  4. 服务端执行：校验 Query → 调用 Resolver → 按请求结构返回 JSON。
  5. 客户端接收：响应结构与 Query 完全一致，直接渲染。

四、适用场景

  • ✅ 复杂前端应用（如电商、社交）：多数据关联、按需字段。
  • ✅ 移动端/弱网环境：减少请求与数据体积。
  • ✅ 微服务架构：统一网关聚合多服务数据。
  • ✅ 实时功能（聊天、通知、实时看板）：Subscription 原生支持。
  • ❌ 简单 CRUD 服务：REST 更轻量、易维护。
  • ❌ 高缓存吞吐场景：REST HTTP 缓存更高效。

第四章：RocketMQ 核心概念与架构

概念基础：RocketMQ 是什么

Apache RocketMQ 是源自阿里巴巴电商场景的分布式消息中间件：低延迟、高并发、业务消息能力开箱即用。本文侧重 MQ / 微服务视角。

  1. 本质是「Topic + Queue」：消息按 Topic 分类，每个 Topic 切成多个 Message Queue（读写队列），Queue 是并行与顺序的基本单位——角色类似 Kafka 的 Partition，但围绕它的消费语义更「业务」。
  2. 为什么业务系统选它：延迟消息、事务消息、顺序消息、消费重试与死信队列都是内置能力，不必像 Kafka 那样自建重试 Topic / 延迟调度器。
  3. 三大角色：NameServer（无状态路由中心）、Broker（存储与转发）、Producer / Consumer。客户端先问 NameServer 拿路由，再直连 Broker 收发。
  4. 权衡：流式生态（Streams / Connect 类）不如 Kafka；但 Java 技术栈、国内云厂商与 Spring Cloud Alibaba 集成更顺。对照见本章「与 Kafka 的对照」小节。

先看整体架构：

架构组件



flowchart TB
  P[Producer] --> B[Broker Master]
  B --> NS[NameServer 路由]
  C[Consumer Group] --> B
  NS -.-> P
  NS -.-> C
组件 作用 要点
NameServer 路由注册中心，轻量、无状态 节点间互不通信，客户端轮询任一节点；几乎没有运维成本
Broker 存储与转发，分 Master / Slave 所有消息写入 CommitLog（单一文件顺序写），再异步分发到各 Queue 的索引
Producer 发送消息 与 Broker 直连发送；NameServer 只用于找地址
Consumer 拉取消息 Push 模式底层是长轮询拉取，并非服务端真推送

客户端通过 NameServer 发现 Broker 地址；Broker 每 30s 向 NameServer 上报路由，客户端在本地缓存路由表。

Topic 与 Queue

  • Topic：逻辑分类。
  • Message Queue：Topic 下分片（类似 Kafka 分区，语义略有不同）；Queue 数 = 消费并行度上限。
  • Tag / Key：Tag 用于消费端二级过滤；Key 建立哈希索引，供控制台按业务键查询。

理解要点：与 Kafka「分区数决定并行度」同理，Consumer 实例数超过 Queue 数时多出的实例空闲；规划 Topic 时先估消费并行度再定 Queue 数。

消费模型

模式 说明
CLUSTERING 同组负载均衡，一条消息只被一个实例消费
BROADCASTING 组内每实例全量接收
重试 / DLQ 消费失败进入重试队列（%RETRY%组名）延时重投，默认 16 次，超限进死信（%DLQ%组名）

理解要点：重试 + 死信是 RocketMQ 相对 Kafka 最大的「开箱能力差」——消费失败自动按递增间隔重试，业务只需监听死信 Topic 做人工兜底，不需要自建重试机制。

消息可靠性：刷盘与复制

维度 同步 异步
刷盘 SYNC_FLUSH：落盘才返回成功，不丢但延迟高 ASYNC_FLUSH：写入 page cache 即返回，宕机可能丢少量
复制 SYNC_MASTER：Slave 同步完成后返回 ASYNC_MASTER：默认，性能优先

生产常见组合：ASYNC_FLUSH + SYNC_MASTER（或 DLedger 自动主从切换）；金融级再上同步刷盘。这与 Kafka 的 acks=all + ISR 解决的是同一件事——「写成功」的定义。

顺序、延迟与事务

1. 顺序消息

同一 MessageQueue 内 FIFO；发送端按 orderId 等 sharding key 用 MessageQueueSelector 固定路由，消费端用 Orderly 监听器串行处理。代价：该 Queue 所在实例故障期间，对应分片的顺序消费会短暂阻塞。

2. 延迟消息

内置延迟级别（1s、5s、1m…2h 共 18 级），适合订单超时关闭、失败退避重试；5.x 起支持任意时间精度（基于时间轮）。

3. 事务消息

Half 消息 + 本地事务 + 回查：先发半消息（对消费者不可见）→ 执行本地事务 → 提交 / 回滚；Broker 对未决事务定时回查生产者。与 Seata 同步事务可对照选型（见 第一章：cloud 微服务工程架构总览与生产落地 当前 Feign + Seata 链路）。

第一章：Kafka 消息中间件入门：核心概念与架构

概念基础：Kafka 是什么

Apache Kafka 是分布式事件流平台：高吞吐、持久化、可回放的分区日志，用于消息队列、日志管道、流式处理与数据集成。本文侧重 MQ / 微服务视角。

  1. 本质是「分区日志」：每条消息只是追加到分区末尾的日志记录，不消费即删除，消费只移动游标（offset）——所以消息可以被多组消费者反复回放，这是它与 RabbitMQ 这类「消费即删除」传统 MQ 最大的差别。
  2. 为什么快：磁盘顺序写 + page cache + 零拷贝 + 批量压缩，单机即可达到十万级 TPS 量级；吞吐是 Kafka 设计的第一目标。
  3. 三大角色：当消息队列（削峰、解耦）、当日志总线（各系统日志/埋点统一进 Kafka）、当流计算数据源（Flink/Spark 从 Kafka 读）。本站对应：微服务集成见 第十一章：Spring Cloud 集成 RocketMQ：异步消息与事件驱动扩展，大数据总线见 第三章：Kafka 大数据数据总线。
  4. 权衡：为吞吐放弃了部分「业务 MQ」能力（无内置延迟消息、事务消息偏流式），这些场景通常选 RocketMQ（见本章对照小节与 第四章：RocketMQ 核心概念与架构）。

先看它的整体架构：

生产消费架构

核心概念

概念 说明
Topic 逻辑消息流名称
Partition Topic 的分片，有序日志；并行度与分区数相关
Offset 分区内每条消息的唯一递增序号
Producer 写入消息，可指定 key 做分区路由
Consumer Group 组内消费者分摊分区，同组不重复消费同一分区
Broker 存储与 Serving 分区的服务器进程

消息持久化在磁盘（顺序写 + page cache），可配置保留时间与大小。

理解要点：「分区内有序、分区间无序」——需要顺序的业务（同一订单的状态变更）必须用同一 key 路由到同一分区；并行度上限 = 分区数，消费者实例多于分区数时空闲。

生产者与消费者

1. 生产者

  • acks：0 / 1 / all 权衡延迟与持久性。
  • 幂等生产者：避免重试导致重复（下游仍可能需要业务去重）。
  • 事务：跨分区 exactly-once 与 Kafka Streams 场景。

2. 消费者

  • auto.offset.reset：earliest / latest。
  • 手动提交 offset：处理成功后再 commitSync / commitAsync。
  • 再均衡（Rebalance）：组成员变化时重新分配分区；消费逻辑应支持幂等。

3. 投递语义（需业务配合）

语义 说明
At most once 先提交 offset 再处理，可能丢
At least once 先处理再提交，可能重复
Exactly once 事务 + 幂等存储，成本高

分区、副本与 ISR

  • Leader / Follower：每个分区一个 Leader 负责读写，Follower 同步。
  • ISR（In-Sync Replicas）：与 Leader 差距在阈值内的副本；min.insync.replicas 与 acks=all 共同定义「写成功」。
  • 扩容：增加分区数不会重分布历史 key；规划分区数宜前置。

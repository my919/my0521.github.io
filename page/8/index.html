第六章：PostgreSQL 并发与 MVCC 入门

概念基础：并发与 MVCC 是什么

  1. 并发问题：多个事务同时读写同一批行时，会出现脏读、不可重复读、幻读与丢失更新；数据库必须给出确定性的答案——这就是隔离级别要解决的问题。
  2. MVCC（多版本并发控制）：每行保留多个版本，行头部的 xmin / xmax 记录创建与删除它的事务；读按快照判断可见性，做到读写互不阻塞。
  3. 隔离级别决定快照粒度：默认 READ COMMITTED 每条语句一个快照；REPEATABLE READ 整个事务一个快照；SERIALIZABLE 进一步检测读写冲突，冲突时需应用重试。
  4. MVCC 不是免费的：旧版本（死元组）要靠 VACUUM 回收；「先读后改」的临界区仍需显式行锁（FOR UPDATE），并发抢任务用 SKIP LOCKED。

一、快照与默认隔离级别

  • 默认 READ COMMITTED：单条 SQL 内看到语句开始时已提交的数据版本。
  • REPEATABLE READ：事务内首条 SQL 建立快照，后续读一致。
  • SERIALIZABLE：可检测读写依赖，失败时返回 40001 serialization_failure，应用应重试。

二、显式行锁：FOR UPDATE / FOR SHARE

  • FOR UPDATE：排他行锁，用于「先读后改」的临界区。
  • FOR SHARE：共享行锁，允许他人并发读，阻塞写。

三、SKIP LOCKED 与 NOWAIT（队列与抢锁）

SKIP LOCKED：跳过已被其他事务锁定的行，取下一批可用行——常用于任务队列、公平抢单。

NOWAIT：若不能立即加锁则立刻报错，适合避免长时间等待（由应用捕获错误后重试或放弃）。

四、死锁（deadlock detected）

PostgreSQL 会自动检测事务间循环等待，回滚其中一个事务（报错 40P01 deadlock_detected）。
规避思路与 MySQL 类似：固定加锁顺序、缩短事务、避免无关长耗时在事务内执行。

五、与 MySQL InnoDB 的粗对照（防混）

第五章：PostgreSQL 索引与性能优化

发表于 2026-05-03 更新于 2026-08-30 分类于 PostgreSQL 本文字数： 1.4k 阅读时长 ≈ 5 分钟

第五章：PostgreSQL 索引与性能优化

概念基础：索引与性能优化是什么

  1. 索引 = 用空间换时间的检索结构：默认 B-Tree 以平衡树组织键值，把等值 / 范围查询从全表扫描降为树查找；代价是占存储、拖慢写入。
  2. 慢的常见根源：大表 Seq Scan、统计信息过期导致选错计划、死元组堆积（表膨胀）、函数包裹列让索引失效。
  3. 优化是闭环不是玄学：慢日志 / pg_stat_statements 抓 Top SQL → EXPLAIN (ANALYZE, BUFFERS) 看真实计划 → 改索引或改写法 → VACUUM ANALYZE 更新统计再验证。
  4. 性能之外还有「稳」：事务隔离级别选型、VACUUM/autovacuum 运维、备份恢复（pg_dump / PITR） 演练，都是可靠性的一部分。

先建立对默认索引的直觉：

一、索引在干什么：B-Tree 直觉（默认）

PostgreSQL 默认 CREATE INDEX 多为 B-Tree（USING btree，可省略）。
直觉与 MySQL InnoDB 二级索引类似：以平衡树组织键，等值 / 范围查询减少随机读；主键 / 唯一约束底层也会建索引。

其他索引类型（点到为止）：GIN（全文、jsonb 含键）、GiST（地理、范围类型）、BRIN（超大顺序相关表）等，选型需读官方文档与压测。

二、联合索引与最左前缀

联合索引 CREATE INDEX idx_abc ON t (a, b, c); 的排序语义仍是先 a 再 b 再 c。
WHERE a = ? AND b = ? 易命中；仅 WHERE b = ? 往往用不上该索引（与 MySQL 同款直觉）。
函数包裹列（如 WHERE lower(email) = ?）常导致无法走 btree，需表达式索引（CREATE INDEX ON t ((lower(email)))）或改写法。

三、仅索引扫描（Index Only Scan）

若查询列均可由某索引覆盖，且可见性映射（VM）允许优化器认为堆页全可见，EXPLAIN 可能出现 Index Only Scan。
与 MySQL 的 Using index 类似但不等价；仍以 EXPLAIN (ANALYZE, BUFFERS) 实测为准。

四、怎么看执行计划：EXPLAIN / EXPLAIN ANALYZE

入门优先看：

字段 / 标记 含义（入门）
Seq Scan 顺序扫表，大表 + 高 rows 要警惕
Index Scan / Index Only Scan 走索引访问
Nested Loop / Hash Join / Merge Join 连接策略
ANALYZE 的 actual time、rows 真实耗时与行数（与统计信息、缓存有关）
BUFFERS 读了多少共享缓冲区（判断是否 I/O 重）

统计信息维护：ANALYZE tbl;（VACUUM ANALYZE 亦可），大变更后应跑。

五、事务与隔离级别（用法向）

1. 基本写法

默认 READ COMMITTED：每条语句看到语句开始时已提交的快照（简化理解）。
REPEATABLE READ：事务内第一条语句建立快照，读一致性更强。
SERIALIZABLE：最强，可能出现 serialization_failure，应用需重试。

与 MySQL InnoDB 默认 RR 不同：PostgreSQL 默认 RC；跨库迁移时注意语义差异。行级锁、FOR UPDATE、死锁见 第六章：PostgreSQL 并发与 MVCC 入门。

六、慢语句与观测「三板斧」（点到为止）

1. 日志：log_min_duration_statement

在 postgresql.conf 或 ALTER SYSTEM（需 reload）中设置，例如记录超过 200ms 的语句（数值按环境调）。

2. pg_stat_statements（扩展）

需 shared_preload_libraries 预加载（运维配置），此处不展开。

3. auto_explain（扩展）

自动对超时语句打计划，适合测试环境；生产按规范启用。

落地顺序：先慢日志或 pg_stat_statements 抓 Top SQL → EXPLAIN (ANALYZE, BUFFERS) → 改索引或改写法 → VACUUM ANALYZE。

七、VACUUM 与膨胀（可靠性常识）

PostgreSQL 的 MVCC 会使更新/删除留下死元组；VACUUM（通常由 autovacuum 自动跑）回收空间、更新统计信息。长期不 vacuum 会导致表膨胀、性能变差。
日常开发：大批量导入/更新后，测试库可手动 VACUUM ANALYZE；生产依赖 autovacuum 参数与监控。

八、备份恢复与 PITR 概念

1. 逻辑备份 pg_dump / pg_restore

-Fc 为自定义目录格式，便于并行恢复；纯 SQL 可用 -Fp。

2. 物理与 WAL

PITR 依赖：基础备份（文件系统级或 pg_basebackup）+ 连续归档的 WAL + 恢复目标时间。与 MySQL binlog 地位类似的是 PostgreSQL WAL；具体恢复命令属 DBA 手册级。

3. 与 Docker 的关系

容器内 $PGDATA 一般在卷上（见 第二章：Docker 部署 PostgreSQL 实践）；备份策略要约定「从宿主机 pg_dump 连容器端口」还是「卷快照 + WAL 归档」，并做恢复演练。

第三章：PostgreSQL 存储引擎与表访问方法

发表于 2026-05-03 更新于 2026-08-30 分类于 PostgreSQL 本文字数： 1.1k 阅读时长 ≈ 4 分钟

第三章：PostgreSQL 存储引擎与表访问方法

概念基础：存储引擎与表访问方法是什么

  1. 表访问方法（Table Access Method）：PostgreSQL 12+ 把「表数据如何组织与读写」抽象为可插拔接口，建表时可用 USING 指定，默认即 heap——这是 PostgreSQL 语境里最接近 MySQL「引擎」的概念。
  2. 堆表（Heap）：行按写入顺序无序堆放在页中，用 tid（块号 + 行号） 定位；索引里存的是 tid，查数据通常要「索引 → 回表」。
  3. MVCC 是配套设计：行头维护 xmin / xmax 版本信息，更新与删除产生新版本 / 死元组，由 VACUUM 回收——这直接决定了 PostgreSQL 的性能调优姿势。
  4. 与 MySQL 的本质差别：MySQL 建表时选 ENGINE=InnoDB，PostgreSQL 没有这个开关：统一内核 + 统一 heap，列存、分片等需求走扩展与架构层，而不是换「引擎」。

先看默认的存储方式：

一、表数据默认怎么存：Heap（堆表）

  • 普通 CREATE TABLE 默认即 heap 表：行以堆页存放，通过 tid（块号 + 行号） 定位。
  • MVCC 在元组头维护版本信息（xmin / xmax 等），更新与删除产生新版本/死元组，依赖 VACUUM 回收（见 第五章：PostgreSQL 索引与性能优化）。
  • 与 InnoDB 聚簇索引即整表不同：PostgreSQL 主键索引是二级索引，堆上存行，主键查找通常「索引 → 回表 tid」。

二、表访问方法（Table Access Method）

PostgreSQL 12+ 起，表可指定 USING heap（默认）；理论上可挂自定义表访问方法（需扩展提供）。
生产常见仍是 heap；列存、混存等多在扩展或外部产品（如某些分析型方案）中实现，不等价于 MySQL 换一个 ENGINE 字符串。

三、与「引擎」易混的几个概念

概念 说明
TABLESPACE 表/索引的文件放置位置（如 pg_default），不是另一种行存储引擎。
TOAST 大字段行外存储机制，对用户基本透明。
Foreign Data Wrapper（FDW） 外部表：数据在远程；语法像本地表，语义与本地 heap 完全不同，不是换存储引擎。
内置索引类型 B-Tree、Hash、GiST、GIN、BRIN 等是索引访问方法，不是替换 heap 的「表引擎」。

四、和 MySQL InnoDB 的粗对照（选型沟通用）

话题 MySQL（MySQL引擎.md） PostgreSQL（本文）
建表选「引擎」 ENGINE=InnoDB 等 无；默认 heap + 统一内核
行存与主键 InnoDB 聚簇主键与数据同树 堆行 + 主键索引
并发读写的核心 InnoDB MVCC + 锁 MVCC + 行锁（见 第六章：PostgreSQL 并发与 MVCC 入门）

五、实务建议

  1. 学习 PostgreSQL 时少问「用哪个引擎」，多问索引类型、执行计划、VACUUM、隔离级别与锁。
  2. 需要列存、分片、多副本高可用时，在架构层选专用扩展或产品（如 Citus、云厂商数仓、读写分离），而不是在 CREATE TABLE 里找一个 ENGINE 开关。
  3. 版本升级（14 → 16 → 17）会带执行器与优化器演进，「升级引擎」口语上常指升级主版本，与 MySQL 的 ENGINE 不是同一概念。

第六章：MySQL 存储引擎

概念基础：存储引擎是什么、为什么重要

存储引擎是 MySQL 「表数据如何存、如何取」的可插拔实现：

  1. 分层架构的产物：Server 层负责 SQL 解析、优化、权限；引擎层负责数据在磁盘与内存上的组织——索引结构、事务、锁、崩溃恢复都由引擎决定；同一份表结构，换引擎行为完全不同。
  2. InnoDB 是唯一默认答案：支持 ACID 事务、行级锁、MVCC、崩溃恢复（redo / undo）、聚簇索引与外键；官方默认且推荐，第五章讲的 B+ 树与回表，说的就是 InnoDB 的组织方式。
  3. MyISAM 是历史遗产：表级锁、不支持事务、崩溃安全性弱，只存在于老系统与只读库中；新业务一律避开——它也解释了第三章「表锁并发差」的历史背景。
  4. 换引擎不解决性能问题：性能瓶颈优先从索引、SQL 写法、事务与连接设计入手（第三、四、五章的内容）；引擎选型是「事务要不要」的问题，不是「快不快」的问题。
  5. 插件式带来专用选择：ARCHIVE（冷归档压缩）、CSV（数据管道交换）、BLACKHOLE（写入即弃的中继）、NDB（分布式集群）各有专属场景，是否可用以 SHOW ENGINES 为准。

第五章：MySQL 索引与性能优化

概念基础：索引是什么、为什么能加速

索引是数据库用额外空间与写成本换取查询速度的有序数据结构：

  1. 本质是一棵 B+ 树：把无序的表数据额外组织成有序树，查询从「全表逐行扫」变成「沿树下降读少量页」——随机 I/O 大幅减少；代价是每次 INSERT/UPDATE/DELETE 都要同步维护树，所以索引不是越多越好。
  2. 聚簇索引即数据本身：InnoDB 表数据按主键组织成 B+ 树，叶子节点存「主键 + 整行」；二级索引叶子只存「索引列 + 主键」，命中后常需回表再查一次聚簇索引——这就是主键要自增、查询要少 SELECT * 的根因。
  3. 联合索引遵守最左前缀：(a, b, c) 先按 a 排、a 相同再按 b、再按 c；跳过 a 的条件用不上树，等值列在前、范围列在后是最常见的设计。
  4. 覆盖索引是回表的解药：查询列全在索引里就只扫索引不回表（EXPLAIN 显示 Using index）；与之配套的 ICP 把过滤条件下推到引擎层，进一步少回表。
  5. 优化是一个闭环而非玄学：慢日志抓 Top SQL → EXPLAIN 看 type / key / rows / Extra → 改索引或改写法 → 再对比慢日志；本章同时覆盖事务隔离与备份恢复，给出完整的「开发侧性能地图」。

从 B+ 树的直觉开始：

一、索引在干什么：B+ 树直觉（够用版）

InnoDB 里，表数据按主键组织成一棵 B+ 树（聚簇索引）：叶子节点存「主键 + 整行数据」。
二级索引（你建的 INDEX / UNIQUE）叶子节点存「索引列 + 主键」，需要整行时往往要再回表到聚簇索引取数据。

下图便于建立直觉（示意：键值与层数为教学简化，与真实页大小、填充率无关）。

读图要点：上层结点只存分界键与子树指针；最底层叶子由双向链表串起，方便范围扫描；聚簇索引叶子是主键 + 行数据；二级索引叶子多一步按主键回表读完整行。

直觉：

  • 等值 / 范围命中索引列 → 树高度低、少读页 → 随机 I/O 变少。
  • 全表扫 → 叶子链顺序读，数据量一大就慢。
  • 索引不是越多越好：每次 INSERT/UPDATE/DELETE 都可能维护多棵索引树。

二、联合索引与最左前缀

联合索引 KEY idx_abc (a, b, c) 的排序语义是：先按 a，再 a 相同时按 b，再按 c。

能较好利用该索引的典型条件（示意）：

  • WHERE a = ?
  • WHERE a = ? AND b = ?
  • WHERE a = ? AND b BETWEEN ? AND ?

容易用不上或只用一截的情况：

  • WHERE b = ? AND c = ?（缺 a，与「最左」不一致）
  • WHERE a = ? OR d = ?（OR 另一侧常走另一条路径，易优化成 UNION 或改写法）
  • 对 a 做函数/隐式类型转换导致无法走树（例如 WHERE DATE(a_col) = ...）。

设计经验：把区分度高、过滤性大的列尽量放左侧；把范围查询列放联合索引右侧更常见（仍要结合 EXPLAIN 验证）。

三、覆盖索引（Using index）

若 SELECT 里出现的列都能从某条二级索引的叶子直接凑齐（含 WHERE 用到的索引列），InnoDB 可能只扫索引、不回表，EXPLAIN 的 Extra 常见 Using index。

典型收益：大宽表上只查少数列 + 条件列恰好在同一联合索引上，I/O 明显下降。

四、索引条件下推 ICP（一眼带过）

Index Condition Pushdown：把部分 WHERE 条件下推到存储引擎层，在索引扫描过程中就过滤，少回表。
在 EXPLAIN 里常见 Using index condition（与 Using index 不同：后者多为覆盖索引）。不必一次讲透优化器细节，看到术语知道「在索引层多干了一点过滤」即可。

第四章：MySQL 高级查询

概念基础：高级查询是什么、为什么难写对

高级查询是超越单表 SELECT ... WHERE 的多表、分组、窗口类查询，核心是把拆开存的关系拼回来：

  1. 为什么数据要拆开存：关系模型按范式把业务拆成多张表（如 emp 员工表与 dept 部门表），避免重复存储；查询的本质就是用 JOIN / 子查询按关联字段把数据重新拼装——第一章建的表结构，在这里被「消费」。
  2. JOIN 的语义差异决定丢不丢数据：INNER JOIN 只保留两表都匹配的行；LEFT JOIN 保留左表全量、右表无匹配补 NULL。选错连接类型，统计结果会悄悄少行，是报表错乱的头号来源。
  3. 聚合把「多行」压成「一行」：GROUP BY 分组后才能用 COUNT / SUM / AVG；过滤顺序是 WHERE（分组前滤行）→ GROUP BY → HAVING（分组后滤组），颠倒位置直接报错或结果不对。
  4. MySQL 8.0+ 的两大武器：CTE（WITH） 把复杂查询拆成可读的「临时结果」并支持 RECURSIVE 查树；窗口函数在不减少行数的前提下做组内排名、累计——「每组 Top N」从此有了标准解法。
  5. 性能意识贯穿始终：判断存在性优先 EXISTS，合并结果优先 UNION ALL（免去去重排序），深分页 LIMIT 大 OFFSET 会越来越慢、生产改用键集分页——写法差异就是性能差异。

第三章：MySQL 锁详解

概念基础：锁是什么、为什么需要锁

锁是数据库的并发控制机制，让多个事务在共享同一份数据时「不打架」：

  1. 没有锁会发生什么：多个会话同时读写同一行，会出现脏读、不可重复读、幻读与更新丢失；锁的本质是给「当前读」排队，保证数据一致性。
  2. 核心权衡是一致性 vs 并发：锁粒度越粗（全局锁、表锁）越安全但并发差，粒度越细（行锁）并发越高但开销越大——InnoDB 的答案是以行锁为主 + MVCC 快照读，普通 SELECT 不加锁，读写大部分场景互不阻塞。
  3. InnoDB 行锁的本质是锁索引：锁加在索引记录上而不是物理数据行上；查询条件无索引或索引失效时，行锁会退化为表锁，并发直接崩塌，这是本章最重要的一条结论。
  4. 隔离级别决定加锁行为：**RR（可重复读）默认用临键锁（记录锁 + 间隙锁）**抑制幻读，代价是范围锁会阻塞插入；**RC（读已提交）**没有间隙锁，并发更高但存在幻读。
  5. 锁是双刃剑：用好了高并发不冲突，用坏了就是锁等待、死锁、业务雪崩——长事务、无索引更新、交叉加锁是线上三大事故来源，本章实验与面试题全部围绕这些展开。

作用：快速判断表内有没有行锁，避免全表扫行锁

  2. 意向锁之间完全兼容

五、InnoDB 行锁三大算法（RR 隔离级别默认）

1）记录锁（Record Lock）

  • 锁：单个索引记录
  • 触发：唯一索引 + 精准等值查询（命中）

2）间隙锁（Gap Lock）

  • 锁：索引之间的间隙（不包含记录）
  • 目的：防止幻读（禁止区间插入）
  • 示例：表有 id=1,3,5
  • 特点：间隙锁之间兼容，只与插入意向锁互斥

3）临键锁（Next-Key Lock）= 记录锁 + 间隙锁

  • 锁：左开右闭区间 (min, max]
  • InnoDB RR 默认，解决幻读
  • 示例：id=1,3,5
    • 查 id=3 → 锁 (1,3]
    • 查 id=4 → 锁 (3,5]

  • 不可剥夺：不能强行抢锁
  • 循环等待：A 等 B，B 等 A

3）如何避免

  • 按固定顺序访问资源（先 id=1 再 id=2）

七、实战高频坑（必避）

  1. 无索引 → 行锁变表锁：UPDATE t SET name='a' WHERE age=20;（age 无索引）
  2. 长事务 + 慢查询 → 锁等待堆积

  • 粒度：全局 > 表 > 行（粒度越小，并发越高、开销越大）

  • 行锁三形态：记录锁、间隙锁、临键锁（RR 防幻读）
  • 死锁四条件：互斥、持有等待、不可剥夺、循环等待

统一前提：

  • 引擎：InnoDB
  • 隔离级别：RR 可重复读（默认）
  • 锁粒度：行锁依赖索引，无索引降级为表锁

实验一：行排他锁 FOR UPDATE 阻塞演示

执行流程

会话1：开启事务 → id=1 加 FOR UPDATE 不提交
会话2：修改 id=1 被阻塞；修改 id=2 正常执行

现象

  1. 同一条主键记录：写操作被阻塞
  2. 不同主键记录：完全不受影响
  3. 会话1 commit 后，会话2立刻执行成功

底层原理

  1. FOR UPDATE 加 行级排他锁（X锁）
  2. 排他锁规则：写写互斥、读写互斥
  3. InnoDB 行锁只锁索引命中的单行，不影响其他行

面试标准答案

InnoDB 中通过主键/唯一索引精准查询加 FOR UPDATE，会加行级排他锁；只锁定当前命中的单行记录，其他行不受影响，能保证高并发。排他锁与任何读写操作都互斥，事务提交后锁自动释放。

实验二：无索引导致行锁退化为表锁

执行流程

按无索引字段 age=20 更新，会话1不提交，会话2更新完全无关的 id=2 也被阻塞

现象

明明更新不同行，却整张表都被锁住，所有写操作全部阻塞

底层原理

  1. InnoDB 行锁是锁索引，不是锁数据行
  2. 条件字段无索引，MySQL 无法定位具体行
  3. 只能逐行加行锁扫描全表，最终退化成表级锁

面试标准答案

InnoDB 行锁必须依赖索引。如果更新/删除条件没有索引或索引失效，MySQL 无法精确定位行记录，会扫描全表并逐行加锁，最终行锁降级为表锁，严重降低并发性能，开发中必须保证更新条件走索引。

实验三：共享锁与读写互斥演示

执行流程

会话1：LOCK IN SHARE MODE 加共享锁
会话2：普通SELECT能查，UPDATE/DELETE被阻塞

现象

  1. 多个事务可以同时加共享锁（读读兼容）
  2. 加了共享锁后，其他事务不能加排他锁、不能修改数据
  3. 事务提交后，写操作立刻放行

底层原理

  • 共享锁（S锁）：读读兼容，读写互斥
  • 意向锁辅助，S锁阻塞所有写操作，保证数据当前快照不被修改

面试标准答案

共享锁（S锁）又叫读锁，使用 LOCK IN SHARE MODE 加锁。特性是读读可以并发，读写、写写互斥；适合需要强一致性、临时禁止别人修改数据的场景，事务提交自动释放锁。

实验四：间隙锁与临键锁阻塞插入（RR 与幻读）

执行流程

会话1：范围查询 between 1 and 3 for update 不提交
会话2：插入区间内新 ID，直接被阻塞

现象

没有任何行被修改，只是范围加锁，却无法往区间里插入新数据

底层原理

  1. MySQL RR 隔离级别默认使用 Next-Key Lock 临键锁
  2. 临键锁 = 记录锁 + 间隙锁
  3. 范围查询会锁住索引区间间隙，禁止其他事务插入新记录，解决幻读
  4. 间隙锁只在 RR 存在，RC 隔离级别没有间隙锁

面试标准答案

InnoDB 在 RR 可重复读隔离级别下，采用临键锁（Next-Key Lock） 解决幻读。临键锁由记录锁+间隙锁组成，范围查询会锁定索引左右间隙，禁止其他事务在区间内插入数据；RC 读已提交级别会关闭间隙锁，因此无法彻底避免幻读，但并发更高。

实验五：经典死锁复现

执行流程

  • 事务1：先锁 id=1 → 再请求锁 id=2
  • 事务2：先锁 id=2 → 再请求锁 id=1
  • 互相等待，立刻触发死锁，MySQL 自动回滚一个事务

现象

  1. 互相持有对方需要的锁，循环等待
  2. InnoDB 自动死锁检测，回滚代价小的事务，抛出死锁异常
  3. 不会无限阻塞

底层原理

死锁产生四个必要条件同时满足：

  1. 互斥条件：锁资源独占
  2. 持有并等待：自己拿着锁，还等别人的锁
  3. 不可剥夺：锁不能被强行抢占
  4. 循环等待：事务形成等待环路

面试标准答案（必背）

死锁产生必须同时满足四个条件：互斥、持有并等待、不可剥夺、循环等待。
规避方案：

  1. 统一多事务访问资源的顺序；
  2. 拆分长事务，尽早提交；
  3. 避免在事务中做无关耗时操作；
  4. 合理设置锁等待超时时间。
    InnoDB 自带死锁检测机制，发现循环等待会自动回滚一个事务，避免程序卡死。

十一、面试高频一句话速记

  1. 行锁靠索引，无索引变表锁
  2. S 锁读读兼容，X 锁完全独占
  3. RR 有间隙锁防幻读，RC 没有
  4. 交叉改不同行、顺序乱写易出死锁

十二、二十道高频面试题与标准答

全部面试可直接背诵，基于 InnoDB、RR 隔离级别，精简不废话。

1. MySQL 有哪些锁分类？

答案

  1. 按粒度：全局锁、表级锁、行级锁
  2. 按读写：共享锁S、排他锁X
  3. InnoDB 特有：意向锁、记录锁、间隙锁、临键锁

2. 全局锁作用是什么？怎么加？

答案
整库只读，所有库表只能读不能写、阻塞 DDL/DML。
加锁：FLUSH TABLES WITH READ LOCK;
解锁：UNLOCK TABLES;
多用于全库逻辑备份；生产优先用 mysqldump --single-transaction 快照备份，不加锁。

3. 什么是 MDL 元数据锁？

答案
访问表时自动加，保护表结构不被中途修改/删除。
长事务不提交 + 执行 DDL 改表结构，会造成 MDL 锁等待阻塞，线上高发故障点。

4. 表锁和行锁区别？

答案

  • 表锁：粒度大、开销小、并发低、MyISAM 默认
  • 行锁：粒度小、开销大、并发高、InnoDB 支持
    InnoDB 优先用行锁提升并发。

5. 共享锁S、排他锁X 特性？

答案

  • 共享锁S：读读兼容，读写/写写互斥
  • 排他锁X：读写、写写全部互斥，独占资源
    加锁：
    S：select ... lock in share mode
    X：select ... for update

6. 意向锁 IS/IX 作用？

答案
意向锁是表级锁，事务加行锁前必须先加意向锁。
作用：快速判断表内是否有行锁，不用遍历所有行锁，提升加锁效率。

  • IS：要加 S 行锁
  • IX：要加 X 行锁
    意向锁之间互相兼容，只和表级 S/X 锁互斥。

7. InnoDB 行锁本质是什么？

答案
行锁锁的是索引，不是物理数据行。
查询条件无索引、索引失效，行锁会退化成表锁，并发骤降。

8. 什么情况下行锁会降级为表锁？

答案

  1. where 条件无索引字段
  2. 索引失效（函数、隐式类型转换、like 前缀模糊等）
  3. 没有命中任何记录，全表扫描加锁

9. InnoDB 三种行锁算法？

答案

  1. 记录锁：锁单行索引记录
  2. 间隙锁 Gap Lock：锁索引间隙，不锁记录，防止幻读插入
  3. 临键锁 Next-Key Lock = 记录锁+间隙锁，左开右闭区间，RR 默认

10. 间隙锁什么时候生效？什么时候关闭？

答案

  • 生效：RR 可重复读隔离级别、范围查询/不走唯一索引等值查询
  • 关闭：RC 读已提交 没有间隙锁，并发更高，但会有幻读

11. 临键锁解决了什么问题？

答案
在 RR 隔离级别下，通过临键锁+间隙锁彻底解决幻读，禁止其他事务在索引区间插入新数据。

12. 什么是幻读？怎么解决？

答案
同一事务内，前后两次范围查询，查到别人新插入的数据。
解决：

  • 数据库层：InnoDB RR + 临键锁
  • 业务层：悲观锁、分布式锁限制插入

13. 死锁产生的四个必要条件？

答案

  1. 互斥：锁资源独占
  2. 持有并等待：拿着自己的锁，等待别人的锁
  3. 不可剥夺：锁不能被强行抢占
  4. 循环等待：事务互相等待形成环路

14. MySQL 怎么处理死锁？

答案
InnoDB 有自动死锁检测，检测到循环等待后，自动回滚代价更小的一个事务，抛出死锁异常，避免无限阻塞。

15. 如何避免 MySQL 死锁？

答案

  1. 统一所有事务访问资源/更新行的顺序
  2. 精简事务，避免长事务，尽早 commit
  3. 事务内不做耗时网络/IO 操作
  4. 合理设置锁等待超时 innodb_lock_wait_timeout

16. for update 和 lock in share mode 区别？

答案

  • for update：加排他锁X，别人不能读也不能改
  • lock in share mode：加共享锁S，别人可以读、不能改

17. RR 和 RC 在锁层面最大区别？

答案

  1. RR 有间隙锁/临键锁，防幻读；RC 没有
  2. RC 行锁范围更小、并发更高，但存在幻读
  3. RC 锁释放更早，阻塞更少

18. 长事务有什么锁风险？

答案
长事务不提交：

  1. 行锁、MDL 锁长期不释放
  2. 造成大量锁等待、业务阻塞
  3. undo log 不能清理，占用磁盘
  4. 容易触发死锁、数据库性能雪崩

20. 线上开发写 UPDATE 防锁坑要注意什么？

答案

  1. 更新条件必须走索引，防止行锁变表锁
  2. 尽量用主键/唯一索引精准等值，少用范围查询
  3. 事务尽量短小，及时提交

常见问题

KMS encryption service is not initialized

RustFS 服务端 Bucket 默认启用了 KMS/SSE，但 KMS 未初始化。在 RustFS 控制台关闭该 Bucket 的默认加密，或完成 KMS 配置。属于服务端问题，非应用代码错误。

启用开关不生效

确认 app.rustfs.oss.enabled=true，且未在测试 Profile 中被覆盖为 false。

404 / 签名错误

  • 检查 endpoint 是否为 API 根路径
  • 确认 path-style: true
  • 核对 Access Key / Secret 与 Bucket 名

Redisson 红锁

Redisson 红锁（RedLock）完整使用教程

最标准、生产可直接用的 Redisson RedLock 实现，包含：配置 + 代码 + 原理 + 生产注意事项

一、先记住一句话

RedLock = 多个独立 Redis 主节点 + 过半写入成功才算加锁成功
目的：彻底解决主从切换丢锁问题

二、环境要求

  1. 至少 3 个独立的 Redis 主节点（无主从、无集群、互相独立）
  2. Redisson 版本 >= 3.5.0
  3. SpringBoot / Java 项目均可

三、Maven 依赖

四、Redisson 配置（连接多个独立 Redis）

方式：创建多个 RedissonClient

五、RedLock 代码使用（生产标准写法）

六、RedLock 加锁成功规则（必须记住）

3个节点：
必须 ≥ 2 个节点加锁成功 + 加锁耗时 < 锁超时时间
才算加锁成功。

5个节点：
必须 ≥ 3 个节点加锁成功

七、RedLock 看门狗（自动续期）生效吗？

生效！

RedLock 会对每个节点的锁自动续期。
只要过半节点存活，锁就不会失效。

八、生产使用注意事项（非常重要）

1. 必须使用 奇数个节点

3、5、7 个，不能用 2、4、6 个。

2. 节点之间完全独立

不能是主从、不能是集群，必须是独立 Master。

3. 性能比普通锁低

因为要写多个 Redis，高并发秒杀可以接受。

4. 核心业务才用 RedLock

  • 秒杀、库存、订单、支付、账务 → 用 RedLock
  • 后台任务、非核心 → 普通锁即可

5. 不要把 leaseTime 设置太长

默认 30s 足够，看门狗会自动续期。

九、最终结论

RedLock 是生产上唯一能彻底解决 Redis 主从丢锁的方案
金融、电商、支付、秒杀必须使用！

说明：bind 与 quic_bind 都写 127.0.0.1:4433 时，在 Linux 上可同时监听 TCP 与 UDP（端口号相同、协议不同）。这样 Chrome / Firefox / Edge 打开 https://127.0.0.1:4433/ 会先走 TCP TLS 拿到页面；支持 HTTP/3 的浏览器还可能通过 Alt-Svc 等机制再尝试 QUIC。若坚持只开 UDP（例如 cfg.bind = []），多数浏览器无法仅靠 https:// 完成首次加载，因为常见实现会先做 TCP 连接。

为何浏览器还常要 TCP、和 QUIC 设计是否冲突

不冲突。 QUIC（RFC 9000）只规定跑在 UDP 上；HTTP/3 也完全可以在只有 UDP 的情况下工作（例如本节的 aioquic 客户端直连 quic_bind）。

浏览器在地址栏输入 https://主机:端口/ 时，多数实现仍沿用历史习惯：先按「TLS over TCP」去建第一条连接，再通过响应里的 Alt-Svc、或 DNS HTTPS/SVCB 等线索，得知同一站点也可用 HTTP/3，之后才发起 QUIC。这是浏览器与 Web 生态的部署/发现策略，不是 QUIC 协议里「必须先有 TCP」的要求。本地演示若没有 DNS、没有事先缓存的 Alt-Svc，只监听 UDP 时，用户只输入 https:// 就容易连不上，因此示例里同时开同端口的 TCP TLS 是为了兼容这种建连路径，属于工程上的折中，与 QUIC 规范无矛盾。

在浏览器里打开时的证书提示

自签名证书会触发「不安全」或「您的连接不是私密连接」：本地实验可在 高级 中选择继续访问（Chrome），或把 cert.pem 导入系统/浏览器的受信任根（更安全、少打扰）。不要用这种方式处理公网真实用户流量。

MyBatis-Flex 分页原理（通俗易懂 + 流程拆解 + 和 MP 对比）

一、核心结论

MyBatis-Flex 底层也是基于 MyBatis 拦截器，原理和 MyBatis-Plus 大体一样，但设计更轻、SQL 解析更强、自动 count 更智能。

核心逻辑：
MyBatis 拦截器 → 拦截查询SQL → 自动生成 count 总数 → 原SQL 拼接 LIMIT → 封装分页结果

二、核心组件

  1. MyBatisFlexInterceptor
    Flex 全局核心拦截器，替代 MP 的 MybatisPlusInterceptor
  2. PageInterceptor
    专门负责分页拦截，Flex 分页核心逻辑都在这
  3. Page、IPage
    分页载体，和 MP 几乎一模一样：当前页、页大小、总条数、分页数据

三、完整分页执行流程（流程图版）

四、和 MyBatis-Plus 分页原理关键区别

对比点 MyBatis-Plus MyBatis-Flex
拦截器结构 插件嵌套式，较重 极简拦截器，更轻量
Count SQL 生成 简单直接，复杂SQL容易生成低效count 智能优化：自动去掉 order by、优化嵌套SQL
多表/复杂SQL 偶尔分页解析失败 解析器更强，兼容复杂联表、子查询
分页参数传递 必须 Mapper 方法带 Page 参数 支持 Mapper、也支持 Db 静态工具直接分页
配置 必须手动注册分页插件 自动配置，开箱即用，不用手动@Bean

五、代码使用（和 MP 几乎一模一样）

1. 无需手动配置分页插件

Flex 自动自动注入分页拦截器，不用写任何 @Bean 配置

2. 业务分页代码

写法和 MP 完全兼容，无缝切换。

六、底层关键亮点（Flex 比 MP 强的地方）

  1. 自动优化 Count SQL
    原SQL 有 order by，Flex 会自动剔除，避免 count 也排序，提升性能。
  2. 无需手动配置拦截器
    自动装配，少写配置类，少踩坑。
  3. 支持更多数据库方言
    MySQL、PostgreSQL、Oracle、SQLite 等自动适配 LIMIT 语法。
  4. Lambda 分页更丝滑
    不用写 Wrapper，链式直接分页。

七、一句话总结

MyBatis-Flex 分页原理：
复用 MyBatis 拦截机制 → 拦截SQL → 智能生成count → 自动加LIMIT → 封装分页
和 MP 原理同源，但解析更强、配置更少、性能更好、坑更少。

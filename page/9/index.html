HTTPS 详解：TLS 握手、证书与 openssl/curl 示例

发表于 2026-05-01 更新于 2026-05-04 分类于 Protocol 本文字数： 617 阅读时长 ≈ 2 分钟

HTTPS = HTTP + TLS（Transport Layer Security）：在 TCP 连接建立后先做 TLS 握手，再在加密记录层上传输 HTTP 语义。默认端口 443。下面从「作用与威胁模型 → TLS 握手与密钥派生（原理） → 证书链与主机名校验 → ALPN 与 HTTP/2、HTTP/3 → openssl / curl 示例」顺序写清楚；HTTP/3 传输见 QUIC。

一、作用与威胁模型

1. TLS 提供什么

  • 机密性：对称加密载荷，防窃听。
  • 完整性：MAC / AEAD 防篡改。
  • 身份认证：服务端（可选客户端）X.509 证书链。

2. 不解决什么

TLS 不能替代应用层鉴权与输入校验；https:// 也不等于站点无 XSS/CSRF 等业务漏洞。

二、TLS 1.2 / 1.3 握手（原理简述）

1. 共同目标

客户端与服务端协商出对称会话密钥，后续 HTTP 记录用对称算法加密以获得性能。

2. TLS 1.3 特点（相对 1.2）

  • 常 1-RTT 完成握手（0-RTT 可选，有重放风险，敏感操作应禁用或二次校验）。
  • 废弃一批不安全算法；Hello 中即携带密钥共享材料。

三、证书链与主机名（作用）

浏览器/客户端会校验：

  1. 证书是否由受信任 CA 签发，链是否完整。
  2. Subject Alternative Name（SAN） 或兼容字段是否覆盖当前访问主机名。
  3. 有效期、吊销信息（OCSP Stapling 等）。

自签名证书仅适合内网或开发，公网须使用可信 CA 或组织内 PKI。

四、ALPN

在 TLS 握手中通过 ALPN 协商应用层协议：h2 表示后续走 HTTP/2 帧；h3 与 QUIC / HTTP/3 相关（QUIC 内含 TLS 1.3 集成握手）。

HTTP 详解：报文、方法、版本与 curl/nc 示例

发表于 2026-05-01 更新于 2026-05-04 分类于 Protocol 本文字数： 652 阅读时长 ≈ 2 分钟

HTTP（Hypertext Transfer Protocol）是 Web 的应用层协议：基于请求 / 响应模型，在语义层使用方法、URI、首部与可选正文表达操作。下面从「无状态与资源模型 → 报文结构原理 → 方法与幂等 → 状态码 → HTTP/1.1 与 HTTP/2 → curl 与原始报文示例」顺序写清楚；传输层默认依赖 TCP，安全传输见 HTTPS，全双工见 WebSocket，HTTP/3 见 QUIC。

一、无状态与资源模型（原理）

HTTP 本身无状态：服务器默认不记住「上一次请求」；会话常靠 Cookie、Token、服务端会话存储实现。REST 风格强调用 URI 表示资源，用 HTTP 方法表达操作（与 RPC 风格对照）。

二、报文结构（作用）

1. 请求

  • 请求行：方法、请求目标（路径或绝对 URI）、版本。
  • 首部：Host 在 HTTP/1.1 中语义必填；Content-Length / Transfer-Encoding: chunked 控制正文边界。

2. 响应

三、常用方法与幂等（原理）

方法 典型语义 幂等
GET 读取资源 是
POST 创建 / 提交 否
PUT 整体替换 是
PATCH 部分更新 视实现
DELETE 删除 是
HEAD 同 GET 无正文 是
OPTIONS 探测支持的方法 是

幂等：多次执行相同请求不应带来额外副作用（仍可能每次返回相同结果）。

四、状态码（分类）

范围 含义 例
2xx 成功 200、201、204
3xx 重定向 301、302、304
4xx 客户端错误 400、401、403、404
5xx 服务器错误 500、502、503

五、HTTP/1.1 与 HTTP/2（演进）

  • HTTP/1.1（RFC 9112）：文本形态；Keep-Alive 复用连接；队头阻塞限制并发效率。
  • HTTP/2（RFC 9113）：二进制帧；单连接多路复用；HPACK 压缩首部；浏览器场景几乎总与 TLS 同用。
  • HTTP/3（RFC 9114）：基于 QUIC（UDP）。

TCP 协议详解：连接、可靠传输与编程示例

发表于 2026-05-01 更新于 2026-05-04 分类于 Protocol 本文字数： 772 阅读时长 ≈ 3 分钟

TCP（Transmission Control Protocol）在 IP 之上提供面向连接的、可靠的、按序的字节流抽象，是 HTTP、HTTPS、SSH 等协议的主要载体。下面从「设计目标 → 连接状态与握手/挥手原理 → 可靠性与拥塞控制概念 → 端口与套接字 → 抓包与编程示例」顺序写清楚。

一、设计目标与作用

1. 解决什么问题

  • 进程到进程：仅靠 IP 只能定位到主机；TCP 用源端口 / 目的端口区分同一主机上的不同应用。
  • 可靠有序字节流：通过序号（Sequence）、确认（ACK）、重传、按序重组隐藏丢包与乱序。
  • 流量控制与拥塞控制：用接收窗口限制发送端速率；用拥塞窗口与多种算法（Cubic、BBR 等，依系统）减轻网络拥塞。

2. 与 UDP 的取舍

需要稳定管道、文件传输、远程登录时选 TCP；可容忍丢包、强实时见 UDP 与 QUIC。

二、连接：三次握手与四次挥手（原理）

1. 建立连接（简化）

SYN 洪泛、半连接队列长度与 SYN Cookie 属于安全与调优范畴。

2. 关闭连接（简化）

任一方发送 FIN 表示本方向不再发送数据；双方都可能 FIN，经过 TIME_WAIT（约 2MSL）状态以便旧报文从网络中消散。RST 表示异常复位。

三、可靠性与窗口（原理要点）

  • 字节序号：每个方向独立编号；ACK 表示「期望收到的下一个序号」。
  • 滑动窗口：已发送未确认的字节不能无限堆积；窗口大小受接收方通告与拥塞算法共同约束。
  • Nagle 与延迟 ACK：小报文合并与确认延迟可能增加交互延迟；低延迟场景可在套接字层关闭 Nagle（TCP_NODELAY），需权衡带宽。

四、四元组与套接字

唯一确定一条 TCP 连接：（源 IP，源端口，目的 IP，目的端口）。服务端 LISTEN 在固定端口（如 80），客户端端口通常由内核临时分配。

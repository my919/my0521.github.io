DL

发表于 2026-05-01 更新于 2026-07-04 分类于 AI 本文字数： 1.1k 阅读时长 ≈ 4 分钟

深度学习（Deep Learning，DL） 使用多层神经网络自动学习层次化特征，在视觉、语音、自然语言等领域取得突破。下面从「神经网络基础 → CNN / RNN / Transformer → 训练技巧 → 框架与硬件 → 与 LLM 的关系」顺序写清楚。

训练反向传播



flowchart LR
  X[输入] --> F[前向传播]
  F --> L[损失 Loss]
  L --> B[反向传播梯度]
  B --> U[更新权重]

一、神经网络基础

  • 前向传播：输入 → 各层线性变换 + 非线性激活 → 输出。
  • 损失函数：分类 Cross-Entropy、回归 MSE 等。
  • 反向传播：链式法则计算梯度，SGD/Adam 等优化器更新参数。

1. 为什么需要非线性激活

若每层只有线性变换 ，多层堆叠仍等价于单层线性模型，无法拟合 XOR、边界弯曲等复杂模式。激活函数 引入非线性，使网络能学习层次化特征。

2. 常见激活函数

函数 公式 值域 特点
ReLU 计算快；正区间梯度恒为 1，缓解梯度消失
Sigmoid 输出可解释为概率；两端饱和，易梯度消失
GELU 近似 平滑、非单调；Transformer 默认选择之一

ReLU： 时输出 0， 时等于 ；负半轴梯度为 0（Dead ReLU），实践中仍是最常用的隐层默认项。

Sigmoid：把实数压到 ，适合二分类输出层或门控（LSTM 门）；隐层深层堆叠时两端饱和导致梯度接近 0，训练变慢。

GELU：在 0 附近平滑过渡，负值有小幅度非零响应；BERT、GPT 等 Transformer 隐层常用，表达力与训练稳定性通常优于 ReLU，但计算略贵。

3. 如何选择（以及为什么）

场景 推荐 原因
CNN / MLP 隐层 ReLU 实现简单、收敛快；大量视觉与表格任务验证有效
输出层（二分类概率） Sigmoid 输出天然在 ，与 BCE 损失配套
输出层（多分类） Softmax（非 Sigmoid） 各类概率和为 1
Transformer / 大语言模型 GELU 平滑非线性利于深层 Self-Attention 训练；与 Layer Norm 等组合成熟
RNN / 门控结构 Sigmoid / Tanh 门控需要 或有界输出；Tanh 零中心，有时优于 Sigmoid
需要概率且要可导 Sigmoid / GELU Sigmoid 有界；GELU 在 0 附近更平滑，梯度更友好

经验法则：

  1. 没有特殊理由时，隐层先用 ReLU（或 Leaky ReLU 减轻 Dead ReLU）。
  2. 输出层跟任务走：回归用线性/无激活，分类用 Softmax 或 Sigmoid。
  3. 复现 Transformer 或 LLM 结构时用 GELU，与论文和主流实现一致。
  4. 深层旧架构（VGG 之前） 曾广泛用 Sigmoid/Tanh，现多被 ReLU 取代，除非门控或概率语义需要。

二、典型架构

架构 适用
MLP 表格、简单向量
CNN 图像、局部空间模式
RNN/LSTM/GRU 序列（较长依赖现多被 Transformer 补充）
Transformer NLP、多模态；Self-Attention 建模长距离依赖

ResNet、U-Net、BERT、GPT 等均建立在上述组件之上。

三、训练技巧

  • Batch Normalization / Layer Norm：稳定训练。
  • Dropout：减轻过拟合。
  • 学习率调度：Warmup、Cosine Decay。
  • 混合精度（AMP）：FP16/BF16 加速、省显存。
  • 梯度裁剪：RNN/大模型训练防爆炸。

数据：增强（随机裁剪、翻转）、归一化；划分训练/验证，早停（Early Stopping）。

四、框架与硬件

  • PyTorch：研究与应用主流（见 PyTorch）。
  • TensorFlow/JAX：生产与 TPU 生态。
  • GPU/CUDA：大规模训练依赖；推理可用 ONNX Runtime、TensorRT 等。

五、与 ML、LLM

  • 传统 ML：小数据、表格、可解释场景仍常用 GBDT。
  • DL：表示学习为主。
  • LLM：超大 Transformer 预训练 + 微调/对齐；视觉侧有 ViT、Diffusion 等并行发展。

计算机视觉入门可结合 OpenCV。

ML

发表于 2026-05-01 更新于 2026-07-04 分类于 AI 本文字数： 689 阅读时长 ≈ 2 分钟

机器学习（Machine Learning，ML） 让计算机从数据中学习规律，对新样本做预测或决策，而无需为每种情况手写规则。下面从「问题类型 → 典型流程 → 常用算法 → 评估与过拟合 → 与 DL/LLM 的关系」顺序写清楚。

典型流程



flowchart LR
  Raw[原始数据] --> Clean[清洗特征]
  Clean --> Train[训练模型]
  Train --> Eval[验证集评估]
  Eval --> Deploy[部署推理]

一、问题类型

类型 目标 示例
监督学习 有标签，学输入→输出映射 分类（垃圾邮件）、回归（房价）
无监督学习 无标签，发现结构 聚类、降维、异常检测
强化学习 智能体与环境交互最大化回报 游戏、机器人控制

二、典型流程

  1. 问题定义与指标（准确率、F1、AUC、RMSE 等）。
  2. 数据收集与清洗：缺失值、异常值、泄漏（train/test 混用未来信息）。
  3. 特征工程：数值缩放、类别编码、时间特征。
  4. 模型训练与验证：训练集 / 验证集 / 测试集或 K 折交叉验证。
  5. 部署与监控：数据漂移、模型退化、在线 A/B。

三、常用算法（概览）

  • 线性模型：逻辑回归、线性回归、SVM（核方法）。
  • 树模型：决策树、随机森林、GBDT、XGBoost/LightGBM（表格数据仍强）。
  • 距离方法：KNN。
  • 无监督：K-Means、PCA、t-SNE（可视化）。

四、过拟合与正则

  • 过拟合：训练集很好、泛化差 → 更多数据、简化模型、L1/L2 正则、Dropout（神经网络侧）。
  • 偏差-方差权衡：模型容量与数据量匹配。
  • 交叉验证：稳定估计泛化性能。

五、与 DL、LLM 的分工

层次 说明
传统 ML 表格、小数据、可解释性要求高
DL 图像、语音、复杂非线性表示
LLM 自然语言理解与生成；下游常 微调 或 RAG

深度学习框架见 PyTorch；Python 工程见 Python-UV。

Docker 用容器封装应用及其依赖，在隔离的命名空间与 cgroup 中运行，共享宿主机内核，实现「一次构建、到处运行」。下面从「镜像与容器 → 常用命令 → Dockerfile 要点 → 网络与卷 → Compose 与生产 → 与本站其它文章的关系」顺序写清楚。

三、Dockerfile 要点

Zigbee

发表于 2026-05-01 更新于 2026-05-31 分类于 Embedded 本文字数： 349 阅读时长 ≈ 1 分钟

Zigbee 是基于 IEEE 802.15.4 的低功耗 mesh 物联网协议：2.4 GHz（亦有个别 sub-GHz），Coordinator + Router + End Device，应用配置文件如 Home Automation。下面从「网络层 → 设备类型 → ZCL 集群 → 与 Bluetooth/LoRaWAN 对照 → 开发栈」顺序写清楚。

Mesh 拓扑



flowchart TB
  C[Coordinator 协调器] --> R1[Router 路由]
  R1 --> R2[Router]
  R2 --> E1[End Device 传感器]
  R1 --> E2[End Device 开关]

一、802.15.4 基础

  • PHY/MAC：短帧、CSMA-CA、AES-128 链路加密。
  • Zigbee 在之上定义 NWK、APS、ZDO 与应用层 ZCL。

二、设备角色

角色 说明
Coordinator 建网、分配 PAN ID、短地址，通常 1 个
Router 中继、常供电
End Device 叶子节点，可 Sleep，通过父节点通信

Mesh 多跳扩展覆盖；路由表由 AODV 类机制维护（依栈实现）。

三、ZCL（Zigbee Cluster Library）

与 Bluetooth GATT 类似：标准化集群/属性/命令，保证互操作。

四、与其它无线

协议 特点
Zigbee 家居 mesh、中等数据率、低功耗
BLE Mesh 蓝牙生态、手机直连
LoRaWAN 公里级、星型、极低速率
Wi-Fi 高吞吐、功耗高

网关常把 Zigbee 转 MQTT / HTTP 上云。

五、开发与认证

  • 芯片：Silicon Labs、TI CC2652、NXP JN5169 等。
  • 栈：Zigbee PRO、Z3Gateway；开源 Z-Stack 部分版本。
  • Zigbee 认证：互操作 logo 需过联盟测试。

联盟：https://csa-iot.org/all-solutions/zigbee/

USB

发表于 2026-05-01 更新于 2026-05-31 分类于 Embedded 本文字数： 335 阅读时长 ≈ 1 分钟

USB（Universal Serial Bus）是主机–设备型串行总线：2.0 / 3.x / USB-C，供电与数据一体，广泛用于 PC 外设、调试下载、存储。下面从「拓扑与角色 → 描述符与类 → CDC 虚拟串口 → 与 UART 的关系 → 嵌入式 Device 开发」顺序写清楚。

主机–设备拓扑



flowchart LR
  Host[USB Host PC] --> Hub[Hub 可选]
  Hub --> Dev1[Device 键鼠]
  Hub --> Dev2[Device CDC 串口]

一、拓扑

  • Host 发起事务；Device 响应。
  • OTG 设备可切换 Host/Device（手机接 U 盘）。

二、速度等级

版本 速率（量级）
USB 2.0 HS 480 Mbps
USB 3.x 5 Gbps+
USB4 基于 Thunderbolt 生态

Full Speed 12 Mbps 仍常见于 MCU Device。

三、描述符与 Class

  • 设备描述符 → 配置 → 接口 → 端点。
  • Class：HID（键鼠）、MSC（U 盘）、CDC-ACM（虚拟 UART）、Audio、Video 等。
  • Vendor Specific：自定义 Bulk/Interrupt 端点 + 主机驱动/libusb。

四、CDC 虚拟串口

MCU 通过 USB CDC ACM 暴露 /dev/ttyACM0（Linux）或 COM 口（Windows），应用层与 UART 类似发字节，物理层是 USB 包。

与 RS232：USB 转串口 芯片（CH340、CP2102、FT232）内部即 UART ↔ USB 桥接。

五、嵌入式开发要点

  • STM32 USB Device Library、TinyUSB、ESP32-S2/S3 USB OTG。
  • 枚举失败：检查 D+/D-、1.5k 上拉（Full Speed Device）、供电与描述符。
  • USB 3 / Type-C：PD 协商、Alt Mode（DP/Thunderbolt）另论。

规范：https://www.usb.org/documents

NFC

发表于 2026-05-01 更新于 2026-05-31 分类于 Embedded 本文字数： 328 阅读时长 ≈ 1 分钟

NFC（Near Field Communication）是近场无线通信（约 < 10 cm）：13.56 MHz，基于 RFID 演进，支持读卡、点对点、支付与配网。下面从「工作模式 → Tag 类型 → NDEF → 与 Bluetooth/USB 配合 → 安全」顺序写清楚。

读卡模式



sequenceDiagram
  participant R as NFC Reader 手机
  participant T as NFC Tag 卡
  R->>T: 射频场供电 + 轮询
  T-->>R: NDEF URL / 文本

一、工作模式

模式 说明
Reader/Writer 读或写 passive Tag
Card Emulation 手机模拟门禁/交通卡
Peer-to-Peer 两设备交换小数据（较少用）

二、Tag 标准

  • Type 1~4 Tag：不同容量与协议（NFC Forum）。
  • MIFARE Classic/Ultralight：交通、门禁（Classic 安全性已弱，新项目慎用）。
  • ISO 14443 A/B、ISO 15693（稍远，仍近场）。

三、NDEF（NFC Data Exchange Format）

常用 payload 格式，可封装：

  • URI（打开网页）
  • 文本
  • Wi-Fi 配置（WSC）
  • Bluetooth LE 配对 OOB 数据

手机贴近 Tag 即可触发系统动作（依 OS 策略）。

四、与其它接口

  • Bluetooth：NFC 传递配对密钥，BLE 传大数据。
  • USB：PC 用 USB NFC 读卡器 开发调试。
  • 支付：EMVCo、HCE（Host Card Emulation）在 SE/TEE 中存密钥。

五、开发

  • Android：NfcAdapter、enableReaderMode。
  • MCU：PN532、MFRC522（SPI/I2C）+ 天线设计。
  • 安全：Tag 可只读；支付与门禁依赖芯片级密钥，勿明文存敏感数据于可写 Tag。

Bluetooth

发表于 2026-05-01 更新于 2026-05-31 分类于 Embedded 本文字数： 321 阅读时长 ≈ 1 分钟

蓝牙（Bluetooth） 是短距离无线标准：2.4 GHz ISM，经典分为 BR/EDR（经典蓝牙） 与 BLE（低功耗蓝牙，Bluetooth Low Energy）。下面从「BLE 架构 → GATT 服务 → 配对与安全 → 与 Zigbee/NFC 对照 → 开发」顺序写清楚。

BLE GATT 模型



flowchart TB
  Central[Central 手机] -->|连接| Peripheral[Peripheral 设备]
  Peripheral --> Svc[Service UUID]
  Svc --> Char[Characteristic 读写 Notify]

一、BLE 角色

角色 说明
Central 发起连接，如手机、网关
Peripheral 广播、被连接，如手环、温湿度计
Broadcaster / Observer 仅广播/扫描（Beacon）

连接后通过 ATT/GATT 读写特征值（Characteristic）。

二、GATT 模型

  • UUID：16 位标准 UUID 或 128 位自定义。
  • Notify/Indicate：外设主动推送数据，省 polling 功耗。

三、配对与安全

  • Just Works / Passkey / OOB 等配对模式。
  • LE Secure Connections（ECDH）防中间人。
  • 与 NFC tap-to-pair：NFC 交换临时信息辅助 BLE 配对。

四、经典蓝牙 vs BLE

经典 BLE
功耗 较高 极低
吞吐 音频、SPP 串口 小数据、传感器
协议 RFCOMM、A2DP 等 GATT

音频耳机等多用 经典 + BLE 双模芯片。

五、开发工具

  • nRF Connect（手机抓包 GATT）。
  • 芯片：Nordic nRF、ESP32（Bluedroid/NimBLE）、TI CC2340。
  • 与 USB：BLE dongle 常通过 USB 接 PC；逻辑仍是无线 GATT。

官方：https://www.bluetooth.com/specifications/

LoRaWAN

发表于 2026-05-01 更新于 2026-05-31 分类于 Embedded 本文字数： 352 阅读时长 ≈ 1 分钟

LoRaWAN 是基于 LoRa 物理层的远距离广域网协议：星型拓扑，终端 ↔ 网关 ↔ 网络服务器，低功耗、公里级距离、kbps 级速率。下面从「频段与速率 → Class A/B/C → 入网与密钥 → 与 CoAP/MQTT → 应用场景」顺序写清楚。

星型拓扑



flowchart TB
  Dev1[终端节点] --> GW[LoRa 网关]
  Dev2[终端节点] --> GW
  GW --> NS[Network Server]
  NS --> App[应用服务器]

一、架构

  • Gateway：只做射频转发，不解密应用 payload（取决于模式）。
  • ADR（Adaptive Data Rate）：网络侧调节 SF/功率平衡距离与容量。

二、区域参数

区域 典型频段
EU868 863–870 MHz
US915 902–928 MHz
CN470 470–510 MHz

需遵守当地无线电法规；模块需合规认证。

三、设备 Class

Class 下行窗口 功耗
A 仅上行后两个短窗口 最低，传感器常用
B 附加信标窗口 中
C 几乎常开接收 高，供电设备

四、安全

  • Join：OTAA（Over-The-Air Activation，推荐）或 ABP（预置密钥）。
  • AES-128：NwkSKey、AppSKey 分层加密与完整性。
  • 应用层仍可封装 CoAP 或自定义二进制。

五、与其它物联网协议

  • 长距离、低带宽、电池 → LoRaWAN。
  • 有 Wi-Fi/以太网、高吞吐 → MQTT、HTTP。
  • 局域 mesh → Zigbee、Bluetooth Mesh。

开源栈：LoRaMac-node、Semtech LoRaWAN Stack；云平台：TTN、ChirpStack 等。

CoAP

发表于 2026-05-01 更新于 2026-05-31 分类于 Embedded 本文字数： 373 阅读时长 ≈ 1 分钟

CoAP（Constrained Application Protocol，RFC 7252）是面向受限设备的应用层协议：二进制紧凑、基于 UDP（可 DTLS 加密），语义类似 REST（GET/PUT/POST/DELETE），与 HTTP 对照学习。下面从「报文结构 → 请求响应 → Observe 订阅 → 与 MQTT 对照 → 应用场景」顺序写清楚。

REST over UDP



sequenceDiagram
  participant C as CoAP Client
  participant S as CoAP Server
  C->>S: GET /temp
  S-->>C: 2.05 Content 25.3
  C->>S: Observe 订阅
  S-->>C: 推送变化

一、设计目标

  • 低开销：适合 MCU、6LoWPAN、低带宽链路。
  • 异步：支持 Separate 响应（ACK 先回，结果稍后 CON 通知）。
  • 发现：.well-known/core 资源目录。

默认端口 5683（CoAPS 5684）。

二、报文（简化）

Type 含义
CON 需确认
NON 不需确认
ACK 确认
RST 复位

Code：0.xx 请求（GET=0.01），2.xx 成功，4.xx/5.xx 错误（类比 HTTP）。

三、Observe（RFC 7641）

客户端带 Observe Option 订阅资源；服务器在资源变化时 NOTIFY，适合传感器推送，比轮询省流量。

四、与 MQTT

CoAP MQTT
模型 REST 资源 发布/订阅 Topic
传输 UDP 为主 TCP 常见
代理 CoAP-HTTP 代理 Broker 中心化

物联网选型：资源型设备、LwM2M（基于 CoAP）vs 海量消息经 Broker 的 MQTT。

五、应用

  • 智能抄表、楼宇传感器、Edge 网关 南向 CoAP、北向 HTTP/MQTT。
  • 安全：DTLS 预共享密钥或证书；与 LoRaWAN 可组合（应用 payload 再解析）。

库：libcoap、aiocoap（Python）、Californium（Java）。

第五章：Docker 部署 RocketMQ 实践

概念基础：容器化部署 RocketMQ 的四个要点

  1. 没有「单容器一体」形态：NameServer 与 Broker 是两个独立进程（5.x 还有一个可选的 Proxy），最小栈就是两个容器——这与 Kafka 的 KRaft 单进程不同，下文用「网络 → NameServer → Broker」三步完成最小栈。
  2. brokerIP1 是第一坑：Broker 启动时把自己注册到 NameServer 的地址就是 brokerIP1，客户端拿这个地址直连 Broker——容器内不显式指定时往往是内网容器 IP，宿主机客户端会「能拿到路由却连不上」。本机访问写 127.0.0.1、跨机写宿主机可达 IP（对照 Kafka 的 advertised.listeners）。
  3. 端口按角色记忆：9876 NameServer；10909 / 10911 / 10912 分别是 Broker 的 VIP / 主 / HA 端口；8080 / 8081 是 5.x Proxy 的 gRPC 端口——只用经典 Remoting 客户端时，Proxy 端口可以不映射。
  4. 数据目录与边界：Broker 数据在 /home/rocketmq/store（日志在 logs），必须挂卷；单机部署面向开发验证，生产多 Master/Slave 或 DLedger 自动切换请用 RocketMQ Operator 或官方推荐拓扑。

概念基础：为什么用 Docker 部署 PostgreSQL

  1. PostgreSQL 是 C/S 架构的关系库：服务端 postgres 进程监听 5432 端口，客户端（psql、JDBC）通过连接串访问；「部署」的本质就是两件事——把服务端进程跑起来、让数据落在可靠的地方。
  2. 容器化 = 环境即代码：镜像内置二进制与依赖，一条命令起库；POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB 环境变量完成初始化，首次空数据目录时还会自动执行 /docker-entrypoint-initdb.d 下的脚本。

第二章：Windows 上 WSL（Rocky Linux）与 Docker Desktop

概念基础：WSL 是什么/为什么

  1. WSL 是什么：WSL（Windows Subsystem for Linux）让 Windows 直接运行真正的 Linux 发行版，无需双系统或整机虚拟机，一条命令即可进出 Linux 环境。
  2. WSL2 的意义：WSL2 基于轻量级虚拟机，系统调用兼容性完整，是 Docker Desktop 官方推荐的运行后端——没有 WSL2 就没有流畅的容器体验。
  3. 为什么选 Rocky Linux：与 RHEL 同源的企业级发行版，dnf 生态与生产服务器一致，作为本地演练环境最贴近真实运维。
  4. Docker Desktop 的角色：提供图形化引擎管理（更新、证书、镜像加速），通过 WSL integration 把 docker CLI 注入各发行版，Rocky 内无需再装 dockerd。
  5. 适用场景：在 Windows 机器上做 Linux 运维演练与容器开发；代码放在发行版内的 Linux 文件系统中可获得最佳 I/O 性能。

概念基础：容器化部署 Kafka 的四个要点

  1. KRaft 让单进程成为可能：旧版 Kafka 需要 ZooKeeper + Kafka 两个进程；KRaft 模式下一个容器同时扮演 controller + broker，单机一条命令即可起集群（本章单容器示例的核心）。

Docker 部署 ZooKeeper

概念基础：ZooKeeper 是什么/为什么

  1. 分布式协调服务：ZooKeeper 为分布式系统提供配置管理、命名服务、分布式锁与选主等基础原语，是 Kafka、Hadoop 等大数据组件的经典协调底座。
  2. 数据模型像文件树：数据组织为 ZNode 树，节点可存少量元数据，客户端可挂 Watcher 监听节点变化，适合读多写少场景。
  3. 一致性与仲裁：基于 ZAB 协议，集群需奇数个节点投票形成多数派（3 节点容忍 1 节点故障），保证强一致。

概念基础：为什么用 Docker 部署 MySQL

  1. 环境一致、随起随删：一条命令拉起带指定版本、字符集、账号密码的实例，不污染宿主机；卸载即删容器，重装零成本——这正是第一章建好表结构之后最需要的环境。

第七章：OpenSSL 密钥派生与随机数：PBKDF2、rand 与推荐用法

概念基础：密钥从哪来、为什么是根基

  1. 随机数是密码学之根：密钥、IV/nonce、salt、session token、HMAC secret 全部来自 CSPRNG（openssl rand 内部即此）——随机性不足，再强的算法也是空谈。
  2. 口令 ≠ 密钥：人类口令熵低、可猜测、常重复，直接当 AES 密钥会被暴力破解；必须经 KDF（密钥派生函数） 处理。
  3. KDF 的两大武器：salt（防彩虹表与预计算）+ 高迭代次数（把每次猜测的成本拉高千万倍），PBKDF2 建议迭代 ≥ 600000。
  4. 场景分流：文件加密口令 → PBKDF2（enc -pbkdf2 已内置，见第四章）；协议密钥 → HKDF（TLS 1.3 内部自动完成）；口令存储 → Argon2id（应用层专用库）。
  5. 本章定位：作为末章收束全书——把前几章密钥的「来源」讲透：第四章的 AES 密钥、第六章的 HMAC secret，都在这里生成与派生。

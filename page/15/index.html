第一章：PostgreSQL 概述与 DDL 入门

概念基础：PostgreSQL 与 DDL 是什么

  1. PostgreSQL 是开源的对象-关系型数据库：以 SQL 标准兼容与丰富的数据类型、扩展生态著称；数据按 数据库 → 模式（SCHEMA）→ 表 分层组织，客户端用 psql 或 JDBC 等驱动访问。
  2. SQL 按职责分两层：DDL（数据定义语言）管结构——库、模式、表、列、索引等对象的创建与变更；DML（数据操作语言）管数据——行级增删改查。本章聚焦 DDL。
  3. 为什么从 DDL 学起：结构是一切的地基——后面的高级查询、索引与性能、并发与 MVCC 都建立在「先有表结构」之上；类型与约束设计得当，能直接挡住一大批脏数据。
  4. 一条主线：CREATE 建、ALTER 改、DROP 删；生产环境永远先确认影响面（活跃连接、依赖对象），并养成 IF EXISTS 幂等习惯。

第一章：MySQL DDL 语句与表设计入门

概念基础：DDL 与表结构是什么

DDL（Data Definition Language，数据定义语言）是 MySQL 中定义「结构」的语言：

  1. 管结构，不管数据：DDL 负责定义/修改/删除数据库、表、字段、索引、视图等对象，不操作表里的业务数据；管数据的是 DML（INSERT / UPDATE / DELETE / SELECT）——一句话记忆：「DDL 改架子，DML 改数据」。
  2. 建表即建模：把业务对象翻译成表，核心是选字段类型（INT / VARCHAR / DATETIME…）与定约束（主键、非空、唯一、默认值、外键）；结构一次设计、长期使用，返工成本高，所以建表是数据库学习的第一课。
  3. 结构最终落在存储引擎上：客户端 SQL 经 MySQL Server 交给 InnoDB，数据按主键组织成 B+ 树，通过 Buffer Pool 缓存、Redo Log 保证崩溃安全——表与索引结构如何组织，直接决定后面的查询性能（详见第五章、第六章）。
  4. 三大类对象：库操作、表操作，以及视图 / 索引 / 存储过程等对象定义；语句形式永远是 CREATE / ALTER / DROP 三板斧。
  5. 约束的权衡：FOREIGN KEY、UNIQUE 等约束由数据库兜底完整性，但会带来额外维护开销、且不利于分库分表，互联网业务常改用「逻辑外键」；入门先学会用，进阶再权衡取舍。

DDL 主要分 3 大类

  1. 库操作：CREATE / ALTER / DROP 数据库
  2. 表操作：CREATE / ALTER / DROP 数据表
  3. 其他（仍是 DDL：定义「对象结构」，不直接改表内业务行）
    • 视图（VIEW）：CREATE VIEW / ALTER VIEW / DROP VIEW。把一段查询保存成虚拟表名，查询时动态算出结果；本身不单独存一份业务数据，常用于简化复杂 SQL、封装列权限。
    • 索引（INDEX）：CREATE INDEX，或 ALTER TABLE ... ADD INDEX、DROP INDEX 等。在列（或列组合）上维护辅助查找结构，加快 SELECT，但会占磁盘、拖慢部分 INSERT/UPDATE/DELETE；与表强相关，属结构的延伸。
      存储过程、触发器等也可由 DDL 创建/删除对象。

第一章：Redis 概述、安装与 CLI 入门

概念基础：Redis 是什么

Redis（REmote DIctionary Server）是一个基于内存的键值（KV）存储系统：

  1. 数据在内存：读写不落盘，单次操作微秒级，比磁盘数据库快 1~2 个数量级；同时提供 RDB / AOF 持久化把数据落到磁盘。
  2. KV 模型，值有类型：键（key） 永远是字符串；值（value） 支持多种数据类型（String / Hash / List / Set / ZSet 等），不同类型对应不同命令族与底层结构，这是 Redis 与 Memcached 这类「纯字符串 KV」最大的差别。
  3. 单线程命令执行：命令在单线程事件循环中顺序执行（基于 epoll / IO 多路复用），单个命令天然原子；Redis 6.0+ 引入的「多线程」只用于网络 IO 读写，命令执行仍是单线程。
  4. 为什么快：内存操作 + IO 多路复用 + 单线程无锁竞争 + 针对各类型优化的高效底层结构（SDS、跳表、quicklist 等）。
  5. 定位：缓存为主，兼任分布式锁、计数器、排行榜、消息队列、地理位置等；缓存 ≠ 数据库，关键数据以关系库为准，Redis 丢数据要有降级与重建预案。

第三章：MyBatis-Plus 快速上手与分页原理

概念基础：MyBatis-Plus 是什么、为什么

MyBatis-Plus（简称 MP） 是 MyBatis 的增强工具，定位是「只做增强不做改变」：

  1. 通用 CRUD：Mapper 继承 BaseMapper 即可获得 selectById、insert、update 等单表增删改查能力，免写 XML。
  2. 插件体系：通过 MybatisPlusInterceptor 注册分页、乐观锁、防全表更新等内部拦截器，按需装配。
  3. 分页零侵入：内置 PaginationInnerInterceptor，基于 MyBatis 拦截器自动生成 count 语句、改写 SQL 拼接 LIMIT，业务代码只传 Page 参数。
  4. 代码生成：配合 IDEA 插件（如 MyBatisX-Generator）可从数据库表直接生成 Entity / Mapper / Service 代码。
  5. Spring Boot 集成：提供 mybatis-plus-spring-boot*-starter 起步依赖，配好 mapper-locations 与驼峰映射即可使用。

一、核心一句话

MP 分页本质：MyBatis 拦截器 + 自动改写 SQL

  1. 你传入 Page<>(当前页,每页条数)
  2. MP 分页拦截器拦截 Mapper 查询方法
  3. 自动帮你生成 count 总数SQL + 拼接 limit 分页SQL
  4. 执行两条 SQL：查总数 → 查当前页数据
  5. 把总数、页码、数据封装到 IPage 返回

二、关键核心组件

  1. MybatisPlusInterceptor
    MP 核心插件容器，所有插件（分页、防全表更新、乐观锁）都往里注册。
  2. PaginationInnerInterceptor
    MP 真正的分页拦截器，核心逻辑全在这。
  3. Page / IPage
    分页参数载体，存：当前页、每页条数、总记录数、总页数、分页数据。

三、完整执行流程（一步一步走）

1. 配置分页拦截器（必须配置，否则分页无效）

2. 业务代码使用

3. 底层执行步骤

  1. 进入 Mapper 方法前
    PaginationInnerInterceptor 拦截到 selectPage 查询。
  2. 判断是否是分页查询
    检测方法参数里有没有 IPage/Page 对象，有就走分页逻辑。
  3. 自动生成 COUNT 语句
    原SQL：select id,name from user
    自动生成：select count(*) from user → 查询总记录数
  4. 改写原SQL 加 LIMIT
    原SQL 被改写为：
    select id,name from user limit 0,10
  5. 执行两条 SQL
    • 第一条：查总条数
    • 第二条：查分页数据
  6. 封装分页信息
    把总条数、当前页、每页大小、总页数、数据列表 全部塞进 IPage 返回。

四、为什么不用自己写 limit、不用自己写 count？

MP 拦截器动态解析 SQL、动态拼接 limit、动态生成 count，完全无侵入。

五、分页两个重要特性

1. 分页合理化 reasonable=true

  • 输入页码 <=0 自动变成第 1 页
  • 输入页码 大于总页数 自动返回最后一页

2. 溢出总页数后是否查最后一页

PaginationInnerInterceptor 可配置，防止页码乱输报错。

六、常见坑（原理衍生出来的）

  1. 没配置 PaginationInnerInterceptor → 分页无效，查全部数据
  2. 只有 Mapper 层用 Page 参数才生效，Service 自己写 list 不分页
  3. 自定义 XML SQL 也能自动分页，MP 照样拦截加 limit、count
  4. 多表联查、复杂 SQL 也支持，拦截器会解析原有 SQL 结构

七、极简总结

MP 分页 = 拦截器拦截SQL → 自动查总数 → 自动拼接LIMIT → 封装分页结果

不用手写 count、不用手写 limit，全靠拦截器动态代理实现。

Flask 是 Python 轻量级 Web 框架（微框架）：

  1. 微内核：核心只提供路由与 WSGI 请求处理（底层为 Werkzeug），ORM、表单、认证等能力皆以扩展按需拼装，项目再大也不被框架绑架。
  2. 视图函数极简：一个函数 + @app.route 装饰器即一个接口；视图返回 dict 会被自动序列化为 JSON，非常适合 API 开发。
  3. 模块化组织：用 Blueprint（蓝图） 把路由按业务拆分（如 /api/v1），Jinja2 模板负责 HTML 渲染，大型项目也能保持结构清晰。
  4. 与 uv 无缝协作：延续前几章的项目化工作流——uv add flask 安装、uv run flask --app app run --debug 启动开发服务器，本地与 CI 环境一致。

Hexo 博客

Hexo 是基于 Node.js 的静态博客框架，用 Markdown 写作，一键生成全站并可免费部署到 GitHub Pages。下面从准备、安装、写作、预览、部署、主题与常用命令，一步步讲清楚。

概念基础：Hexo 是什么/为什么

  1. 静态站点生成器（SSG）：Hexo 把 Markdown 源文件在本地渲染成纯 HTML/CSS/JS，无数据库、无后端，托管成本几乎为零。
  2. Node.js 生态：基于 Node.js 运行，hexo-cli 脚手架 + npm 插件体系，主题、部署、压缩、搜索等能力均可插件化扩展。
  3. 写作即发文：hexo new 生成带 front-matter（title/date/tags/categories）的 Markdown 文章，放入 source/_posts/（可按子目录组织）即被站点收录。
  4. 部署自由：GitHub Pages 免费上线，也可用 hexo-deployer-git 推送到 Gitee Pages、VPS 或对象存储。
  5. 主题可定制：NexT 等主题提供分类、标签、站内搜索、SEO、评论等成熟能力，站点配置集中在 _config.yml。

TCP 协议详解：连接、可靠传输与编程示例

发表于 2026-05-01 更新于 2026-05-31 分类于 Protocol 本文字数： 1.6k 阅读时长 ≈ 5 分钟

TCP（Transmission Control Protocol）在 IP 之上提供面向连接的、可靠的、按序的字节流抽象，是 HTTP、HTTPS、SSH 等协议的主要载体。下面从「设计目标 → 连接与完整通信流程（握手、传数据、挥手） → 可靠性与拥塞控制概念 → 端口与套接字 → 抓包 → C / Python 套接字示例」顺序写清楚。

三次握手（简化）



sequenceDiagram
  participant C as 客户端
  participant S as 服务端
  C->>S: SYN
  S->>C: SYN-ACK
  C->>S: ACK
  Note over C,S: ESTABLISHED

一、设计目标与作用

1. 解决什么问题

  • 进程到进程：仅靠 IP 只能定位到主机；TCP 用源端口 / 目的端口区分同一主机上的不同应用。
  • 可靠有序字节流：通过序号（Sequence）、确认（ACK）、重传、按序重组隐藏丢包与乱序。
  • 流量控制与拥塞控制：用接收窗口限制发送端速率；用拥塞窗口与多种算法（Cubic、BBR 等，依系统）减轻网络拥塞。

2. 与 UDP 的取舍

需要稳定管道、文件传输、远程登录时选 TCP；可容忍丢包、强实时见 UDP 与 QUIC。

二、连接：三次握手与四次挥手（原理）

1. 建立连接（简化）

SYN 洪泛、半连接队列长度与 SYN Cookie 属于安全与调优范畴。

2. 关闭连接（简化）

任一方发送 FIN 表示本方向不再发送数据；双方都可能 FIN，经过 TIME_WAIT（约 2MSL）状态以便旧报文从网络中消散。RST 表示异常复位。

3. 完整通信流程（与套接字 API 对应）

把「原理」落到一次典型会话上，顺序如下。

  1. 服务端：socket(AF_INET, SOCK_STREAM, 0) → bind 监听地址与端口 → listen（内核维护 LISTEN 与半连接/全连接队列）→ accept 阻塞直至三次握手完成，返回已连接套接字。
  2. 客户端：socket → connect（内核发出 SYN，完成握手后返回）→ 双方进入 ESTABLISHED。
  3. 传数据：send / write 与 recv / read 在用户态与内核发送/接收缓冲区之间搬运字节；TCP 在协议层做序号、确认、重传、按序递交；滑动窗口与拥塞控制限制未确认数据量。
  4. 关闭：任一方 close 或 shutdown(SHUT_WR) 触发本方向 FIN；对端 ACK 后可能仍可收数据（半关闭）；双方都发完 FIN 并确认后，主动关闭端常经历 TIME_WAIT，再回收端口与连接控制块。

三、可靠性与窗口（原理要点）

  • 字节序号：每个方向独立编号；ACK 表示「期望收到的下一个序号」。
  • 滑动窗口：已发送未确认的字节不能无限堆积；窗口大小受接收方通告与拥塞算法共同约束。
  • Nagle 与延迟 ACK：小报文合并与确认延迟可能增加交互延迟；低延迟场景可在套接字层关闭 Nagle（TCP_NODELAY），需权衡带宽。

四、四元组与套接字

唯一确定一条 TCP 连接：（源 IP，源端口，目的 IP，目的端口）。服务端 LISTEN 在固定端口（如 80），客户端端口通常由内核临时分配。

Kafka 大数据数据总线

发表于 2026-05-01 更新于 2026-05-31 分类于 BigData 本文字数： 555 阅读时长 ≈ 2 分钟

Apache Kafka 在大数据链路中常作为统一数据总线：采集日志与业务变更 → 流式计算（Flink/Spark Streaming）→ 数仓（ClickHouse/Hive/Iceberg）。本文侧重数据平台视角；消息语义、生产者/消费者基础见 Kafka 消息中间件入门。

数据管道



flowchart LR
  SRC[业务库 / 日志 / IoT] --> CDC[Debezium / Connect]
  CDC --> K[Kafka Topic]
  K --> F[Flink / Spark]
  F --> WH[(ClickHouse / 湖仓)]

一、在数据架构中的位置

  • 解耦：生产者与消费者独立扩缩容。
  • 回放：按 Offset 重读，便于补数与审计。
  • 多订阅：同一 Topic 可被实时计算与离线同步同时消费（不同 Consumer Group）。

二、Topic 设计要点

实践 说明
分区数 并行度上限；扩容分区易，缩容难
Key 同 Key 进同一分区，维持局部顺序（如 userId）
保留策略 retention.ms / retention.bytes；合规需更长保留或冷归档
Compact cleanup.policy=compact 存 Key 最新状态（Connect、Streams）
命名 domain.event.v1 便于治理与 Schema 演进

三、Kafka Connect 与 CDC

组件 作用
Connect Source/Sink 插件，同步 DB、ES、S3
Debezium 基于 binlog/WAL 的 CDC，将 MySQL、PostgreSQL 变更写入 Kafka
Schema Registry Avro/Protobuf/JSON Schema 版本与兼容性

四、与流批引擎集成

引擎 集成要点
Flink Kafka Source + Checkpoint 精确一次（见 Flink）
Spark Structured Streaming kafka 格式，微批提交 offset（见 Spark）
ClickHouse Kafka 引擎表或 Materialized View 入库（见 ClickHouse）

五、数据质量与治理

  • Schema 演进：新增字段用兼容模式（BACKWARD/FULL），避免消费端反序列化失败。
  • 死信 Topic：解析失败、业务拒绝的消息进入 DLQ 人工处理。
  • 幂等写入：OLAP 侧按 主键 + 版本 或 ReplacingMergeTree 去重。

六、运维与监控

指标 含义
Consumer Lag 消费落后生产，告警阈值按 SLA 设
Under-replicated 副本未同步，影响可用性
Broker 磁盘 顺序写仍可能打满，需 retention 与扩容

工具：kafka-consumer-groups.sh、Cruise Control（ rebalance）、Kafka UI（本站 服务 :30013）。

部署：Docker 部署 Kafka、K8s Strimzi。

Flink

发表于 2026-05-01 更新于 2026-05-31 分类于 BigData 本文字数： 433 阅读时长 ≈ 1 分钟

Apache Flink 是流优先的分布式计算引擎：事件时间、Watermark、状态与精确一次语义，适合实时风控、大屏指标、CEP 等低延迟场景。下面从「DataStream API → 时间与窗口 → 状态与 Checkpoint → Flink SQL → 与 Spark/Kafka 的关系」顺序写清楚。

流处理数据流



flowchart LR
  K[Kafka Source] --> Map[map/filter]
  Map --> Key[keyBy]
  Key --> Win[Window + Watermark]
  Win --> Sink[Sink JDBC/ES]
  Win -.-> CP[Checkpoint 状态快照]

一、编程模型

  • Transformation：map/filter/keyBy/window 等。
  • Source / Sink：Kafka、JDBC、文件系统、Pulsar 等连接器。

二、事件时间与窗口

概念 说明
Processing Time 算子机器本地时钟
Event Time 数据自带业务时间戳
Watermark 衡量事件时间进度，触发窗口计算
Window Tumbling、Sliding、Session

乱序数据需 Watermark 延迟 与 allowedLateness 平衡准确性与延迟。

三、状态与 Checkpoint

  • Keyed State：与 keyBy 绑定，如 ValueState、ListState。
  • Checkpoint：异步分布式快照，配合 Kafka 两阶段提交 实现 端到端 exactly-once（依 Sink 支持）。
  • Savepoint：手动一致性快照，用于升级与扩缩容。

四、Flink SQL

Table API / SQL 与 DataStream 可互转；CDC（Flink CDC）常用于同步 MySQL 到数仓或 Kafka。

五、与 Spark 选型

需求 倾向
超大离线批、ML 生态 Spark
毫秒~秒级实时、复杂事件处理 Flink
消息入口 Kafka 消息中间件入门

官方文档：https://nightlies.apache.org/flink/flink-docs-stable/

Spark

发表于 2026-05-01 更新于 2026-05-31 分类于 BigData 本文字数： 445 阅读时长 ≈ 1 分钟

Apache Spark 是统一的大规模数据处理引擎：内存计算、RDD/DataFrame/Dataset API，支持 批处理、SQL、流（Structured Streaming）、MLlib、GraphX。下面从「架构 → RDD 与 DataFrame → Spark SQL → 与 Flink/Kafka 的关系 → 部署模式」顺序写清楚。

一、架构组件

组件 说明
Driver 运行 main，构建 DAG、调度 Stage
Executor Worker 上执行 Task，缓存分区数据
Cluster Manager Standalone、YARN、Kubernetes、Mesos
SparkContext / SparkSession 程序入口；SparkSession 统一 SQL 与 DataFrame

计算图划分为 Stage（宽依赖处切开），Stage 内为并行 Task。

DAG 执行模型



flowchart LR
  D[Driver 构建 DAG] --> S1[Stage 1 Tasks]
  S1 --> S2[Stage 2 shuffle]
  S2 --> S3[Stage 3 Tasks]
  S3 --> Out[输出 HDFS/Console]

二、RDD 与 DataFrame

1. RDD（弹性分布式数据集）

  • 不可变、分区、 lineage 容错。
  • Transformation 懒执行；Action（count、collect）触发计算。

2. DataFrame / Dataset

Catalyst 优化器与 Tungsten 执行引擎提升 SQL 与结构化 API 性能；生产更推荐 DataFrame/SQL 而非裸 RDD。

三、Spark SQL 与表

可读写 Parquet/ORC/Hive/Iceberg 等；分区裁剪与列式存储是性能关键。

四、流处理与周边

  • Structured Streaming：将流视为无界表，微批或连续处理（版本依发行版）。
  • 数据源/汇：Kafka（见 Kafka 大数据数据总线）、文件、Socket。
  • 与 Flink：Spark 偏批为主、流为微批/连续；Flink 偏低延迟流（见 Flink）。

五、部署与调优要点

  • Shuffle：spark.sql.shuffle.partitions、AQE（Adaptive Query Execution）。
  • 内存：Executor heap + overhead；避免 collect 大结果到 Driver。
  • 本地学习：Docker 或 standalone 模式 + PySpark。

官方文档：https://spark.apache.org/docs/latest/

NFT

发表于 2026-05-01 更新于 2026-05-31 分类于 Blockchain 本文字数： 543 阅读时长 ≈ 2 分钟

NFT（Non-Fungible Token，非同质化代币）是区块链上的唯一数字凭证：每个 Token ID 对应不同元数据（URI），不可互换，常用于数字艺术、游戏资产、会员与版权登记。下面从「与 FT 的区别 → ERC-721 / ERC-1155 → 元数据与存储 → 铸造与交易流程 → 风险与合规 → 与区块链总览的关系」顺序写清楚。

一、同质化 vs 非同质化

类型 特点 示例
FT（同质化） 可互换、可细分 ETH、USDT
NFT 每个 ID 唯一、通常不可分割（或按标准批量） 藏品 #1024、游戏皮肤

链上通常只存 Token ID 与 owner；图片/属性多在 链下 JSON（tokenURI）。

二、常见标准（以太坊系）

1. ERC-721

每个 Token 独立 ID，适合「一物一证」：

2. ERC-1155

单合约多类型 ID，适合游戏批量道具、半同质化场景。

其它链有各自 NFT 标准（如 Solana Metaplex 等），概念类似。

三、元数据示例

  • IPFS / Arweave：去中心化存储，降低单点删链风险；ipfs:// 需网关访问。
  • 中心化 URL：简单但依赖服务器可用性与诚信。

四、铸造与交易（流程）

  1. 部署 NFT 合约或调用已有 mint 接口。
  2. 上传元数据与媒体 → 得到 URI。
  3. mint(to, tokenId, uri) 写入链上所有权。
  4. 二级市场：OpenSea、Blur 等通过 Seaport 等协议撮合，链上 transferFrom 变更 owner。

Gas 费、版税（EIP-2981 等）、二级市场规则依链与平台而异。

五、风险与合规

  • 版权：Mint 不自动等于拥有作品版权；需法律合同明确。
  • 投机与欺诈：假项目、刷量、钓鱼签名。
  • 监管：各国对证券型 NFT、跨境交易要求不同。
  • 环保争议：PoW 链能耗高；PoS（如以太坊合并后）显著降低（见 区块链）。

代码示例可参考 区块链代码示例；元宇宙 资产场景见 元宇宙。

元宇宙(Metaverse)

发表于 2026-05-01 更新于 2026-05-05 分类于 Blockchain 本文字数： 1.6k 阅读时长 ≈ 5 分钟

一、元宇宙的起源与定义

1. 起源

  • 1992年：美国作家尼尔·斯蒂芬森在科幻小说《雪崩》（Snow Crash）中首次提出 Metaverse（元宇宙），描述一个平行于现实、可永久在线、人人拥有数字分身的三维虚拟世界。
  • 2021年：元宇宙元年
    • 3月：游戏公司 Roblox 在招股书中明确“元宇宙”定位，上市后市值一度突破400亿美元。
    • 10月：Facebook更名为Meta，宣布全面转向元宇宙，投入数百亿美元研发。
    • 资本疯狂涌入：2021年全球元宇宙相关融资超45起，商标申请量暴增。

2. 定义（通俗+学术）

  • 通俗理解：元宇宙是下一代互联网，从“平面网页”升级为三维沉浸式空间，你用虚拟身份社交、工作、娱乐、交易，虚实融合、永久在线、自主创造。
  • 学术定义：元宇宙是由物理世界、数字孪生世界、原生虚拟世界叠加而成的、可实时交互、永续演化、开放互联的数字社会生态。

二、核心特征（4大关键）

  1. 沉浸性（XR）：VR/AR/MR设备带来“身临其境”的感官体验。
  2. 永续性：虚拟世界24小时运行，数据永久保存、持续演化。
  3. 开放性与互操作性：跨平台互通，身份、资产可跨平台流动（如NFT）。
  4. 创作者经济：用户可自由创作内容并拥有数字资产所有权，实现“边玩边赚”。

三、六大技术支柱（缺一不可）

  1. XR（扩展现实）：VR（虚拟现实）、AR（增强现实）、MR（混合现实）——入口级硬件。
  2. 区块链+NFT：确权、交易、隐私保护，保障数字资产唯一与安全。
  3. 人工智能（AI/AIGC）：智能NPC、自动生成3D内容、虚拟人、空间感知。
  4. 数字孪生（Digital Twin）：现实世界1:1虚拟映射，用于工业、城市、医疗仿真。
  5. 高速网络（5G/6G）+云计算：低延迟、高并发、强算力，支撑大规模实时交互。
  6. 游戏引擎技术：Unity、Unreal——构建3D场景、物理渲染、实时交互的基础。

四、当前发展状态（2026年5月，最关键部分）

1. 整体阶段：从“泡沫”到“理性落地”

  • 行业共识：2021–2022 狂热期 → 2023–2025 泡沫破裂、资本撤退 → 2026 理性复苏、B端先行、技术深耕。
  • Gartner曲线：已跨过“炒作顶峰”，进入“低谷期+启蒙期”，离大规模普及仍需5–10年。

2. 市场规模（权威预测）

  • 全球：
    • 2025年：约 8790亿美元
    • 2026年：预计 1.5万亿美元，年增速约 35%
  • 中国：
    • 2025年：约 766亿元人民币
    • 2026年：预计 4500–5000亿元，增速超 28%

3. 巨头现状：收缩消费级，加码企业级

Meta（原Facebook）

  • 累计投入超 800亿美元，持续巨额亏损（Reality Labs部门）。
  • 2026年重大转折：关闭旗舰VR社交平台 Horizon Worlds，裁员千人，缩减VR预算 30%，重心转向AI+轻量AR眼镜。
  • 结论：C端元宇宙社交基本失败，转向B端与AI融合。

苹果（Apple）

  • 2024年发布 Vision Pro（MR头显，售价2.5万元），销量远低于预期，但被视为“空间计算”长期布局。
  • 策略：慢工出细活，不炒作“元宇宙”概念，主打“空间计算+企业办公+内容消费”。

中国企业

  • 字节（Pico）：2021年90亿收购Pico，2023年后大规模裁员、收缩VR硬件，转向行业应用。
  • 腾讯：XR团队裁员，暂停消费级VR，聚焦数字人、虚拟社交、游戏内元宇宙。
  • 工业元宇宙：中国最强项，数字孪生工厂、虚拟仿真、远程运维已大规模落地，2025年市场规模超170亿元。

4. 硬件现状：VR降温，AR/MR蓄力

  • VR头显：2024年全球出货量同比**-12%**，连续3年下滑，消费级市场遇冷。
  • AR眼镜：轻量化、低功耗、与AI结合（如Meta Ray-Ban、华为Vision Glass），2026年起加速渗透。
  • 痛点：眩晕、重量、续航、价格高、内容少。

5. 应用落地：B端（工业/政务/教育）> C端（游戏/社交）

✅ 已规模化落地

  • 工业元宇宙（最强）：数字孪生工厂、虚拟装配、远程运维、质量检测，降本增效30%+。
  • 数字人：直播带货、客服、新闻播报，2026年中国市场规模超500亿。
  • 文旅/会展：虚拟演唱会、数字博物馆、元宇宙展会（如进博会）。
  • 教育/培训：虚拟实验室、技能仿真（如手术、维修）。

⚠️ C端仍在试点

  • 游戏：Roblox、The Sandbox、Decentraland，用户增长放缓，活跃度低。
  • 社交：Meta Horizon倒闭，国内如百度希壤用户少、商业化难。

区块链

发表于 2026-05-01 更新于 2026-05-31 分类于 Blockchain 本文字数： 965 阅读时长 ≈ 3 分钟

一、定义

区块链（Blockchain） 是一种去中心化、分布式账本技术，把数据打包成“区块”，按时间顺序用密码学链接成“链”，全网节点共同维护、同步，实现不可篡改、全程可追溯、公开透明、多方共识。

  • 2008年由中本聪在比特币白皮书中首次提出，作为比特币的底层技术。
  • 通俗理解：全网共享、共同记账的公开透明大账本，无中心管理员。

区块链接结构



flowchart LR
  B1[区块 N-1 Hash] --> B2[区块 N 交易 Merkle]
  B2 --> B3[区块 N+1]
  B3 --> Net[全网节点共识]

二、核心特点

  • 去中心化：无中央服务器/权威机构，数据分散在全网节点，避免单点故障与篡改风险。
  • 不可篡改：每个区块含前一区块哈希值；改1块需重构后续所有块并控制全网51%以上算力，成本极高。
  • 公开透明：交易数据（除身份外）全网可见、可查、可验证。
  • 可追溯：每笔交易从创建到当前的完整链路可追踪审计。
  • 匿名性（伪匿名）：用户以公钥地址标识身份，交易公开但不直接关联真实身份。

三、工作原理（关键概念）

  1. 交易（Transaction）：一次账本状态变更（如转账、数据写入）。
  2. 区块（Block）：打包一段时间内的交易数据，含区块头（版本、前块哈希、Merkle根、时间戳等）+ 交易列表。
  3. 链（Chain）：区块按时间顺序通过哈希指针串联，形成链式结构。
  4. 共识机制：全网节点同步确认数据一致性的算法，常见：
    • PoW（工作量证明）：比特币，算力竞争记账，耗能高。
    • PoS（权益证明）：以太坊2.0，持币越多记账概率越大，节能。
    • DPoS（委托权益证明）：EOS，节点投票选代表记账，效率高。
  5. 密码学：
    • 哈希函数：任意长度数据→固定长度字符串；输入微变→输出巨变，用于校验数据完整性。
    • 非对称加密：公钥（公开，地址）+ 私钥（保密，签名），保障交易安全与身份验证。

四、区块链类型

  • 公有链：全网公开，任何人可参与（比特币、以太坊）。
  • 私有链：仅特定组织/节点参与，权限可控（企业内部数据管理）。
  • 联盟链：多个机构共同管理，半公开（供应链金融、跨境支付）。

五、核心应用场景

  • 加密货币：比特币、以太坊等，去中心化支付，降低跨境成本。
  • 供应链溯源：商品全流程上链，防伪造（如沃尔玛食品溯源）。
  • 金融服务（DeFi）：去中心化借贷、交易、保险，无中介。
  • 政务存证：身份认证、不动产登记、社保数据共享，防篡改、提效率。
  • 知识产权与NFT：数字艺术品、版权确权、元宇宙资产（如NFT）。
  • 医疗健康：病历加密共享、隐私保护、数据可信交换。

六、技术架构（六层模型）

从上到下：应用层 → 合约层 → 激励层 → 共识层 → 网络层 → 数据层。

七、优势与挑战

  • 优势：去中介降成本、防篡改保安全、透明可追溯、高可用（无单点故障）。
  • 挑战：交易吞吐量低（如比特币约7笔/秒）、能耗高（PoW）、隐私保护难、监管不完善、跨链互操作复杂。

八、总结

区块链是信任机器：用技术实现去中介的可信协作，重构金融、供应链、政务等领域的价值交换体系，是Web3.0、元宇宙、数字经济的核心基础设施。

一、C 语言是什么

C 语言由 Dennis Ritchie 在 1970 年代为 Unix 系统实现而设计，至今仍是操作系统内核、嵌入式、高性能库的事实标准之一。程序经编译器翻译成机器码再执行，不依赖虚拟机，因此执行路径清晰、开销可预期。

二、语言特点（为何仍值得学）

  • 贴近机器模型：整型与指针宽度、内存布局、调用约定都可由实现定义，便于写驱动、解释器底层、与汇编或硬件协同。
  • 表达力强、语法紧凑：少量关键字即可完成算法与数据结构；没有面向对象语法糖，但可用结构体 + 函数指针组织模块。
  • 可移植性：遵循 ISO C（如 C99、C11）的代码在多数平台用对应工具链即可重新编译；与平台相关的部分通常隔离在少量文件中。
  • 生态成熟：几乎所有系统提供 C 调用约定，其他语言常以 C ABI 为边界导出/导入库。

三、最小程序与翻译单元

每个可执行程序必须有一个 main 入口（宿主环境下常见两种签名之一）：

  • #include：预处理阶段把头文件文本插入当前翻译单元；<stdio.h> 等尖括号形式通常表示系统/实现提供的头。
  • return 0：向操作系统报告成功退出；省略时 C99 起对 main 有特殊规则（等价于返回 0），其他函数仍必须显式返回值（或 void）。

四、基本类型与字面量

4.1 整数与字符

  • char：至少 8 位，可表示字符（常与 unsigned char 用于字节）；signed char / unsigned char 与 char 是否带符号由实现定义。
  • short / int / long / long long：各有 signed / unsigned 变体；宽度随平台变化，可移植代码应使用 <stdint.h> 中的 int32_t、uint64_t 等定宽别名（若平台提供）。
  • 整数字面量：42（int）、42U（unsigned）、42L（long）、0x2A（十六进制）、052（八进制，易踩坑，少用）。

4.2 浮点

  • float / double / long double：遵循 IEEE 754 的实现上，double 最常用；不要用 == 比较浮点相等，应比较误差或使用整数域计算。

4.3 void 与派生类型

  • void：无值类型，用于「无返回值」或「通用指针」void *（可指向任意对象，不能直接解引用，需先转换）。

五、变量、作用域与存储期

  • 自动变量：块内 int x = 1;，进入块分配（概念上在栈帧），离开块结束生命期；未初始化则值不确定。
  • static（局部）：仍只在块内可见，但只初始化一次，生命期贯穿程序。
  • static（全局/函数）：内部链接，仅在当前翻译单元可见，避免符号冲突。
  • extern：声明在其他翻译单元定义的全局对象或函数。

六、运算符与控制流

6.1 常用运算符

  • 算术：+ - * / %；整数相除向零截断。
  • 关系与逻辑：< <= > >= == !=、&& || !；短路求值：a && b 中 a 为假则不计算 b。
  • 位运算：& | ^ ~ << >>；仅对无符号或明确语义时使用移位更安全。
  • 三元：cond ? a : b。
  • 复合赋值：+=、-= 等。

6.2 分支与循环

  • switch 的 case 通常需要 break，否则落入下一分支（fall-through），有时故意利用，多数情况要避免。

七、数组与指针

7.1 数组

  • 数组名在大多数表达式中会退化为指向首元素的指针，不携带长度信息；跨函数传递数组时常传指针 + 长度或使用哨兵（如字符串的 '\0'）。

7.2 指针

  • NULL：空指针常量；解引用空指针是未定义行为。
  • 指针算术：p + 1 按所指类型大小移动；仅对同一数组对象内或尾后一位置才有标准保证。

7.3 字符串

  • C 字符串是以 '\0' 结尾的 char 序列；字面量 "hi" 类型为 char 数组，在表达式中退化为 char *（C++ 中为 const char *）。
  • 常用 <string.h>：strlen、strcmp、strcpy（注意缓冲区溢出，优先 strncpy/snprintf 或自行边界检查）。

八、函数

  • 按值传递：形参是实参的副本；要通过函数修改调用方变量，传指针。
  • 原型：C99 起调用前必须可见原型，否则旧式隐式声明规则已移除，利于编译器检查实参个数与类型。
  • static 函数：仅本翻译单元可见。

九、结构体、联合体与枚举

9.1 结构体

  • 内存布局：可能有填充字节以满足对齐；不要假设 sizeof 等于各成员之和。
  • typedef 可为 struct 起别名，减少每次写 struct 关键字。

9.2 联合体与枚举

  • union：成员共享同一块存储，同一时刻通常只应语义上使用其中一个成员；写入与读取不同类型成员涉及有效类型规则，滥用为未定义行为。
  • enum：提供命名整型常量；底层仍为整数类型，不提供新类型安全边界。

十、动态内存

  • malloc / calloc / realloc / free：成对使用；双重 free、使用已 free 的指针均为未定义行为。
  • 谁分配谁释放：在模块边界约定清晰，避免交叉所有权。

十一、预处理与宏

  • #include / #define / #if 在编译前由预处理器处理；宏不做类型检查，复杂逻辑优先 static inline 函数 或枚举常量。

十二、与「安全可移植」相关的习惯

  • 显式 {} 包住 if/for 体，避免宏或维护时出错。
  • 比较时把常量放左侧：if (NULL == p) 可防止误写 =。
  • 整数运算注意溢出（有符号溢出为未定义行为）；必要时用更大宽度或检查范围。
  • 使用 -Wall -Wextra -Werror（在可接受时）与静态分析工具，尽早暴露问题。

IDE 体验 跳转、重构、补全更可靠
大型项目可维护 接口与类型即文档，跨团队协作成本更低
渐进式采用 allowJs、// @ts-check 可逐步迁移

与纯 JS：运行时行为一致；类型在 tsc 或 esbuild/swc 链路中被擦除。

  • 字面量类型：'GET' | 'POST'

四、tsconfig 要点

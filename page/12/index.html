发表于 2026-05-01 更新于 2026-09-01 分类于 FFmpeg 本文字数： 1.6k 阅读时长 ≈ 5 分钟

第三章：音视频编辑处理

概念基础

  1. 编辑操作多在「容器/时间」层：裁剪、截图、合并、抽取音轨，多数可 -c copy 不重编码，秒级完成；只有变速、加滤镜才需重编码。
  2. 时间精度取决于关键帧：-c copy 裁剪只能切在关键帧，可能比目标点晚几帧；要精确到帧需重编码或先对齐关键帧。
  3. 合并与拆分：同编码参数的多段用** concat 协议/滤镜**无损拼接；异构参数需重编码统一后再拼。
  4. GIF 是特殊输出：调色板优化是高质量 GIF 的关键，直接转 GIF 易有色带。
  5. 本章目标：覆盖日常编辑 90% 需求——裁剪、截图、GIF、提取/分离音轨、合并、变速、音量调整。

本章承接 第二章：编解码与转码，操作多可 -c copy，速度优先。

一、裁剪与切片

1. 按时间裁剪

  • -ss 在 -i 前：解封装快速跳转（推荐），可能不精确到帧。
  • -t：时长；-to：结束时间点。
  • -c copy：裁剪只能切在关键帧，开头可能略偏；要精确用重编码。

2. 等分切片

二、截图与序列帧

  • -frames:v 1：只输出 1 帧。
  • -vf "fps=N"：每秒 N 帧采样，用于连续截图/缩略图。

三、GIF 生成

直接转 GIF 易有色带，先生成调色板再引用是高质量做法：

  • fps=10：帧率（GIF 体积敏感，10–15 帧够用）。
  • scale=480:-1：宽度 480，高度按比例。
  • flags=lanczos：高质量缩放算法。
  • palettegen/paletteuse：生成与使用调色板，显著减少色带。

四、音频提取与分离

  • -vn：丢视频；-map 0:a:N：选第 N 路音轨（从 0 起）。
  • -c:a copy：原样抽出，不重编码（仅改封装）。

五、合并

1. concat 协议（同编码参数，无损最快）

-safe 0：允许 list.txt 用绝对路径或相对路径。

2. concat 滤镜（异构参数，需重编码）

n=2：段数；v=1:a=1：各段有 1 路视频 1 路音频。

3. 音视频合并（独立视频 + 独立音频）

-shortest：以最短流为准截断（防音频比视频长导致黑屏拖尾）。

六、变速

  • setpts=N*PTS：视频时间戳缩放，<1 加速、>1 慢放。
  • atempo=N：音频变速，范围 0.5–2.0；更大倍率需链式 atempo=2,atempo=2（4 倍）。

七、音量与静音处理

  • volume=N：线性增益，1.0 原音量。
  • loudnorm：EBU R128 响度归一化，适合多段混剪统一音量。

八、旋转与翻转

transpose：0=逆90、1=顺90、2=逆90+垂直翻转、3=顺90+垂直翻转。

九、常见陷阱

陷阱 说明
concat 协议参数不一 各段编码/分辨率/时间基不同会花屏或失败，需先用重编码统一
裁剪开头黑帧 -c copy 切在关键帧，开头可能有几帧偏差；精确需重编码
GIF 体积爆炸 不限帧率/尺寸 GIF 极大；用 fps+scale+调色板控制
变速没动音频 只 setpts 视频变速，音频仍原速，导致不同步；必须同步 atempo
合并音视频拖尾 音频比视频长，未加 -shortest 导致黑屏拖尾
截图无 -frames:v 1 不限制会输出该时间点后所有帧到文件序列
-map 选错流 多音轨源默认只取第一路；需用 -map 0:a:N 指定

要点 结论
裁剪 -ss+-t/-to，-ss 在 -i 前快速；-c copy 切关键帧，精确需重编码
截图 -frames:v 1 单帧；fps=N 连续截图
GIF 先 palettegen 再 paletteuse，配 fps+scale+lanczos 控体积质量
音频提取 -vn 丢视频；-map 0:a:N 选音轨；-c:a copy 原样抽
合并 同参数用 concat 协议（无损）；异构用 concat 滤镜（重编码）
音视频合 -map 选流 + -shortest 防拖尾
变速 setpts 视频变速 + atempo 音频变速必须同步
音量 volume=N 线性增益；loudnorm 统一响度

第六章：高级技巧与性能调优

概念基础

  1. 批量与自动化：生产环境很少单条命令手敲，更多是批处理转码、管道串联、监听目录——把 ffmpeg 嵌入脚本与流水线。
  2. 硬件加速链路：单独用硬件编码器只是冰山一角，真正的提速是 解码→缩放→编码全链路走 GPU，避免 CPU↔GPU 来回拷贝。
  3. 性能瓶颈在 I/O 与编码：磁盘读写、编码 preset、滤镜复杂度决定吞吐；调优先量化（-progress/time），再针对性优化。
  4. 质量度量要客观：肉眼判断不可靠，PSNR/SSIM/VMAF 给出客观分数，用于对比编码器与参数。
  5. 本章定位：把前五章零散的硬件、批处理、监控手段系统化，给出生产级调优清单与陷阱汇总，是 FFmpeg 进阶的收尾。

本章综合 第二章：编解码与转码 编解码与 第五章：流媒体与直播推流 流媒体，面向高吞吐生产场景。

一、硬件加速全链路

仅用 -c:v h264_nvenc 只加速编码，解码与缩放仍走 CPU，且数据要 CPU↔GPU 拷贝。全链路 GPU 才是最大化提速：

  • -hwaccel cuda：硬件解码。
  • -hwaccel_output_format cuda：解码后帧留在 GPU 显存，避免拷回 CPU。
  • scale_cuda：GPU 缩放滤镜（替代 scale）。
  • h264_nvenc：GPU 编码。

对应 Intel QSV：-hwaccel qsv -c:v h264_qsv -vf scale_qsv；Apple VideoToolbox 链路类似。

取舍：全链路 GPU 提速数倍，但滤镜生态不如 CPU 丰富（subtitles/drawtext 等多在 CPU），需在 GPU 滤镜前后用 hwdownload/hwupload 转换，复杂度上升。纯转码提速用全链路；复杂滤镜用 CPU 或混合。

二、管道串联与多路输出

1. 管道：一帧编码下一工具接手

pipe:1/pipe:0 用标准输入输出串联，适合把 ffmpeg 接入已有处理管线。

2. 一条命令多路输出

一次解码多次编码，比跑三条命令快（解码只做一遍）。

七、生产级调优清单

维度 调优项
编码速度 软编调 -preset（medium→fast）；硬编全链路 GPU
画质体积 -crf 选 18–23；2-pass 精控体积
I/O 源与输出分盘，避免磁盘带宽瓶颈；SSD 加速小文件
并行 软编并行度 ≤ CPU 核数；硬编监控 GPU 路数上限
内存 大文件 -analyzeduration/-probesize 限制探测；高分辨率留意帧缓冲
直播延迟 zerolatency + 小 GOP + nobuffer + flush_packets
监控 -progress 接脚本；speed < 1 即跟不上实时，直播会丢帧
质量验证 上线前用 PSNR/VMAF 对比，防画质回退

八、常见陷阱汇总

陷阱 说明
硬编画质差却不知 NVENC 默认参数偏弱，需 -preset p5+/-cq 调优，并用 VMAF 对比
GPU 显存泄漏 全链路 GPU 异常退出未释放显存，需监控 nvidia-smi
并行超 CPU 软编 -P 超核数反而争抢变慢
预设误用 归档用 ultrafast 导致体积翻倍；实时用 veryslow 跟不上
-c copy 改滤镜 任何滤镜都需重编码，copy 模式滤镜静默无效
批处理无 -y 输出已存在 ffmpeg 交互询问，脚本卡死；脚本必加 -y 或 -n
进度解析错 frame 是累计帧非实时；实时看 fps 与 speed
音频采样率不匹配 不同源混音/拼接前统一 -ar 44100，否则爆音或失败
10bit/HDR 降级 不加 -pix_fmt yuv420p 普通播放器黑屏或偏色

要点 结论
全链路 GPU -hwaccel cuda+scale_cuda+h264_nvenc，帧留显存免拷贝；复杂滤镜仍走 CPU
多路输出 一次解码多次编码，比多次命令快
批处理 shell 循环 + xargs -P/parallel -j 并行；脚本必加 -y
进度 -progress pipe:1 输出 key=value；speed<1 跟不上实时
质量度量 PSNR/SSIM/VMAF 客观对比，防画质回退
软硬字幕 软字幕 -c:s mov_text 可开关；硬字幕 subtitles 滤镜烧画面
调优 速度靠 preset/GPU，画质靠 crf/2-pass，I/O 靠分盘，监控靠 progress
陷阱 硬编需调参、并行勿超核、copy 不能加滤镜、批处理必 -y

第二章：GraphQL 服务端实战

概念基础

  1. Apollo Server 是标准起点：Schema-first（SDL 定义契约）+ Resolver-map（函数实现），一文件即可起服务，内置 Sandbox 调试。
  2. context 是请求级管道：认证信息、数据库连接、DataLoader 实例都在 context 里注入——Resolver 保持无状态。
  3. N+1 是 GraphQL 头号性能坑：每个字段的 Resolver 独立触发，一个列表查询可能打出 1+N 次数据库请求；DataLoader 用「批处理 + 请求级缓存」根治。
  4. 分页用 Relay Cursor 规范：(first, after) + pageInfo { hasNextPage endCursor }，比 offset 分页稳定且天然适配无限滚动。
  5. 防护三件套：查询深度/复杂度限制、@auth 指令或 context 校验做鉴权、错误信息脱敏（生产禁带 stackTrace）。

本章承接 第一章：GraphQL 入门与 Schema 设计 的 Schema 语法；代码按 Apollo Server 4 / graphql 16 / DataLoader 2.x 官方 API 书写（沙箱网络受限无法安装依赖，未逐条运行验证；语法可在本地 npm i 后复核）。

一、最小可运行服务

执行模型：Query 入口先解析，返回对象后每个嵌套字段再查 Resolver map——Post.author 这种「字段级解析」正是灵活性与 N+1 风险的共同来源。

二、DataLoader：根治 N+1

问题现场：posts { author { name } } 会先查 posts（1 次），再对每篇 post 查 author（N 次）。

DataLoader 两个机制：

机制 说明
批处理 同一 tick 内的多次 load() 合并成一次 batchUsers（1+N → 1+1）
请求级缓存 同一请求内相同 key 只查一次；必须每请求新建实例，否则跨用户脏缓存

四、分页：Relay Cursor 规范

cursor vs offset：offset 分页在插入新数据时会重复/漏掉记录，cursor（基于排序键）不受影响；无限滚动场景天然匹配 endCursor + after。

五、生产防护与运维

防护点 手段
恶意深查询 graphql-depth-limit / 复杂度计算（graphql-query-complexity）
超时 网关层 proxy_read_timeout + Resolver 内部超时（见 第二章：Nginx 反向代理与负载均衡）

第一章：GraphQL 入门与 Schema 设计

发表于 2026-05-01 更新于 2026-09-01 分类于 GraphQL 本文字数： 1.1k 阅读时长 ≈ 4 分钟

第一章：GraphQL 入门与 Schema 设计

概念基础

  1. API 查询语言：GraphQL 由 Facebook 开源，客户端在单一端点上按需声明「要哪些字段」，服务端精确返回同构数据，避免多余传输。
  2. Schema 即契约：用 SDL 强类型定义数据模型与入口（Query / Mutation / Subscription），前后端基于同一份 Schema 协作、文档自动生成。
  3. Resolver 解析数据：每个字段对应一个解析器函数，可对接数据库、微服务或第三方 API，天然适合多数据源聚合。
  4. 直击 REST 痛点：避免过度获取（over-fetching）与多次请求瀑布，弱网与移动端收益明显。
  5. 取舍清晰：HTTP 缓存不如 REST 天然、需要防「恶意深查询」；简单 CRUD 留在 REST，复杂关联与聚合才是 GraphQL 主场。

本章是 GraphQL 系列起点：Schema 设计与查询语法。服务端落地见 第二章：GraphQL 服务端实战。

  • Query：查询（读操作）入口
  • Mutation：变更（写操作）入口
  • Subscription：订阅（实时更新，基于 WebSocket）

二、与 REST 对比

维度 GraphQL REST
数据获取 客户端精准指定字段，无过度获取 固定返回结构，易冗余
请求次数 单一请求聚合多资源 多端点请求，易「请求瀑布」
版本控制 Schema 渐进演进，无需版本号 维护 v1/v2 多版本
文档 基于 Schema 自动生成（GraphiQL） 手动维护（Swagger 等）
实时能力 原生 Subscription（WebSocket） 轮询/SSE，成本高
缓存 依赖客户端实体缓存（Apollo） 天然适配 HTTP 缓存

结论：GraphQL 显著减少传输量与请求次数，弱网/移动端收益极大；REST 更简单、成熟、缓存友好。两者互补，按场景选择。

三、工作流程



flowchart LR
  Client[GraphQL Client] -->|单 POST /graphql| S[Schema 校验]
  S --> R[Resolver 执行]
  R --> DB[(多数据源)]
  R --> Client
  1. 定义 Schema：服务端用 SDL 定义类型、Query、Mutation。
  2. 实现 Resolver：每个字段对应解析器，对接数据源。
  3. 客户端请求：POST 单一端点（/graphql），携带 Query/Mutation。
  4. 服务端执行：校验 Query → 调用 Resolver → 按请求结构返回 JSON。
  5. 客户端接收：响应结构与 Query 完全一致，直接渲染。

四、适用场景

  • ✅ 复杂前端应用（电商、社交）：多数据关联、按需字段
  • ✅ 移动端/弱网环境：减少请求与数据体积
  • ✅ 微服务架构：统一网关聚合多服务数据
  • ✅ 实时功能（聊天、通知、看板）：Subscription 原生支持
  • ❌ 简单 CRUD 服务：REST 更轻量、易维护
  • ❌ 高缓存吞吐场景：REST 的 HTTP 缓存更高效

第四章：RocketMQ 核心概念与架构

发表于 2026-05-01 更新于 2026-09-01 分类于 MQ 本文字数： 1.5k 阅读时长 ≈ 5 分钟

第四章：RocketMQ 核心概念与架构

概念基础

Apache RocketMQ 是源自阿里巴巴电商场景的分布式消息中间件：低延迟、高并发、业务消息能力开箱即用。本文侧重 MQ / 微服务视角。

  1. 本质是「Topic + Queue」：消息按 Topic 分类，每个 Topic 切成多个 Message Queue（读写队列），Queue 是并行与顺序的基本单位——角色类似 Kafka 的 Partition，但围绕它的消费语义更「业务」。
  2. 为什么业务系统选它：延迟消息、事务消息、顺序消息、消费重试与死信队列都是内置能力，不必像 Kafka 那样自建重试 Topic / 延迟调度器。
  3. 三大角色：NameServer（无状态路由中心）、Broker（存储与转发）、Producer / Consumer。客户端先问 NameServer 拿路由，再直连 Broker 收发。
  4. 权衡：流式生态（Streams / Connect 类）不如 Kafka；但 Java 技术栈、国内云厂商与 Spring Cloud Alibaba 集成更顺。对照见本章「与 Kafka 的对照」小节。

先看整体架构：

架构组件



flowchart TB
  P[Producer] --> B[Broker Master]
  B --> NS[NameServer 路由]
  C[Consumer Group] --> B
  NS -.-> P
  NS -.-> C
组件 作用 要点
NameServer 路由注册中心，轻量、无状态 节点间互不通信，客户端轮询任一节点；几乎没有运维成本
Broker 存储与转发，分 Master / Slave 所有消息写入 CommitLog（单一文件顺序写），再异步分发到各 Queue 的索引
Producer 发送消息 与 Broker 直连发送；NameServer 只用于找地址
Consumer 拉取消息 Push 模式底层是长轮询拉取，并非服务端真推送

客户端通过 NameServer 发现 Broker 地址；Broker 每 30s 向 NameServer 上报路由，客户端在本地缓存路由表。

Topic 与 Queue

  • Topic：逻辑分类。
  • Message Queue：Topic 下分片（类似 Kafka 分区，语义略有不同）；Queue 数 = 消费并行度上限。
  • Tag / Key：Tag 用于消费端二级过滤；Key 建立哈希索引，供控制台按业务键查询。

理解要点：与 Kafka「分区数决定并行度」同理，Consumer 实例数超过 Queue 数时多出的实例空闲；规划 Topic 时先估消费并行度再定 Queue 数。

消费模型

模式 说明
CLUSTERING 同组负载均衡，一条消息只被一个实例消费
BROADCASTING 组内每实例全量接收
重试 / DLQ 消费失败进入重试队列（%RETRY%组名）延时重投，默认 16 次，超限进死信（%DLQ%组名）

理解要点：重试 + 死信是 RocketMQ 相对 Kafka 最大的「开箱能力差」——消费失败自动按递增间隔重试，业务只需监听死信 Topic 做人工兜底，不需要自建重试机制。

消息可靠性：刷盘与复制

维度 同步 异步
刷盘 SYNC_FLUSH：落盘才返回成功，不丢但延迟高 ASYNC_FLUSH：写入 page cache 即返回，宕机可能丢少量
复制 SYNC_MASTER：Slave 同步完成后返回 ASYNC_MASTER：默认，性能优先

生产常见组合：ASYNC_FLUSH + SYNC_MASTER（或 DLedger 自动主从切换）；金融级再上同步刷盘。这与 Kafka 的 acks=all + ISR 解决的是同一件事——「写成功」的定义。

顺序、延迟与事务

1. 顺序消息

同一 MessageQueue 内 FIFO；发送端按 orderId 等 sharding key 用 MessageQueueSelector 固定路由，消费端用 Orderly 监听器串行处理。代价：该 Queue 所在实例故障期间，对应分片的顺序消费会短暂阻塞。

2. 延迟消息

内置延迟级别（1s、5s、1m…2h 共 18 级），适合订单超时关闭、失败退避重试；5.x 起支持任意时间精度（基于时间轮）。

3. 事务消息

Half 消息 + 本地事务 + 回查：先发半消息（对消费者不可见）→ 执行本地事务 → 提交 / 回滚；Broker 对未决事务定时回查生产者。与 Seata 同步事务可对照选型（见 第一章：cloud 微服务工程架构总览与生产落地 当前 Feign + Seata 链路）。

第一章：Kafka 消息中间件入门：核心概念与架构

概念基础

Apache Kafka 是分布式事件流平台：高吞吐、持久化、可回放的分区日志，用于消息队列、日志管道、流式处理与数据集成。本文侧重 MQ / 微服务视角。

  1. 本质是「分区日志」：每条消息只是追加到分区末尾的日志记录，不消费即删除，消费只移动游标（offset）——所以消息可以被多组消费者反复回放，这是它与 RabbitMQ 这类「消费即删除」传统 MQ 最大的差别。
  2. 为什么快：磁盘顺序写 + page cache + 零拷贝 + 批量压缩，单机即可达到十万级 TPS 量级；吞吐是 Kafka 设计的第一目标。
  3. 三大角色：当消息队列（削峰、解耦）、当日志总线（各系统日志/埋点统一进 Kafka）、当流计算数据源（Flink/Spark 从 Kafka 读）。本站对应：微服务集成见 第十一章：Spring Cloud 集成 RocketMQ：异步消息与事件驱动扩展，大数据总线见 第三章：Kafka 大数据数据总线。
  4. 权衡：为吞吐放弃了部分「业务 MQ」能力（无内置延迟消息、事务消息偏流式），这些场景通常选 RocketMQ（见本章对照小节与 第四章：RocketMQ 核心概念与架构）。

先看它的整体架构：

生产消费架构



flowchart LR
  P[Producer] --> B[Broker]
  B --> Part[Topic 分区]
  Part --> C1[Consumer 实例 1]
  Part --> C2[Consumer 实例 2]
  C1 & C2 --> G[同一 Consumer Group]

核心概念

概念 说明
Topic 逻辑消息流名称
Partition Topic 的分片，有序日志；并行度与分区数相关
Offset 分区内每条消息的唯一递增序号
Producer 写入消息，可指定 key 做分区路由
Consumer Group 组内消费者分摊分区，同组不重复消费同一分区
Broker 存储与 Serving 分区的服务器进程

消息持久化在磁盘（顺序写 + page cache），可配置保留时间与大小。

理解要点：「分区内有序、分区间无序」——需要顺序的业务（同一订单的状态变更）必须用同一 key 路由到同一分区；并行度上限 = 分区数，消费者实例多于分区数时空闲。

生产者与消费者

1. 生产者

  • acks：0 / 1 / all 权衡延迟与持久性。
  • 幂等生产者：避免重试导致重复（下游仍可能需要业务去重）。
  • 事务：跨分区 exactly-once 与 Kafka Streams 场景。

2. 消费者

  • auto.offset.reset：earliest / latest。
  • 手动提交 offset：处理成功后再 commitSync / commitAsync。
  • 再均衡（Rebalance）：组成员变化时重新分配分区；消费逻辑应支持幂等。

3. 投递语义（需业务配合）

语义 说明
At most once 先提交 offset 再处理，可能丢
At least once 先处理再提交，可能重复
Exactly once 事务 + 幂等存储，成本高

分区、副本与 ISR

  • Leader / Follower：每个分区一个 Leader 负责读写，Follower 同步。
  • ISR（In-Sync Replicas）：与 Leader 差距在阈值内的副本；min.insync.replicas 与 acks=all 共同定义「写成功」。
  • 扩容：增加分区数不会重分布历史 key；规划分区数宜前置。

概念基础

  1. 缓存在网关层最划算：proxy_cache 让重复的后端响应停在 Nginx 本地磁盘/内存，QPS 高峰被削平，后端直接减负。

  4. 容量公式要心里有数：最大连接 ≈ worker_processes × worker_connections；长连接 keepalive 减少握手次数。

第三章：Nginx HTTPS 与安全

概念基础

  1. TLS 终结点：证书挂在 Nginx，客户端到 Nginx 走加密，Nginx 到后端走内网明文——证书申请、续期、算法升级集中在一处。
  2. 证书链要完整：浏览器校验的是「站点证书 → 中间证书 → 根证书」整条链，漏发中间证书是「本地 curl 通、用户浏览器报错」的常见根因。
  3. 301 比配置加密更重要：HTTP 全站 301 跳转 HTTPS，并配合 HSTS 头让浏览器后续强制走 TLS。
  4. 安全是分层的：TLS 之外，还有限流（limit_req）、访问控制（allow/deny、auth_basic）、安全响应头，每层挡一类攻击。
  5. 密码学背景看 OpenSSL：算法、密钥、证书格式等原理见 第一章：OpenSSL 命令行入门与常用操作总览，本章聚焦落地。

本章 openssl 自签命令已在 OpenSSL 3.x 验证；nginx 配置基于官方语法书写（沙箱未装 nginx）。

四、限流：limit_req 与 limit_conn

参数 含义
rate=10r/s 平均速率（也可 30r/m）
burst=20 允许突发排队 20 个请求
nodelay 突发请求立刻处理不排队（超 burst 即 503）

打点验证：被限流的请求会写 error.log（limiting requests, excess: ...），状态码默认 503，可用 limit_req_status 429; 改成更语义化的 429。

五、安全响应头

要点 结论

第二章：Nginx 反向代理与负载均衡

概念基础

  1. 反向代理是系统入口：客户端只认识 Nginx，真实后端（Spring Boot/Node/Go）藏在 upstream 里——发布、扩缩容、灰度都对客户端无感。
  2. upstream 是逻辑集群：多个后端实例组成一个名字，proxy_pass http://集群名 即完成负载均衡；默认轮询，还有权重、ip_hash、least_conn。
  3. 转发要补头：后端想拿到真实 IP、真实协议，必须配 X-Real-IP、X-Forwarded-For、X-Forwarded-Proto——漏配是日志全是 127.0.0.1 的元凶。
  4. proxy_pass 末尾斜杠有语义：带 / 会替换 location 前缀，不带则原样拼接——路径多一层/少一层的事故九成出在这。
  5. 连接也要调参：proxy_http_version 1.1 + keepalive 复用连接，超时/缓冲/大文件上传各有专属参数。

本章承接 第一章：Nginx 入门与静态服务 的 location 语法，配置基于 nginx 1.24+ 官方语法书写（沙箱未装 nginx，未逐条运行验证）。

一、最小反向代理

头 作用
Host 透传原域名，后端按域名路由/生成绝对链接
X-Real-IP 客户端真实 IP（单层代理）
X-Forwarded-For 代理链 IP 列表，$proxy_add_x_forwarded_for 自动追加
X-Forwarded-Proto 客户端是 http 还是 https（后端生成 https 链接必需）

二、proxy_pass 路径规则（高频坑）

记忆法：proxy_pass 的 URL 部分会替换掉 location 匹配的部分；不带路径（只有 host:port）则原样透传。改一条 proxy_pass 必跑 nginx -t + 抓包/日志确认后端实际收到的路径。

三、upstream 与负载均衡策略

策略对比：

策略 写法 适用
轮询（默认） 无参数 无状态服务
加权轮询 weight=n 机器配置不均
ip_hash ip_hash; 会话粘性（同 IP 固定打同实例）
least_conn least_conn; 请求耗时不均，优先打空闲实例

故障摘除：后端挂掉 Nginx 自动重试下一个（proxy_next_upstream），配合 max_fails=3 fail_timeout=30s 控制判定阈值。

四、超时、缓冲与大文件

SSE/流式响应必须关缓冲：proxy_buffering off;（或后端发 X-Accel-Buffering: no），否则事件被攒着不吐。

Java动态数据源

发表于 2026-05-04 分类于 Java 本文字数： 897 阅读时长 ≈ 3 分钟

简介

多数据源常见于：主从读写分离、按库分业务、迁移期新旧库并存等。Baomidou 的 dynamic-datasource 在 Spring Boot 下用统一抽象管理多个 DataSource，通过注解或上下文切换当前线程使用的数据源，对 MyBatis-Plus、MyBatis、Spring Data JDBC、JdbcTemplate 等常见访问方式都适用。

下文以 Spring Boot 4、MyBatis-Plus 3.5.x 与 dynamic-datasource 4.x 为例（Boot 3 请改用 dynamic-datasource-spring-boot3-starter、mybatis-plus-spring-boot3-starter 坐标）。

添加依赖

说明：

  • 切面：@DS 依赖 AOP，此处使用 spring-boot-starter-aspectj（与当前工程一致）。
  • MyBatis-Plus：与 Boot 4 配套使用 mybatis-plus-spring-boot4-starter；Boot 3 使用 mybatis-plus-spring-boot3-starter。具体版本与 MyBatis-Plus 安装说明 及 JDK 要求一致即可。
  • 版本：其余坐标与 Spring Boot、JDK 对齐，以 Maven Central 上各 artifact 说明为准。

Spring Boot 配置

要点：

  • primary：未加 @DS 时默认使用的数据源逻辑名，需与 datasource 下某一键一致。
  • 逻辑名：mysql、pgsql 等为自定义别名，在 @DS("pgsql") 等处引用。

使用 @DS 切换数据源

在 类 或 方法 上使用 @DS("逻辑名")；方法级优先于类级。

Controller 上也可标注，但更推荐标在 Service 或 Mapper 层，避免 Web 层与持久化策略绑死。

编程式切换

需要按参数、分支在运行时决定库时，可使用上下文（用完建议清理，避免线程池复用线程时串库）：

与 @DS 混用时，以官方文档当前版本行为为准；同一调用链内尽量只采用一种风格，降低心智负担。

事务与边界情况

  • 同一事务内：已进入 @Transactional 且已绑定连接后，再切换数据源通常不会按预期切到新库（连接已固定）。多数据源写操作应拆到不同事务方法，或调整事务边界，使切换发生在开启事务之前。
  • 只读事务：若使用 @Transactional(readOnly = true)，仍要注意连接从哪个数据源取得，与 @DS 所在方法的事务传播一致。
  • 自调用：同类内 this.method() 不会经过 Spring 代理，@DS 可能不生效，应抽到另一个 Bean 或通过代理调用。

与 MyBatis-Plus / MyBatis 的配合

引入 MyBatis-Plus 后，SqlSessionFactory 仍使用 Spring 容器中的动态 DataSource，与 dynamic-datasource 无额外冲突。Mapper（含继承 BaseMapper 的接口）或 XML 无需单独为多数据源改一套配置即可随当前线程数据源路由；若某几个 Mapper 固定走副库，可在 Mapper 接口上加 @DS("pgsql")。

常见问题

现象 可能原因
始终走 primary 未走到带 @DS 的代理方法；或自调用绕过代理
切换无效 已在事务中取连接；或 push 后未 poll 导致线程本地状态错乱
启动报错找不到驱动 driver-class-name 与 runtimeOnly 驱动依赖不一致
Boot 版本不匹配 Boot 4 用 spring-boot4-starter，Boot 3 用 spring-boot3-starter

更细的读写分离、分片与 Seata 等组合方案见 Baomidou 动态数据源文档。

Redis Geospatial 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 411 阅读时长 ≈ 1 分钟

Redis 3.2+ 提供 GEO 相关命令：底层用 Sorted Set 存储经编码的坐标，对外提供距离计算、半径查询、哈希等能力。适合「附近的人 / 门店」等 LBS。

一、Geospatial 是什么

  1. 数据仍落在 ZSet 上：TYPE key 一般为 zset；member 为地点 ID，score 为 Geohash 编码（使用者通常只调 GEO 命令）。
  2. 坐标使用经度、纬度（GEOADD 参数顺序为 lon lat，勿写反）。
  3. 地球模型为球面近似，极高精度场景需自行评估误差。

二、常用命令

命令 作用
GEOADD key lon lat member 添加或更新坐标
GEODIST key m1 m2 [单位] 两点距离；单位 m / km / ft / mi
GEORADIUS / GEORADIUSBYMEMBER 以坐标点 / 已知成员为中心，半径内成员（新版本有 GEOSEARCH，以文档为准）
GEOPOS / GEOHASH 取坐标 / Geohash 字符串

三、典型应用场景

  1. 附近门店：GEOADD shops …，用户定位后 GEORADIUS。
  2. 配送范围校验：GEODIST 与阈值比较。
  3. 与外部地图：Redis 做粗筛，精确路径导航交给地图 API。

四、综合案例（redis-cli）

五、注意事项

  1. 经度纬度顺序：lon 在前 lat 在后。
  2. 跨版本 API：Redis 6.2+ 引入 GEOSEARCH 等，生产以当前版本文档为准。
  3. 数据量：全国级 POI 全进一个 key 可能过大，可按城市分片多个 GEO key。

Redis Bitmap 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 474 阅读时长 ≈ 2 分钟

Bitmap 不是独立「类型名」出现在 TYPE 里：底层仍是 String，通过 SETBIT / GETBIT 把值当作位数组操作（偏移上限很大，实际受配置 proto-max-bulk-len 与内存约束）。适合签到、日活标记、布隆过滤器的底层等。

一、Bitmap 是什么

  1. 按位偏移读写 0/1，可 BITCOUNT 统计 1 的个数，BITOP AND/OR/XOR/NOT 做位运算。
  2. 省空间：大量布尔标记时比「每个用户一个 String key」更紧凑（仍要算总内存）。
  3. offset 从 0 开始；未设置位视为 0。

二、常用命令

命令 作用
SETBIT key offset value value 为 0 或 1
GETBIT key offset 读某一位
BITCOUNT key [start end] 统计 1 的个数（字节区间可选）
BITOP operation destkey key [key ...] 多 key 位运算写入 dest
BITPOS 找第一个 0/1 的位置

三、典型应用场景

  1. 签到：sign:2026:05:user:1001 用日期映射 offset（需统一映射规则防冲突）。
  2. 日活标记：dau:2026-05-03 下 offset = 用户整型 ID（ID 空间稀疏时浪费内存，要评估）。
  3. 与 HyperLogLog：Bitmap 偏「谁来了」的位图；UV 近似可用 HLL。

四、综合案例（redis-cli）

五、注意事项

  1. 稀疏 ID：用户 ID 为 十亿级 时，SETBIT dau 1000000000 1 会促使底层分配很长空间，可能极度浪费；需分桶（按用户段拆 key）或换结构。
  2. TTL：位图也是 String，可 EXPIRE。
  3. 统计口径：BITCOUNT 是「1 的个数」，业务上对应「签到天数」等要先设计好 offset 含义。

Redis HyperLogLog 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 396 阅读时长 ≈ 1 分钟

HyperLogLog（HLL） 是 Redis 2.8.9+ 提供的概率型数据结构：用固定约 12KB（标准实现）内存估算集合基数（不重复元素个数），结果有误差（标准误差约 0.81%），换极低内存统计 UV。部署见 Redis-Docker.md。

一、HyperLogLog 是什么

  1. 不是存明细，只支持 PFADD 添加元素、PFCOUNT 估算基数、PFMERGE 合并多个 HLL。
  2. 适合：海量 UV、IP 去重计数等允许近似的报表。
  3. 不适合：必须精确计数、需要枚举曾出现过的元素。

二、常用命令

命令 作用
PFADD key element [element ...] 向 HLL 增加元素（可批量）
PFCOUNT key [key ...] 单个或合并估算基数
PFMERGE destkey sourcekey [sourcekey ...] 合并到 dest

三、典型应用场景

  1. 页面 / 活动 UV：PFADD uv:2026-05-03:page1 <userId 或 sessionId>，定时 PFCOUNT。
  2. 多维度合并：按天分 key，日报用 PFMERGE 聚合成周 UV。

四、综合案例（redis-cli）

五、注意事项

  1. 误差：报表若要求精确 UV，需 Set（内存大）或离线数仓。
  2. 元素语义：PFADD 把参数当字节串；业务上应用统一 ID（如用户 ID），勿混多种粒度。
  3. 无法查询成员：不能问「谁访问过」，只能问「大约多少人」。

Redis ZSet（Sorted Set）数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 414 阅读时长 ≈ 1 分钟

Redis ZSet（Sorted Set） 是成员唯一、且每个成员带一个 score（双精度浮点） 的有序集合；按 score 排序，score 相同则按字典序排成员。适合排行榜、延时队列（score=时间戳）等。Set数据类型、应用场景及案例.md；部署 Redis-Docker.md。

一、ZSet 是什么

  1. TYPE key 为 zset。
  2. member 唯一；同一 member 再次 ZADD 会更新 score。
  3. 范围查询、排名 ZRANK/ZREVRANK 为高频 API。

二、常用命令（必会子集）

命令 作用
ZADD key score member 添加或更新分值
ZRANGE / ZREVRANGE 按排名升/降序取片段（WITHSCORES 带出分数）
ZRANGEBYSCORE 按 score 区间取
ZRANK / ZREVRANK 升序 / 降序名次（0 基）
ZSCORE / ZCARD / ZINCRBY 查分 / 成员数 / 原子加分
ZREM / ZPOPMIN / ZPOPMAX 删除成员 / 弹出最小/大

三、典型应用场景

  1. 游戏 / 活动排行榜：member=用户 ID，score=积分。
  2. 延时任务：score=执行时间戳，定时 ZRANGEBYSCORE 拉到期任务再 ZREM。
  3. 热搜权重：结合时间衰减可周期性重算 score（逻辑在应用层）。

四、综合案例（redis-cli）

五、注意事项

  1. 热 key：单排行榜 key 超高并发时考虑分片或本地缓存 + 合并。
  2. 大 ZSet：避免一次 ZRANGE 0 -1；分页用 ZRANGE 窗口。
  3. score 精度：浮点比较注意误差；时间戳建议统一毫秒或秒。

Redis Hash 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 470 阅读时长 ≈ 2 分钟

Redis Hash 是一个 field → value 的映射表，适合表示「一个对象的多属性」：可对单个字段读写，避免整颗 String JSON 反复序列化/反序列化。下文按「命令 → 场景 → redis-cli 案例 → 注意点」组织,部署见 Redis-Docker.md。

一、Hash 是什么

  1. 一个 key 下挂多对 field / value，field 与 value 均为字符串（二进制安全）。
  2. TYPE key 显示 hash。
  3. 适合「用户资料、购物车行、配置项分组」等属性较多且常单独更新的场景。

二、常用命令（必会子集）

命令 作用
HSET key field value [field value …] 设置一个或多个字段（Redis 4.0+ 推荐 HSET 多字段；旧 HMSET 已废弃）
HGET / HMGET / HGETALL 读单字段 / 多字段 / 全表
HDEL 删字段
HEXISTS / HLEN 字段是否存在 / 字段个数
HINCRBY / HINCRBYFLOAT 字段数值原子增减
HSCAN 大 Hash 迭代遍历（生产避免 HGETALL 撑爆网络）

三、典型应用场景

  1. 用户资料：user:1001 下 name / vip / city 等，改一项只动一个 field。
  2. 购物车行：cart:uid:1001 下 sku:2001 → 数量 JSON 或纯数字。
  3. 对象缓存：比整串 String 更易做局部更新；仍要注意过期策略与缓存一致性。

四、综合案例（redis-cli）

五、注意事项

  1. 大 Hash：字段极多时 HGETALL 成本高，列表页用 HSCAN 或只取需要的 HMGET。
  2. 小 Hash 编码：字段少且短时可能 ziplist 等紧凑编码，内存更省（OBJECT ENCODING 可观察）。
  3. 与 String JSON 选型：读多写少、整体替换频繁 → String；字段独立更新多 → Hash。

Redis Set 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 396 阅读时长 ≈ 1 分钟

Redis Set 是无序字符串集合，成员唯一（再次 SADD 同一成员不会重复插入）。适合标签、去重集合、交并差集合运算等。姊妹文：ZSet数据类型、应用场景及案例.md（需分值排序时用 ZSet）；部署 Redis-Docker.md。

一、Set 是什么

  1. TYPE key 为 set。
  2. 不保证顺序（遍历顺序实现依赖，勿当有序结构用）。
  3. 成员即字符串；集合间可做 SINTER / SUNION / SDIFF。

二、常用命令（必会子集）

命令 作用
SADD / SREM 增删成员
SMEMBERS 返回全部成员（大集合慎用）
SISMEMBER / SCARD 是否在集合 / 成员个数
SRANDMEMBER / SPOP 随机读 / 随机弹出
SINTER / SUNION / SDIFF 交 / 并 / 差（可带 STORE 写到新 key）

三、典型应用场景

  1. 标签：SADD article:7:tags Java Redis。
  2. 抽奖池 / 去重 ID 池：SPOP 不放回抽样（需理解并发下多个客户端抢 SPOP 的语义）。
  3. 共同关注：SINTER user:1:following user:2:following。

四、综合案例（redis-cli）

五、注意事项

  1. 大 Set：SMEMBERS 一次性拉全量可能阻塞与占带宽，用 SSCAN 迭代。
  2. 与 List：Set 无序且唯一；List 有序可重复。
  3. 需要按分数排序（排行榜）→ 用 ZSet，不要用 Set 硬撑。

Redis List 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 484 阅读时长 ≈ 2 分钟

Redis List 是双向链表上的字符串元素序列，按下标与范围访问，两端 LPUSH / RPUSH / LPOP / RPOP 时间复杂度多为 O(1)。适合队列、栈、最新 N 条动态等场景。写法对齐同仓库 Hexo 教程：小节 + 命令表 + 可复制示例。部署见 Redis-Docker.md。

一、List 是什么

  1. 有序、可重复；同一 value 可出现多次。
  2. TYPE key 为 list。
  3. 中间插入/删除代价高于两端（需遍历指针）；设计时尽量从两头消费。

二、常用命令（必会子集）

命令 作用
LPUSH / RPUSH 左/右入队
LPOP / RPOP 左/右出队
LRANGE key start stop 闭区间下标范围（-1 表末尾）
LLEN 长度
LINDEX / LSET 按下标读 / 写
BLPOP / BRPOP 阻塞出队（简单队列常用）

说明：高版本提供 LMOVE / BLMOVE 等，用于安全队列迁移元素；与已废弃的 BRPOPLPUSH 同类需求可查当前版本文档。

三、典型应用场景

  1. FIFO 队列：RPUSH + LPOP（或反向一对）。
  2. 最新消息流：LPUSH + LTRIM key 0 99 保留最近 100 条。
  3. 阻塞消费：BLPOP 多个 key 时按顺序等待，可做简单任务队列（复杂语义建议 Stream 或专业消息中间件）。

四、综合案例（redis-cli）

五、注意事项

  1. 消费者崩溃：LPOP 后数据即丢，需业务确认机制或改用 BRPOP + 处理完再 ack` 等模式；严肃场景评估 Stream、RabbitMQ 等。
  2. 长列表：LRANGE 0 -1 大列表慎用；分页用 LRANGE 分段。
  3. 与 Set/ZSet 区别：List 有序可重复；Set 无序唯一；ZSet 有序唯一带分值。

第十五章：USB 总线：拓扑、描述符与 CDC 虚拟串口

发表于 2026-05-01 更新于 2026-08-30 分类于 Embedded 本文字数： 630 阅读时长 ≈ 2 分钟

第十五章：USB 总线：拓扑、描述符与 CDC 虚拟串口

概念基础：USB 是什么

  1. USB（Universal Serial Bus，通用串行总线）是 主机中心（Host-centric） 的有线总线：所有事务都由 Host 发起，Device 只能被动响应——与 CAN 的多主对等、LIN 的主从调度都不相同。
  2. 树形寻址：Host 经 Root Hub → Hub 树形扩展挂载设备，靠枚举过程为每个设备分配唯一地址，再读描述符获知它是谁、能做什么。
  3. 描述符即自描述：设备描述符 → 配置 → 接口 → 端点层层描述，插入即枚举，无需跳线或硬编码地址——「即插即用」的机制本质。
  4. 速度分级演进：Low/Full/High Speed（1.5M/12M/480 Mbps）→ USB 3.x（5 Gbps+）→ USB4；MCU 侧 Full Speed 12 Mbps 仍最常见。
  5. 定位：PC 与外设的标准互联；嵌入式里最常见的玩法是 CDC 虚拟串口与 HID，Type-C 时代还要关注 PD 供电协商与 Alt Mode。

主机-设备树形拓扑：

主机–设备拓扑



flowchart LR
  Host[USB Host PC] --> Hub[Hub 可选]
  Hub --> Dev1[Device 键鼠]
  Hub --> Dev2[Device CDC 串口]

一、拓扑

  • Host 发起事务；Device 响应。
  • OTG 设备可切换 Host/Device（手机接 U 盘）。

二、速度等级

版本 速率（量级）
USB 2.0 HS 480 Mbps
USB 3.x 5 Gbps+
USB4 基于 Thunderbolt 生态

Full Speed 12 Mbps 仍常见于 MCU Device。

三、描述符与 Class

  • 设备描述符 → 配置 → 接口 → 端点。
  • Class：HID（键鼠）、MSC（U 盘）、CDC-ACM（虚拟 第四章：UART）、Audio、Video 等。
  • Vendor Specific：自定义 Bulk/Interrupt 端点 + 主机驱动/libusb。

四、CDC 虚拟串口

MCU 通过 USB CDC ACM 暴露 /dev/ttyACM0（Linux）或 COM 口（Windows），应用层与 UART 类似发字节，物理层是 USB 包。

与 第五章：RS232：USB 转串口 芯片（CH340、CP2102、FT232）内部即 UART ↔ USB 桥接。

五、嵌入式开发要点

  • STM32 USB Device Library、TinyUSB、ESP32-S2/S3 USB OTG。
  • 枚举失败：检查 D+/D-、1.5k 上拉（Full Speed Device）、供电与描述符。
  • USB 3 / Type-C：PD 协商、Alt Mode（DP/Thunderbolt）另论。

规范：https://www.usb.org/documents

本章小结

要点 结论
拓扑 Host 中心 + Hub 树形扩展，事务全部由 Host 发起
即插即用 枚举分配地址 + 分层描述符自描述
复用机制 Class 驱动标准化（HID/MSC/CDC 等），免装驱动
嵌入式常用 CDC 虚拟串口、HID；协议栈可上 TinyUSB
排障要点 枚举失败先查 D+/D-、1.5k 上拉、供电与描述符

第十四章：NFC 近场通信：工作模式与 NDEF

发表于 2026-05-01 更新于 2026-08-30 分类于 Embedded 本文字数： 665 阅读时长 ≈ 2 分钟

第十四章：NFC 近场通信：工作模式与 NDEF

概念基础：NFC 是什么

  1. NFC（Near Field Communication，近场通信）工作在 13.56MHz，通信距离仅几厘米——「近」是刻意设计：贴一下才触发，天然防误触，适合支付与门禁。
  2. 有源与无源：Reader 产生射频场并为 passive Tag 供电（无源卡没有电池，靠感应取电通信），这是它与蓝牙等「双方都要电池」技术最本质的差别。
  3. 三种工作模式：读卡/写卡（碰 Tag）、卡模拟（手机变门禁卡/交通卡）、点对点（两设备交换小数据，已较少用）。
  4. NDEF 是通用数据格式：把 URI、文本、Wi-Fi 配置、蓝牙配对信息统一封装进 Tag，手机一碰即触发对应系统动作。
  5. 定位：身份识别、小额支付、设备配对加速器（给 BLE 递密钥）；大数据传输交给 Wi-Fi/蓝牙，NFC 只负责「握手」。

最典型的读卡交互：

读卡模式交互



sequenceDiagram
  participant R as NFC Reader 手机
  participant T as NFC Tag 卡
  R->>T: 射频场供电 + 轮询
  T-->>R: NDEF URL / 文本

一、工作模式

模式 说明
Reader/Writer 读或写 passive Tag
Card Emulation 手机模拟门禁/交通卡
Peer-to-Peer 两设备交换小数据（较少用）

二、Tag 标准

  • Type 1~4 Tag：不同容量与协议（NFC Forum）。
  • MIFARE Classic/Ultralight：交通、门禁（Classic 安全性已弱，新项目慎用）。
  • ISO 14443 A/B、ISO 15693（稍远，仍近场）。

三、NDEF（NFC Data Exchange Format）

常用 payload 格式，可封装：

  • URI（打开网页）
  • 文本
  • Wi-Fi 配置（WSC）
  • Bluetooth LE 配对 OOB 数据

手机贴近 Tag 即可触发系统动作（依 OS 策略）。

四、与其它接口

  • 第十三章：Bluetooth 与 BLE：GATT 模型与低功耗设计：NFC 传递配对密钥，BLE 传大数据。
  • 第十五章：USB 总线：拓扑、描述符与 CDC 虚拟串口：PC 用 USB NFC 读卡器 开发调试。
  • 支付：EMVCo、HCE（Host Card Emulation）在 SE/TEE 中存密钥。

五、开发

  • Android：NfcAdapter、enableReaderMode。
  • MCU：PN532、MFRC522（SPI/第七章：I2C）+ 天线设计。
  • 安全：Tag 可只读；支付与门禁依赖芯片级密钥，勿明文存敏感数据于可写 Tag。

本章小结

要点 结论
物理层 13.56MHz、几厘米近场，Reader 射频场为无源 Tag 供电
工作模式 读卡/写卡、卡模拟、点对点三类
数据格式 NDEF 统一封装 URI/文本/Wi-Fi/蓝牙配对数据
典型组合 NFC 递密钥加速 BLE 配对，大数据走 BLE/Wi-Fi
安全边界 Tag 勿存明文敏感数据，支付依赖 SE/TEE 芯片级密钥

第十三章：Bluetooth 与 BLE：GATT 模型与低功耗设计

发表于 2026-05-01 更新于 2026-08-30 分类于 Embedded 本文字数： 671 阅读时长 ≈ 2 分钟

第十三章：Bluetooth 与 BLE：GATT 模型与低功耗设计

概念基础：Bluetooth 是什么

  1. Bluetooth（蓝牙）工作在 2.4GHz ISM 频段，是短距离无线技术；今天物联网的主角是 BLE（Bluetooth Low Energy，蓝牙低功耗，4.0 起），为纽扣电池供电的小设备而生。
  2. BLE 的核心是 GATT：设备暴露服务（Service）→ 特征值（Characteristic）的属性树，手机等 Central 通过读写/订阅特征值与 Peripheral 交互，数据模型像访问资源一样清晰。
  3. 广播先行：BLE 设备平时广播（可携带自定义数据，即 Beacon），Central 扫描后再发起连接——不连不上、先广播，这与 Wi-Fi「先关联再通信」完全不同。
  4. 为什么省电：深度休眠 + 快速建立连接，只在事件发生时短暂收发；配合 Notify/Indicate 让外设主动推送，避免轮询空耗电。
  5. 定位：手环、传感器、智能家居直连手机的场景；需要跨厂商标准化互操作时选 Zigbee（见 第十六章：Zigbee：基于 802.15.4 的 Mesh 组网），配对加速可用 NFC 递密钥。

BLE 连接后的 GATT 数据模型：

BLE GATT 模型



flowchart TB
  Central[Central 手机] -->|连接| Peripheral[Peripheral 设备]
  Peripheral --> Svc[Service UUID]
  Svc --> Char[Characteristic 读写 Notify]

一、BLE 角色

角色 说明
Central 发起连接，如手机、网关
Peripheral 广播、被连接，如手环、温湿度计
Broadcaster / Observer 仅广播/扫描（Beacon）

连接后通过 ATT/GATT 读写特征值（Characteristic）。

二、GATT 模型

  • UUID：16 位标准 UUID 或 128 位自定义。
  • Notify/Indicate：外设主动推送数据，省 polling 功耗。

三、配对与安全

  • Just Works / Passkey / OOB 等配对模式。
  • LE Secure Connections（ECDH）防中间人。
  • 与 第十四章：NFC 近场通信：工作模式与 NDEF tap-to-pair：NFC 交换临时信息辅助 BLE 配对。

四、经典蓝牙 vs BLE

经典 BLE
功耗 较高 极低
吞吐 音频、SPP 串口 小数据、传感器
协议 RFCOMM、A2DP 等 GATT

音频耳机等多用 经典 + BLE 双模芯片。

五、开发工具

  • nRF Connect（手机抓包 GATT）。
  • 芯片：Nordic nRF、ESP32（Bluedroid/NimBLE）、TI CC2340。
  • 与 第十五章：USB 总线：拓扑、描述符与 CDC 虚拟串口：BLE dongle 常通过 USB 接 PC；逻辑仍是无线 GATT。

官方：https://www.bluetooth.com/specifications/

本章小结

要点 结论
角色 Central 发起连接、Peripheral 广播被连，另有纯广播 Beacon
数据模型 GATT：Service → Characteristic → Value/Descriptor
交互方式 读写特征值 + Notify/Indicate 主动推送，省轮询功耗
安全 Just Works/Passkey/OOB 配对，LE Secure Connections 防 MITM
选型 小数据直连手机选 BLE，跨厂商互操作选 Zigbee

第十二章：LoRaWAN：远距离低功耗星型组网

发表于 2026-05-01 更新于 2026-08-30 分类于 Embedded 本文字数： 749 阅读时长 ≈ 2 分钟

第十二章：LoRaWAN：远距离低功耗星型组网

概念基础：LoRaWAN 是什么

  1. LoRaWAN 是构建在 LoRa 扩频射频之上的开放网络协议：终端节点通过网关接入 Network Server，典型覆盖公里级，专为电池供电、小数据量、上报为主的物联网场景设计。
  2. LoRa ≠ LoRaWAN：LoRa 是 Semtech 的物理层调制技术（Chirp Spread Spectrum，灵敏度高、抗干扰强）；LoRaWAN 是其上的 MAC 层协议（入网激活、速率自适应、双向调度）——「电台」与「通信规约」的关系。
  3. 星型拓扑换功耗：节点只与网关直连一跳，不做 mesh 路由转发，省去中继耗电，换来数年电池寿命；覆盖靠增加网关与 ADR 速率自适应来平衡。
  4. 速率换距离：SF（扩频因子）越大，速率越低、传得越远，网络侧按链路质量动态调整，本质是「速率-距离-容量」的三角权衡。
  5. 定位：智能抄表、资产追踪、农业监测等公里级、极低速率场景；高吞吐走 Wi-Fi/以太网 + MQTT/HTTP，局域 mesh 则选 Zigbee / 蓝牙 Mesh。

先看整体架构：

星型拓扑架构



flowchart TB
  Dev1[终端节点] --> GW[LoRa 网关]
  Dev2[终端节点] --> GW
  GW --> NS[Network Server]
  NS --> App[应用服务器]

一、架构

  • Gateway：只做射频转发，不解密应用 payload（取决于模式）。
  • ADR（Adaptive Data Rate）：网络侧调节 SF/功率平衡距离与容量。

二、区域参数

区域 典型频段
EU868 863–870 MHz
US915 902–928 MHz
CN470 470–510 MHz

需遵守当地无线电法规；模块需合规认证。

三、设备 Class

Class 下行窗口 功耗
A 仅上行后两个短窗口 最低，传感器常用
B 附加信标窗口 中
C 几乎常开接收 高，供电设备

四、安全

  • Join：OTAA（Over-The-Air Activation，推荐）或 ABP（预置密钥）。
  • AES-128：NwkSKey、AppSKey 分层加密与完整性。
  • 应用层仍可封装 第十一章：CoAP：REST over UDP 的物联网应用协议 或自定义二进制。

五、与其它物联网协议

  • 长距离、低带宽、电池 → LoRaWAN。
  • 有 Wi-Fi/以太网、高吞吐 → 第十二章：MQTT 详解：发布订阅、QoS 与 mosquitto / Python 示例、第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例。
  • 局域 mesh → 第十六章：Zigbee：基于 802.15.4 的 Mesh 组网、第十三章：Bluetooth 与 BLE：GATT 模型与低功耗设计 Mesh。

开源栈：LoRaMac-node、Semtech LoRaWAN Stack；云平台：TTN、ChirpStack 等。

本章小结

要点 结论
架构 节点 → 网关（仅射频转发）→ Network Server → 应用服务器
功耗 星型无路由转发，Class A 可电池工作数年
速率 SF 越大越远越慢，ADR 动态平衡速率与距离
入网安全 推荐 OTAA 动态激活；NwkSKey/AppSKey 双层 AES-128
选型边界 公里级低速率选 LoRaWAN，局域 mesh 选 Zigbee/蓝牙 Mesh

第十一章：CoAP：REST over UDP 的物联网应用协议

发表于 2026-05-01 更新于 2026-08-30 分类于 Embedded 本文字数： 718 阅读时长 ≈ 2 分钟

第十一章：CoAP：REST over UDP 的物联网应用协议

概念基础：CoAP 是什么

  1. CoAP（Constrained Application Protocol，受限应用协议）是给单片机、低带宽网络用的应用层协议：把 Web 的 REST 模型（GET / PUT / POST / DELETE 操作资源）搬到 UDP 之上。
  2. 为什么轻量：报文头仅 4 字节起（对比 HTTP 动辄数百字节），二进制紧凑编码，默认端口 5683 / 5684（DTLS），RAM/Flash 占用极小，可直接跑在 6LoWPAN 等受限链路上。
  3. 请求/响应 + 订阅两种模式：既支持类 HTTP 的请求-响应，又通过 Observe（RFC 7641） 让服务器在资源变化时主动推送 NOTIFY，传感器上报无需反复轮询。
  4. 可靠性自选：UDP 本身不可靠，CoAP 用 CON / NON / ACK / RST 消息类型自己决定要不要确认重传——把「要不要可靠」交给应用按需选择。
  5. 定位：资源型设备（一台设备就是一组可读写的资源）的首选；海量消息汇聚与发布订阅则更适合 Broker 型的 MQTT，二者在同一系统里常互补出现。

一次典型交互长这样：

REST over UDP 交互



sequenceDiagram
  participant C as CoAP Client
  participant S as CoAP Server
  C->>S: GET /temp
  S-->>C: 2.05 Content 25.3
  C->>S: Observe 订阅
  S-->>C: 推送变化

一、设计目标

  • 低开销：适合 MCU、6LoWPAN、低带宽链路。
  • 异步：支持 Separate 响应（ACK 先回，结果稍后 CON 通知）。
  • 发现：.well-known/core 资源目录。

默认端口 5683（CoAPS 5684）。

二、报文（简化）

Type 含义
CON 需确认
NON 不需确认
ACK 确认
RST 复位

Code：0.xx 请求（GET=0.01），2.xx 成功，4.xx/5.xx 错误（类比 HTTP）。

三、Observe（RFC 7641）

客户端带 Observe Option 订阅资源；服务器在资源变化时 NOTIFY，适合传感器推送，比轮询省流量。

四、与 MQTT

CoAP 第十二章：MQTT 详解：发布订阅、QoS 与 mosquitto / Python 示例
模型 REST 资源 发布/订阅 Topic
传输 UDP 为主 TCP 常见
代理 CoAP-HTTP 代理 Broker 中心化

物联网选型：资源型设备、LwM2M（基于 CoAP）vs 海量消息经 Broker 的 MQTT。

五、应用

  • 智能抄表、楼宇传感器、Edge 网关 南向 CoAP、北向 HTTP/第十二章：MQTT 详解：发布订阅、QoS 与 mosquitto / Python 示例。
  • 安全：DTLS 预共享密钥或证书；与 第十二章：LoRaWAN：远距离低功耗星型组网 可组合（应用 payload 再解析）。

库：libcoap、aiocoap（Python）、Californium（Java）。

本章小结

要点 结论
模型 REST 风格操作资源，类 HTTP 但跑在 UDP 上
开销 头部 4 字节起，二进制紧凑，适合 MCU 与受限网络
可靠性 CON/NON/ACK/RST 自选确认与重传
推送 Observe 订阅-通知，比轮询省流量
安全 DTLS（PSK 或证书），默认端口 5683/5684

第十章：LIN 总线：单主多从与调度表

发表于 2026-05-01 更新于 2026-08-30 分类于 Embedded 本文字数： 636 阅读时长 ≈ 2 分钟

第十章：LIN 总线：单主多从与调度表

概念基础：LIN 是什么

  1. LIN（Local Interconnect Network，局部互联网络）是低成本的单主多从串行总线：一根总线挂一个 Master 与若干 Slave，常见于车窗、座椅、雨刮等车身电子。
  2. 为什么便宜：基于普通 UART 硬件即可实现，物理层常用单线、12V 电平，收发器（如 TJA1021）远比 CAN 便宜，从节点甚至可用廉价 8 位 MCU——它就是 CAN 的「经济版补充」。
  3. 无仲裁、靠调度：与 CAN 的竞争仲裁不同，LIN 由 Master 固定调度：Master 发 Header（含 PID），对应 Slave 填 Response，时序确定、天然无冲突。
  4. 帧结构简单：Break + Sync(0x55) + PID + Data(1~8) + Checksum，速率约 20 kbps，只适合非安全、低带宽场景。
  5. 定位：动力底盘走 CAN、车身舒适系统走 LIN，网关 ECU 常同时挂两种总线；它的「单主轮询」思想与工业里的 Modbus 主从也一脉相承。

先看单主多从的拓扑：

单主多从拓扑



flowchart LR
  Master[LIN Master ECU] --- Bus[LIN 总线]
  S1[从节点 门窗] --- Bus
  S2[从节点 座椅] --- Bus

一、角色

  • Master：通常由 Body ECU 担任，发送 Header（含 PID）。
  • Slave：响应 Data 或发布自身数据；无仲裁，时隙由 Master 调度。

二、帧结构（简化）

  • Break：显性低电平较长，同步从机。
  • PID：含 6 位 ID + 2 位奇偶。
  • Checksum：Classic 或 Enhanced（LIN 2.x）。

三、调度表（Schedule Table）

Master 按固定周期发送各 Frame ID，保证确定性延迟；配置在 LDF（LIN Description File）中，工具链生成驱动代码。

四、与 CAN

LIN 第九章：CAN 总线：帧结构、多主仲裁与 CAN FD

第九章：CAN 总线：帧结构、多主仲裁与 CAN FD

发表于 2026-05-01 更新于 2026-08-30 分类于 Embedded 本文字数： 788 阅读时长 ≈ 3 分钟

第九章：CAN 总线：帧结构、多主仲裁与 CAN FD

概念基础：CAN 是什么

  1. CAN（Controller Area Network，控制器局域网）是 Bosch 为汽车电子设计的多主串行总线：所有 ECU 节点挂在一对差分线（CAN_H / CAN_L）上，以广播帧通信，各节点按 ID 自行过滤收帧。
  2. 为什么抗干扰：差分传输让共模噪声相互抵消，配合总线两端的 120Ω 终端电阻抑制信号反射，适合发动机舱等电磁环境恶劣的场景——这与单端电平的 RS232 是本质差别。
  3. 多主无损仲裁：总线空闲时任意节点都可发送，逐 bit 仲裁中发显性 0 的胜出、ID 越小优先级越高，败者自动退为接收方，既不丢帧也不需要中心主站。
  4. 硬件级可靠性：帧尾 CRC + ACK 硬件检错与确认，出错自动重发；故障节点经错误计数进入 bus-off 主动离线，不会拖垮整条总线。
  5. 定位：汽车动力、底盘、网关等实时、安全相关场景的主力总线，速率 125 kbps ~ 1 Mbps；CAN FD 把数据段扩到 64 字节并提升数据段速率；车身低成本传感器则交给 LIN（见 第十章：LIN 总线：单主多从与调度表）。

  • 新车载网络大量采用 CAN FD；旧 ECU 可能仅 Classic CAN。

第八章：SPI

概念基础：SPI 是什么/为什么

  1. SPI（Serial Peripheral Interface）是 Motorola 提出的四线同步全双工总线：SCLK / MOSI / MISO / CS，板级高速外设互联的主力。
  2. 主驱时钟：主站产生 SCLK，数据按约定边沿采样；主从的 CPOL/CPHA 模式必须一致（Mode 0~3），这是 SPI 调试最常见的坑。
  3. 片选寻址：没有地址概念，每个从机一根独立 CS 线，多占一根线换取高速度；MISO 未选中时需保持三态。
  4. 为什么快：无地址开销、全双工、时钟可达几十 MHz，Flash、SD 卡、TFT 屏等高带宽外设首选。
  5. 取舍：线数多（每从机 +1 CS）、只适合短 PCB 走线；长距离/多机改用 RS485，少线低速场景可用 I2C，异步调试打印仍用 UART。

二、CPOL / CPHA（模式 0~3）

  • CPOL：空闲时 SCLK 电平（0=低，1=高）。
  • CPHA：第几个边沿采样（0=第一边沿，1=第二边沿）。

主从 模式必须一致（数据手册会写 Mode 0 等）。

三、多从机

  • 独立 CS：每个从机一根 CS，MOSI/MISO/SCLK 共享（MISO 需三态，未选中不高驱）。
  • Daisy Chain：如部分 Shift Register、LED 驱动，数据串行穿过多芯片。

四、典型应用

  • Flash（W25Q）、SD 卡（SPI 模式）、ADC/DAC、TFT 屏、RF 模块（NRF24L01）。
  • 速率常 MHz~ tens of MHz，短 PCB 走线；长距离不如 第六章：RS485。

第七章：I2C

概念基础：I2C 是什么/为什么

  1. I2C（Inter-Integrated Circuit）是 Philips 发明的两线同步总线：SCL 时钟 + SDA 数据，是板级互联传感器/存储器等外设的事实标准。
  2. 地址寻址多从：每个从设备有 7 位地址（0x00~0x7F），主设备以地址帧寻址——两根线即可挂多个器件，扩展外设几乎不加线。
  3. 开漏 + 上拉：SDA/SCL 均为开漏输出加上拉电阻，天然支持多主仲裁与时钟同步，也决定了速率上限（100k/400k/1M/3.4M）。
  4. 协议机制清晰：START/STOP 条件界定传输，逐字节 ACK/NACK 确认；读操作用重复 START 切换方向。
  5. 取舍：线最少、成本低，EEPROM/RTC/IMU/OLED 全支持；但速率不如 SPI，上拉取值需按总线电容与速率权衡。

四、典型设备

  • 同一地址冲突：部分芯片有 ADDR 引脚改地址；否则需不同总线（I2C mux）。

第六章：RS485

概念基础：RS485 是什么/为什么

  1. RS485（TIA/EIA-485） 是差分电气标准：用 A/B 两线电压差表示信号，抗共模干扰强、可达上千米，是工业现场最常用的物理层。
  2. 总线型多机：一条双绞线手拉手（daisy-chain）挂多个节点，配合地址协议实现多机组网；总线两端各接 120Ω 终端电阻。
  3. 半双工：两线制同一时刻只能一个方向发送，收发器需 DE/RE 引脚切换方向。
  4. 只管电气不管语义：RS485 只解决「电信号怎么传」，上层要跑 Modbus RTU 等主从协议才能完成有效通信。
  5. 与 UART 的关系：MCU 的 UART 产生字节流，经 MAX485/SN65HVD 收发器转成差分信号——UART 管逻辑、485 管物理。

五、布线注意

  • 终端电阻 120Ω 仅在总线两端；中间节点不加。
  • GND 参考：虽为差分，仍建议可靠参考地，避免共模超范围。
  • ESD 与浪涌：户外/电机旁加保护器件。

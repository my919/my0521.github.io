第三章：SpringBoot 集成 RustFS 对象存储

概念基础：RustFS 对象存储是什么

对象存储以「Bucket + objectKey」平铺组织文件，通过 HTTP API 读写，适合图片、附件等非结构化数据：

  1. S3 兼容协议：RustFS 提供 S3 兼容 API，凡支持 AWS S3 协议的客户端均可直接对接，迁移成本低。
  2. SDK 与访问风格：本工程使用 AWS SDK for Java v2 访问，并开启 forcePathStyle: true（路径风格访问，兼容 MinIO/RustFS 等自建服务）。
  3. 预签名 URL：服务端签发带过期时间的临时链接（本项目 15 分钟），客户端直连存储完成下载，应用不代理文件流量。
  4. 开关与外部化：app.rustfs.oss.enabled 控制装配（@ConditionalOnProperty），endpoint 与密钥经环境变量注入，生产勿写入仓库。
  5. 测试友好：单元测试默认关闭 OSS，真实环境联调用 RUSTFS_LIVE_TEST=true 单独触发。

前置条件

  1. 已部署 RustFS 服务（示例：http://192.168.1.22:30009）
  2. 在控制台创建 Access Key：http://<host>:<port>/rustfs/console/access-keys
  3. 创建或确认 Bucket 名称

注意：SDK 的 endpoint 填 S3 API 根地址，不要带 /rustfs/console/... 路径。

常见问题

KMS encryption service is not initialized

RustFS 服务端 Bucket 默认启用了 KMS/SSE，但 KMS 未初始化。在 RustFS 控制台关闭该 Bucket 的默认加密，或完成 KMS 配置。属于服务端问题，非应用代码错误。

启用开关不生效

确认 app.rustfs.oss.enabled=true，且未在测试 Profile 中被覆盖为 false。

404 / 签名错误

  • 检查 endpoint 是否为 API 根路径
  • 确认 path-style: true
  • 核对 Access Key / Secret 与 Bucket 名

第二章：SpringBoot 多环境配置：Profile 激活与优先级

概念基础：多环境配置是什么

多环境配置让同一份代码在开发、测试、生产之间只切换配置、不改代码：

  1. Profile 机制：Spring 用 Profile 在 dev / test / prod 之间切换配置；本仓库（springboot）以 application.yaml 承载公共配置，各环境文件只写差异项；相同 key 时环境文件覆盖公共配置。
  2. 激活方式多样：配置文件 spring.profiles.active、环境变量 SPRING_PROFILES_ACTIVE、启动参数 --spring.profiles.active=prod，本项目默认 dev。
  3. 职责划分：端口、应用名、框架级默认值放公共；数据库/Redis 地址与密码、日志级别、Swagger 开关放环境。
  4. 敏感信息外部化：密码经环境变量注入，生产禁止提交 Git；更大规模可接 Nacos 配置中心（共享 dataId + 环境 dataId，后者覆盖前者）。
  5. 测试隔离：src/test/resources/application.yaml 独立于业务 Profile，用 H2 内存库与 Mock 中间件保证 gradlew test 稳定可重复。

微服务多模块 + Nacos spring.config.import 见 第二章：Spring Cloud 多环境配置与 Nacos：Profile 与 config.import 分层（2025.1.x 无 bootstrap，与单体 Profile 思路不同）。

第一章：SpringBoot 工程概览与快速启动

概念基础：SpringBoot 是什么

Spring Boot 是构建在 Spring 之上、遵循「约定优于配置」的快速开发框架：

  1. 自动配置：@SpringBootApplication 组合了 @Configuration、@EnableAutoConfiguration、@ComponentScan，依据依赖自动装配 Bean，免去大量手写配置；业务配置类通过 @ConfigurationProperties + @EnableConfigurationProperties 绑定 application.yaml 中的 app.* 前缀。
  2. 起步依赖（Starter）：一个 starter 聚合一组版本兼容的依赖（如 spring-boot-starter-data-redis），版本由 BOM 统一管理。
  3. 内嵌容器：内嵌 Tomcat，gradlew bootRun 一键启动；本项目默认端口 8082、默认 Profile dev（可通过 SPRING_PROFILES_ACTIVE 覆盖）。
  4. 生产级能力：Actuator 提供健康检查与指标，配合 Profile 多环境、application.yaml 外部化配置与 Spring Boot Admin 形成可观测能力。
  5. 本仓库定位：Spring Boot 4.0.6 + Java 21 + Gradle 后端示例，三层架构、统一 Result、多数据源、Redis、RustFS、监控与 AOP 基础设施均已就绪；本目录按功能模块拆分集成与搭建流程，单篇 md 已带 Hexo Front Matter（title / tags / categories / date），可直接复制到 Hexo _posts 发布。

第十一章：Java本地持久化队列方案与实战

发表于 2026-05-08 更新于 2026-08-30 分类于 Java 本文字数： 1.7k 阅读时长 ≈ 6 分钟

第十一章：Java本地持久化队列方案与实战

概念基础：本地持久化队列是什么

  1. 是什么：任务先写入磁盘再消费的本地队列——进程重启、宕机后任务不丢失，重启自动恢复继续消费。
  2. 为什么需要：内存队列（如 LinkedBlockingQueue）重启即丢；引入 Redis/MQ 又增加部署与运维成本——本地持久化队列在轻量与可靠之间取得平衡。
  3. 三大成熟方案：Chronicle Queue（MMAP 磁盘映射、零依赖、超高吞吐、金融级）、LMDBQueue（嵌入式 KV、极轻量）、MapDB（纯 Java、一行代码建队列）。
  4. 核心能力：磁盘存储 + 重启恢复 + 自动序列化——任务对象只要实现 Serializable 即可入队出队。
  5. 选型记忆：最强成熟方案选 Chronicle Queue，最简单上手选 MapDB。

🔥 最佳推荐（3 个真正的本地持久化队列）

按易用性、性能、成熟度排序：

1. Chronicle Queue（企业级首选，零依赖、高性能）

最适合你：本地持久化 + 可序列化 + 超高吞吐 + 重启不丢

  • 纯 Java 本地队列
  • 磁盘持久化（MMAP）
  • 支持任意对象序列化
  • 无锁、低延迟、生产级稳定
  • 支持多线程读写
  • 重启自动恢复数据

  • 支持超大队列（GB 级）

2. LMDBQueue（极轻量、嵌入式、超快）

极简本地持久化队列

  • 极快、极小、稳定

五、核心特性

  1. 重启不丢数据
    程序停止、重启后，重新 new 相同路径和队列名，自动加载历史任务。
  2. 自动序列化
    只要继承 BaseTask（实现 Serializable），任意业务对象直接入队。
  3. 线程安全
    方法加 synchronized，支持多线程生产、多线程消费。
  4. 轻量无中间件
    纯本地文件存储，不需要 Redis/MQ。

六、使用注意

  1. 任务类所有字段必须可序列化，不要包含非序列化对象；
  2. 程序优雅退出时务必调用 close()；
  3. 不要多个进程同时打开同一个 db 文件，会锁文件报错。

总结

真正的 Java 本地持久化队列 = 磁盘存储 + 重启不丢失 + 可序列化

第十章：Redisson 红锁 RedLock 原理与生产实践

概念基础：红锁（RedLock）是什么

  1. 要解决的问题：普通 Redis 锁是单主节点锁——加锁成功后尚未同步到从节点就宕机，主从切换后锁凭空消失，两个客户端可能同时持锁。
  2. 核心思想：把锁同时写到 N 个完全独立的 Redis 主节点上，过半节点加锁成功且总耗时小于锁有效期才算加锁成功。
  3. 为什么有效：基于**多数派（quorum）**机制，任一节点宕机/切换都不影响多数节点上的锁记录，从根本上规避单点故障丢锁。
  4. 代价：要写多个节点，性能低于普通锁；节点必须相互独立（非主从、非集群）且为奇数个。
  5. 适用边界：秒杀、库存、支付、账务等核心强一致场景用 RedLock；后台任务等非核心场景普通 Redisson 锁即可。

第八章：Java并发锁全解与选型

概念基础：并发锁是什么

  1. 为什么需要锁：多个线程同时读写共享变量（如 count++）会因原子性、可见性、有序性三大问题产生数据错乱，锁是保证线程安全最直接的手段。
  2. 两大流派：悲观锁先加锁再操作（synchronized、ReentrantLock），乐观锁先操作再校验冲突（Atomic 原子类的 CAS 机制）。
  3. JVM 内置锁 vs JDK 显式锁：synchronized 由 JVM 自动加解锁、可重入、非公平；Lock 接口（ReentrantLock 等）额外支持超时、可中断、公平锁、多 Condition 精准唤醒。
  4. 读写分离优化：读多写少场景用 ReentrantReadWriteLock（读读共享）；追求极致读性能再上 StampedLock 的无锁乐观读。
  5. 无锁更轻：单变量的计数/状态标志可用 Atomic 原子类或 volatile（保证可见性、禁止重排），避免加锁开销。

为何浏览器还常要 TCP、和 QUIC 设计是否冲突

不冲突。 QUIC（RFC 9000）只规定跑在 UDP 上；HTTP/3 也完全可以在只有 UDP 的情况下工作（例如本节的 aioquic 客户端直连 quic_bind）。

浏览器在地址栏输入 https://主机:端口/ 时，多数实现仍沿用历史习惯：先按「TLS over TCP」去建第一条连接，再通过响应里的 Alt-Svc、或 DNS HTTPS/SVCB 等线索，得知同一站点也可用 HTTP/3，之后才发起 QUIC。这是浏览器与 Web 生态的部署/发现策略，不是 QUIC 协议里「必须先有 TCP」的要求。本地演示若没有 DNS、没有事先缓存的 Alt-Svc，只监听 UDP 时，用户只输入 https:// 就容易连不上，因此示例里同时开同端口的 TCP TLS 是为了兼容这种建连路径，属于工程上的折中，与 QUIC 规范无矛盾。

MyBatis-Flex 分页原理（通俗易懂 + 流程拆解 + 和 MP 对比）

一、核心结论

MyBatis-Flex 底层也是基于 MyBatis 拦截器，原理和 MyBatis-Plus 大体一样，但设计更轻、SQL 解析更强、自动 count 更智能。

核心逻辑：
MyBatis 拦截器 → 拦截查询SQL → 自动生成 count 总数 → 原SQL 拼接 LIMIT → 封装分页结果

二、核心组件

  1. MyBatisFlexInterceptor
    Flex 全局核心拦截器，替代 MP 的 MybatisPlusInterceptor
  2. PageInterceptor
    专门负责分页拦截，Flex 分页核心逻辑都在这
  3. Page、IPage
    分页载体，和 MP 几乎一模一样：当前页、页大小、总条数、分页数据

三、完整分页执行流程（流程图版）

四、和 MyBatis-Plus 分页原理关键区别

对比点 MyBatis-Plus MyBatis-Flex
拦截器结构 插件嵌套式，较重 极简拦截器，更轻量
Count SQL 生成 简单直接，复杂SQL容易生成低效count 智能优化：自动去掉 order by、优化嵌套SQL
多表/复杂SQL 偶尔分页解析失败 解析器更强，兼容复杂联表、子查询
分页参数传递 必须 Mapper 方法带 Page 参数 支持 Mapper、也支持 Db 静态工具直接分页
配置 必须手动注册分页插件 自动配置，开箱即用，不用手动@Bean

五、代码使用（和 MP 几乎一模一样）

Flex 自动自动注入分页拦截器，不用写任何 @Bean 配置

2. 业务分页代码

写法和 MP 完全兼容，无缝切换。

六、底层关键亮点（Flex 比 MP 强的地方）

  1. 自动优化 Count SQL
    原SQL 有 order by，Flex 会自动剔除，避免 count 也排序，提升性能。
  2. 无需手动配置拦截器
    自动装配，少写配置类，少踩坑。
  3. 支持更多数据库方言
    MySQL、PostgreSQL、Oracle、SQLite 等自动适配 LIMIT 语法。
  4. Lambda 分页更丝滑
    不用写 Wrapper，链式直接分页。

和 MP 原理同源，但解析更强、配置更少、性能更好、坑更少。

发表于 2026-05-04 更新于 2026-08-30 分类于 Java 本文字数： 1.3k 阅读时长 ≈ 4 分钟

第六章：Java 动态数据源：@DS 切换与事务边界

概念基础：动态数据源是什么、为什么

  1. 为什么需要多数据源：主从读写分离、按库分业务、迁移期新旧库并存等场景，要求应用在运行时切换数据库连接。
  2. 动态数据源方案：Spring 提供 AbstractRoutingDataSource 路由骨架；Baomidou 的 dynamic-datasource 在此之上提供开箱即用的实现。
  3. 核心注解 @DS：通过 @DS("逻辑名") 声明当前类/方法使用的数据源，底层借助 AOP 代理 + ThreadLocal 上下文完成切换，对 MyBatis-Plus、MyBatis-Flex、JdbcTemplate 等均透明适用。
  4. 切换时机是关键：数据源在获取连接时确定；已开启事务并绑定连接后，再切换通常不会生效，须注意事务边界。
  5. 常见陷阱：同类自调用绕过 Spring 代理导致 @DS 失效；编程式切换 push 后忘记 poll 会污染线程上下文。

springboot 仓库落地见 第五章：SpringBoot 集成 MyBatis-Flex 与多数据源。下文以 Boot 4 + MyBatis-Plus 3.5.x + dynamic-datasource 4.x 为例。

Controller 上也可标注，但更推荐标在 Service 或 Mapper 层，避免 Web 层与持久化策略绑死。

事务与边界情况

  • 同一事务内：已进入 @Transactional 且已绑定连接后，再切换数据源通常不会按预期切到新库（连接已固定）。多数据源写操作应拆到不同事务方法，或调整事务边界，使切换发生在开启事务之前。
  • 只读事务：若使用 @Transactional(readOnly = true)，仍要注意连接从哪个数据源取得，与 @DS 所在方法的事务传播一致。
  • 自调用：同类内 this.method() 不会经过 Spring 代理，@DS 可能不生效，应抽到另一个 Bean 或通过代理调用。

与 MyBatis-Plus / MyBatis 的配合

引入 MyBatis-Plus 后，SqlSessionFactory 仍使用 Spring 容器中的动态 DataSource，与 dynamic-datasource 无额外冲突。Mapper（含继承 BaseMapper 的接口）或 XML 无需单独为多数据源改一套配置即可随当前线程数据源路由；若某几个 Mapper 固定走副库，可在 Mapper 接口上加 @DS("pgsql")。

第六章：MySQL 存储引擎

概念基础：存储引擎是什么、为什么重要

存储引擎是 MySQL 「表数据如何存、如何取」的可插拔实现：

  1. 分层架构的产物：Server 层负责 SQL 解析、优化、权限；引擎层负责数据在磁盘与内存上的组织——索引结构、事务、锁、崩溃恢复都由引擎决定；同一份表结构，换引擎行为完全不同。
  2. InnoDB 是唯一默认答案：支持 ACID 事务、行级锁、MVCC、崩溃恢复（redo / undo）、聚簇索引与外键；官方默认且推荐，第五章讲的 B+ 树与回表，说的就是 InnoDB 的组织方式。
  3. MyISAM 是历史遗产：表级锁、不支持事务、崩溃安全性弱，只存在于老系统与只读库中；新业务一律避开——它也解释了第三章「表锁并发差」的历史背景。
  4. 换引擎不解决性能问题：性能瓶颈优先从索引、SQL 写法、事务与连接设计入手（第三、四、五章的内容）；引擎选型是「事务要不要」的问题，不是「快不快」的问题。
  5. 插件式带来专用选择：ARCHIVE（冷归档压缩）、CSV（数据管道交换）、BLACKHOLE（写入即弃的中继）、NDB（分布式集群）各有专属场景，是否可用以 SHOW ENGINES 为准。

先看怎么查看与确认当前引擎：

一、如何查看支持的引擎与默认值

建表未写 ENGINE 时使用 default_storage_engine（一般为 InnoDB）。

二、InnoDB（事实上的唯一首选）

维度 说明
事务 ACID；COMMIT / ROLLBACK、崩溃恢复（redo / undo）。
锁与并发 以行锁为主；隔离级别与间隙锁等见 MySQL锁详解.md。
索引与数据 聚簇索引即主键 B+ 树，二级索引叶子存主键；详见 MySQL索引与性能优化.md。
外键 支持 FOREIGN KEY（与 MySQL.md 中 DDL 一致）。
适用 OLTP、绝大多数业务库；官方默认与推荐。

三、MyISAM（ legacy，新业务避免）

维度 说明
事务 不支持事务与崩溃安全意义上的 InnoDB 同级别恢复。
锁 表级锁，写多读少场景易成为瓶颈。
索引 数据与索引布局与 InnoDB 不同；无聚簇主键同义实现。
典型遗留场景 老系统、只读库、部分空间索引历史用法；新表请勿选用。

四、MEMORY（内存表，谨慎）

  • 数据驻内存，进程崩溃或重启后易失；容量受 max_heap_table_size 等限制。
  • 曾用于临时高速缓存；现代实践更常见 Redis 或 InnoDB + 足够内存 + 合理索引。

五、其它引擎（知道名字即可）

引擎 一句话
ARCHIVE 高压缩追加存储，适合冷归档、很少更新。
CSV 以 CSV 形式存文件，多用于导入导出管道，非通用 OLTP。
BLACKHOLE 写入即丢弃，有时用于复制拓扑中的「中继」等特殊场景。
NDB（MySQL Cluster） 分布式集群专用，与普通单机 InnoDB 运维模型不同。

具体是否编译进你的 mysqld，以 SHOW ENGINES 为准。

六、选型与迁移建议

  1. 新表一律 ENGINE=InnoDB，并显式 DEFAULT CHARSET=utf8mb4（与 MySQL.md 一致）。
  2. 发现 MyISAM 老表：评估后 ALTER TABLE … ENGINE=InnoDB（需在低峰窗口做；大表走 gh-ost / pt-online-schema-change 等在线 DDL 工具，属运维专题）。
  3. 不要用 ENGINE 解决「性能问题」：优先索引、SQL、连接与事务设计。

第五章：MySQL 索引与性能优化

概念基础：索引是什么、为什么能加速

索引是数据库用额外空间与写成本换取查询速度的有序数据结构：

  1. 本质是一棵 B+ 树：把无序的表数据额外组织成有序树，查询从「全表逐行扫」变成「沿树下降读少量页」——随机 I/O 大幅减少；代价是每次 INSERT/UPDATE/DELETE 都要同步维护树，所以索引不是越多越好。
  2. 聚簇索引即数据本身：InnoDB 表数据按主键组织成 B+ 树，叶子节点存「主键 + 整行」；二级索引叶子只存「索引列 + 主键」，命中后常需回表再查一次聚簇索引——这就是主键要自增、查询要少 SELECT * 的根因。
  3. 联合索引遵守最左前缀：(a, b, c) 先按 a 排、a 相同再按 b、再按 c；跳过 a 的条件用不上树，等值列在前、范围列在后是最常见的设计。
  4. 覆盖索引是回表的解药：查询列全在索引里就只扫索引不回表（EXPLAIN 显示 Using index）；与之配套的 ICP 把过滤条件下推到引擎层，进一步少回表。
  5. 优化是一个闭环而非玄学：慢日志抓 Top SQL → EXPLAIN 看 type / key / rows / Extra → 改索引或改写法 → 再对比慢日志；本章同时覆盖事务隔离与备份恢复，给出完整的「开发侧性能地图」。

从 B+ 树的直觉开始：

一、索引在干什么：B+ 树直觉（够用版）

InnoDB 里，表数据按主键组织成一棵 B+ 树（聚簇索引）：叶子节点存「主键 + 整行数据」。
二级索引（你建的 INDEX / UNIQUE）叶子节点存「索引列 + 主键」，需要整行时往往要再回表到聚簇索引取数据。

读图要点：上层结点只存分界键与子树指针；最底层叶子由双向链表串起，方便范围扫描；聚簇索引叶子是主键 + 行数据；二级索引叶子多一步按主键回表读完整行。

直觉：

  • 等值 / 范围命中索引列 → 树高度低、少读页 → 随机 I/O 变少。
  • 全表扫 → 叶子链顺序读，数据量一大就慢。
  • 索引不是越多越好：每次 INSERT/UPDATE/DELETE 都可能维护多棵索引树。

二、联合索引与最左前缀

联合索引 KEY idx_abc (a, b, c) 的排序语义是：先按 a，再 a 相同时按 b，再按 c。

能较好利用该索引的典型条件（示意）：

  • WHERE a = ?
  • WHERE a = ? AND b = ?
  • WHERE a = ? AND b BETWEEN ? AND ?

容易用不上或只用一截的情况：

  • WHERE b = ? AND c = ?（缺 a，与「最左」不一致）
  • WHERE a = ? OR d = ?（OR 另一侧常走另一条路径，易优化成 UNION 或改写法）
  • 对 a 做函数/隐式类型转换导致无法走树（例如 WHERE DATE(a_col) = ...）。

设计经验：把区分度高、过滤性大的列尽量放左侧；把范围查询列放联合索引右侧更常见（仍要结合 EXPLAIN 验证）。

三、覆盖索引（Using index）

若 SELECT 里出现的列都能从某条二级索引的叶子直接凑齐（含 WHERE 用到的索引列），InnoDB 可能只扫索引、不回表，EXPLAIN 的 Extra 常见 Using index。

典型收益：大宽表上只查少数列 + 条件列恰好在同一联合索引上，I/O 明显下降。

四、索引条件下推 ICP（一眼带过）

Index Condition Pushdown：把部分 WHERE 条件下推到存储引擎层，在索引扫描过程中就过滤，少回表。
在 EXPLAIN 里常见 Using index condition（与 Using index 不同：后者多为覆盖索引）。不必一次讲透优化器细节，看到术语知道「在索引层多干了一点过滤」即可。

八、备份恢复与 PITR 概念

1. 逻辑备份（mysqldump）

  • --single-transaction：InnoDB 下用一致性读做导出，尽量避免 FLUSH TABLES WITH READ LOCK 式全库只读（与全局锁备份对比，见 MySQL锁详解.md 中「全局锁 + mysqldump --single-transaction」相关说明）。
  • 恢复：mysql -uroot -p < backup.sql（注意字符集与目标实例版本）。

2. 物理备份与快照

对大数据量，常用物理热备（厂商工具或存储快照）+ binlog；与 Docker 场景结合时，数据在卷上，备份策略要在「卷快照 / 容器外 mysqldump」之间选一种或组合，并做恢复演练（参见 MySQL-Docker.md 中数据卷与持久化思路）。

3. PITR（Point-in-Time Recovery，按时间点恢复）

含义：不只恢复到「昨晚整库备份」，而是恢复到某事故前一秒。通常需要：

  1. 周期全量 / 增量（逻辑或物理）；
  2. 连续归档的 binlog（log_bin 打开，并安全保存 binlog 文件）；
  3. 恢复时：先还原备份到某一时刻，再重放 binlog 到目标时间点（具体命令与工具因版本与平台而异，属 DBA 操作手册级）。

可靠性＝备份自动化 + 定期恢复演练 + binlog 留存策略；开发至少要懂「为什么不能只靠一台机子从不备份」。

第四章：MySQL 高级查询

概念基础：高级查询是什么、为什么难写对

高级查询是超越单表 SELECT ... WHERE 的多表、分组、窗口类查询，核心是把拆开存的关系拼回来：

  1. 为什么数据要拆开存：关系模型按范式把业务拆成多张表（如 emp 员工表与 dept 部门表），避免重复存储；查询的本质就是用 JOIN / 子查询按关联字段把数据重新拼装——第一章建的表结构，在这里被「消费」。
  2. JOIN 的语义差异决定丢不丢数据：INNER JOIN 只保留两表都匹配的行；LEFT JOIN 保留左表全量、右表无匹配补 NULL。选错连接类型，统计结果会悄悄少行，是报表错乱的头号来源。
  3. 聚合把「多行」压成「一行」：GROUP BY 分组后才能用 COUNT / SUM / AVG；过滤顺序是 WHERE（分组前滤行）→ GROUP BY → HAVING（分组后滤组），颠倒位置直接报错或结果不对。
  4. MySQL 8.0+ 的两大武器：CTE（WITH） 把复杂查询拆成可读的「临时结果」并支持 RECURSIVE 查树；窗口函数在不减少行数的前提下做组内排名、累计——「每组 Top N」从此有了标准解法。
  5. 性能意识贯穿始终：判断存在性优先 EXISTS，合并结果优先 UNION ALL（免去去重排序），深分页 LIMIT 大 OFFSET 会越来越慢、生产改用键集分页——写法差异就是性能差异。

第三章：MySQL 锁详解

概念基础：锁是什么、为什么需要锁

锁是数据库的并发控制机制，让多个事务在共享同一份数据时「不打架」：

  1. 没有锁会发生什么：多个会话同时读写同一行，会出现脏读、不可重复读、幻读与更新丢失；锁的本质是给「当前读」排队，保证数据一致性。
  2. 核心权衡是一致性 vs 并发：锁粒度越粗（全局锁、表锁）越安全但并发差，粒度越细（行锁）并发越高但开销越大——InnoDB 的答案是以行锁为主 + MVCC 快照读，普通 SELECT 不加锁，读写大部分场景互不阻塞。
  3. InnoDB 行锁的本质是锁索引：锁加在索引记录上而不是物理数据行上；查询条件无索引或索引失效时，行锁会退化为表锁，并发直接崩塌，这是本章最重要的一条结论。
  4. 隔离级别决定加锁行为：**RR（可重复读）默认用临键锁（记录锁 + 间隙锁）**抑制幻读，代价是范围锁会阻塞插入；**RC（读已提交）**没有间隙锁，并发更高但存在幻读。
  5. 锁是双刃剑：用好了高并发不冲突，用坏了就是锁等待、死锁、业务雪崩——长事务、无索引更新、交叉加锁是线上三大事故来源，本章实验与面试题全部围绕这些展开。

作用：快速判断表内有没有行锁，避免全表扫行锁

  • IX：意向排他锁（要加 X 行锁）

五、InnoDB 行锁三大算法（RR 隔离级别默认）

1）记录锁（Record Lock）

  • 锁：单个索引记录
  • 触发：唯一索引 + 精准等值查询（命中）

2）间隙锁（Gap Lock）

  • 锁：索引之间的间隙（不包含记录）
  • 目的：防止幻读（禁止区间插入）
  • 示例：表有 id=1,3,5
  • 特点：间隙锁之间兼容，只与插入意向锁互斥

3）临键锁（Next-Key Lock）= 记录锁 + 间隙锁

  • 锁：左开右闭区间 (min, max]
  • InnoDB RR 默认，解决幻读
  • 示例：id=1,3,5
    • 查 id=3 → 锁 (1,3]
    • 查 id=4 → 锁 (3,5]

  • 不可剥夺：不能强行抢锁
  • 循环等待：A 等 B，B 等 A

七、实战高频坑（必避）

  1. 无索引 → 行锁变表锁：UPDATE t SET name='a' WHERE age=20;（age 无索引）
  2. 长事务 + 慢查询 → 锁等待堆积

  • 死锁四条件：互斥、持有等待、不可剥夺、循环等待

统一前提：

  • 锁粒度：行锁依赖索引，无索引降级为表锁

实验一：行排他锁 FOR UPDATE 阻塞演示

执行流程

会话1：开启事务 → id=1 加 FOR UPDATE 不提交
会话2：修改 id=1 被阻塞；修改 id=2 正常执行

现象

  1. 同一条主键记录：写操作被阻塞
  2. 不同主键记录：完全不受影响
  3. 会话1 commit 后，会话2立刻执行成功

底层原理

  1. FOR UPDATE 加 行级排他锁（X锁）
  2. 排他锁规则：写写互斥、读写互斥
  3. InnoDB 行锁只锁索引命中的单行，不影响其他行

面试标准答案

InnoDB 中通过主键/唯一索引精准查询加 FOR UPDATE，会加行级排他锁；只锁定当前命中的单行记录，其他行不受影响，能保证高并发。排他锁与任何读写操作都互斥，事务提交后锁自动释放。

实验二：无索引导致行锁退化为表锁

执行流程

按无索引字段 age=20 更新，会话1不提交，会话2更新完全无关的 id=2 也被阻塞

现象

明明更新不同行，却整张表都被锁住，所有写操作全部阻塞

底层原理

  1. InnoDB 行锁是锁索引，不是锁数据行
  2. 条件字段无索引，MySQL 无法定位具体行
  3. 只能逐行加行锁扫描全表，最终退化成表级锁

面试标准答案

InnoDB 行锁必须依赖索引。如果更新/删除条件没有索引或索引失效，MySQL 无法精确定位行记录，会扫描全表并逐行加锁，最终行锁降级为表锁，严重降低并发性能，开发中必须保证更新条件走索引。

实验三：共享锁与读写互斥演示

执行流程

会话1：LOCK IN SHARE MODE 加共享锁
会话2：普通SELECT能查，UPDATE/DELETE被阻塞

现象

  1. 多个事务可以同时加共享锁（读读兼容）
  2. 加了共享锁后，其他事务不能加排他锁、不能修改数据
  3. 事务提交后，写操作立刻放行

底层原理

  • 共享锁（S锁）：读读兼容，读写互斥
  • 意向锁辅助，S锁阻塞所有写操作，保证数据当前快照不被修改

面试标准答案

共享锁（S锁）又叫读锁，使用 LOCK IN SHARE MODE 加锁。特性是读读可以并发，读写、写写互斥；适合需要强一致性、临时禁止别人修改数据的场景，事务提交自动释放锁。

实验四：间隙锁与临键锁阻塞插入（RR 与幻读）

执行流程

会话1：范围查询 between 1 and 3 for update 不提交
会话2：插入区间内新 ID，直接被阻塞

现象

没有任何行被修改，只是范围加锁，却无法往区间里插入新数据

底层原理

  1. MySQL RR 隔离级别默认使用 Next-Key Lock 临键锁
  2. 临键锁 = 记录锁 + 间隙锁
  3. 范围查询会锁住索引区间间隙，禁止其他事务插入新记录，解决幻读
  4. 间隙锁只在 RR 存在，RC 隔离级别没有间隙锁

面试标准答案

InnoDB 在 RR 可重复读隔离级别下，采用临键锁（Next-Key Lock） 解决幻读。临键锁由记录锁+间隙锁组成，范围查询会锁定索引左右间隙，禁止其他事务在区间内插入数据；RC 读已提交级别会关闭间隙锁，因此无法彻底避免幻读，但并发更高。

实验五：经典死锁复现

执行流程

  • 事务1：先锁 id=1 → 再请求锁 id=2
  • 事务2：先锁 id=2 → 再请求锁 id=1
  • 互相等待，立刻触发死锁，MySQL 自动回滚一个事务

现象

  1. 互相持有对方需要的锁，循环等待
  2. InnoDB 自动死锁检测，回滚代价小的事务，抛出死锁异常
  3. 不会无限阻塞

底层原理

死锁产生四个必要条件同时满足：

  1. 互斥条件：锁资源独占
  2. 持有并等待：自己拿着锁，还等别人的锁
  3. 不可剥夺：锁不能被强行抢占
  4. 循环等待：事务形成等待环路

面试标准答案（必背）

死锁产生必须同时满足四个条件：互斥、持有并等待、不可剥夺、循环等待。
规避方案：

  1. 统一多事务访问资源的顺序；
  2. 拆分长事务，尽早提交；
  3. 避免在事务中做无关耗时操作；
  4. 合理设置锁等待超时时间。
    InnoDB 自带死锁检测机制，发现循环等待会自动回滚一个事务，避免程序卡死。

十一、面试高频一句话速记

  1. 行锁靠索引，无索引变表锁
  2. S 锁读读兼容，X 锁完全独占
  3. RR 有间隙锁防幻读，RC 没有
  4. 交叉改不同行、顺序乱写易出死锁

十二、二十道高频面试题与标准答

全部面试可直接背诵，基于 InnoDB、RR 隔离级别，精简不废话。

1. MySQL 有哪些锁分类？

答案

  1. 按粒度：全局锁、表级锁、行级锁
  2. 按读写：共享锁S、排他锁X
  3. InnoDB 特有：意向锁、记录锁、间隙锁、临键锁

2. 全局锁作用是什么？怎么加？

答案
整库只读，所有库表只能读不能写、阻塞 DDL/DML。
加锁：FLUSH TABLES WITH READ LOCK;
解锁：UNLOCK TABLES;
多用于全库逻辑备份；生产优先用 mysqldump --single-transaction 快照备份，不加锁。

3. 什么是 MDL 元数据锁？

答案
访问表时自动加，保护表结构不被中途修改/删除。
长事务不提交 + 执行 DDL 改表结构，会造成 MDL 锁等待阻塞，线上高发故障点。

4. 表锁和行锁区别？

答案

  • 表锁：粒度大、开销小、并发低、MyISAM 默认
  • 行锁：粒度小、开销大、并发高、InnoDB 支持
    InnoDB 优先用行锁提升并发。

5. 共享锁S、排他锁X 特性？

答案

  • 共享锁S：读读兼容，读写/写写互斥
  • 排他锁X：读写、写写全部互斥，独占资源
    加锁：
    S：select ... lock in share mode
    X：select ... for update

6. 意向锁 IS/IX 作用？

答案
意向锁是表级锁，事务加行锁前必须先加意向锁。
作用：快速判断表内是否有行锁，不用遍历所有行锁，提升加锁效率。

  • IS：要加 S 行锁
  • IX：要加 X 行锁
    意向锁之间互相兼容，只和表级 S/X 锁互斥。

7. InnoDB 行锁本质是什么？

答案
行锁锁的是索引，不是物理数据行。
查询条件无索引、索引失效，行锁会退化成表锁，并发骤降。

8. 什么情况下行锁会降级为表锁？

答案

  1. where 条件无索引字段
  2. 索引失效（函数、隐式类型转换、like 前缀模糊等）
  3. 没有命中任何记录，全表扫描加锁

9. InnoDB 三种行锁算法？

答案

  1. 记录锁：锁单行索引记录
  2. 间隙锁 Gap Lock：锁索引间隙，不锁记录，防止幻读插入
  3. 临键锁 Next-Key Lock = 记录锁+间隙锁，左开右闭区间，RR 默认

10. 间隙锁什么时候生效？什么时候关闭？

答案

  • 生效：RR 可重复读隔离级别、范围查询/不走唯一索引等值查询
  • 关闭：RC 读已提交 没有间隙锁，并发更高，但会有幻读

11. 临键锁解决了什么问题？

答案
在 RR 隔离级别下，通过临键锁+间隙锁彻底解决幻读，禁止其他事务在索引区间插入新数据。

12. 什么是幻读？怎么解决？

答案
同一事务内，前后两次范围查询，查到别人新插入的数据。
解决：

  • 数据库层：InnoDB RR + 临键锁
  • 业务层：悲观锁、分布式锁限制插入

13. 死锁产生的四个必要条件？

答案

  1. 互斥：锁资源独占
  2. 持有并等待：拿着自己的锁，等待别人的锁
  3. 不可剥夺：锁不能被强行抢占
  4. 循环等待：事务互相等待形成环路

14. MySQL 怎么处理死锁？

答案
InnoDB 有自动死锁检测，检测到循环等待后，自动回滚代价更小的一个事务，抛出死锁异常，避免无限阻塞。

15. 如何避免 MySQL 死锁？

答案

  1. 统一所有事务访问资源/更新行的顺序
  2. 精简事务，避免长事务，尽早 commit
  3. 事务内不做耗时网络/IO 操作
  4. 合理设置锁等待超时 innodb_lock_wait_timeout

16. for update 和 lock in share mode 区别？

答案

  • for update：加排他锁X，别人不能读也不能改
  • lock in share mode：加共享锁S，别人可以读、不能改

17. RR 和 RC 在锁层面最大区别？

答案

  1. RR 有间隙锁/临键锁，防幻读；RC 没有
  2. RC 行锁范围更小、并发更高，但存在幻读
  3. RC 锁释放更早，阻塞更少

18. 长事务有什么锁风险？

答案
长事务不提交：

  1. 行锁、MDL 锁长期不释放
  2. 造成大量锁等待、业务阻塞
  3. undo log 不能清理，占用磁盘
  4. 容易触发死锁、数据库性能雪崩

20. 线上开发写 UPDATE 防锁坑要注意什么？

答案

  1. 更新条件必须走索引，防止行锁变表锁
  2. 尽量用主键/唯一索引精准等值，少用范围查询
  3. 事务尽量短小，及时提交

概念基础：容器化部署 RocketMQ 的四个要点

  1. 没有「单容器一体」形态：NameServer 与 Broker 是两个独立进程（5.x 还有一个可选的 Proxy），最小栈就是两个容器——这与 Kafka 的 KRaft 单进程不同，下文用「网络 → NameServer → Broker」三步完成最小栈。
  2. brokerIP1 是第一坑：Broker 启动时把自己注册到 NameServer 的地址就是 brokerIP1，客户端拿这个地址直连 Broker——容器内不显式指定时往往是内网容器 IP，宿主机客户端会「能拿到路由却连不上」。本机访问写 127.0.0.1、跨机写宿主机可达 IP（对照 Kafka 的 advertised.listeners）。

第二章：Windows 上 WSL（Rocky Linux）与 Docker Desktop

概念基础：WSL 是什么/为什么

  1. WSL 是什么：WSL（Windows Subsystem for Linux）让 Windows 直接运行真正的 Linux 发行版，无需双系统或整机虚拟机，一条命令即可进出 Linux 环境。
  2. WSL2 的意义：WSL2 基于轻量级虚拟机，系统调用兼容性完整，是 Docker Desktop 官方推荐的运行后端——没有 WSL2 就没有流畅的容器体验。
  3. 为什么选 Rocky Linux：与 RHEL 同源的企业级发行版，dnf 生态与生产服务器一致，作为本地演练环境最贴近真实运维。
  4. Docker Desktop 的角色：提供图形化引擎管理（更新、证书、镜像加速），通过 WSL integration 把 docker CLI 注入各发行版，Rocky 内无需再装 dockerd。
  5. 适用场景：在 Windows 机器上做 Linux 运维演练与容器开发；代码放在发行版内的 Linux 文件系统中可获得最佳 I/O 性能。

环境与版本说明

  1. 操作系统：Windows 10（建议 22H2 及以后）或 Windows 11。
  2. 体系结构：下载 Rocky Linux 镜像时选 x86_64 或 aarch64，与 Windows、Docker Desktop 安装包一致。
  3. WSL：使用 WSL2；Docker Desktop 的 WSL 2 后端依赖此版本。
  4. Rocky Linux：官方 .wsl 镜像（推荐）或 wsl --import。
  5. 权威文档：
    • Rocky Linux（本文默认 10，文档内可切换版本）：Import Rocky Linux to WSL or WSL2
    • Microsoft：安装 WSL
    • Docker：Docker Desktop on Windows、WSL 与 Docker Desktop

安装与配置 Docker Desktop（配合 WSL2）

1. 下载并安装

  1. 打开 https://www.docker.com/products/docker-desktop/ ，下载 Docker Desktop for Windows。
  2. 安装向导中保持 Use WSL 2 instead of Hyper-V（或等价选项，以当前安装界面为准）。
  3. 安装结束若提示注销或重启，按提示操作。

2. 确认使用 WSL 2 后端

打开 Docker Desktop → Settings（设置）→ General（常规）：

  • 勾选 Use the WSL 2 based engine（使用基于 WSL 2 的引擎）。

应用后必要时 Restart Docker Desktop。

3. 与 Rocky Linux 发行版集成（核心）

Settings → Resources → WSL integration（WSL 集成）：

  1. 打开 Enable integration with my default Wsl distro（与默认 WSL 发行版集成）（按需）。
  2. 在 Enable integration with additional distros 中，打开你的 Rocky Linux 名称（例如 Rocky-10）。
  3. 点击 Apply & restart。

之后在 wsl -d Rocky-10 的 shell 中应能直接执行 docker、docker compose，实际引擎由 Docker Desktop 提供，无需在 Rocky 里再装 dockerd 或配置 rootful 独立引擎（避免与 Desktop 抢端口、重复占资源）。

4. 验证（在 Rocky Linux 内）

若提示找不到 docker：回到上一步检查该发行版集成开关，并执行 wsl --shutdown 后重新打开 Docker Desktop 与 WSL 终端。

5. 镜像加速与构建缓存（Docker Engine）

在 Docker Desktop → Settings（设置）→ Docker Engine 中编辑 JSON（与引擎配置同源，保存后 Apply & restart 生效）。若已有其它键（如 insecure-registries），请把下面片段合并进现有对象，不要整段覆盖导致丢配置。

  • registry-mirrors：拉取镜像时优先走列表中的镜像站，减轻访问 docker.io 的延迟与失败（镜像站可用性与合规以你网络环境为准，可日后替换为团队提供的地址）。
  • builder.gc：为 BuildKit 构建缓存开启自动回收，defaultKeepStorage 限制默认保留量（示例 20GB），避免构建缓存占满磁盘。

修改后点击 Apply & restart；再在 Rocky 或 PowerShell 中执行 docker info，在输出里确认 Registry Mirrors 已包含上述地址。

6. 文件与性能建议

  • 项目代码放在 WSL 发行版自己的 Linux 文件系统里（例如在 wsl -d Rocky-10 里用 ~/project，即 /home/你的用户/project），不要放在 /mnt/c/... 下做大量编译与 Docker 构建，可减少跨系统 I/O 延迟。

  • Docker Desktop 的 Settings → Resources 可调 CPU、内存、磁盘镜像上限，与 Rocky 其它进程共用本机资源，按机器配置酌情调大。

7. 与「在 Rocky 里单独装 Docker Engine」的区别

方式 说明

2. 是否需要「登录」、如何设置与验证 root 密码

是否要登录：WSL 从 Windows Terminal、wsl -d Rocky-10 等方式进入时，一般是直接进入已配置的默认 Linux 用户的 shell，不会像 SSH 那样再在终端里提示输入一次用户名（除非你主动执行 login、su 等）。首次安装某些发行版时会交互式让你创建 UNIX 用户名与密码；Rocky 官方 .wsl 导入后的默认用户以该镜像说明为准（常见为 root 或需自行建普通用户，见下节）。

root 密码是什么、要不要设：root 账户始终存在；若从未执行过 passwd，root 可能没有可用登录密码（或镜像预置了密码，以发行版文档为准）。日常维护建议用带 sudo 的普通用户；需要 root shell 时再切。

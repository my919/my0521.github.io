第二章：Rust 类型系统与 trait

概念基础

  1. trait 是接口：定义一组方法签名，类型通过 impl Trait for Type 实现，可带默认实现，类似 Go/Java 的 interface。
  2. 泛型是静态分发：编译期单态化（monomorphization）为每个具体类型生成一份代码，零运行时开销，但二进制体积增大。
  3. 生命周期是编译期分析：标注不改变引用实际存活时长，只向编译器声明引用同寿关系，防悬垂引用。
  4. trait object vs 泛型：dyn Trait 运行时虚表分发，可装进同一集合但有一次指针解引用开销；impl Trait 编译期已知，零成本。
  5. 关联类型：trait 内部定义占位类型，让一个类型只为某 trait 实现一次，比泛型参数语义更清晰。

本章聚焦类型系统。所有权与基础语法见 第一章：Rust 入门与所有权系统；并发与错误处理见 第三章：Rust 并发与错误处理；工程实践见 第四章：Rust 工程实践与 Web 开发。

五、生命周期

生命周期标注不改变引用实际存活时长，只是向编译器声明「这些引用的存活期相同」。编译器据此判断引用是否比被引用者活得长（悬垂引用会被拒绝）。

省略规则：函数只有一个输入生命周期参数时，输出生命周期默认与之一致；方法中 &self/&mut self 的输出默认与 self 同寿命。多数场景无需手写标注。

第三章：Rust 并发与错误处理

概念基础

  1. Fearless Concurrency：所有权 + Send/Sync 在编译期阻止数据竞争，称「无畏并发」——多线程代码能编译过，基本就不会有数据竞争。
  2. Send/Sync marker trait：Send 允许跨线程转移所有权，Sync 允许跨线程共享 &T；编译器自动判定，Rc 非 Send、Mutex 内的值变 Sync。
  3. 所有权防数据竞争：多线程共享可变必须经 Arc+Mutex，裸共享 &mut 会被编译器拒绝。
  4. Result/Option 错误模型：可恢复用 Result<T, E>，不可恢复用 panic!；无异常机制，错误是值。
  5. ? 运算符：错误传播语法糖，遇到 Err 提前返回、Ok 取值继续，替代手写 match 层层传播。

本章聚焦并发与错误处理。所有权与基础语法见 第一章：Rust 入门与所有权系统；类型系统与 trait 见 第二章：Rust 类型系统与 trait；工程实践见 第四章：Rust 工程实践与 Web 开发。

四、Send/Sync 深入

Send：类型可跨线程转移所有权；Sync：&T 可跨线程共享（即 T 可安全被多线程读）。Arc<T> 要求 T: Sync + Send。

判定规则：

  • Rc<T> 非 Send（引用计数非原子），不能跨线程。
  • Mutex<T> 使 T 满足 Sync（加锁后可安全共享可变）。
  • RefCell<T> 非 Sync（运行期借用检查非线程安全）。
  • 裸指针 *const T/*mut T 既非 Send 也非 Sync。

五、Mutex/RwLock/Arc

RwLock 用于读多写少（多个读锁或一个写锁）；单线程内 Rc/RefCell 对应 Arc/Mutex。read() 返回多个只读锁，write() 独占写锁。

第二章：微服务架构模式

概念基础

  1. 单体 vs 微服务是取舍而非优劣：单体开发部署简单、跨模块调用是进程内方法调用；微服务独立部署、技术栈异构、故障隔离，代价是分布式带来的网络、一致性、运维复杂度——团队规模小、业务边界不清时别上微服务。
  2. 服务边界靠 DDD 限界上下文：拆分不能按「表」或「分层」，要按业务领域能力，用 DDD 的限界上下文划定边界，上下文内高内聚、跨上下文低耦合，避免拆出「贫血微服务」。
  3. 数据一致性是 BASE 而非 ACID：跨服务无法共享数据库事务，从强一致 ACID 退到最终一致 BASE——基本可用、软状态、最终一致；靠 Saga、本地消息表、事务消息等补偿机制达成。
  4. 同步与异步通信各有代价：同步（REST/gRPC）链路直白但放大故障、级联超时；异步（消息队列）解耦削峰但引入最终一致与消息幂等；选型看场景，关键链路常混用。
  5. 可观测性必须先行：微服务调用链变长、故障定位难，日志+指标+链路追踪三件套要在上线前就位，否则线上出了问题只能盲人摸象。

本章聚焦拆分、通信、事务、容错四大主题；配套落地见 第一章：cloud 微服务工程架构总览与生产落地 与 第七章：集成 Sentinel：流控、熔断与服务保护。

一、服务拆分策略

拆分是微服务成败的第一步——拆错边界，后续全是补救。

按业务能力拆分与 DDD 限界上下文

  • 按业务能力：订单、库存、支付、用户各自成服务，能力即服务边界。
  • DDD 限界上下文映射：每个上下文对应一个服务，上下文间通过**防腐层（ACL）**翻译模型，避免领域模型互相渗透。

拆分粒度权衡与绞杀者模式

  • 粒度权衡：太细则跨服务调用爆炸、运维成本高；太粗则退回单体。经验值：一个服务能由一个「两披萨团队」独立维护。
  • 绞杀者模式 Strangler Fig：老单体不敢一刀切，在边界逐步新建微服务、用网关分流流量，老的逐步下线，平滑迁移。

  • 服务发现：Nacos/Eureka 注册中心，服务启动注册、消费方拉取实例列表。

四、容错与弹性

微服务故障是常态，弹性设计让局部故障不扩散为全局雪崩。

熔断：Sentinel 状态机

  • CLOSED：正常放行；OPEN：直接拒绝、走 fallback；HALF_OPEN：放半数探测请求决定恢复或再开。

限流、降级、隔离

  • 限流算法：计数器（简单有临界突刺）、滑动窗口（平滑）、令牌桶（允许突发）、漏桶（匀速）。
  • 隔离：线程池隔离（资源物理隔离、开销大）、信号量隔离（轻量、限并发数）——即舱壁模式 Bulkhead。
  • 超时级联：上游超时设置应短于下游，避免下游已成功上游却已重试，造成重复。

五、CQRS 与事件溯源

CQRS：读写分离模型

读写负载差异大时，把「命令写模型」与「查询读模型」分离，写走领域模型、读走优化表，二者通过领域事件同步。

事件溯源与快照

  • 事件溯源：不存最终状态，存全量事件序列，状态由回放事件得到，天然有审计与时间旅行能力。
  • 快照：事件太多回放慢，定期打快照保存当前状态，从最近快照 + 增量事件重建。
  • 最终一致：读模型与写库异步同步，存在延迟，查询要容忍。

六、API 网关与 BFF

网关职责与 Spring Cloud Gateway

BFF 与 GraphQL 聚合

  • BFF（Backend For Frontend）：为不同端（Web/App/小程序）定制后端，聚合多个微服务数据，避免前端 N 次调用。
  • GraphQL 聚合层：客户端按需声明字段，聚合层一次返回，解决 REST 过度/不足获取。

第一章：设计模式精要

概念基础

  1. 模式是经验总结而非教条：GoF 23 种模式是前人对「重复出现问题」的可复用解抽象，目的是沟通词汇与复用经验，不是套用即对的银弹；套错场景比不用更糟。
  2. 三大类划分：按职责分创建型（如何new对象：单例/工厂/建造者/原型）、结构型（如何组合对象：适配器/装饰器/代理/外观/组合/享元/桥接）、行为型（对象如何协作：策略/观察者/模板/责任链/命令/状态/迭代器等）。
  3. 模式 vs 反模式：模式是「验证过的好做法」，反模式是「常见却糟糕的做法」；识别反模式往往比背模式更能提升代码质量——上帝类、箭头嵌套、硬编码都是高频反模式。
  4. 语言差异决定落地形态：Java 经典面向对象，继承/接口齐全，模式以「类结构」呈现；Go 无继承、靠组合与接口隐式实现，单例用 sync.Once、策略靠函数值，形态更轻量；Python 鸭子类型+装饰器语法糖让装饰器/策略写法更自然。
  5. 模式常组合使用：真实框架很少只用一种——Spring Bean 默认单例，AOP 用动态代理，JdbcTemplate 是模板方法，三者叠加才构成「声明式事务」；理解组合才能读懂框架。

本章代码以 Java 17 / Go 1.22 / Python 3.12 为基准，结合框架实例识别模式；后续见 第二章：微服务架构模式 与 第三章：高并发系统设计。

一、创建型模式：对象的构造

创建型关注「谁来 new、怎么 new、何时 new」，核心是把「对象创建」与「对象使用」解耦。

单例：Java 双检锁 vs Go sync.Once

枚举单例更安全：Java 用 enum 实现单例天然防反射攻击与反序列化重建，是《Effective Java》首选。

工厂方法：简单工厂 / 工厂方法 / 抽象工厂

建造者：链式调用

原型：深浅拷贝

模式 意图 典型场景 注意点
单例 全局唯一实例 配置/连接池/日志 线程安全与懒加载
简单工厂 按参数造对象 分支少 违反开闭，分支多则臃肿
工厂方法 每产品一工厂 产品族扩展频繁 类爆炸
抽象工厂 产品族统一创建 跨平台 UI 主题 加产品难、加产品族易
建造者 分步构造复杂对象 多参数可选 链式、不可变对象
原型 克隆已有对象 创建成本高 区分深浅拷贝

二、结构型模式：对象的组合

结构型关注「对象怎么拼」，目标是把小对象组合成大结构同时保持松耦合。

适配器：接口转换

代理：远程 / 虚拟 / 保护

三、行为型模式：对象的协作

行为型关注「对象怎么通信、职责怎么分配」。

策略：算法族替换

观察者：发布订阅基础

模板方法、责任链、命令、状态

四、在框架中识别模式

模式真实价值在框架里——读懂框架的「模式骨架」就抓住了扩展点。

  • Spring：代理（AOP @Transactional 织入事务）+ 单例（Bean 默认 singleton）+ 模板方法（JdbcTemplate 把连接/参数/关闭写死，只填 RowMapper）。

第三章：高并发系统设计

概念基础

  1. 高并发三指标 QPS/RT/并发数：QPS 每秒请求数、RT 响应时间（区分 P50/P99/P999）、并发数同时在线请求数，三者满足 QPS = 并发数 / RT——降 RT 与提并发数都能提 QPS，但 RT 是用户体验底线。
  2. 扩展性：垂直 vs 水平：垂直扩展是单机升配（CPU/内存/SSD），有上限且成本指数增长；水平扩展是多实例分摊流量，理论上无上限，但要解决状态分布、数据分片、一致性。
  3. 缓存不是银弹：缓存能扛住读 QPS，但带来一致性、穿透、雪崩、击穿四大难题；写多读少或强一致场景缓存收益小且风险大，滥用缓存是高并发系统最常见的事故源。
  4. 降级保核心：流量洪峰时主动牺牲非核心功能（评论、推荐、日志）保全核心链路（下单、支付），降级要预案先行、开关可灰度，而非临时手忙脚乱。
  5. 容量规划先行：先估算峰值 QPS 与单机容量，倒推实例数与资源水位线，再配弹性伸缩；没有容量规划的高并发是赌博，全链路压测是上线前的强制校验。

本章聚焦缓存、数据库扩展、削峰、限流降级四板斧；缓存与数据库基础见 第一章：Redis 概述、安装与 CLI 入门 与 第一章：MySQL DDL 语句与表设计入门。

一、缓存架构

多级缓存

请求从前到后层层兜底：浏览器 → CDN → Nginx → 本地缓存（Caffeine）→ Redis → DB，每层挡住一部分流量，越靠前越快也越易失效。

缓存穿透 / 击穿 / 雪崩

问题 现象 解决方案
穿透 查不存在的 key，缓存 DB 都没有，每次打 DB 布隆过滤器拦截；空值缓存短 TTL
击穿 单个热点 key 过期瞬间，海量请求直击 DB 互斥锁（只放一个回源）+ 热点永不过期后台刷新
雪崩 大量 key 同时过期，DB 瞬时压力暴增 TTL 加随机偏移；多级缓存兜底；熔断限流

缓存一致性策略

策略 做法 一致性 复杂度
Cache Aside 先更 DB 再删缓存，读时回填 最终一致 低，推荐
Read Through 缓存代理回源，应用只读缓存 较强 中
Write Through 写穿缓存再写 DB，同步 强 中
Write Behind 写缓存即返回，异步刷 DB 弱但快 高

Cache Aside 的删缓存时机：先更 DB 后删缓存，配合延迟双删（删→更→延迟再删）可缓解主从延迟导致的脏读。

热点 Key

热点 Key 单分片扛不住时：本地缓存吸收读、分片打散（key 加随机后缀分散到多分片）、只读副本分流。

二、数据库扩展

读写分离

主库写、从库读，主从复制异步。代码层用 ShardingSphere 自动路由：写走 master、读走 slave。

分库分表

  • 垂直拆分：按字段拆表（商品基本信息 vs 商品详情长文），解决单表字段过多。
  • 水平拆分：按分片键（如 user_id）把数据分散到多库多表，解决单表数据量过大。

分片键选择与全局 ID

  • 分片键：选高频查询条件（如 user_id），避免跨片查询；不带分片键的查询会广播所有分片。
  • 跨片查询：用 ES 建二级索引，或宽表汇总，避免广播扫描。
  • 全局唯一 ID：雪花算法（时间戳+机器 ID+序列号），趋势递增利于 B+树插入。

三、消息队列削峰

消息队列在高并发里干三件事：削峰填谷（把瞬时洪峰蓄进队列、匀速消费）、异步解耦（写完即返回、下游异步处理）、最终一致（事件驱动跨服务状态同步）。

消费者背压与幂等

死信队列：消费失败重试达上限后转入 DLQ 人工介入；位移提交：业务成功后再 MarkMessage，避免处理失败丢消息。MQ 基础见 第一章：Kafka 消息中间件入门：核心概念与架构。

限流算法

算法 特点 场景
计数器 固定窗口、临界突刺 简单限频
滑动窗口 平滑、无突刺 接口 QPS 限流
令牌桶 允许突发、匀速补桶 网关入口限流
漏桶 匀速出水、削峰 下游保护

降级与熔断实战

  • 降级分级：读降级（缓存/默认值）、写降级（同步转异步）、功能降级（关评论/推荐）。
  • 熔断：错误率/RT 超阈值触发，OPEN 直接拒绝，休眠后 HALF_OPEN 探活恢复。

五、CDN 与静态化

CDN 边缘缓存与动静分离

CDN 把静态资源缓存到离用户最近的边缘节点，回源率是成本与体验的关键。动静分离让动态请求走应用、静态走 CDN/Nginx。

第一章：测试方法论与单元测试

概念基础

  1. 测试金字塔 70/20/10：经验比例是 70% 单元 / 20% 集成 / 10% E2E——越往底越便宜、越快、越稳；倒置成「冰淇淋模型」会让 CI 慢得没人敢跑。
  2. 验证正确性 vs 设计反馈：测试一面证明代码做对了，一面反向驱动设计——写不动的测试往往暴露耦合过重的代码，是免费的设计评审。
  3. FIRST 原则：Fast 快、Isolated 隔离、Repeatable 可重复、Self-validating 自验证、Timely 及时；任一条破了，测试就开始腐烂。
  4. 测试不是 QA 专属：开发人员写单元 / 集成测试是职责的一部分；QA 更适合承接探索性测试、E2E、验收，二者互补而非甩锅。
  5. Mock vs Stub vs Fake 区别：Stub 只喂预设返回值，Mock 还验证交互，Spy 包装真实对象记录调用，Fake 是简化但能工作的实现（如内存仓库）；混用会让测试语义模糊。

第二章：集成测试与 E2E 测试

概念基础

  1. 集成测试定义：验证模块间协作是否正确——服务与数据库、服务与服务、模块与模块的接线点，单元测试替不了，E2E 又太贵，集成测试填补中间地带。
  2. E2E：用户视角：从真实入口（浏览器 / App / CLI）走完整业务流，验证「用户真能完成这件事」；它不关心内部实现，只关心端到端结果。
  3. 契约测试：消费者驱动：消费方先写「我期望 Provider 返回什么」的契约，Provider 验证自己满足契约，避免双方联调时的集成地狱。
  4. Testcontainers 革命：用一次性 Docker 容器跑真实依赖（Postgres / Redis / Kafka），让集成测试接近单元测试的速度与隔离性，又不丢真实度。
  5. 测试环境一致性：本地、CI、预发跑的依赖版本必须对齐，否则「我这能过」频发；镜像化依赖是消除环境漂移的根本手段。

本章承接 第一章：测试方法论与单元测试 的单元层，把验证范围抬升到跨模块、真实依赖与浏览器全链路。

一、集成测试策略

模块间集成 vs 外部依赖集成：前者验证自家代码之间的接线（订单服务调用库存服务的客户端）；后者验证自家代码与外部系统（数据库、消息队列、三方 API）的接线。前者偏快、偏纯；后者需要环境，是 Testcontainers 的主战场。

测试双金字塔：金字塔之外再叠一座「契约金字塔」——服务间用契约测试替代大量重型集成测试，E2E 只保留少量关键路径，整体成本骤降。

数据准备：Builder / Fixture / Factory：

  • Fixture：固定数据集（如 users.yml），适合不变的场景底座。
  • Factory：按需造数据（如 OrderFactory.paid()、OrderFactory.pending()），适合多变组合。
  • 原则：测试数据自给自足，不依赖其他测试留下的状态。

事务回滚 vs 清理策略：

策略 做法 优缺点
事务回滚 每个用例开事务，结束回滚 快、干净；不适用于跨连接场景
清理脚本 用例后 TRUNCATE / DELETE 通用；需注意外键顺序
一次性容器 每用例新容器 最隔离；启动开销需用单例缓存优化

第一章：CI/CD 入门与 GitHub Actions

概念基础

  1. CI / CD / Continuous Deployment 是三个递进概念：CI（持续集成） 把代码合并到主干并自动构建测试；CD（持续交付 Continuous Delivery） 在 CI 基础上把可部署产物推到制品库，发布动作仍需人工点击；Continuous Deployment（持续部署） 把人工环节也省掉，每次主干合并自动上线，差异关键在”最后一公里是否需要人“。
  2. 流水线阶段（Pipeline Stages） 通常按 Checkout → Build → Test → Scan → Package → Publish → Deploy 串联，每阶段失败立即中断，避免错误向下传递；阶段之间通过**构建产物（Artifact）**而非源码传递，保证”构建一次、到处部署”。
  3. 声明式 vs 脚本式：声明式（GitHub Actions YAML、Jenkins Declarative Pipeline）用结构化语法描述”做什么”，可读、可静态校验、IDE 友好；脚本式（Jenkins Scripted Pipeline）用 Groovy 编排”怎么做”，灵活但难审阅，复杂分支逻辑才回退脚本式。
  4. 缓存策略 决定流水线是否”快得起来”：依赖（~/.m2、node_modules）按 依赖锁文件 hash 作 cache key 缓存；Docker 层走 BuildKit --mount=type=cache 共享；不可变产物（jar/wheel）只缓存构建输入，不缓存输出，避免污染发布物。
  5. 密钥管理 铁律是”密钥永远不进代码“：GitHub 用 Secrets（加密、日志自动打码）、Actions 用 OIDC 短期令牌替代长期 Access Key；生产环境靠 Environment + 审批 + 分支保护三重门，避免一人推主干即上线。

第二章：Jenkins 与发布策略

概念基础

  1. Jenkins 定位：开源、可自托管的流水线引擎之王，靠插件生态覆盖几乎所有语言/云/部署场景；与 GitHub Actions”云原生 SaaS”不同，Jenkins 强在完全可控、内网部署、Agent 可挂物理机/容器/K8s，劣势是运维成本高、插件兼容性坑多。
  2. Declarative vs Scripted Pipeline：Declarative 用 pipeline { stages {} } 结构化语法，可读、可静态校验、对 IDE 友好，适合 90% 场景；Scripted 用 Groovy 自由编程，灵活但难审阅，仅复杂动态逻辑才回退 Scripted，二者底层都是同一套 Graph 执行模型。
  3. 蓝绿 / 金丝雀 / 滚动 是三大发布策略：蓝绿准备一套完整备用环境瞬间切流（需双倍资源）；金丝雀按小比例流量灰度观察后再放量（需流量分流能力）；滚动逐批替换 Pod（默认策略，资源增量小但发布期间新旧并存）。
  4. 回滚策略遵循”代码可秒退，数据需慢退“：K8s rollout undo 与 Helm rollback 可瞬间切回上一版本镜像；但数据库 schema 变更必须前向兼容（扩列先加后删），靠”发布分两步“避免锁死回滚路径。
  5. 基础设施即代码（IaC） 是 GitOps 的前提：K8s 清单、Helm values、Kustomize overlay 全部进 Git，Git 即单一可信源，部署不靠”登录 master 手敲 kubectl”，而是PR 合并即同步，可审计、可回滚、可重现。

四、发布策略详解

蓝绿部署（双倍资源 + 切流）

参数 含义 推荐值

数据库变更回滚策略

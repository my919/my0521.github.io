Redis List 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 484 阅读时长 ≈ 2 分钟

Redis List 是双向链表上的字符串元素序列，按下标与范围访问，两端 LPUSH / RPUSH / LPOP / RPOP 时间复杂度多为 O(1)。适合队列、栈、最新 N 条动态等场景。写法对齐同仓库 Hexo 教程：小节 + 命令表 + 可复制示例。部署见 Redis-Docker.md。

一、List 是什么

  1. 有序、可重复；同一 value 可出现多次。
  2. TYPE key 为 list。
  3. 中间插入/删除代价高于两端（需遍历指针）；设计时尽量从两头消费。

二、常用命令（必会子集）

命令 作用
LPUSH / RPUSH 左/右入队
LPOP / RPOP 左/右出队
LRANGE key start stop 闭区间下标范围（-1 表末尾）
LLEN 长度
LINDEX / LSET 按下标读 / 写
BLPOP / BRPOP 阻塞出队（简单队列常用）

说明：高版本提供 LMOVE / BLMOVE 等，用于安全队列迁移元素；与已废弃的 BRPOPLPUSH 同类需求可查当前版本文档。

三、典型应用场景

  1. FIFO 队列：RPUSH + LPOP（或反向一对）。
  2. 最新消息流：LPUSH + LTRIM key 0 99 保留最近 100 条。
  3. 阻塞消费：BLPOP 多个 key 时按顺序等待，可做简单任务队列（复杂语义建议 Stream 或专业消息中间件）。

五、注意事项

  1. 消费者崩溃：LPOP 后数据即丢，需业务确认机制或改用 BRPOP + 处理完再 ack` 等模式；严肃场景评估 Stream、RabbitMQ 等。
  2. 长列表：LRANGE 0 -1 大列表慎用；分页用 LRANGE 分段。
  3. 与 Set/ZSet 区别：List 有序可重复；Set 无序唯一；ZSet 有序唯一带分值。

Redis String 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 1.1k 阅读时长 ≈ 4 分钟

Redis String 是最常用的类型：本质是二进制安全的字节序列（可存文本、JSON、序列化对象、图片片段等），单值上限约 512MB（实际业务应远小于该上限）。下文按「命令 → 场景 → redis-cli 案例 → 注意点」组织，部署见 Redis-Docker.md。

一、String 是什么（和「键」的关系）

  1. Redis 是 KV 模型：键（key） 永远是字符串；值（value） 可以是 String / Hash / List 等类型之一。
  2. 本文说的 String 指 value 的类型为 string（TYPE key 显示 string）。
  3. 编码：底层可能为 int、embstr、raw 等（OBJECT ENCODING key 可查看），对使用者多数时候透明，选型时更关心语义与命令。

二、常用命令（必会子集）

1. 读写与删除

MSET / MGET：一次多键，减少往返（注意原子性与键命名规范）。

2. 带条件的写入与过期（业务高频）

SET 常用选项（Redis 2.6+ 语法，具体以你版本文档为准）：

选项 含义
EX 秒 / PX 毫秒 设置过期时间（TTL）
NX 仅当 key 不存在 时写入（常用于抢锁占位）
XX 仅当 key 已存在 时覆盖

3. 计数器：INCR / DECR / INCRBY

INCR 在值可解析为整数时原子自增；不存在时按 0 开始。

4. 其它实用命令

命令 作用
APPEND 尾部追加字节
STRLEN 返回字节长度
GETRANGE / SETRANGE 按偏移读写子串（仍整体是 String）
GETSET 读旧值并写新值（单原子操作，适合简单状态切换）

三、典型应用场景

  1. 缓存整页或对象：值存 JSON 字符串，配合 EX 做短期缓存；更新数据库后删键或覆盖避免脏读。
  2. 会话 / 登录态：SET … EX … 存 token → 用户信息；过期自动消失。
  3. 计数与限流：INCR 做浏览量、接口调用次数；与滑动窗口等逻辑配合（复杂限流可再引入 Hash / ZSet）。
  4. 分布式锁（谨慎）：SET key token NX PX ttl 仅占位；完整锁需唯一 token、Lua 校验身份释放、续期、Redlock 争议等专题，本文只给入门占位思路。
  5. 配置与功能开关：SET feature:x:enabled 1，读时 GET 转布尔。

五、注意事项与选型

  1. 大 value：单 String 过大占用内存与网络带宽，序列化大对象可评估 Hash 分字段或拆 key。
  2. 热 key：同一 key 超高并发时，单线程处理该 key 易成瓶颈，需业务侧分片或换结构。
  3. KEY 命名：建议 业务:实体:id:属性> 一类可读前缀，避免全局 KEYS * 在生产使用（用 SCAN）。

PostgreSQL 并发与 MVCC 入门

发表于 2026-05-03 分类于 PostgreSQL 本文字数： 576 阅读时长 ≈ 2 分钟

PostgreSQL 以 MVCC（多版本并发控制） 为主：读写通常不互相阻塞读路径；写与写仍可能因行级锁、唯一约束等冲突。本文偏用法与现象，与 PostgreSQL索引与性能优化.md（EXPLAIN、隔离级别配置）互补。若你熟悉 《MySQL锁详解》（MySQL锁详解.md），可对照：InnoDB RR + 间隙锁 与 PostgreSQL 的快照与谓词锁（SSI） 并非一一对应，勿硬套术语。

一、快照与默认隔离级别

  • 默认 READ COMMITTED：单条 SQL 内看到语句开始时已提交的数据版本。
  • REPEATABLE READ：事务内首条 SQL 建立快照，后续读一致。
  • SERIALIZABLE：可检测读写依赖，失败时返回 40001 serialization_failure，应用应重试。

二、显式行锁：FOR UPDATE / FOR SHARE

  • FOR UPDATE：排他行锁，用于「先读后改」的临界区。
  • FOR SHARE：共享行锁，允许他人并发读，阻塞写。

三、SKIP LOCKED 与 NOWAIT（队列与抢锁）

SKIP LOCKED：跳过已被其他事务锁定的行，取下一批可用行——常用于任务队列、公平抢单。

NOWAIT：若不能立即加锁则立刻报错，适合避免长时间等待（由应用捕获错误后重试或放弃）。

四、死锁（deadlock detected）

PostgreSQL 会自动检测事务间循环等待，回滚其中一个事务（报错 40P01 deadlock_detected）。
规避思路与 MySQL 类似：固定加锁顺序、缩短事务、避免无关长耗时在事务内执行。

五、与 MySQL InnoDB 的粗对照（防混）

话题 MySQL InnoDB（见 MySQL锁详解.md） PostgreSQL（入门记法）
默认隔离 常为 RR RC
幻读与范围锁 间隙锁 / Next-Key 叙述多 SSI / 谓词锁 等在 SERIALIZABLE 下讨论多
队列抢任务 FOR UPDATE + 设计索引 FOR UPDATE SKIP LOCKED 一等公民

PostgreSQL 索引与性能优化

发表于 2026-05-03 分类于 PostgreSQL 本文字数： 1.1k 阅读时长 ≈ 4 分钟

面向业务开发与日常运维：能读 EXPLAIN、理解默认隔离级别、会开慢语句日志、知道逻辑备份与 WAL / PITR在说什么。与 PostgreSQL并发与MVCC入门.md（行锁、SKIP LOCKED、死锁与快照）互补；部署与数据卷见 PostgreSQL-Docker.md。

一、索引在干什么：B-Tree 直觉（默认）

PostgreSQL 默认 CREATE INDEX 多为 B-Tree（USING btree，可省略）。
直觉与 MySQL InnoDB 二级索引类似：以平衡树组织键，等值 / 范围查询减少随机读；主键 / 唯一约束底层也会建索引。

其他索引类型（点到为止）：GIN（全文、jsonb 含键）、GiST（地理、范围类型）、BRIN（超大顺序相关表）等，选型需读官方文档与压测。

二、联合索引与最左前缀

联合索引 CREATE INDEX idx_abc ON t (a, b, c); 的排序语义仍是先 a 再 b 再 c。
WHERE a = ? AND b = ? 易命中；仅 WHERE b = ? 往往用不上该索引（与 MySQL 同款直觉）。
函数包裹列（如 WHERE lower(email) = ?）常导致无法走 btree，需表达式索引（CREATE INDEX ON t ((lower(email)))）或改写法。

三、仅索引扫描（Index Only Scan）

若查询列均可由某索引覆盖，且可见性映射（VM）允许优化器认为堆页全可见，EXPLAIN 可能出现 Index Only Scan。
与 MySQL 的 Using index 类似但不等价；仍以 EXPLAIN (ANALYZE, BUFFERS) 实测为准。

四、怎么看执行计划：EXPLAIN / EXPLAIN ANALYZE

入门优先看：

字段 / 标记 含义（入门）
Seq Scan 顺序扫表，大表 + 高 rows 要警惕
Index Scan / Index Only Scan 走索引访问
Nested Loop / Hash Join / Merge Join 连接策略
ANALYZE 的 actual time、rows 真实耗时与行数（与统计信息、缓存有关）
BUFFERS 读了多少共享缓冲区（判断是否 I/O 重）

统计信息维护：ANALYZE tbl;（VACUUM ANALYZE 亦可），大变更后应跑。

五、事务与隔离级别（用法向）

1. 基本写法

默认 READ COMMITTED：每条语句看到语句开始时已提交的快照（简化理解）。
REPEATABLE READ：事务内第一条语句建立快照，读一致性更强。
SERIALIZABLE：最强，可能出现 serialization_failure，应用需重试。

与 MySQL InnoDB 默认 RR 不同：PostgreSQL 默认 RC；跨库迁移时注意语义差异。行级锁、FOR UPDATE、死锁见 PostgreSQL并发与MVCC入门.md。

六、慢语句与观测「三板斧」（点到为止）

1. 日志：log_min_duration_statement

在 postgresql.conf 或 ALTER SYSTEM（需 reload）中设置，例如记录超过 200ms 的语句（数值按环境调）。

2. pg_stat_statements（扩展）

需 shared_preload_libraries 预加载（运维配置），此处不展开。

3. auto_explain（扩展）

自动对超时语句打计划，适合测试环境；生产按规范启用。

落地顺序：先慢日志或 pg_stat_statements 抓 Top SQL → EXPLAIN (ANALYZE, BUFFERS) → 改索引或改写法 → VACUUM ANALYZE。

七、VACUUM 与膨胀（可靠性常识）

PostgreSQL 的 MVCC 会使更新/删除留下死元组；VACUUM（通常由 autovacuum 自动跑）回收空间、更新统计信息。长期不 vacuum 会导致表膨胀、性能变差。
日常开发：大批量导入/更新后，测试库可手动 VACUUM ANALYZE；生产依赖 autovacuum 参数与监控。

八、备份恢复与 PITR 概念

1. 逻辑备份 pg_dump / pg_restore

-Fc 为自定义目录格式，便于并行恢复；纯 SQL 可用 -Fp。

2. 物理与 WAL

PITR 依赖：基础备份（文件系统级或 pg_basebackup）+ 连续归档的 WAL + 恢复目标时间。与 MySQL binlog 地位类似的是 PostgreSQL WAL；具体恢复命令属 DBA 手册级。

3. 与 Docker 的关系

容器内 $PGDATA 一般在卷上（见 PostgreSQL-Docker.md）；备份策略要约定「从宿主机 pg_dump 连容器端口」还是「卷快照 + WAL 归档」，并做恢复演练。

PostgreSQL 存储与执行模型概览

发表于 2026-05-03 分类于 PostgreSQL 本文字数： 742 阅读时长 ≈ 2 分钟

PostgreSQL 没有与 MySQL 建表子句 ENGINE=InnoDB / MyISAM 等价的「多存储引擎二选一」模型：进程内是一套统一的后台执行与存储子系统（常说的 PostgreSQL 引擎多指整个数据库内核版本，而非可选插件式表引擎）。若需对照 MySQL 存储引擎，请读同目录 MySQL引擎.md。

姊妹文：PostgreSQL并发与MVCC入门.md（快照与行锁）、PostgreSQL索引与性能优化.md（EXPLAIN、VACUUM）、PostgreSQL-Docker.md（$PGDATA 与部署）。

一、表数据默认怎么存：Heap（堆表）

  • 普通 CREATE TABLE 默认即 heap 表：行以堆页存放，通过 tid（块号 + 行号） 定位。
  • MVCC 在元组头维护版本信息（xmin / xmax 等），更新与删除产生新版本/死元组，依赖 VACUUM 回收（见 PostgreSQL索引与性能优化.md）。
  • 与 InnoDB 聚簇索引即整表不同：PostgreSQL 主键索引是二级索引，堆上存行，主键查找通常「索引 → 回表 tid」。

二、表访问方法（Table Access Method）

PostgreSQL 12+ 起，表可指定 USING heap（默认）；理论上可挂自定义表访问方法（需扩展提供）。
生产常见仍是 heap；列存、混存等多在扩展或外部产品（如某些分析型方案）中实现，不等价于 MySQL 换一个 ENGINE 字符串。

三、与「引擎」易混的几个概念

概念 说明
TABLESPACE 表/索引的文件放置位置（如 pg_default），不是另一种行存储引擎。
TOAST 大字段行外存储机制，对用户基本透明。
Foreign Data Wrapper（FDW） 外部表：数据在远程；语法像本地表，语义与本地 heap 完全不同，不是换存储引擎。
内置索引类型 B-Tree、Hash、GiST、GIN、BRIN 等是索引访问方法，不是替换 heap 的「表引擎」。

四、和 MySQL InnoDB 的粗对照（选型沟通用）

话题 MySQL（MySQL引擎.md） PostgreSQL（本文）
建表选「引擎」 ENGINE=InnoDB 等 无；默认 heap + 统一内核
行存与主键 InnoDB 聚簇主键与数据同树 堆行 + 主键索引
并发读写的核心 InnoDB MVCC + 锁 MVCC + 行锁（见 PostgreSQL并发与MVCC入门.md）

五、实务建议

  1. 学习 PostgreSQL 时少问「用哪个引擎」，多问索引类型、执行计划、VACUUM、隔离级别与锁。
  2. 需要列存、分片、多副本高可用时，在架构层选专用扩展或产品（如 Citus、云厂商数仓、读写分离），而不是在 CREATE TABLE 里找一个 ENGINE 开关。
  3. 版本升级（14 → 16 → 17）会带执行器与优化器演进，「升级引擎」口语上常指升级主版本，与 MySQL 的 ENGINE 不是同一概念。

MySQL 存储引擎概览

发表于 2026-05-03 分类于 MySQL 本文字数： 697 阅读时长 ≈ 2 分钟

MySQL 在服务器层之下，通过可插拔存储引擎把「行怎么存、事务与锁如何实现」交给不同实现。建表时可指定 ENGINE=…（8.0 起默认 InnoDB）。姊妹文：MySQL-Docker.md（部署）、MySQL锁详解.md（InnoDB 锁）、MySQL索引与性能优化.md。

一、如何查看支持的引擎与默认值

建表未写 ENGINE 时使用 default_storage_engine（一般为 InnoDB）。

二、InnoDB（事实上的唯一首选）

维度 说明
事务 ACID；COMMIT / ROLLBACK、崩溃恢复（redo / undo）。
锁与并发 以行锁为主；隔离级别与间隙锁等见 MySQL锁详解.md。
索引与数据 聚簇索引即主键 B+ 树，二级索引叶子存主键；详见 MySQL索引与性能优化.md。
外键 支持 FOREIGN KEY（与 MySQL.md 中 DDL 一致）。
适用 OLTP、绝大多数业务库；官方默认与推荐。

三、MyISAM（ legacy，新业务避免）

维度 说明
事务 不支持事务与崩溃安全意义上的 InnoDB 同级别恢复。
锁 表级锁，写多读少场景易成为瓶颈。
索引 数据与索引布局与 InnoDB 不同；无聚簇主键同义实现。
典型遗留场景 老系统、只读库、部分空间索引历史用法；新表请勿选用。

四、MEMORY（内存表，谨慎）

  • 数据驻内存，进程崩溃或重启后易失；容量受 max_heap_table_size 等限制。
  • 曾用于临时高速缓存；现代实践更常见 Redis 或 InnoDB + 足够内存 + 合理索引。

五、其它引擎（知道名字即可）

引擎 一句话
ARCHIVE 高压缩追加存储，适合冷归档、很少更新。
CSV 以 CSV 形式存文件，多用于导入导出管道，非通用 OLTP。
BLACKHOLE 写入即丢弃，有时用于复制拓扑中的「中继」等特殊场景。
NDB（MySQL Cluster） 分布式集群专用，与普通单机 InnoDB 运维模型不同。

具体是否编译进你的 mysqld，以 SHOW ENGINES 为准。

六、选型与迁移建议

  1. 新表一律 ENGINE=InnoDB，并显式 DEFAULT CHARSET=utf8mb4（与 MySQL.md 一致）。
  2. 发现 MyISAM 老表：评估后 ALTER TABLE … ENGINE=InnoDB（需在低峰窗口做；大表走 gh-ost / pt-online-schema-change 等在线 DDL 工具，属运维专题）。
  3. 不要用 ENGINE 解决「性能问题」：优先索引、SQL、连接与事务设计。

一、索引在干什么：B+ 树直觉（够用版）

InnoDB 里，表数据按主键组织成一棵 B+ 树（聚簇索引）：叶子节点存「主键 + 整行数据」。
二级索引（你建的 INDEX / UNIQUE）叶子节点存「索引列 + 主键」，需要整行时往往要再回表到聚簇索引取数据。

下图便于建立直觉（示意：键值与层数为教学简化，与真实页大小、填充率无关）。

读图要点：上层结点只存分界键与子树指针；最底层叶子由双向链表串起，方便范围扫描；聚簇索引叶子是主键 + 行数据；二级索引叶子多一步按主键回表读完整行。

直觉：

  • 等值 / 范围命中索引列 → 树高度低、少读页 → 随机 I/O 变少。
  • 全表扫 → 叶子链顺序读，数据量一大就慢。
  • 索引不是越多越好：每次 INSERT/UPDATE/DELETE 都可能维护多棵索引树。

二、联合索引与最左前缀

联合索引 KEY idx_abc (a, b, c) 的排序语义是：先按 a，再 a 相同时按 b，再按 c。

能较好利用该索引的典型条件（示意）：

  • WHERE a = ?
  • WHERE a = ? AND b = ?
  • WHERE a = ? AND b BETWEEN ? AND ?

容易用不上或只用一截的情况：

  • WHERE b = ? AND c = ?（缺 a，与「最左」不一致）
  • WHERE a = ? OR d = ?（OR 另一侧常走另一条路径，易优化成 UNION 或改写法）
  • 对 a 做函数/隐式类型转换导致无法走树（例如 WHERE DATE(a_col) = ...）。

设计经验：把区分度高、过滤性大的列尽量放左侧；把范围查询列放联合索引右侧更常见（仍要结合 EXPLAIN 验证）。

三、覆盖索引（Using index）

若 SELECT 里出现的列都能从某条二级索引的叶子直接凑齐（含 WHERE 用到的索引列），InnoDB 可能只扫索引、不回表，EXPLAIN 的 Extra 常见 Using index。

典型收益：大宽表上只查少数列 + 条件列恰好在同一联合索引上，I/O 明显下降。

四、索引条件下推 ICP（一眼带过）

Index Condition Pushdown：把部分 WHERE 条件下推到存储引擎层，在索引扫描过程中就过滤，少回表。
在 EXPLAIN 里常见 Using index condition（与 Using index 不同：后者多为覆盖索引）。不必一次讲透优化器细节，看到术语知道「在索引层多干了一点过滤」即可。

3. PITR（Point-in-Time Recovery，按时间点恢复）

含义：不只恢复到「昨晚整库备份」，而是恢复到某事故前一秒。通常需要：

  2. 连续归档的 binlog**（**log_bin` 打开，并安全保存 binlog 文件）；

可靠性＝备份自动化 + 定期恢复演练 + binlog 留存策略；开发至少要懂「为什么不能只靠一台机子从不备份」。

MySQL锁详解

发表于 2026-05-03 分类于 MySQL 本文字数： 4.5k 阅读时长 ≈ 15 分钟

结构清晰、实战导向（基于 InnoDB，MySQL 5.7 / 8.0）。

一、锁的核心目的

锁 = 并发控制，解决：

  • 脏读、不可重复读、幻读
  • 防止多个事务同时修改同一数据导致不一致
  • 平衡 数据一致性 vs 并发性能

二、按粒度分类（最核心）

1）全局锁（Global Lock）

  • 粒度：整个数据库实例
  • 命令：
  • 特点：
    • 所有库所有表只能读、不能写
    • 阻塞 DML、DDL
  • 用途：全库逻辑备份
  • 替代方案（InnoDB）：

2）表级锁（Table-level Lock）

  • 粒度：整张表
  • MyISAM 只支持表锁；InnoDB 也有表锁（如 MDL）
  • 常用：
  • 元数据锁（MDL）：
    • 访问表时自动加，防止“查询中表被删/改结构”
    • 长事务 + DDL 极易导致 MDL 锁等待

3）行级锁（Row-level Lock，InnoDB 核心）

  • 粒度：单行或多行索引记录
  • 优点：并发高、冲突小
  • 缺点：开销大、依赖索引
  • 重点：行锁是锁索引，不是锁数据行
    无索引/索引失效 → 行锁退化为表锁（灾难）

三、按读写类型分类（S/X 锁）

1）共享锁（S 锁 / 读锁）

  • 特点：读读兼容、读写互斥
  • 加锁：
  • 场景：要保证数据不被修改，同时允许别人读

2）排他锁（X 锁 / 写锁）

  • 特点：写写互斥、读写互斥（独占）
  • 自动加：UPDATE / DELETE / INSERT
  • 手动加：
  • 场景：修改数据，禁止别人读或写

四、意向锁（IS / IX，表级）

作用：快速判断表内有没有行锁，避免全表扫行锁

  • IS：意向共享锁（要加 S 行锁）
  • IX：意向排他锁（要加 X 行锁）

规则：

  1. 事务加行锁前，必须先加对应意向锁
  2. 意向锁之间完全兼容
  3. 意向锁只和表级 S/X 锁互斥

五、InnoDB 行锁三大算法（RR 隔离级别默认）

1）记录锁（Record Lock）

  • 锁：单个索引记录
  • 触发：唯一索引 + 精准等值查询（命中）

2）间隙锁（Gap Lock）

  • 锁：索引之间的间隙（不包含记录）
  • 目的：防止幻读（禁止区间插入）
  • 示例：表有 id=1,3,5
  • 特点：间隙锁之间兼容，只与插入意向锁互斥

3）临键锁（Next-Key Lock）= 记录锁 + 间隙锁

  • 锁：左开右闭区间 (min, max]
  • InnoDB RR 默认，解决幻读
  • 示例：id=1,3,5
    • 查 id=3 → 锁 (1,3]
    • 查 id=4 → 锁 (3,5]

六、死锁（Deadlock）

1）必要条件（四个同时满足）

  • 互斥：资源独占
  • 持有并等待：拿着锁等别人的锁
  • 不可剥夺：不能强行抢锁
  • 循环等待：A 等 B，B 等 A

2）典型死锁示例

3）如何避免

  • 按固定顺序访问资源（先 id=1 再 id=2）
  • 控制事务大小，避免长事务
  • 合理设置超时：innodb_lock_wait_timeout=50
  • 死锁检测：SHOW ENGINE INNODB STATUS;

七、实战高频坑（必避）

  1. 无索引 → 行锁变表锁：UPDATE t SET name='a' WHERE age=20;（age 无索引）
  2. 长事务 + 慢查询 → 锁等待堆积
  3. RR 间隙锁导致插入阻塞：范围查询容易触发
  4. 忘记提交/回滚：锁一直不释放

八、总结（一句话记）

  • 粒度：全局 > 表 > 行（粒度越小，并发越高、开销越大）
  • 读写：S 锁共享，X 锁独占
  • 行锁三形态：记录锁、间隙锁、临键锁（RR 防幻读）
  • 死锁四条件：互斥、持有等待、不可剥夺、循环等待

十、五大实验：现象、原理与面试标准答

与第九节中五个脚本场景一一对应：现象 → 底层原理 → 面试可直接背诵的表述。

统一前提：

  • 引擎：InnoDB
  • 隔离级别：RR 可重复读（默认）
  • 锁粒度：行锁依赖索引，无索引降级为表锁

实验一：行排他锁 FOR UPDATE 阻塞演示

执行流程

会话1：开启事务 → id=1 加 FOR UPDATE 不提交
会话2：修改 id=1 被阻塞；修改 id=2 正常执行

现象

  1. 同一条主键记录：写操作被阻塞
  2. 不同主键记录：完全不受影响
  3. 会话1 commit 后，会话2立刻执行成功

底层原理

  1. FOR UPDATE 加 行级排他锁（X锁）
  2. 排他锁规则：写写互斥、读写互斥
  3. InnoDB 行锁只锁索引命中的单行，不影响其他行

面试标准答案

InnoDB 中通过主键/唯一索引精准查询加 FOR UPDATE，会加行级排他锁；只锁定当前命中的单行记录，其他行不受影响，能保证高并发。排他锁与任何读写操作都互斥，事务提交后锁自动释放。

实验二：无索引导致行锁退化为表锁

执行流程

按无索引字段 age=20 更新，会话1不提交，会话2更新完全无关的 id=2 也被阻塞

现象

明明更新不同行，却整张表都被锁住，所有写操作全部阻塞

底层原理

  1. InnoDB 行锁是锁索引，不是锁数据行
  2. 条件字段无索引，MySQL 无法定位具体行
  3. 只能逐行加行锁扫描全表，最终退化成表级锁

面试标准答案

InnoDB 行锁必须依赖索引。如果更新/删除条件没有索引或索引失效，MySQL 无法精确定位行记录，会扫描全表并逐行加锁，最终行锁降级为表锁，严重降低并发性能，开发中必须保证更新条件走索引。

实验三：共享锁与读写互斥演示

执行流程

会话1：LOCK IN SHARE MODE 加共享锁
会话2：普通SELECT能查，UPDATE/DELETE被阻塞

现象

  1. 多个事务可以同时加共享锁（读读兼容）
  2. 加了共享锁后，其他事务不能加排他锁、不能修改数据
  3. 事务提交后，写操作立刻放行

底层原理

  • 共享锁（S锁）：读读兼容，读写互斥
  • 意向锁辅助，S锁阻塞所有写操作，保证数据当前快照不被修改

面试标准答案

共享锁（S锁）又叫读锁，使用 LOCK IN SHARE MODE 加锁。特性是读读可以并发，读写、写写互斥；适合需要强一致性、临时禁止别人修改数据的场景，事务提交自动释放锁。

实验四：间隙锁与临键锁阻塞插入（RR 与幻读）

执行流程

会话1：范围查询 between 1 and 3 for update 不提交
会话2：插入区间内新 ID，直接被阻塞

现象

没有任何行被修改，只是范围加锁，却无法往区间里插入新数据

底层原理

  1. MySQL RR 隔离级别默认使用 Next-Key Lock 临键锁
  2. 临键锁 = 记录锁 + 间隙锁
  3. 范围查询会锁住索引区间间隙，禁止其他事务插入新记录，解决幻读
  4. 间隙锁只在 RR 存在，RC 隔离级别没有间隙锁

面试标准答案

InnoDB 在 RR 可重复读隔离级别下，采用临键锁（Next-Key Lock） 解决幻读。临键锁由记录锁+间隙锁组成，范围查询会锁定索引左右间隙，禁止其他事务在区间内插入数据；RC 读已提交级别会关闭间隙锁，因此无法彻底避免幻读，但并发更高。

实验五：经典死锁复现

执行流程

  • 事务1：先锁 id=1 → 再请求锁 id=2
  • 事务2：先锁 id=2 → 再请求锁 id=1
  • 互相等待，立刻触发死锁，MySQL 自动回滚一个事务

现象

  1. 互相持有对方需要的锁，循环等待
  2. InnoDB 自动死锁检测，回滚代价小的事务，抛出死锁异常
  3. 不会无限阻塞

底层原理

死锁产生四个必要条件同时满足：

  1. 互斥条件：锁资源独占
  2. 持有并等待：自己拿着锁，还等别人的锁
  3. 不可剥夺：锁不能被强行抢占
  4. 循环等待：事务形成等待环路

面试标准答案（必背）

死锁产生必须同时满足四个条件：互斥、持有并等待、不可剥夺、循环等待。
规避方案：

  1. 统一多事务访问资源的顺序；
  2. 拆分长事务，尽早提交；
  3. 避免在事务中做无关耗时操作；
  4. 合理设置锁等待超时时间。
    InnoDB 自带死锁检测机制，发现循环等待会自动回滚一个事务，避免程序卡死。

十一、面试高频一句话速记

  1. 行锁靠索引，无索引变表锁
  2. S 锁读读兼容，X 锁完全独占
  3. RR 有间隙锁防幻读，RC 没有
  4. 交叉改不同行、顺序乱写易出死锁

十二、二十道高频面试题与标准答

全部面试可直接背诵，基于 InnoDB、RR 隔离级别，精简不废话。

1. MySQL 有哪些锁分类？

答案

  1. 按粒度：全局锁、表级锁、行级锁
  2. 按读写：共享锁S、排他锁X
  3. InnoDB 特有：意向锁、记录锁、间隙锁、临键锁

2. 全局锁作用是什么？怎么加？

答案
整库只读，所有库表只能读不能写、阻塞 DDL/DML。
加锁：FLUSH TABLES WITH READ LOCK;
解锁：UNLOCK TABLES;
多用于全库逻辑备份；生产优先用 mysqldump --single-transaction 快照备份，不加锁。

3. 什么是 MDL 元数据锁？

答案
访问表时自动加，保护表结构不被中途修改/删除。
长事务不提交 + 执行 DDL 改表结构，会造成 MDL 锁等待阻塞，线上高发故障点。

4. 表锁和行锁区别？

答案

  • 表锁：粒度大、开销小、并发低、MyISAM 默认
  • 行锁：粒度小、开销大、并发高、InnoDB 支持
    InnoDB 优先用行锁提升并发。

5. 共享锁S、排他锁X 特性？

答案

  • 共享锁S：读读兼容，读写/写写互斥
  • 排他锁X：读写、写写全部互斥，独占资源
    加锁：
    S：select ... lock in share mode
    X：select ... for update

6. 意向锁 IS/IX 作用？

答案
意向锁是表级锁，事务加行锁前必须先加意向锁。
作用：快速判断表内是否有行锁，不用遍历所有行锁，提升加锁效率。

  • IS：要加 S 行锁
  • IX：要加 X 行锁
    意向锁之间互相兼容，只和表级 S/X 锁互斥。

7. InnoDB 行锁本质是什么？

答案
行锁锁的是索引，不是物理数据行。
查询条件无索引、索引失效，行锁会退化成表锁，并发骤降。

8. 什么情况下行锁会降级为表锁？

答案

  1. where 条件无索引字段
  2. 索引失效（函数、隐式类型转换、like 前缀模糊等）
  3. 没有命中任何记录，全表扫描加锁

9. InnoDB 三种行锁算法？

答案

  1. 记录锁：锁单行索引记录
  2. 间隙锁 Gap Lock：锁索引间隙，不锁记录，防止幻读插入
  3. 临键锁 Next-Key Lock = 记录锁+间隙锁，左开右闭区间，RR 默认

10. 间隙锁什么时候生效？什么时候关闭？

答案

  • 生效：RR 可重复读隔离级别、范围查询/不走唯一索引等值查询
  • 关闭：RC 读已提交 没有间隙锁，并发更高，但会有幻读

11. 临键锁解决了什么问题？

答案
在 RR 隔离级别下，通过临键锁+间隙锁彻底解决幻读，禁止其他事务在索引区间插入新数据。

12. 什么是幻读？怎么解决？

答案
同一事务内，前后两次范围查询，查到别人新插入的数据。
解决：

  • 数据库层：InnoDB RR + 临键锁
  • 业务层：悲观锁、分布式锁限制插入

13. 死锁产生的四个必要条件？

答案

  1. 互斥：锁资源独占
  2. 持有并等待：拿着自己的锁，等待别人的锁
  3. 不可剥夺：锁不能被强行抢占
  4. 循环等待：事务互相等待形成环路

14. MySQL 怎么处理死锁？

答案
InnoDB 有自动死锁检测，检测到循环等待后，自动回滚代价更小的一个事务，抛出死锁异常，避免无限阻塞。

15. 如何避免 MySQL 死锁？

答案

  1. 统一所有事务访问资源/更新行的顺序
  2. 精简事务，避免长事务，尽早 commit
  3. 事务内不做耗时网络/IO 操作
  4. 合理设置锁等待超时 innodb_lock_wait_timeout

16. for update 和 lock in share mode 区别？

答案

  • for update：加排他锁X，别人不能读也不能改
  • lock in share mode：加共享锁S，别人可以读、不能改

17. RR 和 RC 在锁层面最大区别？

答案

  1. RR 有间隙锁/临键锁，防幻读；RC 没有
  2. RC 行锁范围更小、并发更高，但存在幻读
  3. RC 锁释放更早，阻塞更少

18. 长事务有什么锁风险？

答案
长事务不提交：

  1. 行锁、MDL 锁长期不释放

  3. undo log 不能清理，占用磁盘
  4. 容易触发死锁、数据库性能雪崩

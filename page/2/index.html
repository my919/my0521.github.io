Redis HyperLogLog 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 396 阅读时长 ≈ 1 分钟

HyperLogLog（HLL） 是 Redis 2.8.9+ 提供的概率型数据结构：用固定约 12KB（标准实现）内存估算集合基数（不重复元素个数），结果有误差（标准误差约 0.81%），换极低内存统计 UV。部署见 Redis-Docker.md。

一、HyperLogLog 是什么

  1. 不是存明细，只支持 PFADD 添加元素、PFCOUNT 估算基数、PFMERGE 合并多个 HLL。
  2. 适合：海量 UV、IP 去重计数等允许近似的报表。
  3. 不适合：必须精确计数、需要枚举曾出现过的元素。

二、常用命令

命令 作用
PFADD key element [element ...] 向 HLL 增加元素（可批量）
PFCOUNT key [key ...] 单个或合并估算基数
PFMERGE destkey sourcekey [sourcekey ...] 合并到 dest

三、典型应用场景

  1. 页面 / 活动 UV：PFADD uv:2026-05-03:page1 <userId 或 sessionId>，定时 PFCOUNT。
  2. 多维度合并：按天分 key，日报用 PFMERGE 聚合成周 UV。

四、综合案例（redis-cli）

五、注意事项

  1. 误差：报表若要求精确 UV，需 Set（内存大）或离线数仓。
  2. 元素语义：PFADD 把参数当字节串；业务上应用统一 ID（如用户 ID），勿混多种粒度。
  3. 无法查询成员：不能问「谁访问过」，只能问「大约多少人」。

Redis ZSet（Sorted Set）数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 414 阅读时长 ≈ 1 分钟

Redis ZSet（Sorted Set） 是成员唯一、且每个成员带一个 score（双精度浮点） 的有序集合；按 score 排序，score 相同则按字典序排成员。适合排行榜、延时队列（score=时间戳）等。Set数据类型、应用场景及案例.md；部署 Redis-Docker.md。

一、ZSet 是什么

  1. TYPE key 为 zset。
  2. member 唯一；同一 member 再次 ZADD 会更新 score。
  3. 范围查询、排名 ZRANK/ZREVRANK 为高频 API。

二、常用命令（必会子集）

命令 作用
ZADD key score member 添加或更新分值
ZRANGE / ZREVRANGE 按排名升/降序取片段（WITHSCORES 带出分数）
ZRANGEBYSCORE 按 score 区间取
ZRANK / ZREVRANK 升序 / 降序名次（0 基）
ZSCORE / ZCARD / ZINCRBY 查分 / 成员数 / 原子加分
ZREM / ZPOPMIN / ZPOPMAX 删除成员 / 弹出最小/大

三、典型应用场景

  1. 游戏 / 活动排行榜：member=用户 ID，score=积分。
  2. 延时任务：score=执行时间戳，定时 ZRANGEBYSCORE 拉到期任务再 ZREM。
  3. 热搜权重：结合时间衰减可周期性重算 score（逻辑在应用层）。

四、综合案例（redis-cli）

五、注意事项

  1. 热 key：单排行榜 key 超高并发时考虑分片或本地缓存 + 合并。
  2. 大 ZSet：避免一次 ZRANGE 0 -1；分页用 ZRANGE 窗口。
  3. score 精度：浮点比较注意误差；时间戳建议统一毫秒或秒。

Redis Hash 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 470 阅读时长 ≈ 2 分钟

Redis Hash 是一个 field → value 的映射表，适合表示「一个对象的多属性」：可对单个字段读写，避免整颗 String JSON 反复序列化/反序列化。下文按「命令 → 场景 → redis-cli 案例 → 注意点」组织,部署见 Redis-Docker.md。

一、Hash 是什么

  1. 一个 key 下挂多对 field / value，field 与 value 均为字符串（二进制安全）。
  2. TYPE key 显示 hash。
  3. 适合「用户资料、购物车行、配置项分组」等属性较多且常单独更新的场景。

二、常用命令（必会子集）

命令 作用
HSET key field value [field value …] 设置一个或多个字段（Redis 4.0+ 推荐 HSET 多字段；旧 HMSET 已废弃）
HGET / HMGET / HGETALL 读单字段 / 多字段 / 全表
HDEL 删字段
HEXISTS / HLEN 字段是否存在 / 字段个数
HINCRBY / HINCRBYFLOAT 字段数值原子增减
HSCAN 大 Hash 迭代遍历（生产避免 HGETALL 撑爆网络）

三、典型应用场景

  1. 用户资料：user:1001 下 name / vip / city 等，改一项只动一个 field。
  2. 购物车行：cart:uid:1001 下 sku:2001 → 数量 JSON 或纯数字。
  3. 对象缓存：比整串 String 更易做局部更新；仍要注意过期策略与缓存一致性。

四、综合案例（redis-cli）

五、注意事项

  1. 大 Hash：字段极多时 HGETALL 成本高，列表页用 HSCAN 或只取需要的 HMGET。
  2. 小 Hash 编码：字段少且短时可能 ziplist 等紧凑编码，内存更省（OBJECT ENCODING 可观察）。
  3. 与 String JSON 选型：读多写少、整体替换频繁 → String；字段独立更新多 → Hash。

Redis Set 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 396 阅读时长 ≈ 1 分钟

Redis Set 是无序字符串集合，成员唯一（再次 SADD 同一成员不会重复插入）。适合标签、去重集合、交并差集合运算等。姊妹文：ZSet数据类型、应用场景及案例.md（需分值排序时用 ZSet）；部署 Redis-Docker.md。

一、Set 是什么

  1. TYPE key 为 set。
  2. 不保证顺序（遍历顺序实现依赖，勿当有序结构用）。
  3. 成员即字符串；集合间可做 SINTER / SUNION / SDIFF。

二、常用命令（必会子集）

命令 作用
SADD / SREM 增删成员
SMEMBERS 返回全部成员（大集合慎用）
SISMEMBER / SCARD 是否在集合 / 成员个数
SRANDMEMBER / SPOP 随机读 / 随机弹出
SINTER / SUNION / SDIFF 交 / 并 / 差（可带 STORE 写到新 key）

三、典型应用场景

  1. 标签：SADD article:7:tags Java Redis。
  2. 抽奖池 / 去重 ID 池：SPOP 不放回抽样（需理解并发下多个客户端抢 SPOP 的语义）。
  3. 共同关注：SINTER user:1:following user:2:following。

四、综合案例（redis-cli）

五、注意事项

  1. 大 Set：SMEMBERS 一次性拉全量可能阻塞与占带宽，用 SSCAN 迭代。
  2. 与 List：Set 无序且唯一；List 有序可重复。
  3. 需要按分数排序（排行榜）→ 用 ZSet，不要用 Set 硬撑。

Redis List 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 484 阅读时长 ≈ 2 分钟

Redis List 是双向链表上的字符串元素序列，按下标与范围访问，两端 LPUSH / RPUSH / LPOP / RPOP 时间复杂度多为 O(1)。适合队列、栈、最新 N 条动态等场景。写法对齐同仓库 Hexo 教程：小节 + 命令表 + 可复制示例。部署见 Redis-Docker.md。

一、List 是什么

  1. 有序、可重复；同一 value 可出现多次。
  2. TYPE key 为 list。
  3. 中间插入/删除代价高于两端（需遍历指针）；设计时尽量从两头消费。

二、常用命令（必会子集）

命令 作用
LPUSH / RPUSH 左/右入队
LPOP / RPOP 左/右出队
LRANGE key start stop 闭区间下标范围（-1 表末尾）
LLEN 长度
LINDEX / LSET 按下标读 / 写
BLPOP / BRPOP 阻塞出队（简单队列常用）

说明：高版本提供 LMOVE / BLMOVE 等，用于安全队列迁移元素；与已废弃的 BRPOPLPUSH 同类需求可查当前版本文档。

三、典型应用场景

  1. FIFO 队列：RPUSH + LPOP（或反向一对）。
  2. 最新消息流：LPUSH + LTRIM key 0 99 保留最近 100 条。
  3. 阻塞消费：BLPOP 多个 key 时按顺序等待，可做简单任务队列（复杂语义建议 Stream 或专业消息中间件）。

四、综合案例（redis-cli）

五、注意事项

  1. 消费者崩溃：LPOP 后数据即丢，需业务确认机制或改用 BRPOP + 处理完再 ack` 等模式；严肃场景评估 Stream、RabbitMQ 等。
  2. 长列表：LRANGE 0 -1 大列表慎用；分页用 LRANGE 分段。
  3. 与 Set/ZSet 区别：List 有序可重复；Set 无序唯一；ZSet 有序唯一带分值。

Redis String 数据类型、应用场景及案例

发表于 2026-05-03 分类于 Redis 本文字数： 1.1k 阅读时长 ≈ 4 分钟

Redis String 是最常用的类型：本质是二进制安全的字节序列（可存文本、JSON、序列化对象、图片片段等），单值上限约 512MB（实际业务应远小于该上限）。下文按「命令 → 场景 → redis-cli 案例 → 注意点」组织，部署见 Redis-Docker.md。

一、String 是什么（和「键」的关系）

  1. Redis 是 KV 模型：键（key） 永远是字符串；值（value） 可以是 String / Hash / List 等类型之一。
  2. 本文说的 String 指 value 的类型为 string（TYPE key 显示 string）。
  3. 编码：底层可能为 int、embstr、raw 等（OBJECT ENCODING key 可查看），对使用者多数时候透明，选型时更关心语义与命令。

二、常用命令（必会子集）

1. 读写与删除

MSET / MGET：一次多键，减少往返（注意原子性与键命名规范）。

2. 带条件的写入与过期（业务高频）

SET 常用选项（Redis 2.6+ 语法，具体以你版本文档为准）：

选项 含义
EX 秒 / PX 毫秒 设置过期时间（TTL）
NX 仅当 key 不存在 时写入（常用于抢锁占位）
XX 仅当 key 已存在 时覆盖

3. 计数器：INCR / DECR / INCRBY

INCR 在值可解析为整数时原子自增；不存在时按 0 开始。

4. 其它实用命令

命令 作用
APPEND 尾部追加字节
STRLEN 返回字节长度
GETRANGE / SETRANGE 按偏移读写子串（仍整体是 String）
GETSET 读旧值并写新值（单原子操作，适合简单状态切换）

三、典型应用场景

  1. 缓存整页或对象：值存 JSON 字符串，配合 EX 做短期缓存；更新数据库后删键或覆盖避免脏读。
  2. 会话 / 登录态：SET … EX … 存 token → 用户信息；过期自动消失。
  3. 计数与限流：INCR 做浏览量、接口调用次数；与滑动窗口等逻辑配合（复杂限流可再引入 Hash / ZSet）。
  4. 分布式锁（谨慎）：SET key token NX PX ttl 仅占位；完整锁需唯一 token、Lua 校验身份释放、续期、Redlock 争议等专题，本文只给入门占位思路。
  5. 配置与功能开关：SET feature:x:enabled 1，读时 GET 转布尔。

四、综合案例（redis-cli 可直接敲）

以下默认本机 redis-cli 无密码；若启用了 requirepass，请加 -a <密码>（见 Redis-Docker.md）。

1. 用户信息缓存（带过期）

2. 文章阅读量

3. 简单「占位锁」（演示用，生产请用成熟方案）

4. 条件更新：仅存在时改

五、注意事项与选型

  1. 大 value：单 String 过大占用内存与网络带宽，序列化大对象可评估 Hash 分字段或拆 key。
  2. 热 key：同一 key 超高并发时，单线程处理该 key 易成瓶颈，需业务侧分片或换结构。
  3. KEY 命名：建议 业务:实体:id:属性> 一类可读前缀，避免全局 KEYS * 在生产使用（用 SCAN）。
  4. 持久化与丢失：String 在内存里，是否落盘取决于 RDB/AOF 与策略；缓存≠数据库，关键数据以库为准并设计降级。
  5. 字符集：Redis String 是字节；UTF-8 文本由客户端编码/解码，不要在服务端假设「一定是中文几个字符」与字节长度一一对应。

PostgreSQL 并发与 MVCC 入门

发表于 2026-05-03 分类于 PostgreSQL 本文字数： 576 阅读时长 ≈ 2 分钟

PostgreSQL 以 MVCC（多版本并发控制） 为主：读写通常不互相阻塞读路径；写与写仍可能因行级锁、唯一约束等冲突。本文偏用法与现象，与 PostgreSQL索引与性能优化.md（EXPLAIN、隔离级别配置）互补。若你熟悉 《MySQL锁详解》（MySQL锁详解.md），可对照：InnoDB RR + 间隙锁 与 PostgreSQL 的快照与谓词锁（SSI） 并非一一对应，勿硬套术语。

一、快照与默认隔离级别

  • 默认 READ COMMITTED：单条 SQL 内看到语句开始时已提交的数据版本。
  • REPEATABLE READ：事务内首条 SQL 建立快照，后续读一致。
  • SERIALIZABLE：可检测读写依赖，失败时返回 40001 serialization_failure，应用应重试。

二、显式行锁：FOR UPDATE / FOR SHARE

  • FOR UPDATE：排他行锁，用于「先读后改」的临界区。
  • FOR SHARE：共享行锁，允许他人并发读，阻塞写。

三、SKIP LOCKED 与 NOWAIT（队列与抢锁）

SKIP LOCKED：跳过已被其他事务锁定的行，取下一批可用行——常用于任务队列、公平抢单。

NOWAIT：若不能立即加锁则立刻报错，适合避免长时间等待（由应用捕获错误后重试或放弃）。

四、死锁（deadlock detected）

PostgreSQL 会自动检测事务间循环等待，回滚其中一个事务（报错 40P01 deadlock_detected）。
规避思路与 MySQL 类似：固定加锁顺序、缩短事务、避免无关长耗时在事务内执行。

五、与 MySQL InnoDB 的粗对照（防混）

话题 MySQL InnoDB（见 MySQL锁详解.md） PostgreSQL（入门记法）
默认隔离 常为 RR RC
幻读与范围锁 间隙锁 / Next-Key 叙述多 SSI / 谓词锁 等在 SERIALIZABLE 下讨论多
队列抢任务 FOR UPDATE + 设计索引 FOR UPDATE SKIP LOCKED 一等公民

PostgreSQL 索引与性能优化

发表于 2026-05-03 分类于 PostgreSQL 本文字数： 1.1k 阅读时长 ≈ 4 分钟

面向业务开发与日常运维：能读 EXPLAIN、理解默认隔离级别、会开慢语句日志、知道逻辑备份与 WAL / PITR在说什么。与 PostgreSQL并发与MVCC入门.md（行锁、SKIP LOCKED、死锁与快照）互补；部署与数据卷见 PostgreSQL-Docker.md。

一、索引在干什么：B-Tree 直觉（默认）

PostgreSQL 默认 CREATE INDEX 多为 B-Tree（USING btree，可省略）。
直觉与 MySQL InnoDB 二级索引类似：以平衡树组织键，等值 / 范围查询减少随机读；主键 / 唯一约束底层也会建索引。

其他索引类型（点到为止）：GIN（全文、jsonb 含键）、GiST（地理、范围类型）、BRIN（超大顺序相关表）等，选型需读官方文档与压测。

二、联合索引与最左前缀

联合索引 CREATE INDEX idx_abc ON t (a, b, c); 的排序语义仍是先 a 再 b 再 c。
WHERE a = ? AND b = ? 易命中；仅 WHERE b = ? 往往用不上该索引（与 MySQL 同款直觉）。
函数包裹列（如 WHERE lower(email) = ?）常导致无法走 btree，需表达式索引（CREATE INDEX ON t ((lower(email)))）或改写法。

三、仅索引扫描（Index Only Scan）

若查询列均可由某索引覆盖，且可见性映射（VM）允许优化器认为堆页全可见，EXPLAIN 可能出现 Index Only Scan。
与 MySQL 的 Using index 类似但不等价；仍以 EXPLAIN (ANALYZE, BUFFERS) 实测为准。

四、怎么看执行计划：EXPLAIN / EXPLAIN ANALYZE

入门优先看：

字段 / 标记 含义（入门）
Seq Scan 顺序扫表，大表 + 高 rows 要警惕
Index Scan / Index Only Scan 走索引访问
Nested Loop / Hash Join / Merge Join 连接策略
ANALYZE 的 actual time、rows 真实耗时与行数（与统计信息、缓存有关）
BUFFERS 读了多少共享缓冲区（判断是否 I/O 重）

统计信息维护：ANALYZE tbl;（VACUUM ANALYZE 亦可），大变更后应跑。

五、事务与隔离级别（用法向）

1. 基本写法

默认 READ COMMITTED：每条语句看到语句开始时已提交的快照（简化理解）。
REPEATABLE READ：事务内第一条语句建立快照，读一致性更强。
SERIALIZABLE：最强，可能出现 serialization_failure，应用需重试。

与 MySQL InnoDB 默认 RR 不同：PostgreSQL 默认 RC；跨库迁移时注意语义差异。行级锁、FOR UPDATE、死锁见 PostgreSQL并发与MVCC入门.md。

六、慢语句与观测「三板斧」（点到为止）

1. 日志：log_min_duration_statement

在 postgresql.conf 或 ALTER SYSTEM（需 reload）中设置，例如记录超过 200ms 的语句（数值按环境调）。

2. pg_stat_statements（扩展）

需 shared_preload_libraries 预加载（运维配置），此处不展开。

3. auto_explain（扩展）

自动对超时语句打计划，适合测试环境；生产按规范启用。

落地顺序：先慢日志或 pg_stat_statements 抓 Top SQL → EXPLAIN (ANALYZE, BUFFERS) → 改索引或改写法 → VACUUM ANALYZE。

七、VACUUM 与膨胀（可靠性常识）

PostgreSQL 的 MVCC 会使更新/删除留下死元组；VACUUM（通常由 autovacuum 自动跑）回收空间、更新统计信息。长期不 vacuum 会导致表膨胀、性能变差。
日常开发：大批量导入/更新后，测试库可手动 VACUUM ANALYZE；生产依赖 autovacuum 参数与监控。

八、备份恢复与 PITR 概念

1. 逻辑备份 pg_dump / pg_restore

-Fc 为自定义目录格式，便于并行恢复；纯 SQL 可用 -Fp。

2. 物理与 WAL

PITR 依赖：基础备份（文件系统级或 pg_basebackup）+ 连续归档的 WAL + 恢复目标时间。与 MySQL binlog 地位类似的是 PostgreSQL WAL；具体恢复命令属 DBA 手册级。

3. 与 Docker 的关系

容器内 $PGDATA 一般在卷上（见 PostgreSQL-Docker.md）；备份策略要约定「从宿主机 pg_dump 连容器端口」还是「卷快照 + WAL 归档」，并做恢复演练。

PostgreSQL 存储与执行模型概览

发表于 2026-05-03 分类于 PostgreSQL 本文字数： 742 阅读时长 ≈ 2 分钟

PostgreSQL 没有与 MySQL 建表子句 ENGINE=InnoDB / MyISAM 等价的「多存储引擎二选一」模型：进程内是一套统一的后台执行与存储子系统（常说的 PostgreSQL 引擎多指整个数据库内核版本，而非可选插件式表引擎）。若需对照 MySQL 存储引擎，请读同目录 MySQL引擎.md。

姊妹文：PostgreSQL并发与MVCC入门.md（快照与行锁）、PostgreSQL索引与性能优化.md（EXPLAIN、VACUUM）、PostgreSQL-Docker.md（$PGDATA 与部署）。

一、表数据默认怎么存：Heap（堆表）

  • 普通 CREATE TABLE 默认即 heap 表：行以堆页存放，通过 tid（块号 + 行号） 定位。
  • MVCC 在元组头维护版本信息（xmin / xmax 等），更新与删除产生新版本/死元组，依赖 VACUUM 回收（见 PostgreSQL索引与性能优化.md）。
  • 与 InnoDB 聚簇索引即整表不同：PostgreSQL 主键索引是二级索引，堆上存行，主键查找通常「索引 → 回表 tid」。

二、表访问方法（Table Access Method）

PostgreSQL 12+ 起，表可指定 USING heap（默认）；理论上可挂自定义表访问方法（需扩展提供）。
生产常见仍是 heap；列存、混存等多在扩展或外部产品（如某些分析型方案）中实现，不等价于 MySQL 换一个 ENGINE 字符串。

三、与「引擎」易混的几个概念

概念 说明
TABLESPACE 表/索引的文件放置位置（如 pg_default），不是另一种行存储引擎。
TOAST 大字段行外存储机制，对用户基本透明。
Foreign Data Wrapper（FDW） 外部表：数据在远程；语法像本地表，语义与本地 heap 完全不同，不是换存储引擎。
内置索引类型 B-Tree、Hash、GiST、GIN、BRIN 等是索引访问方法，不是替换 heap 的「表引擎」。

四、和 MySQL InnoDB 的粗对照（选型沟通用）

话题 MySQL（MySQL引擎.md） PostgreSQL（本文）
建表选「引擎」 ENGINE=InnoDB 等 无；默认 heap + 统一内核
行存与主键 InnoDB 聚簇主键与数据同树 堆行 + 主键索引
并发读写的核心 InnoDB MVCC + 锁 MVCC + 行锁（见 PostgreSQL并发与MVCC入门.md）

五、实务建议

  1. 学习 PostgreSQL 时少问「用哪个引擎」，多问索引类型、执行计划、VACUUM、隔离级别与锁。
  2. 需要列存、分片、多副本高可用时，在架构层选专用扩展或产品（如 Citus、云厂商数仓、读写分离），而不是在 CREATE TABLE 里找一个 ENGINE 开关。
  3. 版本升级（14 → 16 → 17）会带执行器与优化器演进，「升级引擎」口语上常指升级主版本，与 MySQL 的 ENGINE 不是同一概念。

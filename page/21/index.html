第三章：PL/SQL 程序设计

概念基础

  1. 过程化 SQL 扩展：PL/SQL 在 SQL 之上加入变量、流程控制、游标、异常、过程/函数/包/触发器，把多步 SQL 与业务逻辑封装成库内可复用的程序单元。
  2. 块结构是基础：所有 PL/SQL 程序都由「声明 - 执行 - 异常」三段式块构成，执行段是唯一必需——这是理解一切存储过程的根基。
  3. 服务端执行减少往返：复杂逻辑下沉库内执行，避免应用与数据库多次网络往返，对批量、循环更新场景提速显著，但也带来「业务与库耦合」的代价。
  4. 静态 SQL + 强类型：PL/SQL 中的 SQL 在编译期校验表/列，变量强类型绑定，比拼接动态 SQL 更安全高效。
  5. 本章目标：掌握块结构、流程控制、游标、异常处理，以及过程/函数/包/触发器四大程序单元，写出可维护的库内逻辑。

包的优势：

九、动态 SQL

静态 SQL 无法满足运行时拼表名/列名时，用动态 SQL：

1. EXECUTE IMMEDIATE（单条）

2. DBMS_SQL / EXECUTE IMMEDIATE USING（绑定变量）

必须用绑定变量：拼接字符串既危险（SQL 注入）又伤性能（每条新 SQL 硬解析）。用 DBMS_ASSERT 校验动态对象名。动态查询多行结果用 DBMS_SQL 或 OPEN FOR 游标变量。

十、批量绑定（BULK COLLECT / FORALL）

批量绑定是 PL/SQL 性能优化的核心——一次往返处理多行，避免循环内逐行 SQL：

语句 作用
BULK COLLECT INTO 一次取多行到集合
FORALL 一次提交多行 DML（非循环，单次往返）
SAVE EXCEPTIONS FORALL ... SAVE EXCEPTIONS 允许个别失败不中断

行级循环 DML 是性能杀手：FOR r IN cursor LOOP UPDATE ... 每行一次往返。改用 BULK COLLECT + FORALL 可提速数十倍。详见 第六章：性能调优与运维。

十一、常见陷阱

陷阱 说明
SELECT INTO 多行/0行 多行抛 TOO_MANY_ROWS、0行抛 NO_DATA_FOUND，用游标或聚合兜底
未 COMMIT 断连 过程内 DML 默认不自动提交，断连回滚
OTHERS 吞错误 兜底不记日志会掩盖问题，应记 FORMAT_ERROR_BACKTRACE
触发器滥用 行级触发器性能差、隐式逻辑难调试，优先用约束/过程
动态 SQL 拼接 拼表名用 DBMS_ASSERT，传值用绑定变量防注入
逐行 DML 循环内 UPDATE 慢，改 FORALL 批量
包状态丢失 包级变量在会话级，重新编译包体可能丢失会话状态
函数中 DML 在 SQL 中调用的函数不能做 DML，否则报 ORA-14551

第二章：SQL 查询与内置函数

概念基础

  1. SQL 标准为主、方言为辅：Oracle 支持 ANSI SQL，但有自己的方言细节——VARCHAR2 而非 VARCHAR、DUAL 伪表、ROWNUM 伪列、字符串拼接用 ||。
  2. 空值是未知而非空：Oracle 中 NULL 表示「未知」，与任何值比较（含 = NULL）都返回未知，必须用 IS NULL / NVL/COALESCE 处理，否则过滤条件静默失效。
  3. 事务默认手动提交：INSERT/UPDATE/DELETE 后必须 COMMIT，与 MySQL 默认 autocommit 相反；DDL（建表/改表）会隐式提交。
  4. 分析函数是杀手锏：ROW_NUMBER/RANK/LAG/LEAD/SUM OVER 等窗口函数能在一条 SQL 内完成排名、同环比、累计——这是 Oracle 区别于早期 MySQL 的强项。
  5. 本章目标：覆盖查询、连接、子查询、分页、分析函数与常用内置函数，写出生产级 SQL。

本章承接 第一章：Oracle 数据库入门 的最小示例，假设已建好 emp 表。SQL 语法不依赖实例状态，可在 SQL*Plus / SQL Developer 中逐条验证。

第一章：Oracle 数据库入门

发表于 2026-05-01 更新于 2026-09-01 分类于 Oracle 本文字数： 2.2k 阅读时长 ≈ 7 分钟

第一章：Oracle 数据库入门

概念基础

  1. 企业级关系型数据库：Oracle Database 是老牌商业 RDBMS，在银行、电信、政务等对稳定性、安全合规与厂商支持要求高的核心系统中长期占主导地位。
  2. 实例与数据库分离：Instance（内存 SGA + 后台进程）挂载并打开 Database（物理文件集合），多实例可共享访问同一套库（即 RAC）。理解「实例是内存进程、数据库是文件」是入门第一关。
  3. 逻辑存储分层：数据组织在表空间（SYSTEM / SYSAUX / USERS / TEMP / UNDO）中，向下再划分为段、区、块——这套分层决定了建库、扩容、调优的思维方式。
  4. 高可用与容灾：RAC 多节点共享存储集群、Data Guard 主备容灾，配合 RMAN 备份恢复构成企业级方案，这是 Oracle 区别于开源库的核心竞争力。
  5. PL/SQL 过程化扩展：存储过程、包、触发器可在库内实现复杂业务逻辑，减少应用与数据库之间的往返——既是优势也是「业务逻辑下沉」的双刃剑。

本章是 Oracle 系列的总览与起点。先建立「实例/数据库/Schema」的体系结构心智模型，再跑通最小 SQL 与连接示例，后续章节逐层深入 SQL、PL/SQL、存储、高可用与调优。

1. 三层对应关系

关键区分：实例是「跑起来的内存进程」，数据库是「磁盘上的文件」。实例挂掉数据不丢（落盘），但内存中的未提交事务会因 undo 回滚。这套机制详见 第四章：体系结构与存储管理。

2. 后台进程速记

第三章：MongoDB 索引、聚合与模式设计

概念基础

  1. MongoDB 慢查询九成是索引问题：无索引的 find 是全集合扫描（COLLSCAN）；建对索引变成 IXSCAN，与关系库的「先看执行计划」哲学一致。
  2. ESR 原则定复合索引字段序：Equality（等值）→ Sort（排序）→ Range（范围），顺序排对一条复合索引能同时服务过滤与排序。
  3. 聚合管道是 MongoDB 的「SQL+ETL」：$match → $group → $sort → $project ... 流水线处理，能下推的尽量下推（先 $match 后 $group）。
  4. 模式设计决定性能上限：文档模型核心取舍是内嵌（embed）还是引用（reference）——按「一起读写就内嵌、各自更新就引用」判断。
  5. explain 是证据不是感觉：executionStats 里的 totalKeysExamined / totalDocsExamined / nReturned 三值关系直接给出诊断。

实践要点：

四、模式设计：内嵌还是引用

判断口诀：

场景 选择

单文档天然原子：把需要原子性的关联数据内嵌进同一文档，很多「事务需求」就直接消失了——这是文档建模的隐藏红利。

第一章：MySQL DDL 语句与表设计入门

概念基础

DDL（Data Definition Language，数据定义语言）是 MySQL 中定义「结构」的语言：

  1. 管结构，不管数据：DDL 负责定义/修改/删除数据库、表、字段、索引、视图等对象，不操作表里的业务数据；管数据的是 DML（INSERT / UPDATE / DELETE / SELECT）——一句话记忆：「DDL 改架子，DML 改数据」。
  2. 建表即建模：把业务对象翻译成表，核心是选字段类型（INT / VARCHAR / DATETIME…）与定约束（主键、非空、唯一、默认值、外键）；结构一次设计、长期使用，返工成本高，所以建表是数据库学习的第一课。
  3. 结构最终落在存储引擎上：客户端 SQL 经 MySQL Server 交给 InnoDB，数据按主键组织成 B+ 树，通过 Buffer Pool 缓存、Redo Log 保证崩溃安全——表与索引结构如何组织，直接决定后面的查询性能（详见第五章、第六章）。
  4. 三大类对象：库操作、表操作，以及视图 / 索引 / 存储过程等对象定义；语句形式永远是 CREATE / ALTER / DROP 三板斧。
  5. 约束的权衡：FOREIGN KEY、UNIQUE 等约束由数据库兜底完整性，但会带来额外维护开销、且不利于分库分表，互联网业务常改用「逻辑外键」；入门先学会用，进阶再权衡取舍。

第一章：Redis 概述、安装与 CLI 入门

概念基础

Redis（REmote DIctionary Server）是一个基于内存的键值（KV）存储系统：

  1. 数据在内存：读写不落盘，单次操作微秒级，比磁盘数据库快 1~2 个数量级；同时提供 RDB / AOF 持久化把数据落到磁盘。
  2. KV 模型，值有类型：键（key） 永远是字符串；值（value） 支持多种数据类型（String / Hash / List / Set / ZSet 等），不同类型对应不同命令族与底层结构，这是 Redis 与 Memcached 这类「纯字符串 KV」最大的差别。
  3. 单线程命令执行：命令在单线程事件循环中顺序执行（基于 epoll / IO 多路复用），单个命令天然原子；Redis 6.0+ 引入的「多线程」只用于网络 IO 读写，命令执行仍是单线程。
  4. 为什么快：内存操作 + IO 多路复用 + 单线程无锁竞争 + 针对各类型优化的高效底层结构（SDS、跳表、quicklist 等）。
  5. 定位：缓存为主，兼任分布式锁、计数器、排行榜、消息队列、地理位置等；缓存 ≠ 数据库，关键数据以关系库为准，Redis 丢数据要有降级与重建预案。

Redis 以键值为核心，值支持多种数据类型（字符串、哈希、列表等）；默认监听 6379。与关系型数据库不同，数据主要在内存中，须结合淘汰策略、持久化与备份设计，避免单点丢数。

MyBatis-Plus（简称 MP） 是 MyBatis 的增强工具，定位是「只做增强不做改变」：

MyBatis-Plus 分页原理

一、核心一句话

MP 分页本质：MyBatis 拦截器 + 自动改写 SQL

  1. 你传入 Page<>(当前页,每页条数)
  2. MP 分页拦截器拦截 Mapper 查询方法
  3. 自动帮你生成 count 总数SQL + 拼接 limit 分页SQL
  4. 执行两条 SQL：查总数 → 查当前页数据
  5. 把总数、页码、数据封装到 IPage 返回

二、关键核心组件

  1. MybatisPlusInterceptor
    MP 核心插件容器，所有插件（分页、防全表更新、乐观锁）都往里注册。
  2. PaginationInnerInterceptor
    MP 真正的分页拦截器，核心逻辑全在这。
  3. Page / IPage
    分页参数载体，存：当前页、每页条数、总记录数、总页数、分页数据。

3. 底层执行步骤

  1. 进入 Mapper 方法前
    PaginationInnerInterceptor 拦截到 selectPage 查询。
  2. 判断是否是分页查询
    检测方法参数里有没有 IPage/Page 对象，有就走分页逻辑。
  3. 自动生成 COUNT 语句
    原SQL：select id,name from user
    自动生成：select count(*) from user → 查询总记录数
  4. 改写原SQL 加 LIMIT
    原SQL 被改写为：
    select id,name from user limit 0,10
  5. 执行两条 SQL
    • 第一条：查总条数
    • 第二条：查分页数据
  6. 封装分页信息
    把总条数、当前页、每页大小、总页数、数据列表 全部塞进 IPage 返回。

四、为什么不用自己写 limit、不用自己写 count？

MP 拦截器动态解析 SQL、动态拼接 limit、动态生成 count，完全无侵入。

五、分页两个重要特性

1. 分页合理化 reasonable=true

  • 输入页码 <=0 自动变成第 1 页
  • 输入页码 大于总页数 自动返回最后一页

2. 溢出总页数后是否查最后一页

PaginationInnerInterceptor 可配置，防止页码乱输报错。

六、常见坑（原理衍生出来的）

  1. 没配置 PaginationInnerInterceptor → 分页无效，查全部数据
  2. 只有 Mapper 层用 Page 参数才生效，Service 自己写 list 不分页
  3. 自定义 XML SQL 也能自动分页，MP 照样拦截加 limit、count
  4. 多表联查、复杂 SQL 也支持，拦截器会解析原有 SQL 结构

七、极简总结

MP 分页 = 拦截器拦截SQL → 自动查总数 → 自动拼接LIMIT → 封装分页结果

不用手写 count、不用手写 limit，全靠拦截器动态代理实现。

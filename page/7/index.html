OpenSSL 常用操作完整指南

OpenSSL 是生成、管理非对称密钥和数字证书的标准工具，广泛用于 HTTPS、SSL/TLS、身份认证等。能力概览见 OpenSSL 功能；本文侧重命令行操作。

一、核心概念（快速看懂）

  1. 私钥（private key）：.key / .pem，必须保密，用于解密、签名
  2. 公钥（public key）：从私钥导出，公开分发，用于加密、验签
  3. 证书（certificate）：.crt / .pem，包含公钥 + 身份信息 + 签名，证明公钥合法
  4. CSR（证书签名请求）：.csr，向 CA 机构申请正式证书的文件

二、摘要与编码（不依赖证书）

1. 文件摘要（MD5、SHA-256）

对任意文件计算密码学摘要，常用于校验下载包、比对文件是否一致。

其他算法同理，例如 -sha512、-sha1（SHA-1 已不推荐用于安全场景）。

2. 字符串 / 管道内容哈希

把待哈希内容通过标准输入喂给 dgst。注意 echo 默认会带换行，校验短字符串时一般用 echo -n。

3. Base64 编码与解码

适合在文本通道里传输二进制，或快速查看二进制内容（Base64 不是加密）。

三、RSA 密钥：生成与导出公钥

1. 生成 RSA 私钥（无密码）

  • 2048 是密钥长度（安全推荐）
  • 生成后千万不要泄露

2. 生成带密码保护的私钥（更安全）

每次使用会要求输入密码。

3. 从私钥导出公钥

四、对称加解密（enc）

用口令派生密钥加密文件，算法以 AES-256-CBC 为例；加解密必须使用相同算法与口令，解密侧需带 -d。

  • -salt：加密时加盐，避免相同明文产生相同密文（若版本默认已加盐，可省略显式写法，以本机 openssl enc -help 为准）。
  • 生产环境更推荐 随机二进制密钥 + 明确 KDF/模式（或直接用 age、GnuPG 等高层工具），口令仅作演示或临时场景。

五、非对称：公钥加密与私钥解密（RSA）

RSA 直接加密只适合很短载荷（长度受密钥与填充限制）；长数据应使用「随机对称密钥加密数据 + RSA 加密对称密钥」等混合方案（TLS、CMS 即类似思路）。

六、数字签名与验签

用私钥对消息摘要签名，任意持有公钥的一方可验证完整性及来源（前提是公钥可信）。

1. 私钥签名、公钥验签

十一、生产环境标准流程

  1. 生成安全私钥（4096 位，带密码）
  2. 生成 CSR

  4. 部署证书（Nginx/Apache/IIS）

总结

  1. 概念：私钥、公钥、证书、CSR 分工明确；私钥绝对不能泄露（证书失效且签名可被伪造）。
  2. 摘要与编码：md5 / sha256 / dgst（文件或管道）；base64 与 -d 解码。
  3. 密钥：genrsa 生成、-aes256 保护、rsa -pubout 导出公钥。
  4. 加解密：对称 enc（算法与口令一致）；非对称短数据 pkeyutl；长数据走混合加密或 TLS。
  5. 签名：dgst -sign / -verify；可从 x509 -pubkey 取公钥验签。
  6. 证书：开发用自签名；生产用 CSR → CA；会查看、匹配 modulus、格式转换与部署。

GraphQL

发表于 2026-05-01 更新于 2026-05-05 分类于 GraphQL 本文字数： 757 阅读时长 ≈ 3 分钟

GraphQL 是由 Meta（原 Facebook）于 2012 年创建、2015 年开源的一种用于 API 的查询语言与运行时，核心是让客户端精确请求所需数据，解决 REST 的“过度获取”和“多次请求”问题。下面从核心概念、优势、与 REST 对比、基本用法四方面详细说明。

一、核心概念

  • Schema（模式）：用强类型定义数据结构与关系，是 GraphQL 的“契约”，包含：
    • Query：查询（读操作）入口
    • Mutation：变更（写操作）入口
    • Subscription：订阅（实时更新，基于 WebSocket）
  • Type（类型）：定义对象结构，如 User、Post，含字段与类型（标量/对象/列表/非空）。
  • Resolver（解析器）：服务端函数，负责按字段获取/处理数据（数据库、微服务、第三方 API 均可）。
  • Query（查询）：客户端声明式请求，结构即响应结构。
  • Mutation（变更）：用于创建/更新/删除数据，语法类似 Query。

二、核心优势（对比 REST）

维度 GraphQL REST
数据获取 客户端精准指定字段，无过度获取 固定返回结构，易冗余
请求次数 单一请求获取多资源（如用户+文章） 需多端点请求，易“请求瀑布”
版本控制 Schema 渐进演进，无需版本号 需维护 v1/v2 多版本
文档 基于 Schema 自动生成（如 GraphiQL） 需手动维护（Swagger 等）
实时能力 原生支持 Subscription（WebSocket） 需轮询/SSE，成本高
缓存 依赖客户端/实体缓存（如 Apollo） 天然适配 HTTP 缓存

关键结论：GraphQL 显著减少数据传输量与请求次数，弱网/移动端收益极大；REST 更简单、成熟、缓存友好，适合简单场景。

三、工作流程

  1. 定义 Schema：服务端用 SDL（Schema Definition Language）定义类型、Query、Mutation。
  2. 实现 Resolver：每个字段对应解析器，对接数据源。
  3. 客户端请求：发送 POST 到单一端点（如 /graphql），携带 Query/Mutation。
  4. 服务端执行：校验 Query → 调用 Resolver → 按请求结构返回 JSON。
  5. 客户端接收：响应结构与 Query 完全一致，直接渲染。

四、适用场景

  • ✅ 复杂前端应用（如电商、社交）：多数据关联、按需字段。
  • ✅ 移动端/弱网环境：减少请求与数据体积。
  • ✅ 微服务架构：统一网关聚合多服务数据。
  • ✅ 实时功能（聊天、通知、实时看板）：Subscription 原生支持。
  • ❌ 简单 CRUD 服务：REST 更轻量、易维护。
  • ❌ 高缓存吞吐场景：REST HTTP 缓存更高效。

五、常用工具

  • 服务端：Apollo Server、Relay、Hasura（自动生成 GraphQL）。
  • 客户端：Apollo Client（React/Vue/Angular）、Relay（Meta）、urql。
  • 开发工具：GraphiQL（内置 IDE）、Playground、GraphQL Voyager（可视化 Schema）。

RocketMQ 消息中间件入门

发表于 2026-05-01 更新于 2026-05-31 分类于 MQ 本文字数： 429 阅读时长 ≈ 1 分钟

Apache RocketMQ 是阿里开源后捐赠的分布式消息中间件：支持顺序消息、延迟消息、事务消息、死信队列，在国内电商与微服务场景广泛使用。本文侧重 MQ 通用概念；Spring Cloud Stream 集成见 Spring Cloud 集成 RocketMQ。

一、架构组件

组件 作用
NameServer 路由注册中心，轻量、无状态
Broker 存储与转发，分 Master / Slave
Producer 发送消息
Consumer 拉取消息，Push 底层为长轮询

客户端通过 NameServer 发现 Broker 地址。

二、Topic 与 Queue

  • Topic：逻辑分类。
  • Message Queue：Topic 下分片（类似 Kafka 分区，语义不同）。
  • Tag / Key：二级过滤与索引。

三、消费模型

模式 说明
CLUSTERING 同组负载均衡，一条消息只被一个实例消费
BROADCASTING 组内每实例全量接收
重试 / DLQ 消费失败进入重试队列，超限进死信

四、顺序、延迟与事务

1. 顺序消息

同一 MessageQueue 内 FIFO；发送端按 orderId 等 sharding key 固定路由。

2. 延迟消息

内置延迟级别（1s、5s、1m…），适合订单超时关闭。

3. 事务消息

Half 消息 + 本地事务 + 回查；与 Seata 同步事务可对照选型（见 cloud 当前 Feign + Seata 链路）。

五、与 Kafka 的对照

场景 更常选
日志、CDC、流计算生态 Kafka 消息中间件入门
电商订单、定时、事务消息 RocketMQ
Spring Cloud Alibaba Spring Cloud 集成 RocketMQ

六、部署与运维

Docker：RocketMQ-Docker。局域网见 服务（NameServer :30876、Dashboard :30877）。

项 注意
磁盘 CommitLog 顺序写，监控刷盘与磁盘
主从 Master 故障切换策略依版本（DLedger 等）
版本 客户端与 Broker 主版本对齐

官方文档：https://rocketmq.apache.org/docs/

Kafka 消息中间件入门

发表于 2026-05-01 更新于 2026-05-31 分类于 MQ 本文字数： 746 阅读时长 ≈ 2 分钟

Apache Kafka 是分布式事件流平台：高吞吐、持久化、可回放的分区日志，用于消息队列、日志管道、流式处理与数据集成。本文侧重 MQ / 微服务 视角；大数据总线、CDC、Flink 集成见 Kafka 大数据数据总线。

一、核心概念

概念 说明
Topic 逻辑消息流名称
Partition Topic 的分片，有序日志；并行度与分区数相关
Offset 分区内每条消息的唯一递增序号
Producer 写入消息，可指定 key 做分区路由
Consumer Group 组内消费者分摊分区，同组不重复消费同一分区
Broker 存储与 Serving 分区的服务器进程

消息持久化在磁盘（顺序写 + page cache），可配置保留时间与大小。

二、生产者与消费者

1. 生产者

  • acks：0 / 1 / all 权衡延迟与持久性。
  • 幂等生产者：避免重试导致重复（下游仍可能需要业务去重）。
  • 事务：跨分区 exactly-once 与 Kafka Streams 场景。

2. 消费者

  • auto.offset.reset：earliest / latest。
  • 手动提交 offset：处理成功后再 commitSync / commitAsync。
  • 再均衡（Rebalance）：组成员变化时重新分配分区；消费逻辑应支持幂等。

3. 投递语义（需业务配合）

语义 说明
At most once 先提交 offset 再处理，可能丢
At least once 先处理再提交，可能重复
Exactly once 事务 + 幂等存储，成本高

三、分区、副本与 ISR

  • Leader / Follower：每个分区一个 Leader 负责读写，Follower 同步。
  • ISR（In-Sync Replicas）：与 Leader 差距在阈值内的副本；min.insync.replicas 与 acks=all 共同定义「写成功」。
  • 扩容：增加分区数不会重分布历史 key；规划分区数宜前置。

四、KRaft 与 ZooKeeper

Kafka 3.x+ 可用 KRaft（内置 Raft 元数据）替代 ZooKeeper。新集群建议 KRaft；存量 ZK 集群按官方迁移指南操作。本站 Docker 部署 Kafka 采用 KRaft 单节点示例。

五、与 RocketMQ 的对照

维度 Kafka RocketMQ
模型 分区日志、流式优先 Topic + Queue、顺序/延迟/事务消息
生态 Connect、Streams、Flink/Spark 国内电商、SCA 集成
典型场景 日志、指标、CDC、流计算 订单、定时、强业务 MQ

RocketMQ 入门见 RocketMQ 消息中间件入门；Spring Cloud 集成见 Spring Cloud 集成 RocketMQ。

六、部署与命令行探测

容器部署：Docker 部署 Kafka。局域网中间件见 服务（:30006 等）。

七、生产注意

项 建议
分区数 与消费者并行度、磁盘并行写相关；不宜过少
保留 retention.ms 与磁盘容量；合规场景可能需归档到对象存储
监控 Under-replicated partitions、请求 P99、磁盘使用率
安全 SASL/SSL、ACL；勿将 9092 裸奔公网

官方文档：https://kafka.apache.org/documentation/
